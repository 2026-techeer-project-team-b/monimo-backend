# 결정 로그 (append-only)

형식: `#NN | YYYY-MM-DD | <결정> | 채택:<A> | 기각:<B>(사유) | 되돌림:<C>`
4요소(채택안 / 기각안 최소 1개 / 기각 사유 / 되돌리는 조건)가 없으면 여기 적지 않고 `02-open-questions.md` 로 반려한다. 기록 후 `00-index.md` 의 `recent decisions` 를 갱신한다.

이 문서는 "무엇을 왜 골랐나" 만 적는다. 옆에 세 가지가 더 있다.

| 무엇 | 어디 |
|---|---|
| 고장 나면 어떻게 되나 (수집 경로) | [`30-failure-modes.md`](30-failure-modes.md) |
| 선택지를 비교한 조사 · 출처 링크 | [`../seungjo/<이슈>/research.md`](../seungjo/README.md) |
| 그 결정을 만들 때 AI 에게 무엇을 어떻게 물었나 | [`../seungjo/<이슈>/prompts.md`](../seungjo/README.md) |

결정을 **프롬프트로 내린 경우에는 그 원문을 결정 항목 안에 같이 둔다**(`#50` 이 첫 사례). 과제 전형에서 프롬프트를 내라고 할 때 그대로 낼 수 있고, 결정과 그 결정을 만든 글이 떨어져 있으면 나중에 짝을 못 찾는다.

- ⚠️ 3단계 구현 주의: 흔히 쓰는 `vector(1)` 상수 Watchdog 알림은 저장소가 가득 차 실제 데이터가 사라져도 계속 발화해 **고장난 스택이 무탐지로 남는** 알려진 결함이 있다(kube-prometheus #2537). 하트비트는 **에이전트 → Kafka → 저장 → 질의를 실제로 관통하는 카나리 신선도**로 잡을 것. 부수효과로 A평면 통합 테스트 겸 데모 소재가 된다.

## `#03` [확정 · 일부 개정됨 → `#09`] 자체 구현 vs 기성 재사용 경계

> 시각화 부분은 `#09` 로 개정되어 **자체 구현**이 되었다. 저장 엔진·질의 엔진은 아래 그대로 유효하다.

2026-09-01 | 사용자 확정 | 데이터 플레인은 자체 구현하고 저장·질의·시각화는 기성을 쓴다
- **채택**: 자체 구현 = 수집기 · 경보 엔진 · 에이전트 / 기성 사용 = 저장 엔진 · 질의 언어 · 시각화
- **기각**: 저장 엔진·질의 엔진까지 자체 구현 — 사유: 수년짜리 제품이다. 2개월에 넣으면 1개월은 인프라 세팅, 2개월째는 에이전트에 소진되어 **경보 기능이 스텁으로 남아 모니터링 제품이 아니게 된다**
- **되돌림**: 사용자 지정 — *"추후에 저장고까지 만들어야 한다면 그때 재검토하고 스킬을 수정한다."* 판단 시점은 2단계 규모 산정 직후 또는 T0+2M 고도화 착수 시점
- 기성을 써도 바운디드 컨텍스트는 유지된다 — 저장 서비스가 스키마·보관정책·다운샘플링·쓰기배칭을 소유한다. 이 경계표는 2단계 완료조건이다.

## `#05` [확정 · 보관 기간 개정됨 → `#10`] 비기능 요구사항 수치

> 보관 기간에 장기 계층(1시간 · 1년)이 `#10` 으로 추가되었다. 나머지 수치는 아래 그대로 유효하다.

2026-09-01 | 사용자 확정 | 1단계 제안값을 그대로 채택한다
- **채택**: 가용성 = 수집 경로 99.9% / 조회·시각화 99.5% · 지연 = 수집→조회 p95 30초 / 경보 발화→알림 p95 60초 · 보관 = 메트릭 15일(1분 다운샘플 후 90일) / 로그 7일 / 트레이스 3일 · 처리량 = 메트릭 10,000 포인트·로그 2,000 라인·트레이스 500 span (초당)
- **기각**: ① 더 낮춘 안(가용성 99.5% / 지연 60초 / 보관 절반) — 사유: 장애 인지까지 1분을 넘기면 모니터링 도구로서의 효용이 급감한다 ② 더 높인 안(99.95% / 지연 10초) — 사유: 다중화·백프레셔 처리가 필수가 되어 팀 4명 2개월 범위를 넘는다
- **되돌림**: 2단계에서 감시 대상 서비스 수 × 인스턴스 수로 역산한 실제 처리량이 제안값의 2배를 넘으면 처리량과 보관 기간을 재산정한다
- 수집 경로를 조회보다 엄격히 둔 이유: 데이터는 놓치면 복구 불가지만 조회는 지연되어도 사후 복구가 된다.

## `#06` [확정] 경보 대상 범위 — 3신호 전부

- **채택**: 지표 임계 규칙 + 로그 패턴 규칙 + 트레이스 이상 규칙을 모두 정의·평가·발화할 수 있다

- 파생: 경보 도메인이 커져 ADR `#04`의 서비스 5~6개 상한에 압박이 생긴다 → `Q10`에서 함께 판단한다.

## `#07` [확정 · 개정됨 → `#14`] OpenTelemetry 채택 경계

2026-09-01 | OTel을 어디까지 쓰는가 = ADR `#03` "자체구현" 의 실체를 결정한다
- **채택(잠정)**: **B안 — OTel Java Agent 골격 + 자체 Extension**, 수집기(S2)는 우리가 구현하고 OTLP를 수신한다. 측정 항목 이름은 OTel Semantic Conventions를 따르고 발명하지 않는다
- **기각**: ① A안(OTLP 형식만 차용, 에이전트 밑바닥 구현) — 사유: 바이트코드 계측을 처음부터 만드는 것은 2개월 범위를 넘고, 그 시간이 경보 엔진에서 빠진다 ② **C안(OTel Collector까지 채택)** — 사유: S2 Collector가 YAML 설정 작업으로 축소되어 자체 구현이 경보 엔진 하나만 남는다. ADR `#03` 붕괴
- **되돌림**: Extension SPI로 필요한 계측(파이프라인 자기 지표·카나리 발행)을 넣지 못하는 것이 확인되면 A안을 재검토한다
- 근거: Agent는 `-javaagent` 부착이라 제약 ④(비침습)를 그대로 만족한다. Extension은 `-Dotel.javaagent.extensions=` 로 주입하며 `AutoConfigurationCustomizerProvider` SPI로 커스텀 SpanProcessor·Sampler·Exporter를 등록한다(에이전트 재빌드 불필요). 우리 수집기가 OTLP를 받으므로 표준 호환과 자체 구현이 동시에 성립한다.
- **측정 항목 2분류(3단계·4단계 입력)**: ⓐ 대상 앱 = 황금 신호 4축(트래픽·오류·지연·포화도) + JVM·시스템·K8s·DB, Semantic Conventions 명칭 사용 ⓑ **우리 파이프라인 자기 지표** = 에이전트 드롭 건수·버퍼 점유율, 수집기 거부 건수(사유별), **Kafka 컨슈머 랙**, 적재 쓰기 실패율, 규칙 평가 지연·누락, 알림 전송 성공률, E2E 카나리 신선도. ⓑ가 B평면의 실제 내용물이며 이력서 규칙 R3의 실측 근거가 나오는 곳이다.

## `#08` [확정] 감시 대상의 1차/2차 표기 정정

2026-09-02 | 사용자 지적 반영 | `10-requirements.md` 의 "감시 대상 1차 = 우리 자신 / 2차 = 샘플 앱" 표기를 폐기한다
- **채택**: 축을 둘로 분리해 표기한다 — **제품 본연**(쿠버네티스 위 MSA 전반, 검증은 샘플 앱) / **자기 자신**(우리 스택, B·C평면). 그리고 **시간 순서는 샘플 앱이 먼저**임을 명시한다
- **기각**: 기존 "1차 = 우리 자신 / 2차 = 샘플 앱" 표기 — 사유: ① 프로젝트 초기에는 우리 서비스가 존재하지 않아 감시할 대상이 없다. 시간 순서상 샘플 앱이 반드시 선행한다 ② "1차/2차"가 시간 순서인지 중요도인지 구분되지 않아 두 축이 한 표기에 섞였다
- **되돌림**: 팀이 샘플 앱 없이 우리 서비스만으로 개발·검증하기로 하면 재검토한다
- 사용자 지적이 옳았다. 도그푸딩은 제품의 차별점이지 주 용도가 아니며, 개발 순서상으로도 뒤에 온다.

## `#09` [확정] 시각화를 자체 구현으로 변경 (`#03` 부분 개정)

2026-09-02 | 사용자 확정 | `#03` 의 "기성 사용" 목록에서 **시각화만 자체 구현으로 옮긴다**
- **채택**: 시각화(FE)를 자체 구현한다 — 서비스별 상태 대시보드 · 트레이스 타임라인 뷰 · 로그 검색 화면 · 경보 규칙 관리 화면. 저장 엔진과 질의 엔진은 `#03` 대로 기성 유지, 질의 파사드(S3)는 자체 유지
- **기각**: 시각화도 기성(Grafana 임베드) — 사유: ① 팀 노션에 `FE` 가 이미 독립 서비스로 잡혀 있고 기능 4건(`FN-28`~`FN-31`)이 등록되어 있어 `#03` 과 정면 모순이었다 ② `FN-31 경보 규칙 관리 화면` 은 **우리가 자체 구현하는 경보 엔진의 규칙**을 다루므로 Grafana로 대체 불가하다 ③ 화면 구현은 차트 라이브러리 사용 시 2~3주 규모로, 저장·질의와 달리 2개월 일정을 위협하지 않는다
- **되돌림**: T0+1M 중간 점검에서 FE 진척이 **대시보드 1종조차 미완**이면 트레이스 타임라인·로그 검색 화면을 Grafana 임베드로 되돌린다. 단 경보 규칙 관리 화면은 대체 불가하므로 자체 유지한다
- 결과적으로 "우리가 만드는 것" = 에이전트 · 수집기 · 경보 엔진 · 질의 파사드 · 화면 5종이 되어 팀의 5서비스 구성(S1~S5 + FE)과 일치한다.
- 저장과 질의 엔진을 함께 묶어 둔 이유: 질의 엔진은 저장 포맷·인덱스에 의존하므로 저장을 기성으로 쓰는 한 분리해서 자체 구현할 수 없다.

- **정정(2026-10-06, 구현 중 확인)**: 되돌림 ③ 의 전제 "pause 가 **파티션 단위로** 동작해서" 는 거꾸로다. `FailedRecordTracker` 가 `BackOffHandler.onNextBackOff(container, Exception, long)` 을 부르고 `ContainerPausingBackOffHandler` 가 그걸 `pause(컨테이너, Duration)` 으로 넘기므로 **컨테이너 전체(파티션 3개 모두)가 멈춘다**(바이트코드 확인). 즉 한 파티션의 장애가 다른 파티션까지 멈추는 것은 "확인되면" 이 아니라 **지금 그렇다.** 다만 지금은 적재 처리기 1대 · ClickHouse 1대라 어느 파티션이든 같은 저장소로 가므로 전체가 멈추는 것이 맞는 동작이고, 결론(여러 대 · 여러 저장소가 되면 `pausePartition` 으로 좁힌다)은 그대로 맞다. 틀린 전제는 AI 가 다듬은 초안에서 들어갔다. 프롬프트 원문은 사용자 글이라 고치지 않고 이 줄로 바로잡는다

공유해서 서로 남의 자리를 밀어버린다. 이번 이슈는 raw.dlq에 넣는 것까지만 한다.

되돌리는 조건은 세 가지다. 10분 넘는 ClickHouse 장애가 반복돼서 DLQ에 쌓이는 양이 사람이
처리할 수 없게 되면 대기 시간을 늘리거나 재처리 잡을 앞당긴다. 모르는 실패로 분류된 독성
메시지 때문에 1분 멈추는 일이 자주 보이면 그 코드를 DLQ 목록에 추가한다. 적재 처리기를
여러 대로 늘렸을 때 pause가 파티션 단위로 동작해서 한 파티션 장애가 다른 파티션까지
멈추는 게 확인되면 pausePartition으로 좁힌다.

그러니 그렇게 구현해줘.
```

**이 프롬프트가 결정의 4요소를 그대로 담고 있다.** 채택(D + 3단 + `319` 제거 + 뒤집기)과 기각 둘(C 는 리밸런스, E 는 안전망이 안 걸림)이 각각 사유와 함께 있고, 마지막 문단이 되돌리는 조건 셋이다.


## `#52` [확정] `transactions` 를 서비스가 받은 요청 기준으로 : 루트만 → SERVER · CONSUMER + `is_root` 컬럼

2026-10-07 | 사용자 결정 (아래 "이 결정을 만든 프롬프트" 가 원문) | 스캐터 `GET /traces/scatter`(`#110`)가 진입 서비스(`shop-gateway`)에서만 점을 보여주고 `shop-order` · `shop-payment` · `shop-inventory` 는 비어 있다. `transactions` 를 채우는 `mv_transactions` 조건이 `parent_span_id = ''`(루트만)이라 요청이 처음 닿는 서비스에만 줄이 생기기 때문이다. 버그가 아니라 **표의 기준(고객 요청 하나 = 1줄)과 화면의 기준(서비스를 골라 본다)이 어긋난 것**이다. 조회 파트(현영)가 발견해 넘어온 건이고 `db/clickhouse/` 가 파트를 넘는 공용 영역이라 수집 쪽이 가져갔다. 로컬 실측(2026-10-07) : `spans` 에는 네 서비스 SERVER 스팬이 다 있다(gateway 30,478 · order 30,356 · inventory 21,447 · payment 21,396). 중간 서비스 `transactions` 에 남아 있던 23 · 21줄은 **헬스체크 39 와 앱 시작 `CREATE TABLE` 5**(자식 없는 SERVER 스팬이 루트로 분류돼 들어간 것. 헬스체크는 `#92` 가 거르기 전 데이터)
- **채택**: ① **MV 조건을 `span_kind IN ('SERVER', 'CONSUMER')` 로 넓힌다.** SERVER 는 HTTP 로 받은 것, CONSUMER 는 큐에서 받은 것이고 둘 다 "일이 그 서비스로 들어온 지점" 이다. 루트는 SERVER 의 부분집합이라 전에 들어오던 줄은 그대로 들어온다 ② **`is_root UInt8` 컬럼을 추가한다**(`toUInt8(parent_span_id = '')`). 조건을 넓히면 "루트였다" 는 정보가 조건에서 사라지므로 컬럼으로 옮긴다. 서비스별은 `service_name` 으로, 고객 요청 수는 `is_root = 1` 로 한 표에서 본다 ③ **운영에서 MV 정의를 바꿀 때는 `ALTER TABLE ... MODIFY QUERY` 를 쓴다.** 집계가 비지도 중복이 생기지도 않는 유일한 방법이다(샌드박스 실험 확인). 바꾼 뒤 각 컬럼에 값이 들어오는지 확인하는 쿼리를 돌린다 ④ **`is_root` 는 `ADD COLUMN` 을 MV 수정보다 먼저** 한다(파일 순서 003 → 004 가 이미 그렇다) ⑤ **과거 구간 백필은 하지 않는다.** "이 시각부터 기준이 바뀌었다" 를 ADR · ERD 에 적는다 ⑥ 정렬 키와 스키핑 인덱스는 건드리지 않는다. 조회 코드는 0줄 바뀐다
- **기각**: ① **`span_kind = 'SERVER'` 단독** : 사유: 일이 서비스로 들어오는 방법이 HTTP 하나가 아니다. 큐에서 받으면 CONSUMER 라 그 서비스 스캐터가 또 빈다. 조사한 여섯 제품 중 SERVER 단독은 Jaeger SPM 하나이고 그 문서가 바로 누락 위험을 경고한다. CONSUMER 는 지금 0건(쇼핑몰이 동기 MVC, ADR `#25`)이라 **비용이 0** 이고, 남의 앱에 에이전트를 붙였을 때 그 앱이 큐를 쓰면 필요하다 ② **`OR parent_span_id = ''` 까지 넣기(Elastic · Datadog · Pinpoint 방식)** : 사유: 아무도 안 불렀는데 서비스가 스스로 시작한 일(앱 시작 DDL · 배치)까지 들어온다. 지금 우리 데이터에서 거기 걸리는 56줄이 전부 `CREATE TABLE` 과 telemetrygen 시험 데이터이고, 운영에서도 파드가 뜰 때마다 생긴다. "어느 서비스가 느린가" 를 보는 화면에 `CREATE TABLE` 점은 도움이 안 된다. 진짜 배치를 만들 때 넓힌다(되돌림 ①) ③ **조회가 `spans` 를 직접 읽기(B)** : 사유: 원본 표라 느리고 히트맵이 `heatmap_1m` 을 못 쓰게 된다. 집계표를 만든 이유가 없어진다 ④ **지금대로 두고 안내 문구(C)** : 사유: 스캐터를 만든 이유가 느린 서비스를 고르려는 건데 못 고르면 기능이 반쪽이다 ⑤ **`is_root` 대신 문서로 "요청 수를 세지 마라" 못 박기** : 사유: 막을 장치가 없다. 규칙을 모르는 사람이 `count()` 를 쓰면 4배 부풀려진 숫자가 화면에 나간다. 표를 둘로 나눈 사례는 조사에서 하나도 없었고 넓게 담고 플래그로 거르는 것(Elastic `transaction.root` · Datadog `_dd.top_level`)이 업계 방식이다 ⑥ **`DROP VIEW` + `CREATE` 로 MV 교체** : 사유: 그 사이 INSERT 가 **영구 유실**된다. 샌드박스에서 MV 를 지우고 4줄 넣고 다시 만들었더니 타깃에 0줄, 에러도 경고도 없었다 ⑦ **새 MV 를 만들어 둘을 같이 돌리기 · `EXCHANGE TABLES`** : 사유: 겹친 기간만큼 정확히 2배로 집계된다(소스 4줄 → 타깃 8줄). `EXCHANGE` 는 교환 뒤에도 둘 다 계속 돈다 ⑧ **과거 구간 백필** : 사유: `transactions` 에 직접 INSERT 해도 `mv_heatmap_1m` 이 따라 돌고(실험 확인) `heatmap_1m` 은 `SummingMergeTree` 라 `cnt` 가 **조용히 합산**된다. 줄 수가 안 늘어 눈에 안 보인다. 복제 표가 아니라 `non_replicated_deduplication_window = 0` 이고 두 번 돌리면 그대로 두 배다. 지금은 배포 전이라 과거가 전부 가짜 데이터다 ⑨ **`is_root` 를 정렬 키나 스키핑 인덱스에 넣기** : 사유: 첫 칸이면 `service_name` 등호로 걸리는 binary search 가 깨지고 마지막 칸은 효과가 없다. 스키핑 인덱스는 `is_root` 가 29% 라 거의 모든 블록에 1 이 섞여 공식 문서가 "쓸모없이 비용만 든다" 고 경고하는 경우다 ⑩ **`span_id` 컬럼 추가** : 사유: 같은 트레이스에서 같은 서비스가 두 번 호출될 때 점을 집는 용도인데, 실측상 겹치는 키가 한 키당 최대 2줄 · 평균 1.00줄이라 드물고 요청 목록 화면 계획(조회 파트)에 달렸다. `trace_id String` 이 이미 디스크의 78% 라 같은 급 컬럼을 더하는 비용이 `is_root` 와 비교가 안 된다 ⑪ **`005_` 마이그레이션 파일을 이 이슈에서 두기** : 사유: 운영에 그 파일을 실행할 수단이 없어 "있는데 안 도는" 상태가 되어 더 헷갈린다. 수단을 정하는 일이 이 이슈보다 크므로 별 이슈(`#119`)로 올린다
- **되돌림**: ① **배치나 스케줄 잡을 만들어 부모 없는 INTERNAL 루트가 생기면** 조건에 `OR parent_span_id = ''` 를 넣어 넓힌다 ② **이 표로 전체 요청 수를 세는 화면이 생기고 `is_root` 로 안 풀리면** 표를 둘로 나눈다 ③ **줄이 3.4배로 늘어 스캐터 조회가 눈에 띄게 느려지면** `ORDER BY` 를 다시 보거나 격자로 접는 기준(`limit` 5000)을 내린다 ④ **한 서비스에 SERVER 스팬이 여러 개 생기는 구성(서비스 메시 사이드카 등)이 들어오면** 중복 계수가 되므로 다시 본다
- **근거(조사 · 실측)**: 선택지 비교 · 업계 여섯 제품 · ClickHouse 샌드박스 실험 · AI 가 틀린 것 · 확인 못 한 것은 [`../seungjo/118-transactions-server-span/research.md`](../seungjo/118-transactions-server-span/research.md). 실측 : 줄 수 30,572 → 103,699(**3.39배**), 디스크 1.23 → 4.06 MiB(줄당 바이트는 42.26 → 41.02 로 오히려 감소), `heatmap_1m` 격자 491 → 1,343(2.74배), 조회 지연 전부 10ms 미만, `is_root` 컬럼 985바이트(+0.04%)이고 `PREWHERE` 자동 적용으로 읽는 바이트가 430 → 147 KiB, 정렬 키 중복은 한 키당 최대 2줄. ClickHouse 26.8.10.6 에서 `MODIFY QUERY` 가 실험 설정 없이 된다. 다른 집계표(`mv_url_stats_1m` · `mv_service_health_1m`)는 이미 `span_kind = 'SERVER'` 였고 `mv_transactions` 만 기준이 달랐다
- **뜻이 바뀐 것**: 「트랜잭션」이 "고객 요청 하나" 에서 "서비스가 받은 요청 하나" 로 바뀐다. 요청 하나가 서비스 4개를 지나면 1줄에서 **4줄**이 된다. 이 표의 `count()` 는 서비스가 처리한 일의 수이지 고객 요청 수가 아니다. 고객 요청 수는 `is_root = 1`. ERD(노션 정본 · 레포 사본 `docs/design/web-v2/erd.md`)의 "트랜잭션(루트 스팬)" 을 "서비스가 받은 요청" 으로 고쳤다
- **범위 밖**: **운영에서 ClickHouse DDL 을 실행하는 수단**(이번에 없다는 것이 드러났다. PG 는 `postgres-migrate`(Flyway)가 있는데 CH 는 initdb 마운트뿐이고 전부 `IF NOT EXISTS` 라 떠 있는 서버에서는 조용히 건너뛴다. 이슈 `#119`) · `GET /traces/transactions` · `GET /traces/heatmap` 구현(조회 파트) · `ttl_only_drop_parts = 1`(독립적 개선) · `trace_id` 가 저장의 78% 인 것
- **검증(2026-10-07, 로컬 compose)**: `down -v` → 켜기 → seed 뒤 `transactions` 102,166줄 = `spans` 의 SERVER 스팬 102,166(정확히 일치). 서비스별 gateway 30,000 · order 30,000 · payment 21,083 · inventory 21,083(**네 서비스 전부 0 아님**). `sum(is_root)` 30,000 = `spans` 의 루트 SERVER 수 30,000. 헬스체크 줄 0. 빈 컬럼 0(`service_name` · `trace_id` · `span_name` · `agent_id` 빈 줄 0, `duration_ms` · `http_status` 0 인 줄 0, `is_root` 값 종류 2). `heatmap_1m` 네 서비스 전부 채워짐(1,219칸)
- **구현**: PR (이슈 `#118`). `db/clickhouse/003_create_rollup_tables.sql` 에 `is_root` 컬럼, `004_create_materialized_views.sql` 의 `mv_transactions` 조건과 SELECT. 수집기 · 적재 처리기 · 조회 코드는 0줄. 팀원은 각자 `docker compose down -v` 로 다시 만들어야 새 MV 가 생긴다(DDL 이 빈 DB 에서만 돈다)

### 이 결정을 만든 프롬프트

2026-10-07 에 사용자가 쓴 글이다. 조사 2건과 질문 스무 번을 거친 뒤에 썼다. 같은 원문이 `docs/seungjo/118-transactions-server-span/research.md` 8절과 `prompts.md` 에 있다.

```
A로 가되 조건은 SERVER 하나가 아니라 CONSUMER까지 넣는 방향으로 가자.

mv_transactions 의 조건을 parent_span_id = '' 에서
span_kind IN ('SERVER','CONSUMER') 으로 바꾼다.

조건을 바꾸는 이유는 세 가지다. 첫째로 지금 비어 있는 게 데이터가 없어서가 아니라 조건이
좁아서인데, spans 에는 네 서비스 SERVER 스팬이 다 있고(gateway 30478 · order 30356
· inventory 21447 · payment 21396) 그중 루트는 gateway 것뿐이라 거기만 점이 찍힌다.
루트는 SERVER의 부분집합이라 조건을 넓혀도 지금 들어오던 건 그대로 들어온다.

둘째로 우리 레포 안에서 이 표만 기준이 다르다. mv_url_stats_1m 이랑
mv_service_health_1m 이 이미 span_kind = 'SERVER' 인데 mv_transactions 만
parent_span_id 를 본다. 한 DB 안에 두 기준이 섞여 있는 거라 맞추는 쪽이 맞다.

셋째로 조회 코드를 안 고친다. ScatterRepository 가 service_name 과 시간 범위로만 읽어서
줄이 들어오면 그대로 돈다. 화면이 서비스를 골라 보는 구조로 이미 만들어져 있으니까 표가
화면을 따라가는 게 맞다.

CONSUMER 를 같이 넣는 이유는 일이 서비스로 들어오는 방법이 HTTP 하나가 아니라서다.
큐에 쌓인 메시지를 받으면 그 스팬이 SERVER 가 아니라 CONSUMER 인데, SERVER 만 조건으로
걸면 그 서비스 스캐터가 또 빈다. 지금 문제와 똑같은 일이 작은 규모로 생기는 거다.
우리 쇼핑몰은 ADR #25에서 동기 MVC로 못 박아서 CONSUMER 가 0건이고, 그래서 지금은
SERVER 만 걸든 CONSUMER 를 같이 걸든 결과가 완전히 같다. 비용이 0이라는 뜻이다.

그런데도 넣는 이유는 쇼핑몰이 감시 대상의 전부가 아니기 때문이다. 우리 제품 전제가
에이전트만 붙이면 쓸 수 있다는 거니까 남의 앱이 들어올 수 있고, 그 앱이 Kafka 를 쓰면
그 서비스 화면이 빈다. 쇼핑몰은 시험 대상일 뿐이다. 토큰 하나 더 쓰는 거라 틀릴 일도 없다.

조건에 OR parent_span_id = '' 까지 넣는 건 지금 안 한다. Elastic 이랑 Datadog,
Pinpoint 는 그걸 다 넣는데 그러면 아무도 안 불렀는데 서비스가 스스로 시작한 일까지
잡힌다. 배치나 스케줄 잡이 거기 들어가니까 언젠가는 필요한데, 지금 우리 데이터에서
거기 걸리는 건 56줄이고 전부 앱 켜질 때 도는 CREATE TABLE 이랑 telemetrygen 이 넣은
시험 데이터다. 운영에서도 파드가 뜰 때마다 생기는 거라 로컬 잡음만이 아니고, 어느
서비스가 느린지 보려는 화면에 CREATE TABLE 점이 찍히는 건 도움이 안 된다. 진짜 배치를
만들 때 넓히는 걸 되돌림 조건에 적어 두자.

B 방식, 조회가 spans 를 직접 읽는 건 안 한다. 원본 표라 느리고 히트맵이 heatmap_1m 을
못 쓰게 되는데 그러면 집계표를 만든 이유가 없어진다.

C 방식, 지금대로 두고 중간 서비스는 안내 문구를 띄우는 것도 안 한다. 스캐터를 만든 이유가
어느 서비스가 느린지 보려는 건데 느린 서비스를 못 고르면 기능이 반쪽이다.

is_root 컬럼을 같이 넣자. toUInt8(parent_span_id = '') 한 줄이면 된다.

이게 필요한 이유는 조건을 넓히면 고객 요청 하나가 여러 줄이 되는데 표만 보고 구분할
방법이 없어지기 때문이다. 요청 하나가 서비스 4개를 지나면 4줄이 되고 count() 가 4를
준다. duration_ms 를 보면 더 분명한데 루트 줄의 240ms 가 고객이 기다린 시간이고 나머지
180 90 40 은 그 안의 부분이라 네 개를 합친 550 은 아무 뜻이 없는 숫자다. 지금은 조건이
그 구분을 해 주고 있는데 조건을 넓히면 사라지니까 조건에서 컬럼으로 옮기는 거다.

문서에 이 표로 요청 수를 세지 마라고 적어 두는 방법도 있는데 그건 막을 장치가 없고
규칙을 모르는 사람이 count() 를 쓰면 틀린 숫자가 화면에 나간다. 컬럼을 두면
service_name 으로 서비스별, is_root = 1 로 고객 요청 수를 한 표에서 다 본다.
조사해 보니 Elastic APM 에 transaction.root 라는 boolean 이 똑같은 용도로 있었다.
설명이 루트 트랜잭션 지표를 식별한다, 트레이스 단위 지표 계산에 쓸 수 있다고 적혀 있다.
표를 둘로 나눈 사례는 하나도 없고 넓게 담고 플래그로 거르는 게 업계 방식이다.

비용도 재 봤는데 985바이트다. 표 전체의 0.04퍼센트고 0과 1 두 가지뿐이라 105대 1로
압축된다. 그리고 조회가 오히려 빨라진다. is_root 는 정렬 키에 없어서 granule 을 건너뛰진
못하는데 ClickHouse 가 자동으로 PREWHERE 로 옮겨서 0.009바이트짜리 플래그를 먼저 읽고
안 맞는 줄은 trace_id 를 아예 안 읽는다. 읽는 바이트가 430KiB 에서 147KiB 로 줄고
3.0ms 가 2.0ms 가 됐다. 손으로 PREWHERE 쓸 필요도 없다.

정렬 키랑 스키핑 인덱스는 건드리지 않는다. 첫 칸에 넣으면 지금 service_name 등호로
걸리는 binary search 가 깨지고 마지막 칸은 효과가 없다. 정렬 키는 표 만들 때만 정할 수
있어서 바꾸려면 표를 다시 만들어야 한다. 스키핑 인덱스는 is_root 가 29퍼센트라 거의 모든
블록에 1이 섞여 있어서 공식 문서가 쓸모없이 비용만 든다고 경고하는 경우에 해당한다.

span_id 는 조회 쪽에 물어보고 정하자. 같은 트레이스에서 같은 서비스가 두 번 호출되면
trace_id 랑 service_name 이 같은 줄이 둘 생기는데 그때 점 하나를 그 구간으로 집으려면
필요하다. 트레이스 상세를 여는 것까지는 trace_id 로 충분하니까 요청 목록에서 줄을 눌러
해당 구간으로 바로 가는 화면을 만들 거면 넣고 아니면 안 넣는다. 재 보니까 겹치는 키가
한 키당 최대 2줄이고 평균 1.00줄이라 드물다. 그리고 trace_id String 이 이미 디스크의
78퍼센트를 먹고 있어서 같은 급 컬럼을 하나 더 넣는 건 is_root 랑 비교할 비용이 아니다.
넣기로 하면 is_root 랑 같이 넣어서 ERD 수정을 한 번에 끝낸다.

MV 를 바꾸는 방법은 ALTER TABLE ... MODIFY QUERY 를 쓴다.

조사가 샌드박스 DB 를 만들어서 여섯 방법을 직접 돌려 봤는데 집계가 비지도 중복이 생기지도
않는 게 이것뿐이었다. DROP VIEW 하고 CREATE 하는 건 운영에서 쓰면 안 된다. MV 를 지우고
4줄 넣고 다시 만들었더니 타깃에 0줄이 들어갔고 에러도 경고도 없었다. 로컬은 down -v 로
리셋하니까 안 보이는데 운영에서는 그 구간 그래프가 영구히 0이 된다. 새 이름으로 MV 를
만들어서 둘을 같이 돌리는 것도 안 된다. 소스 4줄에 타깃 8줄이 들어가서 겹친 기간만큼
정확히 두 배가 되고 우리 transactions 는 평범한 MergeTree 라 되돌릴 방법이 파티션 통째로
버리는 것밖에 없다. EXCHANGE TABLES 는 교환한 뒤에도 두 MV 가 둘 다 계속 돌아서 교체
수단이 아니다.

MODIFY QUERY 쓸 때 조심할 게 하나 있는데 이게 타깃 표 스키마를 검사하지 않는다.
SELECT 에서 컬럼을 빠뜨려도 에러 없이 통과하고 그 컬럼이 타입 기본값으로 채워진다.
service_name 을 빠뜨리면 그 뒤 모든 줄의 서비스 이름이 빈 문자열이 되는데 아무도 모른다.
타깃에 없는 컬럼을 넣어도 조용히 무시되고 타입이 달라도 암묵 캐스팅된다. 그래서 바꾼 뒤에
각 컬럼에 값이 실제로 들어오는지 확인하는 쿼리를 돌리는 단계를 절차에 넣자. 최소한 빈
문자열이나 0이 아닌지 세는 것 하나랑, 서비스가 고르게 나오는지 보는 것 하나다. gateway 만
나오면 안 바뀐 거다.

is_root 를 넣는 순서도 정해져 있다. ADD COLUMN 을 먼저 하고 그 다음에 MV 를 고친다.
거꾸로 하면 조용히 깨진다. 타깃에 없는 컬럼을 MV SELECT 에 넣으면 에러 없이 무시되니까
MV 를 먼저 고치면 그 사이 들어온 줄의 is_root 가 버려진다. 되돌릴 때는 순서가 반대인데
DROP COLUMN 이 MV 가 참조하는 컬럼을 거부하니까 MV 를 먼저 고쳐야 한다.

과거 구간 백필은 안 한다.

ADD COLUMN 의 기본값이 0이라서 지금 들어 있는 3만 줄의 is_root 가 전부 0으로 보이는데
그 줄들은 parent_span_id = '' 조건으로 들어온 거라 사실은 전부 루트다. 즉 과거 구간에서
is_root 가 정확히 거꾸로 거짓이 된다. 그런데도 백필을 안 하는 이유는 지금 배포 전이고
쌓인 게 전부 가짜 데이터라 얻을 게 없는데 위험은 크기 때문이다.

위험이 두 가지인데 하나는 heatmap_1m 이 조용히 두 배가 되는 거다. transactions 에 직접
INSERT 해도 mv_heatmap_1m 이 따라 도는 걸 조사가 실험으로 확인했고, heatmap_1m 은
SummingMergeTree 라서 같은 칸에 들어온 cnt 를 더한다. 원래 100이던 칸이 200이 되는데
줄 수가 안 늘어나니까 눈으로 안 보인다. 중복 제거가 아니라 합산이라서 그렇다.

다른 하나는 두 번 돌리면 그대로 두 배라는 거다. non_replicated_deduplication_window 가
0이고 우리는 복제 표가 아니라서 insert_deduplicate 가 효과가 없다. 되돌릴 수단은
DROP PARTITION 하나뿐이라 줄 단위로 못 지운다.

그래서 백필 대신 이 시각부터 기준이 바뀌었다를 ADR 이랑 ERD 에 적고, is_root 를 믿을 수
있는 시점 경계를 조회 쪽에 알려 주자. 로컬은 down -v 로 다 지우니까 경계가 안 생긴다.
나중에 운영 데이터가 생긴 뒤에 백필이 필요해지면 공식 문서가 권하는 별 표에 채우고
MOVE PARTITION 하는 방식으로 하고, 그 전에 직접 INSERT 가 하위 MV 를 돌리는지 샌드박스에서
한 번 더 재현하자. 조사가 공식 문서 요약과 자기 실험 결과가 반대였는데 원문을 못 봤다고
밝혀 뒀다.

적용 순서는 로컬에서 파일 고치고 down -v 하고 다시 켜고 seed 돌리는 거다. down -v 가
필요한 이유는 옛 줄 때문이 아니라 db/clickhouse/*.sql 이 빈 DB 에서만 돌아서 그냥 켜면
옛 조건 MV 가 그대로 남기 때문이다. PG 볼륨도 같이 지워지니까 seed 를 꼭 다시 돌려야
화면에 뭐가 보인다. 팀원들도 각자 해야 하니까 PR 본문이랑 AGENTS.md 에 적어 두자.

운영 마이그레이션은 별 이슈로 올리자. 조사하다 알게 된 건데 우리 운영에 ClickHouse DDL 을
바꿀 수단이 아예 없다. PG 는 postgres-migrate 컨테이너가 Flyway 로 도는데 CH 는
docker-entrypoint-initdb.d 마운트뿐이고 그게 빈 DB 에서만 돈다. 게다가 우리 파일이 전부
CREATE ... IF NOT EXISTS 라서 004 를 고쳐도 이미 떠 있는 CH 에서는 조용히 건너뛴다.
로컬에서 down -v 가 그걸 가려 주고 있었던 거다.

이번 이슈에서 005_ 파일을 만들어 둘 수도 있는데 그러면 파일은 있는데 그걸 실행할 수단이
없는 상태가 돼서 더 헷갈린다. 수단을 정하는 게 이 이슈보다 큰 일이니까 따로 올리고
AGENTS.md §6 에 적어 두자. 이번에는 004 를 고치고 로컬은 down -v 로 적용한다.

ERD 도 같이 고친다. 레포 사본 docs/design/web-v2/erd.md 의 294줄 트랜잭션(루트 스팬) 과
304줄 MV 조건, 그리고 194줄 spans.parent_span_id 설명에 비어 있으면 루트라 transactions
가 이 조건으로 골라낸다고 적혀 있는데 그 조건이 사라지니까 셋 다 바꾼다. is_root 를
넣으니까 컬럼 목록도 늘어난다. 노션이 정본이라 거기도 같이 간다.

ADR 로 남긴다. 트랜잭션의 뜻이 바뀌는 거라 4요소로 적어야 한다.

되돌리는 조건은 네 가지다. 배치나 스케줄 잡을 만들어서 부모 없는 INTERNAL 루트가 생기면
조건에 OR parent_span_id = '' 를 넣어 넓힌다. 이 표로 전체 요청 수를 세는 화면이 생기고
is_root 로 안 풀리면 표를 둘로 나눈다. 줄이 3.4배로 늘어서 스캐터 조회가 눈에 띄게
느려지면 ORDER BY 를 다시 보거나 격자로 접는 기준인 limit 5000 을 내린다. 한 서비스에
SERVER 스팬이 여러 개 생기는 구성이 들어오면, 서비스 메시 사이드카 같은 게 그런데,
중복 계수가 되니까 그때 다시 본다.

요청 목록 GET /traces/transactions 과 히트맵 GET /traces/heatmap 구현은 조회 파트 몫이라
이번 범위 밖이다. 우리는 표가 채워지게 하는 것까지 한다. ttl_only_drop_parts 를 1로
켜는 것도 조사가 덤으로 제안했는데 이번 변경과 독립적이라 따로 보자.

## `#53` [확정] 샘플링 비율의 정본을 PG 로 옮기고, 서비스별 네 줄 중 최댓값 하나만 쓴다 (`#33` `#37` 구현 · `#38` 보정)

2026-10-08 | 사용자 확정 | `#33` 이 "비율의 정본은 PG 라 재배포 없이 바뀐다" 로 정하고 `#37`(Q23)이 읽는 방법까지 정했는데 코드가 안 따라간 틈을 메운다. 메우다 보니 `#38`("설정 단위는 앱 단위만")이 샘플링에 적용되면 요청 하나가 쪼개진다는 것이 드러났다
- **채택**: ① 수집기가 `application_configs.sampling_rate` 를 **서비스별로 다 읽고 그중 최댓값 하나**를 모든 트레이스에 쓴다. 서비스별로 따로 적용하지 않는다 ② 읽는 방법은 `#37` 그대로 : **PG 직접 조회 · 30초 주기 · 실패 시 마지막 값 유지.** Entity 없이 `JdbcTemplate`, `AtomicReference` 스냅샷, TTL 은 설정으로 뺀다. 적재 처리기 `PostgresServiceCatalog` 와 같은 모양인데 **한 곳만 일부러 다르다** : 거기는 물어볼 때 낡았으면 그 자리에서 읽지만 우리는 `@Scheduled` 가 읽고 `rates()` 는 스냅샷만 준다(기각 ⑭ 의 실측) ③ **첫 조회부터 실패하면 `application.yml` 의 `0.01`**, 읽다가 실패하면 마지막 값 ④ `applications` 에 없는 서비스도 **기본값을 쓰고 그 스팬 수를 카운터로 센다**(`monimo.collector.sampling.unknown_service`) ⑤ `MONIMO_COLLECTOR_SAMPLING_RATIO` 는 **기본값 자리로만** 남긴다. PG 를 읽는 데 성공하면 PG 가 이긴다 ⑥ 로컬 seed(`scripts/seed/postgres-applications.sql`)의 비율을 `1.0000` 으로 바꾼다
- **최댓값인 이유**: 거르는 단위는 **트레이스**(요청 하나)인데 설정은 **서비스**당 한 줄이라 단위가 어긋난다. 서비스마다 다른 선을 쓰면 같은 `trace_id` 의 해시가 한쪽 선 안 · 한쪽 선 밖이 되어 트레이스가 쪼개진다. 깨지는 화면 셋은 전부 **두 서비스의 기록을 맞춰 봐야 하는 화면**이다 : 트레이스 상세는 부모가 버려지면 `(누락된 구간)` 가짜 루트 아래에 매달리고(`#50`), 고객 요청 수는 `count(*)` 와 `count(is_root = 1)`(`#52`)의 비가 깨지고, 서버맵은 간선이 부른 쪽 CLIENT 스팬 · 노드가 받은 쪽 SERVER 스팬이라 서로 다른 비율로 뽑힌다. 한 서비스 안에서 끝나는 화면(스캐터 · 히트맵 · URL 통계 · 서비스 건강)은 표본 밀도만 달라지고 틀리지 않는다. 양도 계산된다 : 1% 대 10% 면 전체 요청의 **9%** 가 고아다. 그리고 에러가 아니라 **경고 없이 틀린 값**이 뜨는 거라 증상이 샘플링 때문이라고 떠올릴 사람이 없다
- **기각**: ① **서비스별로 그대로 적용하고 쪼개짐 수용** : 사유 = 위의 9% 가 상시로 생기고 `(누락된 구간)` 이 늘 떠서 유실 경고 신호가 죽는다. 트레이스 추적은 핵심기능 1번이다. 양이 계산되는데 gateway 1%에 order 10%면 전체 요청의 9%가 고아가 된다. 그리고 에러가
나는 게 아니라 경고 없이 틀린 숫자가 뜨는 거라 증상이 샘플링 때문이라고 떠올릴 사람이
없다. 트레이스 추적은 핵심기능 1번이다. SkyWalking이 우리랑 똑같은 구조로 이 길을 가면서
비율 35 대 55 예시로 일부 세그먼트가 유실될 수 있다고 문서에 적어 놨는데 우리는 안 고른다.

C, 단조성 강제는 안 하고 되돌림에 적어 두자.

조사하다 알게 된 건데 우리 공식이 비율에 대해 단조라서 깨지는 방향이 정해져 있다. 상류
비율이 하류보다 크거나 같으면 하류가 남긴 번호표는 상류에서도 반드시 남으니까 고아가
구조적으로 생길 수가 없다. 자식만 빠지는 꼬리 잘림이 되는데 그건 하위 서비스에 에이전트가
없을 때도 생기는 거라 화면이 이미 다룬다. OTel probabilistic_sampler가 이걸 consistent
probability sampling으로 문서화해 뒀다. 다만 OTel 권장 방향은 자식 >= 부모로 우리랑
반대인데 그쪽은 하위 세부를 더 보려는 목적이고 우리는 루트가 빠지는 게 더 아프니까
반대로 가는 거다. 이건 ADR에 적어 두자.

근데 C는 고아만 막고 숫자 비 모순은 그대로 남는다. 방향만 뒤집혀서 고객 요청 1,000에
order 처리 100이 된다. 표본을 보정할지 표본이라고 표시할지는 아직 팀이 안 정한 거라 같이 풀어야 한다. 검증
코드도 API 서버 몫이라 다른 파트 일이 생기고, 호출 그래프를 코드가 알아야 해서 감시 대상이
늘면 깨진다. D가 C의 특수 경우라 다 같게 두면 조건이 자동으로 만족되니까, 서비스별로
다르게 둘 요구가 나오면 max() 떼고 검증 붙이면 된다. 버릴 코드가 없다.

E, 전역 설정 표를 새로 만드는 것도 안 한다. 참고로 이건 CH가 아니라 PG다.

뜻으로는 그게 제일 정직하다. 샘플링은 애초에 트레이스 단위라 전역 설정인데 그걸 서비스별
칸에 담은 게 어긋남의 뿌리다. 근데 PG에 전역 설정 표가 없어서 줄 하나짜리 표를 새로
만들어야 하고 주인이 API 서버라 API랑 화면이 따라온다. sampling_rate는 enabled_modules랑
log_level이 폐기된 뒤로 application_configs의 유일한 쓸모 있는 칸이라 빼면 표가 거의 빈다.
전역 설정 표 만드는 것 자체가 결정거리라 이 이슈에 끼우기엔 크다. 지금 전역 설정이 셋인데
헬스체크 주소랑 로그 하한이랑 이번 비율이고 다 env에 흩어져 있으니까 따로 올리자.
헬스체크 주소를 env에 둘 때도 샘플링 비율이 PG로 길을 뚫으면 그때 옮기자고 적어 뒀었다.

A, 루트 기준은 하고 싶어도 못 한다.

A가 gateway에서 시작한 요청이면 order 스팬도 gateway 비율을 따르게 하는 거다. 트레이스
하나에 선이 하나만 걸리니까 쪼개질 수가 없다. 조사해 보니 업계 일곱 중 여섯이 이렇게 한다.
Jaeger랑 OTel JaegerRemoteSampler, Datadog, Elastic APM, X-Ray, Pinpoint 전부 비율을 그
서비스가 입구인 트레이스에만 적용하고 하류는 전파된 결정을 따른다. Elastic 문구가 제일
선명한데 하류 서비스는 자기 비율과 무관하게 최초 서비스의 결정을 따른다고 적혀 있다.
X-Ray는 B에 규칙을 걸어도 B가 항상 A에게 불린다면 그 규칙은 영원히 적용되지 않는다고
Common Pitfall로 경고까지 해 뒀다.

못 하는 이유는 order 스팬이 왔을 때 그 트레이스의 입구가 누군지 모르기 때문이다. 스팬에
parent_span_id는 있는데 그 부모가 어느 서비스 건지는 안 적혀 있다. 부모를 못 찾는 게
아니라 부모가 누군지 알려면 기억을 해야 하는 거다. 부모 스팬은 아직 안 왔거나 에이전트
배치가 5초라 늦게 오거나 이미 처리해서 흘려보냈다. 업계가 공짜인 건 에이전트가 입구에서
판정하고 traceparent 헤더로 전파해서 하류는 헤더만 보면 되기 때문인데, 우리는 ADR #33으로
에이전트를 always_on으로 뒀으니까 그 헤더가 없다. 그래서 우리 구조에서 A는 F가 된다.

F, 스팬을 메모리에 모아 두는 것도 안 한다. 병목이 심해진다.

수집기가 스팬 데이터를 기억하는 상태를 갖게 되는데 ADR #33이 수집기 샘플링을 고른 이유가
가볍다는 거였다. 그리고 수집기가 2개 이상이 되면 LB도 필요해진다. OTel tail_sampling
README가 같은 트레이스 스팬은 전부 같은 collector 인스턴스가 받아야 한다고 대문자로 못 박아
놨다. 기본값도 30초 대기에 5만 트레이스 메모리다.

G, 수집기가 무거워지면 샘플링을 에이전트로 옮기는 건데 지금 차례가 아니다.

그게 업계 정석이고 A를 공짜로 얻는 길이긴 하다. 근데 ADR #33이 이걸 이미 되돌리는 조건으로
예약해 뒀다. 수집기 CPU랑 네트워크가 한계를 넘는 게 실측되면 에이전트 헤드 샘플링으로
전환한다고 적혀 있는데 그 실측이 없다. 틀린 방법이 아니라 아직 조건이 안 된 방법이다. 그리고 #33이 자체 Extension을
스레드 덤프 받는 것 하나로 한정해 뒀다.

읽는 방법은 ADR #37에서 이미 정해 놨다. PG를 직접 보고 30초 캐시, 실패하면 마지막 값 유지다.

적재 처리기의 PostgresServiceCatalog를 그대로 베끼면 된다. Entity 없이 JdbcTemplate으로
SQL 한 줄 치고 AtomicReference 스냅샷을 통째로 갈아끼우고, 실패하면 이전 값을 쓰면서 실패
시각은 갱신해서 매 스팬마다 PG를 다시 안 치게 하고 TTL은 설정으로 뺀다. 그 파일 짝인
ServiceCatalog.kt 주석에 수집기가 샘플링 비율을 읽는 것과 같은 성격이라고 미리 적혀 있다.
비율은 Map이 들어가니까 스냅샷 안이 불변이어야 한다. 꺼내서 수정하면 보장이 깨진다.

API 서버 경유는 #37이 이미 기각했다. 조회 장애가 수집 경로로 번지는데 수집은 99.9%,
조회는 99.5%다. 조사해 보니 실패하면 마지막 값 유지는 Jaeger랑 OTel, Elastic, SkyWalking
전원의 공통 동작이고 30초는 Elastic APM Server 기본값하고 똑같다. Jaeger랑 OTel은 60초다.

못 읽을 때 쓸 값은 두 경우로 나눈다. 읽다가 실패하면 마지막 값, 첫 조회부터 실패하면
application.yml의 0.01이다.

들고 있는 값이 있느냐 없느냐가 다르다. 첫 조회 실패에는 쓸 값이 없는데 빈 값을 그냥 쓰면
비율이 0이나 1이 되고 둘 다 사고다. PostgresServiceCatalog는 빈 집합으로 시작해도
괜찮았는데 모르는 주소는 EXTERNAL로 둔다가 틀려도 안전한 쪽이었기 때문이다. 샘플링은
안전한 쪽이 없어서 선례를 그대로 베끼면 안 되는 유일한 자리다.

1.0으로 전부 통과시키는 건 안 한다. 1% 전제로 잡은 Kafka랑 ClickHouse가 100배를 받는다.
Datadog랑 SkyWalking이 이쪽인데 그들은 보내는 쪽이 아니라 백엔드가 비율을 돌려주는 쪽이라
못 받았으면 아직 판단 재료가 없다는 뜻이다. 우리는 뒤에 저장소가 있으니까 Jaeger랑 OTel
쪽이 맞고 둘 다 0.001로 보수적으로 깐다. 0.0으로 전부 버리는 것도 안 한다. PG가 늦게 뜨는
동안 신호가 통째로 사라지고 그게 조용하다. 수집기 기동 실패도 안 한다. 수집 가용성 99.9%를
PG에 묶는 거다. Flyway 이름 규칙이 어긋나면 실행 전체를 실패시키게 해 뒀지만
거긴 기동 시점 마이그레이션이고 여긴 수집 경로라 성격이 다르다.

applications에 없는 서비스도 기본값을 주고 그 수를 카운터로 센다.

확인해 봤는데 적재 처리기가 스팬은 안 거른다. RawConsumer가 activeNames()를 peer_service
분류에만 쓰고 등록 여부랑 무관하게 다 저장한다. agents 표 등록만 건너뛰는데 그것도
application_id가 NOT NULL FK라서 못 넣는 거다. 즉 미등록 서비스를 막는 문은 수집기뿐이고
지금 열려 있다. 여기서 버리면 지금 들어오던 게 안 들어오는 동작 변경이 되고 telemetrygen이
안 보이고 서비스 등록 직후 30초 동안 그 서비스 신호가 사라진다. 이 이슈는 비율을 어디서
읽나를 바꾸는 일이라 범위를 안 넓힌다. 그리고 4317이 평문이라서 누구나 가짜 스팬을 넣을 수
있는 게 더 큰 구멍이니까, 누구를 들여보낼지는 에이전트 mTLS 할 때 한 번에 정하자.

환경변수는 기본값 자리로만 남긴다. MONIMO_COLLECTOR_SAMPLING_RATIO를 유지하되 PG를 읽는
데 성공하면 PG가 이긴다.

PG 무시 스위치로 두는 건 안 한다. 설정하면 env가 이기게 하면 운영에 켜 둔 걸 잊었을 때
화면 조작이 조용히 안 듣는다. #118에서 파일을 고쳐도 조용히 안 듣는 상황이 제일 오래
사람을 헷갈리게 했는데 같은 모양의 함정이다. Elastic도 중앙 설정이 지워지면 로컬 설정으로
돌아가는 쪽이다.

로컬 seed를 1.0000으로 바꾸자. scripts/seed/postgres-applications.sql의 0.0100을 고친다.

지금 로컬이 1.0으로 도는데 PG를 읽기 시작하면 seed 값인 1%가 적용돼서 손님 100명을 넣어도
점 한 개가 된다. 로컬 프로필에서 PG 조회를 끄는 방법도 있는데 그러면 PG 읽는 코드가
로컬에서 안 돌고 CI랑 운영에서 처음 돈다. #118에서 리뷰를 통과시킨 근거가 로컬 실데이터
확인이었으니까 그 자리를 없애지 말자.

30초 엇갈림은 안 고친다.

수집기가 여러 대면 비율을 바꾼 뒤 30초 동안 한쪽은 새 비율 한쪽은 옛 비율로 돈다. 사람이
바꿀 때만 생기고 저절로 복구되고 지금 수집기는 1대다. 없애려면 수집기끼리 설정을 맞추는
장치가 필요한데 전에 Redis를 폐기한 이유랑 같은 크기의 비용이다. SkyWalking이 같은
구조에서 값을 같게 두기를 권한다고 문서에 적어 뒀다. 버그가 아니라는 걸 ADR에 적어 둬야
나중에 누가 이걸 올리지 않는다. Datadog는 비율 상향을 직전 값의 2배까지로 제한해서 급증을
막는데 우리는 1대라 효과가 없으니까 수집기를 늘릴 때 넣는 걸로 되돌림에 적자.

해시를 뒤 7바이트로 바꾸는 것도 안 한다. OTel의 consistent sampling 사양이랑 W3C random
trace flag는 뒤 7바이트 56비트인데 우리는 8바이트에 abs()다. 아직 확정된 사양이 아니고 우리
에이전트가 그 값을 안 보내니까 이번 범위 밖이라고 적어 두자.

구현할 때 조심할 게 하나 있다. upperBound를 지금 생성자에서 한 번 계산하는데 비율이
30초마다 바뀌니까 읽을 때 계산으로 옮겨야 한다. 안 옮기면 PG를 읽어도 판정이 안 바뀌는데
로그에는 새 비율이 찍혀서 찾기 어렵다. TraceSamplerTest가 keep(span)을 7군데서 직접
부르니까 비율 공급자를 테스트에서 갈아끼울 수 있게 만들자.

확인은 PG 한 줄을 0.1로 바꾸고 30초 안에 kept랑 dropped 카운터가 바뀌는지, 네 줄이 다를 때
max()가 쓰이는지, PG 컨테이너를 멈춰도 수집이 계속 도는지, PG를 멈춘 채로 수집기를 띄워서
0.01로 가는지, 없는 서비스 이름으로 telemetrygen을 보내도 안 죽는지, down -v하고 seed
돌려서 로컬에 점이 보이는지를 본다. 적용 비율을 로그에 찍어 두면 나중에도 쓸모 있다.

조회 파트에 알릴 게 하나 있다. 코드는 안 고치는데 입력칸이 서비스별로 네 개인데 실제로는
가장 큰 값 하나만 듣는다. 화면에 한 줄 설명이 없으면 order만 내렸는데 안 듣는다는 문의가
온다. ERD의 application_configs 설명도 같이 고친다.

ADR로 남긴다. 되돌리는 조건은 네 가지다. 서비스별로 다른 비율을 쓸 요구가 나오면 C로
올라가고 그때 화면 호출 수 보정을 같이 정한다. 수집기 한계가 실측되면 ADR #33을 되돌려서
G로 가는데 그러면 전파가 생겨서 이 문제 자체가 사라진다. 외부에 OTLP 문을 열 때
미등록 서비스를 막는 걸 mTLS와 같이 정한다. 수집기를 2대 이상으로 늘릴 때 Datadog 식 2배
상한을 넣는다.

**이 프롬프트가 결정의 4요소를 그대로 담고 있다.** 채택(최댓값 하나 + 읽는 방법 + 못 읽을 때 + 미등록 + 환경변수 + 로컬 seed)과 기각(B 는 고아가 상시 · C 는 숫자 비가 남는다 · E 는 두 파트 · A 는 F 가 된다 · F 는 상태와 LB · G 는 조건 미충족)이 각각 사유와 함께 있고, 마지막 문단이 되돌리는 조건 넷이다.
