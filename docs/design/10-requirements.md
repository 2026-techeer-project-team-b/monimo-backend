# 1단계 · 서비스 정의와 요구사항

## 1. 서비스 정의 (한 문장)

**모니모니터링은 쿠버네티스 위 MSA에서 발생하는 메트릭·로그·트레이스를 에이전트로 비침습 수집해 한곳에서 조회·경보하고, 그 감시 체계 자체가 살아 있는지를 스스로 감시하는 통합 관측 플랫폼이다.**

- **감시 대상 · 제품 본연**: 쿠버네티스 위 MSA 전반. 개발·검증은 데모·부하 테스트용 **샘플 애플리케이션**으로 한다
- **감시 대상 · 자기 자신**: 우리 스택 자체 (ADR `#01` B·C평면 = 도그푸딩). 이 프로젝트의 차별점이며, 우리 서비스가 동작한 뒤부터 가능하다
- **순서**: 샘플 앱이 먼저다. 프로젝트 초기에는 우리 서비스가 아직 없어 감시할 대상이 없다 (ADR `#08`)
- **주 사용자**: 대상 서비스의 개발자·운영자 (장애 인지 → 원인 좁히기 → 대응)
- **차별점**: 감시 도구가 스스로 죽는 상황까지 다룬다 (ADR `#01` C평면)

## 2. 기능 요구사항 (FR)

| # | 기능 | 내용 | 자체/기성 |
|---|---|---|---|
| FR-1 | 에이전트 | 대상 앱에 **코드 수정 없이** 부착되어 메트릭·로그·트레이스 3신호를 수집하고 배치 전송한다. 전송 실패 시 로컬 버퍼링 후 재시도 | 기성(OTel Java Agent) + Extension 1건(스레드 덤프) — ADR `#33` |
| FR-2 | 수집기(컬렉터) | 에이전트 데이터를 수신·검증·정규화하고 Kafka로 발행한다. 스키마 위반·중복·시계 역전 데이터를 걸러낸다 | 자체 |
| FR-3 | 저장 | Kafka에서 소비해 신호별 백엔드에 적재한다. 스키마·보관정책·다운샘플링·쓰기 배칭을 소유한다. 적재 실패분은 Kafka DLQ 토픽(30일)으로, 오래된 데이터는 CH 계층 저장으로 S3에 (ADR `#34`) | 엔진은 기성, 정책은 자체 |
| FR-4 | 질의 (**API 서버**, 구 질의 파사드) | 시간 범위 · 서비스 · 라벨로 3신호를 조회하는 통합 API. 트레이스 ID로 관련 로그·메트릭을 교차 조회할 수 있다 | 파사드 자체, 엔진 기성 |
| FR-5 | 시각화 | 서비스별 상태 대시보드, 트레이스 타임라인, 로그 검색 화면, 경보 규칙 관리 화면 | **자체** (ADR `#09`) |
| FR-6 | 경보 | 규칙 정의 → 주기 평가 → 발화/해소 판정 → 채널 전송(**Slack · 이메일 · HTTPS 웹훅 · PagerDuty** 4종, SMS 없음 — 2026-09-13 사용자 확정, Q25 종결). 중복 억제와 그룹핑 포함. **3신호 전부**를 대상으로 하되 구현은 메트릭 → 로그 → 트레이스 순, 각 단계 독립 배포 (ADR `#06`) | 자체 |
| FR-7 | 메타 감시 (B평면) | FR-1~FR-6 각 서비스에 자체 에이전트를 부착해 자기 데이터를 자기 파이프라인으로 흘린다. 신규 컴포넌트 없음 | 자체 |
| FR-8 | 파수꾼 (C평면) | 스택 **바깥에서** "컬렉터 살아 있는가 / 수집 지연이 늘고 있는가" 2가지만 감시한다. 판정은 상수 하트비트가 아니라 **에이전트→Kafka→저장→질의를 실제로 관통하는 카나리의 신선도**로 한다 (ADR `#01` 주의사항) | 기성 조합 |

## 3. 비기능 요구사항 (NFR) — 확정 (ADR `#05`)

| 항목 | 확정 수치 | 근거 |
|---|---|---|
| **가용성** | 수집 경로(FR-1~FR-3) **99.9%** = 월 다운타임 43분 이내. 조회·시각화(FR-4·5)는 99.5% | 데이터는 잃으면 복구 불가라 수집이 조회보다 엄격해야 한다. 학생 팀이 단일 리전에서 달성 가능한 상한선 |
| **지연** | 수집 → 조회 가능까지 **p95 30초**. 경보 조건 충족 → 알림 발송까지 **p95 60초** | 장애 인지 시간이 1분을 넘으면 모니터링 도구로서 의미가 약해진다. Kafka 경유 파이프라인의 현실적 목표치 |
| **보관 기간** | 메트릭 원본(15초) **15일** → 1분 **90일** → 1시간 **1년** / 로그 **7일** / 트레이스 **3일** (ADR `#10`) | 신호별 데이터량 차이가 크다. 1시간 계층은 원본의 1/240 용량이라 거의 공짜인데 작년 대비 비교가 가능해진다 |
| **처리량** | 메트릭 **10,000 포인트/초** · 로그 **2,000 라인/초** · 트레이스 **500 span/초** (샘플링 후) | 2단계에서 감시 대상 서비스 수 × 인스턴스 수로 역산해 확정한다 |

### 그 밖의 제약형 비기능

- **비침습성** — 대상 앱은 에이전트 부착 외에 코드를 고치지 않는다 (제약 ④)
- **에이전트 오버헤드** — 대상 앱 CPU 3% 이내, 메모리 100MB 이내
- **데이터 유실 허용치** — 수집기 재시작 시 유실 0건(Kafka 커밋 기준), 에이전트 강제 종료 시 로컬 버퍼분만 허용
- **운영 인원** — 4명이 온콜 없이 유지 가능한 수준 (ADR `#04`)
- **유연성** — 수집 대상·저장소·알림 채널을 나중에 바꿔 끼울 수 있어야 한다. 표준 형식(OTLP) 수신과 질의 파사드(S3)가 그 장치다

### 규모 가정 (2단계에서 역산 검증)

- 초당 메트릭 **10,000 포인트** = 15초 간격 기준 **총 시계열 약 15만 개** (서버 1,500대 × 지표 100종 수준)
- **측정 대상 예시** — CPU 사용률 · 메모리 사용량 · 초당 요청 수(rps) · 응답 지연 · 메시지 큐 적체량 · 프로세스/파드 수
- **데이터 접근 패턴** — 쓰기는 항상 막대하고 일정, 읽기는 평소 한산하다 장애 때 폭증(spiky). 저장소는 쓰기 기준으로 고르고 읽기 폭증은 캐시로 받는다
