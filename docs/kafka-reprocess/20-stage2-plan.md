# Kafka 재처리 시 집계 정확성 — 2단계 비교 계획 (초안)

> 2026-10-11 · 알림 파트(박유경) · **계획 초안이다. 공유 환경의 적재 처리기 · 스키마는 바꾸지 않았다.**
> 정답을 미리 정하지 않는다. `ReplacingMergeTree` 나 커밋 방식 변경도 후보에서 빼지 않았지만, 이번 비교 대상은 아래 세 안이다.
> 기준선: [`10-baseline.md`](10-baseline.md) (커밋 전 `kill -9` → 같은 오프셋 재처리 → 원본 110 / 고유 100, 에러율 10% → 18.18%)

## 1. 비교할 세 안

| 안 | 내용 | 바꾸는 곳 |
|---|---|---|
| **0. 기준선** | 지금 설정 그대로 | 없음 |
| **1. 중복 제거 기록만 켬** | 기존 `MergeTree` · `AggregatingMergeTree` 에 `non_replicated_deduplication_window` 를 0 보다 크게 | CH 스키마 (Flyway CH, #119) |

## 2. 이 버전에서 무엇이 가능한가 — 예비 점검 (2026-10-11)

실험 CH(`clickhouse/clickhouse-server:26.8.10.6`)의 별도 DB `exp2` 에서 작은 표(원본 `MergeTree` → MV → `AggregatingMergeTree`)로 확인했다. 적재 처리기와 같은 HTTP + JSONEachRow, 서버 기본 설정. **각 1회 · 실제 `spans` 스키마 · 적재 처리기 · Kafka 는 쓰지 않았다.** 도구 `experiments/dedup_matrix_*.sh`, 원자료 `experiments/dedup-matrix-2026-10-11.txt`.

이 버전에서 확인한 설정 (`system.settings` · `system.merge_tree_settings`):
- `deduplicate_insert=enable` 이 `insert_deduplicate` · `async_insert_deduplicate` 를 대신한다 → 비동기 insert(`async_insert=1`)에서도 중복 제거가 동작했다 (B · G · H)
- `deduplicate_blocks_in_dependent_materialized_views=1` — MV 대상 표도 **자기 창이 있어야** 걸러진다 (B vs G)
- `compatibility` 빈 값(꺼짐)

## 3. 재처리 종류를 나눠서 본다

| 종류 | 언제 | 같은 바이트? | 같은 오프셋? | 안 1 (창만) | 안 2 (창 + 오프셋 토큰) |
|---|---|---|---|---|---|
| **① 같은 오프셋 재처리** | 커밋 전 크래시 · 리밸런싱 (기준선 실험) | 적재 처리기 변환이 결정적이면 같음 (**검증 필요**) | 같음 | 거를 것 (G) — 단 변환 결과 바이트가 같아야 | 거를 것 (H) — 바이트와 무관 |
| **② 새 오프셋 재발행** | 에이전트 재전송 · 수집기 재시도로 **같은 스팬이 다른 레코드**로 다시 옴 | 묶음이 같으면 같을 수도, 다시 묶이면 다름 | **다름** | 바이트가 같을 때만 (D) | **못 거름** (D2) |
| **③ 기록 범위를 넘은 재처리** | 창보다 많은 insert 뒤 재처리 · DLQ 재처리 잡(ADR #34, 다른 group) · 오프셋 되감기 · 보관 7일 재생 | — | 같거나 다름 | **못 거름** (E) | **못 거름** (E) — 토큰도 창 안에서만 기억된다 |

→ 두 안 모두 **①만** 겨냥한다. ② · ③ 은 내용 기준 키(`trace_id`, `span_id`)로 거르는 방식(예: `ReplacingMergeTree` · 조회 때 거르기 · 원본에서 재집계)이 따로 필요하고, 이번 비교 밖이다. 2단계 결과에 이 경계를 그대로 적는다.

## 4. 검증 계획 (기준선과 같은 실패 지점)

같은 도구(`reprocess_exp.sh` v2)로, 같은 입력(정상 90 커밋 → 오류 10 저장 후 커밋 전 `kill -9` → 같은 그룹 재시작)을 세 안에 넣는다.

1. **안 0** — 이미 있음 (4회).
2. **안 1** — 격리 CH 에서 `spans` 와 그 아래 **모든 MV 대상 표**에 창을 켠다: `server_map_1m` · `service_health_1m` · `transactions` · `url_stats_1m`, 그리고 `transactions` 에서 한 번 더 이어지는 `heatmap_1m` (**연쇄 MV 는 예비 점검에 없었다 — 여기서 처음 확인**). 적재 처리기는 그대로. 기대값 `EXPECT_AFTER_ROWS=100 EXPECT_AFTER_ERR=10`, 그리고 다섯 집계 표 모두 재시작 전후 같아야 한다 (도구에 표 추가 필요).
3. **안 2** — 1 + 적재 처리기에 토큰을 넣은 **실험 브랜치 jar** (공유 환경 · develop 에는 넣지 않음). 토큰 = 토픽 · 파티션 · 오프셋 · 대상 표. 기대값 2 와 같음.
4. 각 안에 ② · ③ 모양도 넣어 **못 거르는 것을 실제로 확인**한다: ② 같은 스팬을 새 레코드로 다시 발행 · ③ 창을 작게(예: 2) 두고 다른 레코드 여러 개 뒤 재처리.
5. ① 에서 안 1 이 통하려면 적재 처리기 변환이 같은 레코드에 같은 바이트를 내야 한다 → 같은 레코드를 두 번 처리해 JSON 을 비교하는 확인을 먼저 한다.
6. 반복: 안마다 최소 3회. 결과는 기준선처럼 도구 판 · 실행 환경과 함께 남긴다.

## 5. 비교 기준

| 기준 | 어떻게 재나 |
|---|---|
| 정확성 | ① · ② · ③ 각각 원본 줄 · 고유 스팬 · 다섯 집계 표 값이 기대와 같은가 |
| 정상 경로 지연 | `docs/alert/experiments/ingest_probe.py` 로 평소 · 부하 지연 (안 0 과 비교) |
| 처리량 · CH 부하 | 같은 레코드 N 개를 넣는 시간 · insert 지연 · 중복 제거 기록 파일 크기 (`system.parts` · 디스크) |
| 위험 | 토큰 충돌로 멀쩡한 데이터를 버릴 가능성(C2) · 창 크기와 insert 빈도의 관계(창이 몇 분을 덮는가) |
| 구현 범위 | 스키마만(안 1) vs 스키마 + 적재 처리기(안 2) · 메트릭 · 로그 표에도 같은 문제가 있는지 |

## 6. 수집 파트(승조)에게 공유할 것 — 초안

> 승조야, Kafka 재처리 2단계 계획 초안이야 (`docs/kafka-reprocess/20-stage2-plan.md`). 공유 환경 ingester · 스키마는 아직 안 건드렸고, 격리 CH 에서 예비로만 돌려 봤어.
>
> **알게 된 것 (예비, 각 1회)**
> - `spans` 에만 중복 제거 창(`non_replicated_deduplication_window`)을 켜면 원본은 걸러지는데 **MV 집계는 두 번 세** — 원본이랑 집계가 어긋나. MV 대상 표에도 창이 있어야 둘 다 맞았어.
> - 토큰을 잘못 만들면(내용 다른데 같은 토큰) 멀쩡한 데이터가 사라져.
> - 창이든 토큰이든 **같은 오프셋 재처리**만 막아. 새 오프셋으로 다시 온 같은 스팬, 창을 넘은 재처리(DLQ 재처리 잡 포함)는 못 막아.
>
> **바꾸게 될 수 있는 범위** (비교 끝나고 합의되면 별도 PR)
> - CH: `spans` · `transactions` · `server_map_1m` · `service_health_1m` · `url_stats_1m` · `heatmap_1m` 에 창 설정 (Flyway CH 마이그레이션)
> - (안 2 면) ingester: insert 마다 `insert_deduplication_token` (토픽-파티션-오프셋-표)
> - 메트릭 · 로그 표도 같은 문제가 있을 텐데 이번 범위에 넣을지
>
> **비교 기준**: 정확성(재처리 종류 3가지) · 정상 경로 지연 · insert 처리량 · 토큰 충돌 위험 · 구현 범위.
> 물어보고 싶은 거: ① 창 설정을 스키마에 넣는 것 자체는 괜찮아? ② ingester 코드(토큰)까지 가는 안도 비교해 봐도 될까? ③ DLQ 재처리 잡(ADR #34)이 원래 오프셋을 헤더로 들고 오게 할 계획 있어?
