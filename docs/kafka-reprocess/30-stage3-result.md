## 1. 무엇을 바꿨나

| 바꾼 것 | 자리 |

| 원본과 집계를 대조하는 점검을 더했다 (스팬 쪽 셋. 지표 · 로그는 4-1 의 이유로 뺐다) | `scripts/check-pipeline.sh` |
| 복구 절차를 **돌려 보고** 적었다 | `experiments/reaggregate_window.sh` |

2단계 계획의 **안 1(창만)** 이고 **안 2(토큰)는 안 갔다.** 안 2 는 틀렸을 때 데이터가 사라지는 쪽이라 발표 전에 더 나쁜 실패 모양을 들이지 않았다. 되돌림 조건은 ADR 에 있다.

### 켠 표가 여섯이 아니라 열인 이유

2단계 계획 §4 가 여섯을 적고 "메트릭 · 로그도 넣을지" 를 물었다. DDL 을 그려 보니 넣어야 했다.

```
spans ──┬─> transactions ─> heatmap_1m      ← 연쇄 2단
        ├─> url_stats_1m
        ├─> server_map_1m
        └─> service_health_1m
metrics_raw ─> metrics_1m ─> metrics_1h     ← 연쇄 2단
logs  (MV 없음. 그래도 원본이라 중복된다)
```

`thread_dumps` 는 API 서버가 넣는 표라 넣지 않았다.

## 3. 결과

### 3-1. 창을 켠 뒤 (3회 전부 같음)

| 시점 | 커밋 / 끝 | `spans` | 고유 | 오류 줄 | `service_health_1m` | **에러율** | `transactions` | **`heatmap_1m`** | `url_stats_1m` |
|---|---|---|---|---|---|---|---|---|---|
| 정상 90 커밋 뒤 | n / n | 90 | 90 | 0 | 90 / 0 | 0% | 90 | 90 | 90 |
| 오류 10 저장 · 커밋 전 | n / n+1 | 100 | 100 | 10 | 100 / 10 | 10% | 100 | 100 | 100 |
| `kill -9` 직후 | n / n+1 | 100 | 100 | 10 | 100 / 10 | 10% | 100 | 100 | 100 |
| **같은 그룹으로 재시작 뒤** | n+1 / n+1 | **100** | **100** | **10** | **100 / 10** | **10%** | **100** | **100** | **100** |

중복 스팬(같은 `trace_id` · `span_id` 가 2줄 이상) 조회 결과는 **빈 목록**이었다.

기준선(1단계)은 같은 자리에서 `spans` 110 · 오류 20 · 에러율 **18.18%** 였다.

### 3-2. 음성 대조 : 창을 0 으로 되돌리면 다시 틀어진다

같은 격리 환경에서 표 열 군데의 창을 0 으로 되돌리고 한 번 더 돌렸다.

| 시점 | `spans` | 고유 | `service_health_1m` | 에러율 | `heatmap_1m` |
|---|---|---|---|---|---|
| 재시작 뒤 (창 0) | **110** | 100 | 110 / 20 | **18.18%** | **110** |

1단계 숫자와 정확히 같다. **바뀐 것이 이 설정뿐이라는 증거다.** 연쇄 2단(`heatmap_1m`)도 같이 틀어지는 것을 이번에 처음 쟀다.

### 3-3. 연쇄 2단이 이어진다 (2단계 계획의 미확인 항목)

2단계 계획 §2 의 예비 행렬은 **다리 하나**(원본 → MV 대상)만 봤고 §4 가 "연쇄 MV 는 예비 점검에 없었다" 고 적어 뒀다. 이번에 `spans` → `transactions` → `heatmap_1m` 으로 실제 데이터에서 확인했다 : **다리 둘을 넘는다.** 창을 켜면 `heatmap_1m` 이 100, 끄면 110 이다.

`metrics_raw` → `metrics_1m` → `metrics_1h` 는 **같은 방식으로 재지 않았다.** 대신 롤업 함수를 보니 잴 필요가 없었다 : `avgState` · `minState` · `maxState` · `argMaxState` 는 **같은 값이 두 번 들어와도 결과가 안 바뀐다**(멱등). 즉 지표 쪽은 중복이 롤업을 틀어뜨리지 못하고, `metrics_raw` 원본 줄 수만 늘어난다. 창을 켠 것은 그 원본 줄을 막는다. 대조 점검도 그래서 지표는 원본 줄 수만 본다.

### 3-4. `peer_service` 구멍을 재현했다 (막지 않고 기록만)

조사(`research.md` 2.2)가 코드를 읽고 찾은 구멍이다 : `peer_service` 는 레코드에 없고 **PG 의 감시 대상 목록**으로 채우므로, 첫 처리와 재처리 사이에 목록이 바뀌면 같은 레코드가 다른 바이트를 낸다. 목록 캐시가 30초이고 재처리까지 약 40초라 **그 사이에 반드시 한 번 다시 읽는다.**

1단계 실험은 이 구멍을 건드릴 수 없는 구조였다 : 실험 서비스 이름(`exp-reprocess-<시각>`)이 PG 에 등록되어 있지 않아 `peer_service` 가 두 번 다 빈 글자였다.

이번에는 레코드 하나(SERVER 스팬 + CLIENT 스팬)를 창이 켜진 `spans` 표에 직접 세 번 넣어 쟀다.

| 넣은 것 | `spans` 줄 | `service_health_1m` | |
|---|---|---|---|
| ① 첫 번째 (`peer_service` 빈 글자) | 2 | 1 | |
| ② 같은 바이트 다시 | 2 | 1 | **걸렀다** |
| ③ `peer_service` 만 바뀐 같은 레코드 | **4** | **2** | **못 걸렀다** |

**한 스팬의 한 칸이 바뀌면 레코드 전체가 다른 묶음이 되어, 안 바뀐 SERVER 스팬까지 두 번 들어간다.**

안 한 것을 분명히 적는다 : **적재 처리기를 거친 전 과정으로는 재현하지 않았다.** `peer_service` 는 CLIENT · PRODUCER 스팬에만 채워지는데 실험 발신기(`produce_spans.py`)는 SERVER 스팬만 만든다. 그 길로 재려면 발신기에 CLIENT 스팬을 더하고 PG `applications` 를 실험 중에 바꿔야 한다. 위 셋으로 **중복 제거가 바이트에 민감하다는 것**은 실제 표에서 확인됐고, `peer_service` 가 바뀔 수 있다는 것은 코드로 확인됐다. 둘을 이어 붙인 결론이다.

이것을 고치는 길은 토큰(안 2)이고 이번에 안 갔다. ADR 되돌림 ① 이 그 조건이다.

## 4. 복구 절차 : 적기 전에 돌려 봤고 두 번 틀렸다

`experiments/reaggregate_window.sh <서비스> '<UTC 분>'`. 음성 대조로 망가뜨린 구간에 그대로 돌렸다.

| | 복구 전 | 복구 후 |
|---|---|---|
| `service_health_1m` cnt / err | 110 / 20 (18.18%) | **100 / 10 (10%)** |
| `transactions` | 110 | **100** |
| `heatmap_1m` | 110 | **100** |
| `url_stats_1m` | 110 | **100** |
| 원본 `spans` | 110줄 (고유 100) | 110줄 그대로 |

**처음에 적은 절차는 두 번 안 됐다.** `#119` 가 남긴 교훈("쓰는 것과 돌려 보는 것은 다른 일이다")이 또 맞았다.

1. 중복을 `GROUP BY trace_id, span_id` + `any(...)` 로 뺐고 종류 걸러내기를 **바깥 `WHERE`** 에 뒀다 → ClickHouse 가 그 조건을 안쪽으로 밀어 넣으려다 `Code: 184 Aggregate function any(service_name) AS service_name is found in WHERE in query` 로 멈췄다
2. 조건을 안쪽으로 옮겼는데 **같은 오류가 났다.** 원인이 달랐다 : 안쪽 `WHERE` 의 `service_name` 이 컬럼이 아니라 **같은 이름의 집계 별칭**으로 풀린다
3. `LIMIT 1 BY trace_id, span_id` 로 바꿨다. 집계가 아니라 "키마다 한 줄" 이라 별칭이 안 생기고 컬럼 이름이 그대로 산다 → 통했다

절차에서 알아 둘 것 셋

- **순서가 있다.** `heatmap_1m` 을 먼저 지우고 `transactions` 를 지운 뒤 `transactions` 에 넣는다. 넣으면 MV 가 `heatmap_1m` 을 **자동으로 다시 채우므로**, 순서를 바꾸면 방금 채운 것을 지운다
- **복구 `INSERT` 가 중복 제거에 걸릴 수 있다.** `INSERT SELECT` 는 `deduplicate_insert_select`(기본 `enable_when_possible`)를 먼저 보는데, 질의 모양이 바뀌면 조용히 버려질 수 있다. 그래서 끄는 것을 글자로 적어 뒀다
- **원본 `spans` 의 중복 줄은 남긴다.** 조회 · 콜트리는 `(trace_id, span_id)` 로 가려낼 수 있고, 원본까지 지우고 다시 넣으면 그 사이 콜트리가 빈 구간을 본다

자동화하지 않은 이유 : 이 일이 몇 번 필요한지 아직 세어 본 적이 없다. 되넣는 잡(ADR `#34`)을 만들 때 그때까지 손으로 돌린 횟수를 보고 정한다.

## 4-1. 대조 점검이 거짓 경보를 한 번 냈다

처음에 지표 중복도 세게 만들었다 : "한 계열(`series_hash`)의 한 시각에 점은 하나" 라는 전제였다. `check-pipeline.sh` 를 돌리자마자 `metrics_raw 에 중복 1줄` 이 떴고, 실제 데이터를 보니 중복이 아니었다.

| 실측 | |
|---|---|
| `telemetrygen` 이 같은 이름 · 같은 꼬리표(`series_hash` 동일)의 지표 셋을 보낸다 | |
| `metrics_raw.ts` 가 **초 단위**라 둘이 같은 초에 떨어졌다 | |
| **값이 서로 달랐다** (`0` 과 `1`) | 중복이 아니라 **진짜 점 둘**이다 |

값까지 키에 넣어도 낫지 않다 : 안 변하는 게이지가 같은 초에 두 번 찍히면 진짜와 구분이 안 된다. 그리고 지표는 롤업이 멱등이라 중복이 집계를 틀어뜨리지도 못한다(3-3). 그래서 **지표 · 로그 대조를 뺐고 스팬 쪽만 본다.** 사람이 보는 숫자(에러율 · P95 · 히트맵)가 전부 그쪽이다.

최종 점검 결과 : `spans 중복 0줄` · `spans(SERVER) 6 = service_health_1m 6` · `transactions 6 = heatmap_1m 6` · 관통 정상.
