## 결과

- 한 번에 됐나: **구현은 예**. 조사 단계에서는 아니오
- 고쳐 물은 횟수: **2** (둘 다 조사 단계)
- 무엇이 잘못 나왔나:
  1. **답이 두 번 잘렸다.** 60줄 이내로 형식을 정해 줬는데도 표 + 질문 5개 + 미확인 목록이 한 번에 안 들어왔다. 뒷부분(Pinpoint · SigNoz)과 미확인 목록을 따로 받아야 했다
  2. **사실이 틀렸다.** "`http.route` 는 Spring Boot actuator 에서 비어 있고 2.32.0(issue #20215 · PR #20216)에서 채워졌다" 고 단정했다. 우리 로컬 ClickHouse 에는 **에이전트 2.31.1** 로 받은 스팬에 `http.route=/actuator/health` 가 이미 채워져 있었다. 되물으니 정정했다 : 그 이슈는 **starter(라이브러리) 방식**의 라우트 탐지 경로 문제이고, `-javaagent` 는 `HandlerAdapterInstrumentation` 이 Spring 의 `BEST_MATCHING_PATTERN_ATTRIBUTE` 를 읽는 둘째 경로가 있어 actuator 도 채운다
- 고쳐 물은 말: "모순 하나 확인해 주세요. 우리 로컬 실데이터에는 2.31.1 로 받은 스팬에 `http.route` 가 채워져 있습니다. issue #20215 / PR #20216 의 정확한 범위가 무엇인지 다시 읽어 주세요"

**실데이터와 대조하지 않았으면 "`http.route` 는 못 믿는다" 로 잘못 결론 났을 것이다.** 결론(`url.path` 를 쓴다)은 같지만 근거가 "버전 때문" 에서 "규약 때문" 으로 바뀌었다. 후자가 맞다.

## 내가 틀렸던 것도 하나

설명 과정에서 내가 "쇼핑몰은 actuator `db` 지표가 안 켜져 있다" 고 말했는데 틀렸다. shop-order 는 `spring-boot-starter-jdbc` + MySQL 을 쓰고 actuator 는 DataSource 가 있으면 `db` 지표를 기본으로 켠다. 자식 스팬이 없는 진짜 이유는 그 지표가 **쿼리 대신 `Connection.isValid()`** 로 확인해서 OTel JDBC 계측이 스팬을 안 만드는 것이다. 이 구분이 중요한 이유: "지표를 켜는 날" 이 아니라 **"헬스체크가 실제 쿼리나 HTTP 호출을 하게 되는 날"** 이 고아 스팬 조건이다.
