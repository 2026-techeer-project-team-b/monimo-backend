# 그룹핑 — 한 장애에 알림이 여러 개 터질 때

> 개인 설계안 · 팀 미확정. 2026-10-06 작성. 구현 전 설계.
> 근거: FR-6 "중복 억제와 그룹핑 포함" · FN-31 "같은 경보의 반복 발송을 일정 시간 묶는다" · 알림 파트 핵심 주제 "경보 상태머신(중복 억제 + 그룹핑)".
> 이어지는 문서: `10-state-machine.md`(중복 억제) · `30-delivery.md`(outbox · 워커) · `40-agent-down.md`(전 파드 DOWN 1건)

## 1. 지금 무엇이 되어 있나

| 묶는 것 | 상태 | 어디서 |
|---|---|---|
| **같은 경보가 계속 위반** → 사건 1건, 알림 1번 | ✅ | 상태머신 (FIRING 중 반복 위반은 새 사건을 만들지 않는다) |
| **같은 서비스의 파드가 전부 DOWN** → 1건 | ✅ | AGENT_DOWN 서비스 단위 판정 (#101) |
| 같은 경보를 일정 시간마다 다시 알리기 (리마인더) | 안 함 | FIRING 은 한 번만 보낸다. FN-31 "반복 발송을 묶는다"의 가장 강한 형태 |
| **같은 서비스에서 서로 다른 규칙이 동시에 터짐** → 1건 | ❌ | ← 이번 문서 |

예: 주문 서비스가 죽어 가면 5XX_RATE · P95_LATENCY 규칙이 같이 터진다. 지금은 Slack 에 2건이 따로 간다. 규칙이 늘수록 한 장애에 알림이 N 건 쏟아진다.

## 2. 목표와 제약

- 같은 서비스 · 같은 채널로 **비슷한 시각에** 나가는 알림을 Slack 메시지 1건으로 묶는다.
- **알림 서비스가 기다리는 도중 죽어도 빠지지 않는다** (E9). 묶음 상태를 메모리에 두지 않는다.
- **복구가 발화보다 먼저 나가지 않는다** (E10).
- **NFR**: `fired_at` → Slack 60초 안 (2026-10-06 결정). 지금 실측 최대 45.8초라 **남은 여유는 약 14초**. 기다림을 넣으면 이 안에 들어야 한다.
- 탐지 · 상태머신 · outbox 표 구조는 되도록 그대로 둔다 (이미 검증된 E1~E8 을 다시 깨지 않으려고).

## 3. 사전 사실 — 같은 서비스의 규칙은 같은 주기에 평가된다

탐지는 15초마다 켜진 규칙을 서비스별로 한 번에 평가하고, AGENT_DOWN 도 같은 주기(`EvaluationScheduler.tick`)에서 돈다. 같은 1분 버킷에서 위반이 확정된 규칙들은 **같은 주기 안, 밀리초 차이로** outbox 줄이 생긴다. 그래서 "몇 초만 기다리면 같은 주기의 형제 알림이 모인다".

반대로 5XX 가 10:03 에, P95 가 10:04 에 확정되면 outbox 줄은 약 1분 차이로 생긴다. 이걸 묶으려면 1분 넘게 기다려야 한다.

## 4. 선택지

| | 묶는 범위 | 첫 알림 지연 추가 | NFR (`fired_at` → Slack, 실측 최대 45.8초) |
|---|---|---|---|
| **G1. 짧은 대기 (group_wait 10초)** ← 제안 | 같은 평가 주기에 터진 규칙 | +10초 | 최대 약 56초 ✅ (여유 4초) |
| G2. 긴 대기 (group_wait 60초) | 1분 차이로 터진 규칙까지 | +60초 | 최대 약 106초 ❌ |
| G3. Alertmanager 식 (group_wait 30초 + group_interval 5분) | 같은 그룹의 뒤이은 알림을 5분마다 모아서 | 첫 알림 +30초, 뒤이은 알림 최대 +5분 | ❌ |
| G0. 안 묶음 (지금) | — | 0 | 최대 45.8초 ✅ |

Alertmanager 기본값(group_wait 30초 · group_interval 5분 · repeat_interval 4시간)은 "알림 피로를 줄이는 대신 늦어도 된다"는 쪽이다. 우리는 NFR 60초를 정해 두었으므로 G3 은 맞지 않는다.

**제안: G1.** 같은 주기에 터진 것만 묶어도 "한 장애에 여러 규칙"의 흔한 경우(같은 버킷에서 5XX 와 P95 가 함께 넘음)를 잡는다. 1분 차이로 터지는 경우는 묶지 못하는 것을 **비용으로 인정**하고, 실측(§8 알림 감소 실험)으로 실제로 얼마나 나뉘어 가는지 본 뒤 G2 쪽으로 넓힐지 정한다.

## 5. 설계 결정 (제안)

### D15. 그룹 키 = (채널, 서비스)

- 같은 Slack 채널 · 같은 서비스의 알림을 묶는다. 서비스 이름은 outbox `payload.service_name` 에 이미 있다.
- 다른 서비스끼리는 묶지 않는다. 서비스가 다르면 담당자 · 조치가 다르다.
- 심각도(CRITICAL · WARNING)는 키에 넣지 않는다. 한 메시지에 같이 쓰고 가장 높은 것을 제목에 쓴다.

### D16. 묶음 상태 = outbox 줄 그 자체 (새 표 없음)

- 탐지는 지금처럼 outbox 에 사건 × 전이 × 채널 한 줄씩 넣는다. **바뀌는 것은 알림 서비스의 선점 조건뿐**이다.
- 선점 조건: "기다릴 만큼 기다린 줄이 하나라도 있는 그룹"을 고르고, **그 그룹의 PENDING 줄을 한꺼번에** 잡는다. 늦게 들어온 형제도 같이 나간다 (Alertmanager 에서 그룹 첫 알림이 group_wait 를 정하는 것과 같다).
  ```sql
  -- 개념. 실제 쿼리는 구현 때
  WITH ready AS (                       -- 생긴 지 group_wait 가 지난 줄이 있는 그룹
    SELECT DISTINCT alert_channel_id, payload->>'service_name' AS svc
    FROM notification_outbox
    WHERE status = 'PENDING' AND next_attempt_at <= :now AND created_at <= :now - :groupWait
    LIMIT :groups
  )
  SELECT o.* FROM notification_outbox o JOIN ready r
    ON o.alert_channel_id = r.alert_channel_id AND o.payload->>'service_name' = r.svc
  WHERE o.status = 'PENDING' AND o.next_attempt_at <= :now
  FOR UPDATE OF o SKIP LOCKED
  ```
- **E9 이 공짜로 된다**: 기다리는 동안 알림 서비스가 죽어도 줄은 PG 에 PENDING 으로 남아 있고, 다시 뜨면 같은 조건으로 묶어 보낸다.
- 비용: 형제를 PENDING 상태로 오래 두지 않으므로 표가 커지지 않는다. `payload->>'service_name'` 조회가 늘지만 PENDING 줄만 보는 부분 인덱스(`notification_outbox_due`)를 그대로 탄다.

### D17. 묶음은 한 번에 보내고, 결과는 줄마다 같은 값으로

- 그룹 하나 = Slack 호출 1번. 성공 · 실패 · 재시도 판단(`RetryPolicy`)과 서킷(E8)은 **호출 기준**이다.
- 끝나면 줄마다 `finish` 하고 `notification_history` 도 줄마다 1건 (사건 × 채널 이력 의미는 그대로). 응답 본문은 같다.
- 재시도로 미뤄지면 그룹 전체가 같은 `next_attempt_at` 을 받아 다음에도 같이 나간다. 그 사이 새 형제가 생기면 합류한다.
- 줄 하나만 실패할 수 없다 (한 번의 호출이므로). 채널이 꺼진 경우는 그룹 전체가 CANCELLED.

### D18. 복구는 발화가 끝난 뒤에만 (E10)

- RESOLVED 줄은 **같은 사건 · 같은 채널의 FIRING 줄이 끝난(SENT · FAILED · CANCELLED) 뒤에만** 선점한다. FIRING 이 재시도 대기 중이면 RESOLVED 도 기다린다.
- **보내기 전에 복구된 경우**: FIRING 이 아직 한 번도 시도되지 않았는데(`attempt_count = 0`) RESOLVED 가 생기면 둘 다 CANCELLED ("발송 전 복구"). 사람에게 "터졌다 · 풀렸다"를 연달아 보내지 않는다. N=3 · M=2 · group_wait 10초에서는 FIRING 이 이미 나간 뒤라 거의 일어나지 않고, 채널 장애로 FIRING 이 계속 밀린 경우에 생긴다.
- 같은 그룹 안에 FIRING 과 RESOLVED 가 같이 있으면 한 메시지에 나눠 쓴다.

### D19. 여러 알림 서비스 인스턴스 — 그룹이 쪼개지지 않게

- 인스턴스 두 대가 같은 그룹의 줄을 `SKIP LOCKED` 로 나눠 가지면 메시지가 2건으로 쪼개진다 (유실 · 중복은 아님).
- 막는 방법: 그룹 키로 `pg_try_advisory_xact_lock(hash)` 를 먼저 잡는다. 지금은 인스턴스 1대라 **이번 구현(#116)에는 넣지 않고, 여러 대로 늘릴 때 넣는다.** 쪼개져도 유실 · 중복이 아니라 메시지가 2건이 되는 정도라 급하지 않다.

### D20. 메시지 모양

```
[FIRING][CRITICAL] shop-order 경보 2건
• 주문 5xx 급증 — 5XX_RATE 28.9 GT 5 (발화 10:03:00)
• 주문 p95 지연 — P95_LATENCY 2400 GT 1000 (발화 10:03:00)
```
- 한 건뿐이면 지금 문구 그대로 (묶음 표시 없음).
- Slack Incoming Webhook 은 메시지 수정 · 스레드가 안 된다. 그래서 "앞 묶음에 추가"는 하지 않고, 뒤에 터진 알림은 새 메시지로 간다.

## 7. 남는 위험

- 1분 차이로 터진 규칙은 묶지 못한다 (G1 의 비용). §8 실측으로 크기를 본다.
- group_wait 10초만큼 모든 첫 알림이 늦어진다. NFR 여유가 4초로 줄어든다 → 정착 대기를 15초로 줄이면(D1-실측) 여유가 다시 커진다.
- 묶음 메시지가 길어지면 Slack 한 메시지 길이 제한(약 4만 자)에 걸릴 수 있다 → 그룹당 최대 건수를 두고 넘치면 "외 N건".

## 8. 검증 계획

| 실험 | 방법 | 기대 |
|---|---|---|
| 묶기 | 같은 서비스 규칙 3개를 같은 버킷에서 위반 | Slack 1건, 이력 3줄 |
| 다른 서비스 | 두 서비스가 동시에 위반 | Slack 2건 |
| **E9** | 묶음 대기 중 알림 서비스 종료 → 재시작 | 빠짐 없이 1건 |
| **E10** | FIRING 이 재시도 대기 중일 때 RESOLVED 생성 | RESOLVED 는 FIRING 뒤에 |
| 발송 전 복구 | FIRING 시도 전 RESOLVED | 둘 다 CANCELLED, Slack 0건 |
| **알림 감소 실측** | 쇼핑몰에 k6 에러 + 지연을 같이 넣고 order 정지까지 | 묶기 전후 Slack 건수 · 첫 알림 지연 비교 |
