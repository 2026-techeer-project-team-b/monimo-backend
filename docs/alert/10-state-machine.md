# 경보 상태머신 — 전이표와 설계 결정

> 개인 설계안 · 팀 미확정. 코드: `detector/src/main/kotlin/com/monimo/detector/alert/state/`
> 테스트: `detector/src/test/kotlin/com/monimo/detector/alert/state/` (Kotest BehaviorSpec 25건)

## 1. 용어 — 셋을 섞지 않는다

| 이름 | 뜻 | 저장 위치 |
|---|---|---|
| fingerprint | "같은 규칙 + 같은 대상". 장애가 몇 번 나도 같은 값 | `alert_events.fingerprint`, 평가 상태의 키 |
| alert_event_uuid | "이번 장애 회차". 복구 뒤 재발하면 새 값 | `alert_events.alert_event_uuid` |
| 평가 단계 NORMAL / PENDING / FIRING | 탐지 내부 전용. **공개 API 의 state 는 FIRING / RESOLVED 그대로** | 평가 상태 행 (제안) |

## 2. 전이표

입력 한 번 = **서로 다른 집계 버킷 하나에 대한 판정**(V 위반 / O 정상 / ? 판정 불가).

| 현재 | 입력 | 조건 | 다음 | 사건 · 발송 의도 |
|---|---|---|---|---|
| NORMAL | V | bad+1 < N | PENDING | 없음 |
| NORMAL · PENDING | V | bad+1 ≥ N | FIRING | **Fired**: 새 사건 UUID |
| PENDING | O | — | NORMAL (bad=0) | 없음 |
| FIRING | V | — | FIRING (good=0) | 없음 (중복 억제) |
| FIRING | O | good+1 < M | FIRING | 없음 |
| FIRING | O | good+1 ≥ M | NORMAL | **Resolved**: 같은 사건 UUID |
| 아무 단계 | ? | — | 연속 횟수 0, FIRING 이면 FIRING 유지 | 없음. `consecutive_unknown`+1 |
| 아무 단계 | 같은 버킷 | bucketEnd == last | 그대로 | Ignored `DUPLICATE_BUCKET` |
| 아무 단계 | 과거 버킷 | bucketEnd < last | 그대로 | Ignored `OUT_OF_ORDER_BUCKET` |
| 아무 단계 | 낮은 규칙 판 | ruleVersion < 현재 | 그대로 | Ignored `STALE_RULE_VERSION` |
| 아무 단계 | 높은 규칙 판 | ruleVersion > 현재 | 연속 횟수 0 후 입력 반영, 열린 사건 유지 | 입력에 따름 |
| 아무 단계 | 버킷 간격 초과 | bucketEnd − last > maxBucketGap | 연속 횟수 0 후 입력 반영 | 입력에 따름 |

예시 N=3, M=2: `V V O V V V` → 6번째에서 첫 발화. 이후 `V`×20 → 추가 발화 없음. `O V O V` → 해제 안 됨. `O O` → 해제. 다시 `V V V` → 새 UUID 로 발화.
(테스트 `AlertStateMachineTest` "N=3, M=2 규칙" 이 그대로 확인한다)

## 3. 설계 결정

### D1. N 은 "스케줄 실행 횟수"가 아니라 "서로 다른 버킷 수"로 센다

- **문제**: 평가를 10초마다 돌리고 service-health 가 1분 버킷을 주면, 같은 1분 값을 6번 읽는다. 실행 횟수로 세면 N=3 이 실제로는 "30초 연속 위반"이 되어 1분짜리 튀는 값 하나로 발화한다.
- **선택**: 평가 식별자 = `(fingerprint, bucketEnd)`. 이미 반영한 버킷은 `DUPLICATE_BUCKET` 으로 무시.
- **다른 방법과 비용**: ① 실행 횟수로 세기 — 구현은 쉽지만 평가 주기를 바꾸면 N 의 의미가 바뀐다. ② evaluation_id 를 UUID 로 새로 발급 — 재시도 식별은 되지만 "같은 데이터"는 못 걸러 낸다.
- **코드**: `AlertStateMachine.apply` 첫 부분.
- **검증**: "같은 버킷 · 과거 버킷 · 낡은 규칙 판" 테스트 3건 통과.
- **남은 위험**: 버킷 끝 시각은 API 서버 응답에서 온다. 조회 담당이 버킷 경계를 바꾸면(예: 1분 → 10초) N 의 시간 의미가 바뀐다 → 내부 API 계약에 버킷 크기를 명시해야 한다.

### D1-보강. 버킷으로 세는 정책은 제품 정책이다 — 탐지 지연과 함께 정해야 한다

"같은 버킷을 여러 번 읽어도 1회" 는 테스트로 확인했지만, 그 결과 **발화가 느려진다**. 테스트 통과와 별개로 팀이 원하는 알림 속도와 맞는지 정해야 한다.

**현재 코드가 실제로 하는 것 (사실)**

| 질문 | 지금 코드 | 문제 |
|---|---|---|
| 완료된 버킷만 세나? | **구분 안 함.** 버킷 끝 시각만 본다. 입력 신선도는 `maxStaleness`(너무 낡음)만 검사하고 "너무 최근(아직 채워지는 중)"은 검사하지 않는다 | 채워지는 중인 버킷을 평가하면 일부 표본으로 판정한다 |
| 같은 버킷 값이 나중에 바뀌면? | **무시.** 한 번 반영한 버킷은 `DUPLICATE_BUCKET` | 채워지는 중에 읽은 값(예: 첫 10초 5xx 3건/10건 = 30%)으로 확정되고, 1분 뒤 진짜 값(3건/600건 = 0.5%)은 버려진다 → 위 두 줄이 겹치면 **오발화** |
| 중간 버킷이 빠지면 연속인가? | `maxBucketGap` 설정에 달림. **기본값 null = 빠져도 연속으로 인정** | API 가 빈 버킷을 아예 안 주면(행 없음) `V _ V V` 가 3연속이 된다. 반대로 빈 버킷을 `NO_DATA` 로 주면 연속이 끊긴다 → 조회 계약에 따라 결과가 달라진다 |

**제안 (미합의)**
1. **완료된 버킷만 평가한다**: `bucketEnd ≤ now − settleDelay`. `settleDelay` = 수집 → Kafka → CH → MV 반영 지연 (NFR 수집 → 조회 p95 30초 기준으로 시작, 실측 후 조정). 이러면 "같은 버킷 값이 바뀌는" 경우가 대부분 사라지고, `DUPLICATE_BUCKET` 무시가 안전해진다.
2. **빠진 버킷은 연속을 끊는다**: `maxBucketGap = 버킷 크기(1분)`. 조회 API 가 표본 0 버킷을 행으로 주는지(→ `NO_DATA`), 빼는지 조회 담당과 확인.

**탐지 지연 — 계산값이며 측정이 아니다**

장애가 시작된 순간부터 발화 결정까지 (1분 버킷, 평가 주기 `e`, 반영 대기 `s`):

- 장애 시작이 버킷 중간이면 첫 버킷이 끝날 때까지 최대 60초. 이후 N 번째 버킷이 끝날 때까지 (N−1) × 60초
- 최악 ≈ **N × 60초 + s + e**

| N | s = 30초, e = 15초 일 때 최악 |
|---|---|
| 1 | 약 1분 45초 |
| 2 | 약 2분 45초 |
| 3 | 약 3분 45초 |

여기에 큐 대기 · 발송 시간이 더해진다.

**팀 목표와의 충돌**: NFR(`docs/design/10-requirements.md:42`)은 "**경보 조건 충족 → 알림 발송 p95 60초**". "조건 충족" 이 ① 상태머신이 발화를 결정한 순간이면 N 과 무관하게 큐 · 발송 지연만 60초 안에 들면 된다. ② 지표가 처음 기준선을 넘은 순간이면 1분 버킷으로는 N=1 도 60초를 넘는다 → 버킷 크기 · N 을 다시 정하거나 NFR 문구를 고쳐야 한다. **팀 질문 Q-S4.** 기본값 N=3 은 임시값이다.

**결정 (2026-10-06, 알림 파트 · 박유경)**: "경보 조건 충족" = **규칙 조건이 데이터상 채워진 순간**, 즉 N 번째 나쁜 버킷이 끝나는 시각(`alert_events.fired_at`)으로 본다. NFR 60초는 이 시각부터 Slack 도착까지에 적용한다.
- 근거: 이 기준으로 실측 6회 **32.0~45.8초** (아래 표 `fired_at → Slack`). 에러가 처음 난 순간을 기준으로 하면 1분 버킷 구조상 N=1 로도 30~105초라 맞출 수 없고, N 을 낮추면 오발화만 는다.
- "N 분 지속" 대기는 오발화를 막으려고 고른 값이다 (Prometheus `for:` 와 같은 성격). 그래서 NFR 대상이 아니라 **규칙 설정**으로 본다. 에러 시작부터의 전체 시간은 숨기지 않고 따로 적는다: 실측 **168~207초** (6회, 중앙 181초, N=3).
- 공용 NFR 문서(`docs/design/10-requirements.md`)의 문구는 고치지 않았다. 이 해석은 알림 파트 기준이다.

| 실측 (2026-10-01, 실제 수집 파이프라인 · 6회) | 최소 | 최대 |
|---|---|---|
| 에러 시작 → `fired_at` (N 개 버킷 대기) | 121.9초 | 174.9초 |
| `fired_at` → 판정 저장 (settleDelay + 평가 주기) | 31.7초 | 44.9초 |
| 판정 저장 → Slack 도착 (outbox · 발송) | 0.14초 | 1.16초 |
| **NFR 대상: `fired_at` → Slack** | **32.0초** | **45.8초** |

### D1-실측. 수집 지연 — settleDelay 30초의 근거

`settleDelay` 는 "1분 버킷이 끝나고 이만큼 기다려야 그 1분의 요청이 다 집계에 들어와 있다"는 값이다. 그래서 **요청 1건이 집계에 보이기까지 걸리는 시간**을 쟀다.

- 방법 (2026-10-06, 로컬 compose 한 대): 쇼핑몰 order 에 주문 1건을 보낸 순간 → 그 요청의 SERVER 스팬이 ClickHouse `spans` 에 보이는 순간. `service_health_1m` 은 같은 INSERT 에서 MV 로 채워지므로 같은 시각에 보인다. 시도마다 2~13초 쉬어 에이전트 배치 전송 주기와의 위상을 흩었다. 0.1초 간격으로 조회.
- 경로: 에이전트(스팬 배치 전송, 기본 5초 주기) → 수집기 → Kafka → 적재 처리기 → ClickHouse

| n | 최소 | 중앙 | p95 | 최대 |
|---|---|---|---|---|
| 29 | 0.74초 | 2.65초 | 5.1초 | 5.71초 |

- 30회 중 1회는 측정 방법 문제로 뺐다: 컨테이너 시계가 호스트보다 약 16ms 늦어 스팬 시작 시각(10:26:13.932436)이 측정 시작(10:26:13.932853)보다 0.4ms 앞서 조회 조건에 안 걸렸다. 스팬은 정상 저장돼 있었다.
- 해석: 지연의 대부분은 **에이전트의 배치 전송 대기(0~5초)** 이고, 수집기 → 적재 → 저장은 1초 안쪽이다. 최대 5.7초라 30초는 5배 여유다.
- **결정: 지금은 30초 유지.** 측정이 한 대 · 낮은 부하라 운영(1% 샘플링 · Kafka 지연 · 적재 재시도 #97)의 꼬리를 대표하지 못한다. 30초는 NFR "수집 → 조회 p95 30초"와 같은 값이라 근거가 맞물린다. 부하를 건 실측에서도 꼬리가 짧으면 15초로 줄인다 (설정 한 줄, 판정 지연 최대 15초 단축).

### D2. 판정 불가(?)는 연속을 끊고, 열린 사건은 닫지 않는다

- **문제**: 조회 실패나 표본 0건을 0% 로 바꾸면 장애 중 API 서버가 죽었을 때 "정상 M회"로 오복구한다. 반대로 위반 쪽으로 치면 조회 장애가 경보 폭주가 된다.
- **선택**: `?` 는 양쪽 연속 횟수를 0 으로 되돌린다. FIRING 은 유지. `consecutive_unknown` 으로 "탐지가 눈을 감고 있다"는 사실을 따로 관측한다.
- **다른 방법과 비용**: ① `?` 를 건너뛰고 연속 유지(보수성↓, `V ? V V` 가 발화) ② `?` 를 위반으로 침 → 조회 장애 = 전 규칙 발화.
- **코드**: `AlertStateMachine.apply` 의 `Verdict.Unknown` 가지, `Condition.judge`.
- **검증**: "판정 불가" 테스트 3건, `ConditionTest` NO_DATA · STALE 2건.
- **남은 위험**: 데이터가 들쭉날쭉한 저트래픽 서비스(1% 샘플링)는 영영 발화하지 못할 수 있다. 최소 표본 수 규칙과 함께 실측 필요. **팀 정책 질문 Q-S2.**

### D3. 규칙 판 번호가 바뀌면 연속만 새로 센다

- **문제**: 기준값 1% → 5% 로 고쳤는데 옛 기준으로 쌓은 위반 2회를 이어 세면 새 기준으로는 1회만 넘어도 발화한다. 반대로, 고치는 순간 FIRING 을 닫으면 "규칙 수정 = 장애 복구"가 된다.
- **선택**: 높은 판 도착 → 연속 0, 열린 사건 유지. 낮은 판 도착 → 무시.
- **남은 위험**: `alert_rules` 에 판 번호 컬럼이 없다(C2). `updated_at` 으로 대신하면 같은 밀리초 수정 두 번을 못 가른다. `application_configs.version` 처럼 INT 판 번호 추가를 제안(`20-schema-proposal.md`).

### D4. 순수 함수 + 호출자 잠금으로 동시성을 나눈다

- **문제**: 탐지 인스턴스 2개가 같은 fingerprint 를 동시에 평가하면 둘 다 "사건 없음"을 읽고 사건을 2개 만든다.
- **선택**: 상태머신은 DB 를 모른다. 호출자가 한 트랜잭션에서 ① 평가 상태 행 `SELECT … FOR UPDATE` ② `apply` ③ 상태 · 사건 · 발송 의도 저장 ④ 커밋. 늦게 잠금을 얻은 쪽은 이미 갱신된 `last_bucket_end` 를 보고 `DUPLICATE_BUCKET` 이 된다. 최종 방어선은 `alert_events (fingerprint) WHERE state='FIRING'` 부분 UNIQUE.
- **장애 순서 (방어가 없을 때)**:
  1. 탐지 A: 상태 읽음 (bad=2, NORMAL)
  2. 탐지 B: 상태 읽음 (bad=2, NORMAL)
  3. A: bad=3 → Fired(uuid-a) 저장, 커밋
  4. B: bad=3 → Fired(uuid-b) 저장, 커밋 → **사건 2개, Slack 2번**
- **방어 뒤**: 2 에서 B 는 A 의 커밋까지 대기 → A 커밋 후 B 는 last_bucket_end == 이번 버킷 → Ignored.
- **검증**: 순수 로직 부분만 검증됨. **실제 PG 두 트랜잭션 경쟁 테스트는 아직 없다 (미실행)** — PG 표가 합의돼야 만들 수 있다.

## 4. 정책 공백 — 이 코드가 가정한 값

| 항목 | 코드의 가정 | 합의 필요 |
|---|---|---|
| N · M 저장 위치 | `AlertPolicy` 로 주입 (전역 설정값) | 규칙별 컬럼으로 갈지 (공개 API 변경) — Q-S1 |
| `?` 처리 | 연속 끊음 | Q-S2 |
| maxBucketGap | 설정값, **기본 null = 빠진 버킷도 연속 인정** | 제안: 버킷 크기(1분). 조회 계약과 함께 — D1-보강 |
| settleDelay (완료된 버킷만) | 설정값 **30초** (`monimo.alert.schedule.settle-delay`, #56) | 수집 지연 실측(아래 D1-실측) 5.7초 이하 → 지금은 30초 유지, 부하 실측 뒤 조정 |
| maxStaleness | 설정값 | 수집 → CH → MV 지연 실측 후 |
| 규칙 off | 상태머신 밖. 제안: 평가 중단 + 열린 사건은 그대로 두고 표시만(자동 RESOLVED 금지) | Q-S3 |
