# AGENT_DOWN — 파드가 응답하지 않을 때

> 개인 설계안 · 팀 미확정. 2026-10-05 작성. 구현 전 설계이며 코드는 아직 없다.
> 근거: FN-29 · ERD `agents` · API 명세 40번(`agents/active`) · 아래 §2 실측.
> 재료: `agents` 표(승조 #75 가 적재 때 등록) · `GET /api/v1/internal/agents/active`(현영 10/5 구현 예정)

## 1. 명세가 말하는 것

FN-29: AGENT_DOWN 규칙이 "CH 에 해당 에이전트 데이터가 **90초** 동안 없음"을 **1분 주기**로 평가해 `agents.status` 를 DOWN 으로 바꾸고 알린다. 같은 서비스의 에이전트가 **전부 DOWN 이면 1건**으로 묶는다(ADR #35).

탐지는 1분마다 두 목록을 비교한다.

| 목록 | 출처 |
|---|---|
| 감시 대상 | PG `agents` (적재 처리기가 처음 보는 `agent_key` 를 등록) |
| 최근 데이터를 보낸 것 + 마지막 수신 시각 | `agents/active` (CH `spans` · `metrics_raw`, 파드당 한 줄) |

`agents/active` 계약(현영 답변 2026-10-04): 응답 `service_name` · `agent_key` · `last_signal_at` · `source`. `agent_key` 는 CH `agent_id` 그대로라 `agents.agent_key` 와 같은 글자이고, `agent_id` 가 빈 데이터는 뺀다. `service_name` 을 빼면 전체 서비스를 한 번에 준다. **CH 에는 "정상 종료"를 구분할 정보가 없다** — OTel 에이전트는 종료 신호를 보내지 않아, 배포로 내려간 파드도 죽은 파드처럼 데이터가 끊기기만 한다.

## 2. 실측 — `agent_key` 는 "파드"가 아니라 "JVM 한 번 실행"이다

`agent_key` 는 resource 의 `service.instance.id` → `k8s.pod.name` → `host.name` 순서로 고른다(`ingester/.../OtlpValues.kt`). 쇼핑몰은 `service.instance.id` 를 따로 설정하지 않아 **OTel Java 에이전트가 기동 때 만든 UUID** 가 들어간다.

2026-10-05 로컬 compose 에서 `shop-order` 컨테이너만 재시작해 CH `spans` 를 비교했다.

| 시점 | `agent_id` | 스팬 |
|---|---|---|
| 재시작 전 | `8fed4107-7cce-4e18-b19a-0b30fb073ed7` | 27 |
| `docker restart` 후 | `c97d8793-2910-4c20-9429-ea9a6a9d7611` (새 값) | 25 |

→ **컨테이너가 재시작되면 `agent_key` 가 바뀐다.** 쿠버네티스에서 앱이 죽어 kubelet 이 컨테이너를 다시 띄워도(파드 이름은 그대로) 우리 쪽에서는 "옛 파드가 끊기고 새 파드가 생긴 것"으로 보인다.

참고로 가짜 데이터(`scripts/seed/clickhouse-fake-signals.sql`)는 `agent_id` 를 `shop-order-7c9d5f-2xk8p` 같은 파드 이름으로 넣는다. 실데이터와 모양이 달라 가짜 데이터만으로는 이 동작이 보이지 않는다.

## 3. 문제 — 세 가지 경우가 똑같이 보인다

| 실제로 일어난 일 | 우리 쪽에서 보이는 것 | 알려야 하나 |
|---|---|---|
| 배포 (롤링 교체) | 옛 키 끊김 + 같은 서비스에 새 키 | 아니오 |
| 앱이 죽어 컨테이너 재시작 | 옛 키 끊김 + 같은 서비스에 새 키 | 반복되면 예 |
| 스케일 다운 | 옛 키 끊김 | 아니오 |
| 파드가 죽고 안 살아남 (노드 장애 등) | 옛 키 끊김, 새 키 없음 | 예 |
| 서비스 전체가 죽음 | 그 서비스의 키가 전부 끊김 | **예** |

현영 제안("옛 파드가 끊길 즈음 같은 서비스에 새 파드가 생겼으면 배포 교체", `agents.first_seen_at` 이용)은 첫째 줄을 거르는 데는 맞다. 하지만 §2 때문에 **둘째 줄(크래시 재시작)도 같이 걸러진다.** 키 하나하나로는 배포와 크래시를 가를 수 없다.

## 4. 설계 결정 (제안)

### D10. 키 하나가 끊기면 상태만 바꾸고 알리지 않는다

- **선택**: 90초 넘게 데이터가 없는 키는 `agents.status = DOWN`, 다시 들어오면 `UP`. 이것만으로는 경보를 만들지 않는다. 파드 목록 화면(S04)은 이 상태를 그대로 보여 준다.
- **이유**: §3 표에서 키 단위로 알려야 하는 줄을 가릴 수 없다. 키마다 알리면 배포할 때마다 파드 수만큼 Slack 이 울린다.
- **비용**: 파드 하나만 죽고 안 살아나는 경우(넷째 줄)는 이 규칙으로 알리지 못한다. → D13 이후 다시 본다.

### D11. 경보는 서비스 단위 — 살아 있는 키가 0 이면 발화

- **선택**: AGENT_DOWN 규칙(서비스마다 하나)은 매 분 "이 서비스에 90초 안에 데이터를 보낸 키가 하나라도 있나"를 판정한다. 0 이면 위반, 1 이상이면 정상. 상태머신(N · M)에 그대로 넣는다. fingerprint 대상은 `AlertTarget.Service` (`Fingerprint.kt` 주석의 "AGENT_DOWN 은 파드 단위"를 고친다).
- **이유**: FN-29 의 "전부 DOWN 이면 1건"을 기본 동작으로 삼는 것과 같다. 배포 · 크래시 재시작 · 스케일 다운은 살아 있는 키가 남으므로 울리지 않고, 서비스 전체가 죽으면 1건만 울린다.
- **판정 불가(D2)**: `agents/active` 호출 실패 → 그 주기는 판정 불가. **감시 중인 모든 서비스가 동시에 0** 이면 쇼핑몰이 아니라 우리 파이프라인(수집 · 적재)이 멈췄을 가능성이 크므로 역시 판정 불가로 둔다 — 그건 파수꾼이 잡을 일이다(E11).
- **감시 대상 키**: 그 서비스의 `agents` 줄 중 `status = DOWN` 으로 바뀐 지 24시간이 지난 것은 뺀다. 재시작마다 키가 늘어나므로 옛 키가 영원히 쌓이지 않게 한다(표에서 지우지는 않는다).

### D12. 크래시 반복은 "재시작 잦음"으로 따로 본다 (후속)

- 크래시 재시작은 D11 로 울리지 않는다. 대신 **일정 시간 안에 같은 서비스에 새 키가 여러 번 생기면**(`first_seen_at` 개수) 재시작이 반복되는 것이다. 배포는 몇 분에 한 번 몰려서 생기고 끝나지만 크래시 루프는 계속 생긴다.
- 기준값은 실측 없이 정하지 않는다. 이번 범위에서는 구현하지 않는다.

### D13. 근본 해결 후보 — `service.instance.id` 를 파드 이름으로 (팀 확인 필요)

- 배포 매니페스트에서 쿠버네티스 Downward API 로 `OTEL_RESOURCE_ATTRIBUTES=service.instance.id=$(POD_NAME)` 를 넣으면 컨테이너가 재시작돼도 키가 그대로다. 그러면 "새 키 = 새 파드(배포 · 스케일)", "같은 키가 끊겼다 돌아옴 = 재시작"으로 갈린다.
- 쇼핑몰 · 배포는 승조 담당이고, 승조 할 일 목록에 이미 "쇼핑몰 에이전트가 `service.instance.id` 를 채우도록 설정"이 있다. 이 값을 무엇으로 할지 같이 정하면 된다.
- D13 이 들어와도 D11(서비스 단위 경보)은 그대로 둔다. 파드 단위 알림(넷째 줄)은 그때 다시 정한다.

### D14. 규칙 값 매핑

| 규칙 칸 | AGENT_DOWN 에서 |
|---|---|
| `window_sec` | 쓰지 않는다. 침묵 기준은 FN-29 의 **90초 고정** (API 는 `window_sec` 를 60초 배수로만 받아 90 을 넣을 수 없다) |
| `operator` · `threshold` | 쓰지 않는다. 판정은 "살아 있는 키 0개" 하나뿐 |
| `severity` | 그대로 쓴다 |

**N 문제**: 지금 N=3 은 전역 값이다. AGENT_DOWN 에 그대로 쓰면 90초 침묵 + 2분 더 = 약 3분 반 뒤에 울린다. 90초가 이미 "잠깐 끊긴 것 거르기" 역할을 하므로 AGENT_DOWN 만 N=1 로 두자고 제안한다(종류별 N). 팀 확인 필요.

## 5. 탐지 쪽 판정 순서 (1분마다)

```
1. agents/active(from = now-3분, to = now)  → agent_key → last_signal_at
   실패 → 모든 AGENT_DOWN 규칙 판정 불가, 상태 변경 없음
2. 켜진 AGENT_DOWN 규칙을 읽는다 (서비스마다)
3. 서비스마다:
     keys = agents 중 이 서비스 · (DOWN 된 지 24시간 안 되었거나 UP)
     live = keys 중 last_signal_at ≥ now-90초
     keys 의 status 를 UP/DOWN 으로 맞춘다 (바뀐 것만 UPDATE)
     판정 = keys 가 없으면 판정 불가 / live 가 0 이면 위반 / 아니면 정상
4. 모든 서비스가 동시에 위반이면 → 이번 주기 전부 판정 불가로 바꾼다 (파이프라인 의심)
5. 판정을 상태머신에 넣는다 (버킷 = 평가한 분)
```

## 6. 확인 필요

`agents.status` 갱신은 이미 탐지 몫으로 정해져 있다 (`db/postgres/ingest` agents 마이그레이션 주석 "탐지(생존 상태 갱신) — ADR #39"). D13 은 이번 구현에 필요 없고, 승조 할 일(쇼핑몰 `service.instance.id` 설정)과 같이 처리되면 된다.


| 누구 | 무엇 |
|---|---|
| 팀 | FN-29 의 "AGENT_DOWN 은 파드마다 알린다"를 "서비스에 살아 있는 파드가 없을 때 1건"으로 읽는 것(D10 · D11) |
| 팀 | AGENT_DOWN 만 N=1 (D14) |

## 7. 테스트 계획

- 가짜 `agents/active` 서버로: 서비스 키 2개 중 1개 끊김 → 정상 · 상태만 DOWN / 2개 모두 끊김 → 위반 → N 회 뒤 발화 / 하나 돌아옴 → M 회 뒤 해제
- 배포 흉내: 옛 키 끊기고 새 키 생김 → 발화 없음
- 모든 서비스 동시 0 → 판정 불가, 열린 사건 유지
- API 실패 → 판정 불가
- DOWN 24시간 지난 키는 대상에서 빠짐
- 실측: 쇼핑몰 order 컨테이너 정지 → Slack 도착까지 시간 (실측 E2E 와 같은 방식)
