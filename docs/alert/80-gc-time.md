# GC_TIME — 파드가 GC 에 시간을 너무 많이 쓸 때

> 개인 설계 · 팀 미확정. 2026-10-16 작성, 구현 `#223`.
> 재료: 조회 `#197` `GET /api/v1/internal/metrics/gc-time`(API 명세 51번) · 인증 설정 `#164` `POST /api/v1/internal/thread-dumps`(4-1번) · `agents` 표.

## 1. 무엇을 보나

GC 가 도는 동안 JVM 은 앱 스레드를 멈추는 구간이 있다(stop-the-world). 그래서 "1분 중 GC 에 쓴 시간"은 **그 1분 동안 요청을 못 받은 시간**에 가깝다.
힙이 빠듯해지면 GC 가 더 자주 · 더 오래 돌고 결국 OOM 으로 죽으므로, GC 시간은 **에러율보다 먼저 오는 메모리 압박 신호**다. 경보가 열리는 순간 스레드 덤프를 떠 두면 파드가 죽은 뒤에도 그때 무엇을 하고 있었는지 남는다.

## 2. 판정

| 항목 | 정한 것 | 이유 |
|---|---|---|
| 값 | 그 1분의 `gc_time_ms` | 켜진 뒤 총합 빼기 · 재시작 · GC 종류 합산은 조회(`#197`)가 끝내서 준다. 탐지는 비교만 |
| 단위 | 규칙 `threshold` 는 **ms** | 응답 단위와 같게 |
| 창 | `window_sec` 은 안 쓴다. 1분 버킷마다 판정 | P95 와 같다. "N분 연속"은 상태머신이 센다 |
| N · M | 전역 N=3 · M=2 | 한 번 길게 튀는 full GC 는 정상에서도 난다. **계속** 높은 것만 경보 |
| 대상 | 규칙은 서비스에, 사건은 **파드마다** | fingerprint `rule\|agent\|agent_uuid`, 사건 · 상태의 `agent_id` 를 채운다(`AlertTarget.Agent` 첫 사용) |
| 없는 1분 | 판정 불가(NO_DATA) | 조회가 0 으로 채우지 않는다(값이 안 왔거나 재시작). 0ms 정상으로 치면 압박 중인 파드를 놓친다 |
| 조회 실패 | 가장 최근 버킷 하나만 판정 불가(QUERY_FAILED) | 서비스 단위 평가와 같다 |
| DOWN 파드 | 판정하지 않는다. 단 지금 GC 값을 보내면 판정 | 재시작마다 새 키가 생겨 끊긴 키가 쌓이고 그 키는 영영 NO_DATA 다. status 는 AGENT_DOWN 주기가 15초 늦게 맞춘다 |
| 표에 없는 파드 | 다음 주기로 미룬다 | 사건 · 상태의 `agent_id` 가 `agents` FK 라 적재 처리기가 등록하기 전에는 기록할 수 없다 |

### 기준값 (시작값 제안 · 실측 전)

`GT 6000` = 1분의 **10%**. 근거는 설정값이지 우리 실측이 아니다.

- G1(현재 기본 GC)의 `GCTimeRatio` 기본값 12 → JVM 스스로 "GC 는 전체의 약 1/13 ≈ 8% 이하" 를 목표로 잡는다
- Parallel GC 의 기본 목표는 1%, `GCOverheadLimit` 은 GC 98% · 회수 2% 미만이면 OOM 을 던진다
- 업계 경험칙: GC 시간 5~10% 를 넘는 상태가 이어지면 위험

10% 가 몇 분 이어진다 = JVM 이 스스로 잡은 목표를 못 지키는 상태다. 규칙 값이라 코드에 박지 않았다. 쇼핑몰 부하 실측(평소 · 고부하 · 힙 축소) 뒤 조정한다.

## 3. 자동 스레드 덤프

- 발화(`Transition.Fired`) 직후 그 파드의 `agent_uuid` 로 **한 번** 부른다. 사건 · 발송 의도는 이미 커밋된 뒤라 **기록 트랜잭션 밖**이다
- 실패(503 · 504 · 시간 초과)와 쿨다운(200 + `skipped`, 파드당 5분)은 로그만 남긴다. 경보는 그대로 나간다
- 재시도하지 않는다. 덤프는 "경보가 열린 그 순간"의 모습이라 늦게 다시 뜨면 의미가 달라진다
- 시간 한도 8초 : API 서버가 수집기 쪽 덤프를 5초까지 기다린다. 여기서 끊어도 API 서버는 끝까지 떠서 저장한다
- `monimo.alert.schedule.thread-dump.enabled=false` 로 덤프만 끌 수 있다

## 4. 알림 문구

payload 에 `agent_key` 를 싣고(파드 단위 규칙만, 서비스 단위 payload 는 그대로), 알림은 조건 뒤에 파드를 붙인다.

```
[FIRING][WARNING] 주문 GC 과다 — shop-order GC_TIME 7200.0 GT 6000 (파드 shop-order-local-1) (발화 2026-10-16T10:03:00Z)
```

같은 서비스의 파드 여럿이 동시에 울리면 그룹핑(`50-grouping.md`)이 한 메시지로 묶고, 줄마다 파드가 보인다.

## 5. 남은 것 · 위험

1. **DOWN 이 된 파드의 열린 경보는 닫히지 않는다.** 판정 불가는 사건을 닫지 않는다는 원칙(`50-grouping.md` §8-2 · 상태머신 `resetStreaks`)을 그대로 따른 결과다. OOM 으로 죽은 파드가 새 키로 뜨면 옛 키 사건이 FIRING 으로 남는다. 닫는 방식(예: 파드가 DOWN 이 되면 "대상 사라짐"으로 해제)은 팀과 정한다
2. **운영 전송 간격 60초에서 1분이 비면 다음 1분에 2분치가 들어갈 수 있다.** 조회의 빼기(`CounterDelta`)는 바로 앞 점과 빼고 시간 간격은 보지 않는다. 로컬은 `otel.metric.export.interval=10000` 이라 매 분 점이 있어 해당 없다. 운영(OTel 기본 60초)에서는 전송 틱이 분 경계를 넘으면 한 분이 비고 다음 분 값이 커져 오탐이 날 수 있다 → 조회에 "앞 점이 1분 전이 아니면 버린다" 를 제안할지 실측으로 확인
3. CPU · HEAP 은 조회 내부 문이 생기면 같은 구조(파드 목록 · `AlertTarget.Agent` · 발화 시 덤프)에 붙인다
4. 기준값 6000ms 자체는 아직 실측으로 확인하지 않았다. 아래 §6 은 시험값(20ms)으로 연결만 확인한 것이다. 힙을 줄인 압박 재현으로 따로 본다
5. 로컬 compose 전체(우리 모듈 5 + 쇼핑몰 4 + Kafka · ClickHouse · MySQL)는 Docker VM 7.6GB 로는 부하를 못 버틴다(§6). 부하 실험은 12GB 이상에서 한다

## 6. 실측 (2026-10-16, 로컬 compose, `#223` 브랜치 이미지)

쇼핑몰 실제 GC 값 → gc-time → 탐지 → Slack(실제 워크스페이스) · 자동 덤프 저장까지 끝까지 돌렸다. **연결 확인이 목적이라 기준값을 시험값 `GT 20`ms 로 낮췄다.** 쇼핑몰 힙 2GB(컨테이너 메모리의 1/4, G1)에서 초당 30건이면 1분 GC 가 70~130ms 라 6000ms 는 안 닿는다.

| 시각 (UTC) | 일 | 근거 |
|---|---|---|
| 09:12:00 | k6 초당 30건 6분 (체크 100%) | k6 |
| 09:15:00 | 발화 — `shop-order-local-1`, 관측 129ms, 3분 연속 (N=3) | `alert_events`, `agent_id` 채워짐 |
| 09:15:34 | 자동 덤프 `skipped=false`, `requested_by=detector`, 스레드 171개 (부하 없을 때 손으로 뜬 덤프는 43개) | 탐지 로그 · CH `monimo.thread_dumps` |
| 09:15:45 | Slack FIRING 도착 (발화 후 45초, 문구에 `(파드 shop-order-local-1)`) | `notification_history` SUCCESS |
| 09:20:45 | 부하가 끝나고 정상 2분 → 복구 | `alert_events` |

- **1차 시도(09:04)는 덤프만 503** : 쇼핑몰 이미지가 10/01 빌드라 덤프 Extension(monimo-shop `#35`)이 없어 `AGENT_NOT_REACHABLE`. 경보 · Slack 은 정상으로 나갔다(§3 "덤프 실패는 경보에 영향 없음" 확인). 쇼핑몰 최신 `develop` 으로 다시 빌드해 풀렸다
- **Docker VM 7.6GB 에서는 못 버텼다** : 초당 40건에서 api-server 가 OOMKilled(exit 137), 초당 20건에서도 내부 조회 셋이 3초 시간 초과. 탐지는 전부 판정 불가로 남겨 오탐 · 엉뚱한 Slack 이 0건이었다. 그때 shop-order GC 가 121 → 2,402 → 5,704ms/분까지 올랐다(1회 관측 — 컨테이너 메모리 압박이 GC 시간으로 드러난 예)
- 각 수치는 한 번씩 잰 값이다. NFR 근거로 쓰려면 반복 측정이 필요하다
