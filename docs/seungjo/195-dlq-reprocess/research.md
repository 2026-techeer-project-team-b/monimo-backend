# 리서치 : `raw.dlq` 에 쌓인 것을 되넣는 잡

- 날짜 2026-10-14 / 관련 이슈 [`#195`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/195)
- 쓴 도구: 로컬 재현(떠 있는 개발 스택에 실제로 되넣어 봤다) · 되넣는 잡의 시제품을 돌려 측정 · Kafka 머리말 직접 열어 확인

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

---

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 저장에 실패한 메시지를 안전한 칸으로 옮겨 두기만 했다. 꺼내서 다시 넣는 사람이 없고, 그 칸은 30일 뒤 스스로 지워진다
- **그래서 무엇을 만드나** : 이번 이슈는 **조사**다. 되넣는 일과 집계를 다시 세는 일을 **어떤 모양으로 둘지**를 정한다. 코드를 어디까지 만들지는 8절 뒤에 정한다
- **안 하면 어떻게 되나** : 저장이 10분 넘게 막힌 구간의 신호가 30일 뒤 사라진다. 그 전까지는 **사람이 손으로** 꺼내야 하는데 그 손 절차도 아직 글로 없다

| | |
|---|---|
| 건드리는 모듈 · 파일 | 이번(조사)에는 문서만. 구현까지 가면 `ingester`(되넣는 입구 하나) · `compose.yaml`(한 번 돌고 끝나는 서비스) · `scripts/check-pipeline.sh`(깊이 보기) · `docs/kafka-reprocess/` |
| 건드리지 않는 것 | 지금 돌고 있는 소비 경로(`RawConsumer` · `RawErrorHandlerConfig`). 되넣기는 **읽는 쪽이 하나 더 생기는 일**이고 보내는 쪽은 이미 맞다(`#96`) |
| 이 이슈 범위 밖 (후속) | DLQ 가 쌓이는 것을 **알리는 경보**(탐지 몫) · 쿠버네티스 Job 매니페스트(배포 7~9단계 · monimo-deploy `#14`) · `raw` 보관 7일을 넘긴 되감기 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정이 모양을 미리 정해 뒀다 : **같은 이미지 · 쿠버네티스 Job · `ingester` 가 아닌 다른 그룹.** 고를 것이 많이 남아 있지 않다고 생각했다
- 「집계 중복은 CH 중복 제거 기억으로」 결정 되돌림 ④ 가 **"되넣는 잡을 만들 때는 반드시 재집계를 같이 정한다"** 로 선조건을 걸어 뒀고, 그 이유를 **"기억 밖 재처리를 창도 이름표도 못 막으므로"** 로 적어 뒀다. 그래서 **기억 안이면 괜찮다**고 읽고 있었다
- `#96` 때 머리말 `x-dlq-attempt` 를 "재처리 잡이 N번 넘으면 포기를 판단할 때 쓴다" 는 용도로 미리 만들어 뒀다. 그 머리말이 **어떻게 이어지는지**는 안 재 봤다

**알고 싶었던 것**

① 되넣으면 데이터가 **실제로 돌아오나** ② 잡이 두 번 돌면 **중복**이 생기나 ③ 되넣기로 **집계까지** 고쳐지나 ④ 머리말을 **어디까지** 가져가야 하나 ⑤ 쌓인 깊이를 보는 **올바른 숫자**가 무엇인가 ⑥ 쿠버네티스가 없는 지금 **무엇이 이 잡을 돌리나**

## 2. 작업하기 전에 알아야 하는 것

### 2.1 `raw.dlq` 는 무엇이고 지금 무엇이 들어 있나

- 저장에 실패한 Kafka 메시지를 **원본 그대로** 옮겨 두는 토픽이다
  - 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정 · 「적재 실패 세 단 : pause · 독성만 DLQ · 분류 뒤집기」 결정
- 파티션 1개 · 보관 30일 (`raw` 는 7일)
- 넣는 코드는 `RawErrorHandlerConfig` 의 복구 담당이고 **꺼내는 코드는 없다**

| 재 본 것 | 값 |
|---|---|
| 끝 오프셋 | **6** (조사 전에는 4) |
| 그 4건의 정체 | `Code: 243`(디스크 부족) · 원래 그룹 `exp-diskfull2` = **`#191` 실험이 만든 것**. 트레이스 3건 · 지표 1건 |
| 만들어진 시각 · 지워지는 시각 | 2026-10-14 05:18 → **2026-11-13 05:18** (발표 10/31 보다 **뒤**다) |
| 메시지 하나의 머리말 | **13개 · 약 6,033바이트.** 값은 406바이트다 |
| 머리말에 들어 있는 것 | 우리 둘(`x-dlq-attempt` · `x-dlq-reason`) · 스프링 열(`kafka_dlt-original-topic` · `-partition` · `-offset` · `-timestamp` · `-timestamp-type` · `-consumer-group` · `-exception-fqcn` · `-exception-cause-fqcn` · `-exception-message` · `-exception-stacktrace`) · 수집기가 붙인 `network.peer.address` |
| 읽는 컨슈머 그룹 | **0개** (`ingester` · `exp-diskfull` · `exp-diskfull2` 셋뿐이고 전부 `raw` 를 읽는다) |

**값보다 머리말이 15배 크다.** 스택 추적 한 장이 통째로 실려 있기 때문이다. 되넣을 때 이걸 그대로 가져가면 `raw` 에 스택이 흘러 들어가고, 다시 실패하면 그 위에 또 쌓인다.

### 2.2 데이터는 어디로 흐르나

```
에이전트 → 수집기 → Kafka raw(7일) → 적재 처리기 → ClickHouse 원본 셋 → MV 일곱 → 집계
                          ↑                  │
                          │                  └─ 실패 → Kafka raw.dlq(30일)
                          │                              │
                          └──────────────────────────────┘
                              되넣는 잡 (없다. 이번 조사 대상)
```

| 질문 | 답 |
|---|---|
| 실패한 데이터는 어디에 쌓이나 | Kafka `raw.dlq` 파티션 0 |
| 얼마나 보관하나 | **30일.** 지나면 Kafka 가 지운다. 그때가 진짜 유실이다 |
| 누가 꺼내나 | **아무도.** 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정이 "적재 처리기의 관리 잡" 으로 정해 뒀고 코드는 0줄 |
| 되넣으면 어디로 가나 | `raw` 로 다시 발행한다. 키가 그대로라 같은 파티션에 들어가고, 지금 돌고 있는 `ingester` 그룹이 **평소처럼** 집어 간다. 적재 처리기에 새 코드가 필요 없다 |

### 2.3 되넣기는 중복을 만드나 (실측 : 기억이 막는다)

**두 번 돌려 봤다.** 같은 4건을 서로 다른 그룹으로 두 번 되넣었다.

| | spans | `uniqExact` | metrics_raw | transactions | heatmap_1m 합 |
|---|---|---|---|---|---|
| 되넣기 전 | 228,538 | 228,538 | 44,023 | 103,195 | 103,195 |
| **1차** 되넣기 뒤 | 228,544 (**+6**) | 228,544 | 44,026 (**+3**) | 103,198 (**+3**) | 103,198 (**+3**) |
| **2차** 되넣기 뒤 (같은 4건) | 228,544 | 228,544 | 44,026 | 103,198 | 103,198 |

- **①에 답 : 돌아온다.** 트레이스 3건(스팬 2개씩) · 지표 3줄이 실제로 들어왔고 집계까지 따라왔다
- **②에 답 : 두 번 돌려도 중복이 안 생긴다.** `#187` 이 켠 중복 제거 기억(표 열 군데 · 창 100)이 같은 블록을 버린다. 원본과 집계가 **같이** 안 늘었다
- 단, 이것은 **기억 안에 있을 때**만 참이다. 창 100은 블록 수이고 시간이 아니다. 되넣기와 원래 실패 사이에 블록 100개가 들어갔으면 못 막는다

### 2.4 되넣기는 집계를 못 고친다 (실측 : 기억이 막는 것이 문제다)

- 2.3 이 좋은 소식이면 이쪽은 나쁜 소식이다
- **같은 장치가 원인**이다

- 저장이 중간에 깨지는 모양이 하나 있다
  - **원본에는 들어갔고 MV 중 하나가 터져** 전체가 예외로 끝난다
  - `#191`(디스크 포화를 재서 Q30 · Q31 을 닫은 건) 에서 실제로 본 문구가 `while pushing to view` 였다
- 그러면 그 메시지는 `raw.dlq` 로 가는데 **원본에는 이미 줄이 있다**

- 그 상태를 손으로 만들어 되넣어 봤다
  - 트레이스 하나(`d3de0545…`)의 집계 줄만 지우고 같은 메시지를 다시 넣었다

| | spans | transactions |
|---|---|---|
| 집계 줄을 지운 직후 | 2 | **0** |
| 그 메시지를 되넣은 뒤 | 2 | **0** |

- 적재 처리기 로그는 `spans 적재: 2줄` 을 찍었다
- **보냈지만 아무것도 안 들어갔다**
  - 원본 블록이 기억에 남아 있어 ClickHouse 가 블록을 버렸다
  - `deduplicate_blocks_in_dependent_materialized_views = 1` 때문에 **MV 가 아예 안 돌았다**

- **③에 답 : 안 고쳐진다.** 되넣기는 "원본에 없는 것" 만 되살린다. 원본에 있고 집계에만 없는 구멍은 **되넣기로 영원히 안 메워진다**
- 그 구멍을 메우는 길은 **원본에서 다시 집계하는 것** 하나뿐이다. 지금은 손 절차다(`docs/kafka-reprocess/experiments/reaggregate_window.sh`, `#187` 에서 돌려 보고 적었다)
- 실제로 그 절차로 되돌렸다 : `INSERT ... SELECT` 에 `deduplicate_insert_select = 'disable'` 을 붙여 103,198 로 복구

**「집계 중복은 CH 중복 제거 기억으로」 결정이 적어 둔 이유를 고쳐 읽어야 한다.** 되돌림 ④ 는 재집계가 필요한 이유를 "기억 **밖** 재처리를 못 막으므로" 로 적었다. 측정은 더 센 것을 말한다 : **기억 안에서도 재집계가 필요하다.** 기억이 되넣기의 안전장치이면서 동시에 복구를 막는 장애물이다. 결론(둘을 같이 정한다)은 그대로고 사유가 바뀐다.

**그리고 손으로 고칠 때 순서를 틀리면 다음 단이 틀어진다.** 집계 줄을 되살렸더니 `heatmap_1m` 합이 103,199(+1)가 됐다. `transactions` → `heatmap_1m` 연쇄가 한 번 더 돌았기 때문이다. `reaggregate_window.sh` 가 `heatmap_1m` → `transactions` 순으로 지우는 이유가 이것이고, 조사 중에 그 함정을 그대로 밟았다. 그 분 버킷을 지우고 다시 넣어 103,198 로 맞췄다.

### 2.5 포기 횟수를 세려면 머리말을 가져가야 한다 (실측)

- 되넣은 것이 **또 실패**하면 어떻게 되나
- 독성 메시지(키 `logs` · 값 `0x0F`)를 머리말을 넣은 채와 뺀 채로 각각 한 번 보냈다

| 보낸 모양 | `raw.dlq` 에 다시 들어온 것 |
|---|---|
| `x-dlq-attempt: 1` 을 **가져갔다** | `attempt=2` · `reason=poison` |
| 머리말을 **버렸다** | `attempt=1` · `reason=poison` |

- **④에 답 : `x-dlq-attempt` 는 반드시 가져가고 `kafka_dlt-*` 는 버린다.** 전자를 버리면 횟수가 매번 1로 돌아가 **영원히 도는 고리**가 된다. 후자를 가져가면 6KB 스택이 `raw` 를 타고 다닌다
- `network.peer.address`(수집기가 붙인 보낸 쪽 주소, 「파드 주소는 수집기가 읽어 Kafka 헤더로」 결정)도 가져간다. 버리면 **그 메시지로 처음 등록되는 파드**의 `agents.ip` 가 빈칸이 된다. 이미 등록된 파드는 안 다친다 : `PostgresAgentRegistry.needsWrite()` 가 "주소를 모르는 메시지는 아는 파드라면 할 일이 없다" 로 멀쩡한 주소를 지우지 않게 만들어져 있다(telemetrygen 처럼 메모 없는 메시지가 섞여 들어오기 때문)
- 되넣은 것이 또 실패하면 `raw.dlq` 의 **끝**(새 오프셋)에 붙는다. 그래서 **왕복한다** : 다음에 잡을 돌리면 지난 회차가 남긴 것을 읽어 또 되넣는다. 하루에 한 번 돌리면 **하루에 한 바퀴씩 영원히** 돈다
- 그래서 포기 규칙(`x-dlq-attempt` 가 N 을 넘으면 되넣지 않는다)이 **왕복을 끊는 유일한 장치**다. 「적재 실패 세 단 : pause · 독성만 DLQ · 분류 뒤집기」 결정 결정 프롬프트가 "보통 3번에서 5번 정도" 로 미리 적어 뒀다
- **여기서 내가 두 번 틀렸다.** 처음에는 "한 회차 안에서는 고리가 안 생긴다 : 앞에서부터 읽으니 자기가 만든 것을 다시 안 읽는다" 고 적었다. 구현해서 **돌려 보니 돌았다** : 잡이 빈 poll 이 날 때까지 읽으므로 방금 자기가 만든 실패분을 같은 회차에서 집어 갔다(한 회차 안에서 `attempt 3 → 4` 를 봤다). 그래서 **한 회차는 시작 시점의 끝까지만 읽도록** 경계를 박았다(`consumer.endOffsets` 를 첫 poll 에서 한 번 적어 둔다). 고치고 다시 돌려 `raw.dlq@9 부터는 이번 회차가 만든 것이라 다음 회차로 넘긴다` 를 확인했다

### 2.6 돌릴 수단은 셋 있다 (처음에 "없다" 고 적었는데 틀렸다)

- 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정은 **쿠버네티스 Job** 으로 정했다
- 그런데 쿠버네티스가 아직 없다 (배포 7~9단계 · monimo-deploy `#14` 가 로컬 클러스터부터 시작한다)

| 레포에 이미 있는 "한 번 돌고 끝나는" 모양 | 무엇을 하나 |
|---|---|
| `kafka-init` | 토픽을 만들고 끝난다 |
| `postgres-migrate` · `clickhouse-migrate` | 마이그레이션을 돌리고 끝난다. `infra-ready` 가 정상 종료를 기다린다 |

- **이 절의 제목을 처음에 "돌릴 수단이 없다" 로 적었는데 틀렸다.** 쿠버네티스가 없어서 못 만드는 것은 **「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정이 적어 둔 그 모양**뿐이고, 같은 일을 하는 수단이 지금 레포에 **둘 더** 있다. 레포를 다시 세어 보고 알았다.

    | 모양 | 레포의 선례 | 지금 되나 | 주기 실행 |
    |---|---|---|---|
    | **가.** compose 의 한 번 돌고 끝나는 서비스 + 사람이 부른다 | `kafka-init` · `postgres-migrate` · `clickhouse-migrate` | **된다** | 안 된다(사람이 부른다) |
    | **나.** 적재 처리기 안에 `@Scheduled` | 수집기(샘플링 비율 갱신) · 탐지(`EvaluationRunner`) · 알림(`DeliveryConfig`) | **된다** | **된다** |
    | 다. 쿠버네티스 Job · CronJob (「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정) | 없음 | 안 된다 | 된다 |

- **⑥에 답 : 지금 못 하는 것은 "스스로 주기적으로 도는" 쪽이 아니라 "운영 플랫폼이 실행 기록 · 실패 재시도 · 동시 실행 방지를 대신 해 주는" 쪽이다.** 가와 나는 오늘도 만들 수 있다. 다만 **나(같은 프로세스 안)는 되넣기가 적재와 한 프로세스에서 돌아** 그룹 · ClickHouse 연결 · 실패 처리가 섞인다. `RawErrorHandlerConfig` 주석이 "나중에 이 모듈에 `@Scheduled` 가 들어오면" 을 가정해 `TaskScheduler` 빈을 `defaultCandidate = false` 로 막아 둔 것도(「JDBC socketTimeout 10초 · 낡음 게이지」 결정) 그 섞임을 미리 막은 것이다.
- 그리고 **손으로 시작하는 쪽에 선례가 둘 있다** : 「전역 설정 표는 지금 안 만든다」 결정 · 「배포 순서는 손으로 · 인증서 두 묶음」 결정 ①(순서는 손으로 시작한다) · 「집계 중복은 CH 중복 제거 기억으로」 결정 기각 ⑥("주기로 돌리면 멀쩡한 집계를 매번 다시 쓴다"). 즉 **쿠버네티스가 없다는 것이 진짜 제약이 아니고**, 제약처럼 보였던 것은 내가 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정의 글자를 전제로 읽었기 때문이다.
- 쿠버네티스가 생기면 **같은 이미지 · 같은 명령**을 Job 으로 옮긴다. `#119` 가 `clickhouse-migrate` 에 대해 같은 판단을 적어 뒀다("운영에서 무엇이 이 컨테이너를 실행하나는 배포 7~9단계에 달렸고, 같은 이미지를 쓰면 되므로 그때 정한다")
- 그룹 이름은 `ingester` 가 **아니어야** 한다. **다만 그 이유를 처음에 틀리게 적었다** : "파티션 배분이 섞인다" 고 썼는데 재 보니 **안 섞인다.** `ingester` 라는 같은 이름으로 `raw.dlq` 만 구독해 붙여 보니 받은 것은 `raw.dlq-0` 하나였고 `raw` 파티션은 적재 처리기가 그대로 들고 있었다. 할당은 **구독한 토픽만** 따라간다
- 진짜 비용은 **리밸런스**다. 잡이 붙을 때와 끝날 때 각각 한 번, 적재 처리기의 `raw-0 · raw-1 · raw-2` 가 `revoked` 되고 다시 `assigned` 됐다(실측 **211밀리초 · 229밀리초**). 그 사이 `raw` 소비가 멈춘다. 그리고 장부 하나에 두 토픽이 섞여 `--describe` 로 상태를 볼 때 헷갈린다. 별 이름(예 `dlq-reprocess`)을 쓰면 둘 다 안 생긴다

### 2.7 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| `monimo.ingester.dlq` 가 DLQ 에 쌓인 양이다 | **아니다.** **그 프로세스가 보낸 수**다. 지금 지표는 2 를 말하고 토픽에는 6 건이 있다. 재시작하면 0 으로 돌아간다 |

## 3. 1차 질문 (사람 차례)

> 승조가 2 를 읽고 모르는 것을 여기에 적는다. 답은 바로 아래에 붙인다.
> **비어 있으면 아직 안 물은 것이다. 대신 채우지 않는다.**

- **Q. 그 4건의 정체가 일부러 만든 트레이스 · 지표 하나인 것인지**
  - A. **일부러 만든 것이 맞다.** 넷 다 `#191` 디스크 포화 실험이 만들었고, 데이터 자체도 실제 쇼핑몰이 아니라 **가짜 발신기(telemetrygen)** 가 만든 것이다. 레코드를 열어 보니 트레이스 셋은 `service.name = telemetrygen` · 스팬 이름 `lets-go`(CLIENT) · `okey-dokey-0`(SERVER), 지표 하나는 `service.name = telemetrygen` · 지표 이름 `gen` 세 개다. 즉 **쇼핑몰 데이터는 한 건도 안 들어 있다.**
  - A. **"트레이스 3건 · 지표 1건" 의 단위는 메시지(Kafka 레코드)다.** 스팬 수가 아니다 : 트레이스 레코드 하나에 스팬이 **2개**(SERVER + CLIENT) 들어 있어 셋을 되넣었더니 `spans` 가 **+6** 이었다. 지표 레코드 하나에는 포인트가 **3개** 들어 있어 `metrics_raw` 가 **+3** 이었다. 그래서 "4건" 과 "+6 · +3" 이 안 맞아 보이는 것이 정상이다 (`DlqCounter` 주석도 "단위는 메시지다 : 스팬 수가 아니라 Kafka 레코드 수" 로 적어 뒀다).
  - A. 그래서 **지금 들어 있는 것은 잃어도 되는 데이터다.** 되넣는 잡이 급하지 않은 이유의 절반이 이것이고(나머지 절반은 만료가 2026-11-13 로 발표 뒤라는 것), 반대로 **진짜 데이터가 들어오면 그 시계가 처음부터 돈다**는 뜻이기도 하다.

- **Q. 메시지 머리말에 대한 설명**
  - A. **머리말(Kafka 헤더)은 메시지 봉투에 붙이는 쪽지다.** 봉투 안의 내용물(값 = OTLP protobuf 바이트)은 한 글자도 건드리지 않는다는 약속(「수집기는 OTLP 를 풀지 않고 바이트 그대로 발행」 · 「raw 메시지 형식은 OTLP protobuf 바이트 그대로」 결정)이 있어서, 보내는 쪽만 아는 사실을 받는 쪽에 넘길 때 **내용물 대신 쪽지에 적는다.** 이름 = 글자, 값 = 바이트인 쌍의 목록이고 글자가 아니어도 된다.
  - A. 오프셋 0 의 쪽지 13장을 그대로 열면 이렇다.

    | 쪽지 | 값 | 누가 붙였나 · 왜 |
    |---|---|---|
    | `network.peer.address` | `172.19.0.8` | **수집기**가 gRPC 연결에서 읽어 붙인다(「파드 주소는 수집기가 읽어 Kafka 헤더로」 결정). 적재 처리기가 `agents.ip` 에 적는다 |
    | `kafka_dlt-original-topic` | `raw` | 스프링이 붙인다. **원래 어디 있었나** |
    | `kafka_dlt-original-partition` | `0` (**4바이트 정수**) | 같음. 글자 `"0"` 이 아니라 숫자다 |
    | `kafka_dlt-original-offset` | `0` (**8바이트 정수**) | 같음. `raw` 안의 몇 번째 메시지였나 |
    | `kafka_dlt-original-timestamp` | `1791919934609` (**8바이트 정수**) | 같음. 2026-10-13 19:32:14 UTC |
    | `kafka_dlt-original-timestamp-type` | `CreateTime` | 그 시각이 **보낸 시각**이라는 뜻(브로커가 받은 시각이 아니다) |
    | `kafka_dlt-original-consumer-group` | `exp-diskfull2` | **누가 읽다가 실패했나.** 이 값으로 "내 실험이 만든 것" 을 알아냈다 |
    | `kafka_dlt-exception-fqcn` | `ListenerExecutionFailedException` | 겉껍데기 예외. 스프링이 감싼 것이라 늘 같다 |
    | `kafka_dlt-exception-cause-fqcn` | `com.clickhouse.client.api.ServerException` | **진짜 원인.** 분류(`FailureClassifier`)가 보는 자리 |
    | `kafka_dlt-exception-message` | 388바이트 | 사람이 읽는 한 줄. `Code: 243` 이 여기 있다 |
    | `kafka_dlt-exception-stacktrace` | **5,144바이트** | 스택 추적 한 장 통째로. 머리말 6,033바이트의 **85%** 가 이것이다 |
    | `x-dlq-attempt` | `1` | **우리가** 붙인다. 이 레코드가 DLQ 를 몇 번 거쳤나 |
    | `x-dlq-reason` | `transient` | 우리가 붙인다. 어느 분류로 왔나(`poison` · `transient` · `unknown`) |

  - A. **되넣을 때 셋만 가져가는 이유가 이 표에서 바로 나온다.** `kafka_dlt-*` 열 장은 **그때 그 실패의 기록**이라 되넣는 메시지에는 쓸모가 없고(다시 실패하면 스프링이 새로 붙여 준다) 5KB 스택이 `raw` 를 타고 다니게 된다. 반대로 `x-dlq-attempt` 는 **라운드를 넘어 이어져야 하는 유일한 값**이고(2.5 실측), `network.peer.address` 는 수집기만 알던 값이라 버리면 복구할 데가 없다.
  - A. 자동 쪽지는 카운터로 **못 쓴다** : `stripPreviousExceptionHeaders` 기본값이 `true` 라 다시 실패할 때마다 덮어써진다. 그래서 `#96` 에서 `x-dlq-attempt` 를 따로 만들었고, 같은 이름이 쌓이지 않게 `SingleRecordHeader`(지운 뒤 더하기)로 넣는다.

- **Q. "읽는 컨슈머 그룹 0개" 는 파일을 말하는 건가**
  - A. **파일이 아니다.** 컨슈머 그룹은 **Kafka 안에 있는 장부**다 : "이 이름이 이 토픽의 이 파티션을 어디까지 읽었나" 를 브로커가 기억한다. 그 장부는 Kafka 의 내부 토픽 `__consumer_offsets` 에 들어 있다(이 브로커의 토픽 목록이 `__consumer_offsets` · `raw` · `raw.dlq` 셋이다).
  - A. **파일에 있는 것은 그 이름뿐이다.** `ingester/src/main/resources/application.yml` 의 `spring.kafka.consumer.group-id: ingester` 한 줄이 "나는 `ingester` 라는 이름으로 읽겠다" 고 말하는 자리다. 이름을 바꾸면 **다른 장부**를 쓰게 되고, 그 장부가 비어 있으면 `auto-offset-reset: earliest` 때문에 **토픽을 처음부터 다시 읽는다.**

    **[준비할 때]** 소비자가 붙으면서 이름(`group-id`)을 말한다. 브로커가 그 이름의 장부를 찾아(없으면 만들어) 파티션을 나눠 준다. 같은 이름이 여럿 붙으면 **파티션을 쪼개 나눠 갖는다**
    **[읽을 때마다]** 메시지를 처리한 뒤 "여기까지 했다" 를 그 장부에 적는다(커밋). `ack-mode: RECORD` 라 레코드마다 적는다(`#187`)
    **검사 ①** 지금 이름이 **미리 가진 것**인가 : `application.yml` 에 적힌 `ingester`. 바꾸면 처음부터 다시 읽는다
    **검사 ②** 커밋 위치가 **방금 생긴 것**인가 : 브로커가 들고 있고 재시작해도 남는다. 그래서 적재 처리기를 죽였다 살려도 이어서 읽는다

  - A. 그래서 **"읽는 그룹이 0개" 는 "꺼내는 사람이 없다" 와 같은 말이다.** 이 브로커에 장부가 셋 있는데(`ingester` · `exp-diskfull` · `exp-diskfull2`) 세 장부가 전부 **`raw` 것**이다. `raw.dlq` 앞에 선 이름이 하나도 없다.

    | 장부 이름 | 무엇을 읽나 | 어디까지 · lag |
    |---|---|---|
    | `ingester` | `raw` 파티션 0 · 1 · 2 | 512 / 18 / 0 : **lag 0** (따라잡았다) |
    | `exp-diskfull` | `raw` 파티션 0 · 1 | 64 · 16 : lag 448 · 2 (`#191` 실험이 버리고 간 것) |
    | `exp-diskfull2` | `raw` 파티션 0 | 4 : lag 508 (같음) |
    | **없음** | **`raw.dlq`** | **셀 수 없다** |

  - A. 그리고 이것이 2.7 의 "깊이 = lag" 과 이어진다 : **장부가 없으면 lag 이라는 숫자 자체가 안 생긴다.** 되넣는 잡을 만드는 일은 꺼내는 일만이 아니라 **깊이를 볼 수 있게 만드는 일**이기도 하다.

- **Q. CH 쪽에서 막았는데 Kafka 에서 재처리해 다시 CH 로 넣는 것이면, 나중에 들어온 데이터가 시계열에서 문제가 되지 않나**
  - A. **늦게 들어오지만 늦은 자리에 안 들어간다.** 줄의 시각은 넣은 시각이 아니라 **데이터 안의 시각**(`spans.start_time` · `metrics_raw.ts` · `logs.ts`)이다. 그래서 과거 칸에 꽂힌다. 실측으로 확인했다 : 되넣은 스팬의 `start_time` 은 `2026-10-13 19:32:14` 였고 실제로 넣은 시각은 `21:57` 이다(**2시간 25분 뒤**). `heatmap_1m` 에 생긴 버킷은 `ts_min = 19:32` 였다.
  - A. 그래서 **걱정하지 않아도 되는 것 넷**이 있다.

    | 걱정 | 실제 |
    |---|---|
    | 집계 숫자가 틀어지나 | **아니다.** MV 가 insert 시점에 **그 버킷**에 더하므로 결과가 맞아진다. 「집계 워커 폐지 · 재집계는 적재 처리기 책임」 결정이 이미 "재처리분의 지연 도착도 MV 가 insert 시점에 자동 반영" 으로 적어 뒀다 |
    | TTL 에 걸려 넣자마자 지워지나 | **구조적으로 안 생긴다.** DLQ 는 최대 **30일**인데 TTL 이 `spans` · `transactions` 93일 · `logs` 97일 · `metrics_raw` 105일 · `heatmap_1m` 120일 · `metrics_1m` 180일이다 |
    | 정렬이 깨지나 | 아니다. `ORDER BY` 로 조각을 합치므로 자리를 찾는다. 과거 파티션에 조각이 하나 더 생길 뿐이다(`spans` · `transactions` 는 날짜 단위, 집계는 월 단위) |
    | 죽은 에이전트가 살아 보이나 | 아니다. AGENT_DOWN 은 CH 의 **데이터 시각**으로 "90초 동안 없음" 을 보므로(`docs/alert/40-agent-down.md`) 과거 줄은 그 창에 안 들어간다. PG `agents` 쪽도 `ON CONFLICT DO NOTHING` 이라 `first_seen_at` 이 안 바뀐다 |

  - A. **진짜 문제는 둘이고 둘 다 "시각" 이 아니라 "이미 읽어 간 사람" 쪽이다.**
    - ① **지나간 숫자가 바뀐다.** 같은 화면을 두 번 보면 19:32 가 10건에서 11건이 된다. 과거를 고치는 것이 맞는 동작이지만 **같은 시각을 두 번 조회하면 답이 다르다**
    - ② **경보는 되살아나지 않는다.** 탐지 상태 기계가 과거 버킷을 **`OUT_OF_ORDER_BUCKET` 으로 무시**한다(`docs/alert/10-state-machine.md` : `bucketEnd < last` 면 그대로). 되넣은 에러가 그 1분의 임계값을 넘겼어야 해도 **발화하지 않는다**
  - A. 그래서 **되넣기의 값은 경보가 아니라 기록이다.** 그 1분의 판정은 이미 끝나 있고 사후 보정이 안 된다. 되넣는 잡이 급하지 않다는 판단과 같은 방향이다 : 막는 쪽(`#96` 의 pause 10분)이 경보를 지키고, 되넣기는 **나중에 조회 · 분석할 데이터**를 지킨다.
  - A. **8절에서 정할 것이 하나 늘었다** : 되넣은 뒤 그 구간을 **다시 평가할지**(탐지에 과거 구간 재평가 입구를 두는 것) 또는 **안 한다고 명시할지.** 지금은 둘 다 안 적혀 있어 "조용히 안 한다" 로 동작한다.

## 5. 선택지와 설명

### 조사 프롬프트

- 원문은 같은 폴더의 [`prompts.md`](prompts.md) 에
- 조사 서브에이전트를 쓰지 않았다

### 나온 선택지

- 승조가 3절까지 읽고 직접 적은 것을 그대로 쓴다

```
compose 에 한 번 돌고 끝나는 서비스
적재처리기와 분리 + K8s Job /CronJob으로 넘어가기 쉽다
근데 계속 사람이 한 번씩 관리해줘야 함
적재 처리기 안에 @Scheduled 넣어서 주기적으로 실행
주기적으로 자동으로 재처리 가능
적재처리기와 같은 프로세스로 돌아서 CH 연결이랑 실패 처리가 섞인다
쿠버네티스 Job /CronJob 사용
Job : K8s가 파드를 한 번 띄우고 처음부터 끝까지 돌리는 작업
CronJob : Job을 매 일정시간마다 반복
```

| 방법 | 얻는 것 | 포기하는 것 | 구현 크기 |
|---|---|---|---|
| **가. compose 의 한 번 돌고 끝나는 서비스** | 적재와 **분리**된다 · 다로 옮기기 쉽다(명령 그대로) · 언제 돌렸는지 사람이 안다 | **주기 실행 없음.** 사람이 한 번씩 불러야 한다 | 입구 하나 + compose 10줄 |
| 나. 적재 처리기 안에 `@Scheduled` | **주기 실행이 공짜** · 새 컨테이너 없음 | 적재와 **같은 프로세스** : ClickHouse 연결 · 실패 처리 · 컨슈머 그룹이 섞인다. 끄려면 재배포 | 입구 하나 + `@Scheduled` |
| 다. 쿠버네티스 Job · CronJob (「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정) | 실행 기록 · `backoffLimit` 재시도 · `concurrencyPolicy` 중복 실행 방지를 플랫폼이 해 준다 | **지금 돌릴 클러스터가 없다**(배포 7~9단계) | 가 + 매니페스트 |

**결정을 가르는 축**

| 방법 | 적재와 분리되나 | 주기 실행 | 지금 돌 수 있나 | 다로 옮기는 비용 |
|---|---|---|---|---|
| **가.** | **된다** | 사람이 부른다 | **된다** | **매니페스트만** |
| 나. | 안 된다 | 자동 | **된다** | 코드를 옮겨야 한다 |
| 다. | 된다 | 자동 | 안 된다 | : |

**가** 는 "한 번 돌고 끝나는 컨테이너" 라는 모양이 쿠버네티스 Job 과 **같은 모양**이다. 그래서 `docker compose run --rm dlq-reprocess` 가 나중에 Job 매니페스트의 `command` 로 그대로 옮겨간다. `#119` 가 `clickhouse-migrate` 로 같은 길을 이미 걸어 뒀고 그 ADR(`#57`)이 "운영에서 무엇이 이 컨테이너를 실행하나는 배포 7~9단계에 달렸고, 같은 이미지를 쓰면 되므로 그때 정한다" 로 적어 뒀다.

**나** 는 주기 실행이 공짜인 대신 되넣기가 적재와 한 프로세스에서 돈다. 되넣기가 ClickHouse 를 때리다 실패하면 적재 쪽 실패 처리(`DefaultErrorHandler` · pause)와 엉키고, 끄려면 재배포해야 한다. `RawErrorHandlerConfig` 가 `TaskScheduler` 빈을 `defaultCandidate = false` 로 막아 둔 것도(「JDBC socketTimeout 10초 · 낡음 게이지」 결정) 이 모듈에 `@Scheduled` 가 들어올 때를 미리 대비한 것이다. **그 대비가 있다는 것이 "들어와도 된다" 는 뜻은 아니다.**

**다** 가 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정이 정한 모양이지만 클러스터가 없다. 그리고 주기 실행이 지금 필요한 근거가 없다 : 돌릴 이유가 생긴 횟수가 **0번**이다(`raw.dlq` 6건이 전부 내 실험이 만든 것). 팀이 같은 기준을 세 번 썼다(「전역 설정 표는 지금 안 만든다」 결정 · `#66` ① · `#67` 기각 ⑥ : **기계를 만들기 전에 횟수를 센다**).

### 셋 다 공통으로 필요한 것

- 방법을 어느 것으로 고르든 이 다섯은 같다

| | 무엇 | 근거 |
|---|---|---|
| ① | `raw.dlq` 를 **`ingester` 가 아닌 그룹**(`dlq-reprocess`)으로 읽는다 | 같은 이름이면 리밸런스가 두 번(실측 211 · 229밀리초) 나서 적재가 멈춘다 (2.6) |

### AI 가 틀렸거나 덜 맞았던 것 (남겨 둔다)

- **"같은 그룹을 쓰면 파티션 배분이 섞인다"** : 틀렸다. 재 보니 구독한 토픽만 받는다. 진짜 비용은 리밸런스 두 번이다 (2.6)
- **"되넣은 것이 또 실패해도 고리가 안 된다"** : 두 번 틀렸다. 왕복하는 것이 먼저 드러났고(회차를 넘어), 구현해 돌려 보니 **한 회차 안에서도** 돌았다. 그래서 한 회차의 끝 경계를 코드에 박았다 (2.5)
- **"K8s 가 없어서 못 만든다"** : 틀렸다. 레포에 `@Scheduled` 선례가 세 모듈에 있다. 못 하는 것은 플랫폼이 기록 · 재시도 · 중복 실행 방지를 대신 해 주는 쪽뿐이다 (2.6)
- **"되넣은 메시지만 `agents.ip` 가 빈칸이 된다"** : 과장이었다. **그 메시지로 처음 등록되는 파드**만 그렇다 (2.5)
- **「집계 중복은 CH 중복 제거 기억으로」 결정 되돌림 ④ 의 사유를 그대로 믿었다** : "기억 밖 재처리를 못 막으므로" 로 읽고 있었는데, 재 보니 **기억 안에서도** 재집계가 필요하다 (2.4)

### 확인 못 한 것

- **창 100이 실제 운영 부하에서 몇 분인가.** 개발 스택은 거의 놀고 있어 `traces` 가 148분에 35건이었다. 쇼핑몰에 k6 를 걸고 다시 재야 한다
- **`async_insert = 1` 에서 "insert 하나 = 묶음 하나" 가 유지되나.** `#187` 이 이 설정에서 창이 통하는 것은 확인했지만 서버가 여러 insert 를 한 묶음으로 모으는지는 안 쟀다. 모으면 창 100이 덮는 insert 수가 달라진다
- **부분 쓰기를 진짜로 만들어 본 것은 아니다.** `while pushing to view` 를 재현하지 못해 **집계 줄을 손으로 지워** 그 상태를 모사했다. 결과(MV 가 안 돈다)는 같은 장치를 타므로 같겠지만 실제 경로는 아니다
- **되넣은 구간을 다시 평가하는 길이 있는지.** 탐지 쪽 코드를 안 읽었다. 상태 기계 문서만 봤다

## 7. 2차 정리

- 6절은 비어 있다 : 승조가 5절을 읽고 바로 "구현해줘" 로 넘어갔다
- 5절의 선택지 중 **가**(compose 의 한 번 돌고 끝나는 서비스)를 골랐다

- **구현에서 더 정한 것** : 포기 횟수 3 · 멈춤은 커밋하지 않는다(그래서 lag 이 남아 점검이 말한다) · 독성은 건너뛰고 커밋한다 · 되넣은 구간을 로그에 찍는다 · **한 회차는 시작 시점의 끝까지만 읽는다**

### 구현하면서 또 틀린 것 둘 (돌려 보고 알았다)

- **되넣은 구간을 DLQ 레코드의 시각으로 찍었다.** 그 시각은 DLQ 로 옮겨 적은 때라 실패를 기다린 시간만큼 뒤에 있다. 실측으로 **46분** 벌어졌다(원래 발행 `19:32` · DLQ 기록 `20:18`). 그대로 두면 사람이 **엉뚱한 분**을 재집계한다. `kafka_dlt-original-timestamp`(8바이트 정수)를 읽는 것으로 고쳤다
- **"한 회차 안에서는 고리가 안 생긴다" 가 틀렸다.** 잡이 빈 poll 까지 읽으므로 방금 자기가 만든 실패분을 같은 회차에서 집어 간다. 시작 시점의 끝을 경계로 박아 고쳤다

### 창이 표마다 따로 밀리는 것을 실제로 봤다 (예상한 것이 일어났다)

- 2.3 에 "같은 되넣기가 `spans` 에서는 막히고 `metrics_raw` 에서는 중복이 될 수 있다" 고 적었다
- 구현한 잡을 돌리니 **그대로 일어났다**
- 같은 네 건을 처음 되넣은 때로부터 약 **22시간** 뒤였다

| 표 | 결과 | 왜 |
|---|---|---|
| `spans` | 228,544 그대로 (`uniqExact` 도 같다) | 그동안 `traces` insert 가 거의 없어 창에 지문이 **남아 있었다** |
| `metrics_raw` | 44,026 → **44,029 (+3)** | `metrics` 는 계속 들어와 창 100을 **밀어냈다** |
| `transactions` · `heatmap_1m` | 103,198 그대로 | `spans` 가 안 들어갔으니 MV 도 안 돌았다 |

- 중복된 세 줄은 `telemetrygen` 의 `gen` 지표다 (`19:32:16` 값 0 · 1 · `19:32:17` 값 2)
  - 각각 두 줄이 됐다
- **롤업은 영향을 받지 않았다**
  - `metrics_1m` 의 그 1분은 `avg 1 · min 0 · max 2` 로 중복이 없을 때와 같다
- 「집계 중복은 CH 중복 제거 기억으로」 결정이 적어 둔 "지표 중복은 롤업을 틀어뜨리지 못한다(멱등)" 를 **실측으로 확인한 셈**이다

### 여기서 나온 면접 질문

1. 실패분을 다시 넣는 잡을 만들 때, 왜 "넣는 것" 만으로 복구가 안 되나
2. 같은 메시지를 두 번 넣어도 중복이 안 생기게 하는 장치가 있는데, 그 장치가 오히려 복구를 막는 경우는 무엇인가
3. 재처리한 데이터가 과거 시각으로 들어가면 경보는 어떻게 되나. 왜 그렇게 설계했나
4. 되넣기가 무한히 왕복하지 않게 하는 것은 무엇인가. 읽는 순서로 막을 수 있나

> **아래는 AI 가 쓴 예시다.** 8절은 원래 승조가 직접 쓰는 자리인데, 4 · 5절을 바탕으로

> 승조가 자기 말로 다시 쓰면 **그 글이 정본**이고, 같은 원문을 [`prompts.md`](prompts.md) 와 ADR 안에 둔다.

```
raw.dlq 에 들어간 것을 다시 raw 로 되넣는 잡을 만든다. 모양은 compose 의 한 번 돌고
끝나는 서비스로 하고, 로컬 쿠버네티스가 생기면 같은 이미지 · 같은 명령을 Job 으로 옮긴다.

고른 것

① 모양은 compose 서비스 dlq-reprocess 다. docker compose run --rm dlq-reprocess 로

② 그룹 이름은 dlq-reprocess 다. ingester 를 쓰면 안 된다. 같은 이름이면 잡이 뜰 때와

③ 머리말은 셋만 가져간다. x-dlq-attempt · x-dlq-reason · network.peer.address.

④ x-dlq-reason = poison 은 건너뛴다. 되넣으면 그대로 또 실패한다. 건너뛴 수를 센다.
⑤ x-dlq-attempt 가 3 을 넘으면 되넣지 않고 남겨 둔다. 한 회차 안에서는 고리가 안 생기지만

⑦ 재집계는 같이 정하되 자동화하지 않는다. 잡이 끝나면 "되넣은 구간" 을 화면에 적어 주고,

버린 것과 이유

가. 아무것도 안 한다 : 30일이 지나면 진짜 유실이다. 지금 들어 있는 6건이 내 실험이 만든
    것이어서 아프지 않을 뿐이고, 진짜 데이터가 한 건 들어오는 순간 그 시계가 처음부터 돈다.
나. 적재 처리기 안에 @Scheduled : 되넣기가 적재와 한 프로세스에서 돈다. ClickHouse 연결 ·
    실패 처리 · 컨슈머 그룹이 섞이고 끄려면 재배포해야 한다. 주기 실행이 공짜인 것은 맞지만
    주기 실행이 지금 필요한 근거가 없다 : 돌릴 이유가 생긴 횟수가 0번이다.
다. 쿠버네티스 Job · CronJob 을 지금 : 클러스터가 없다. 그리고 가가 다의 전 단계라
    버리는 것이 아니라 미루는 것이다.
라. 머리말을 전부 가져간다 : 멀쩡한 raw 토픽에 5KB 스택이 7일 동안 실려 다닌다.
마. 머리말을 전부 버린다 : x-dlq-attempt 가 매번 1 로 돌아가 영원히 왕복한다(실측).
바. 독성까지 되넣는다 : 그대로 또 실패해서 DLQ 를 키운다.
사. 재집계를 자동으로 돈다 : 틀어졌는지 아는 쪽(대조 점검)이 이제 막 생겼고 손으로 고친
    횟수가 0번이다. 전역 설정 표 · 배포 순서 · 집계 중복 결정에서 같은 기준을 세 번 썼다.
아. DLQ 를 비운다 : 비울 수 없다. Kafka 는 읽어도 지우지 않고 커밋 위치만 올라간다.
    되넣은 것은 30일이 지나면 스스로 사라진다.

되돌리는 조건

① 사람이 되넣기를 실제로 두 번 부르게 되면 주기 실행(나 또는 다)으로 올린다.
② 되넣은 뒤 집계가 어긋난 일이 실제로 두 번 생기면 재집계를 잡 안으로 넣는다(집계 중복 결정의
   되돌림 ③ 과 같은 기준).
③ x-dlq-attempt 3 에 걸려 남는 메시지가 쌓이면 그 분류를 FailureClassifier 의 독성 목록에
   올린다(적재 실패 세 단 결정의 되돌림 ②).
④ 되넣은 구간의 경보를 놓친 것이 실제로 문제가 되면 탐지에 과거 구간 재평가 입구를 만든다.
   그때 상태 기계의 연속 셈을 어떻게 다룰지 알림 파트와 같이 정한다.
⑤ 적재 처리기가 2대 이상이 되면 창 100 과 함께 이 잡의 동시 실행 방지를 다시 본다.
```
