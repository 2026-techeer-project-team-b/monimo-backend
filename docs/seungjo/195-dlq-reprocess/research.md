# 리서치 : `raw.dlq` 에 쌓인 것을 되넣는 잡

- 날짜 2026-10-14 / 관련 이슈 [`#195`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/195)
- 쓴 도구: 로컬 재현(떠 있는 개발 스택에 실제로 되넣어 봤다) · 되넣는 잡의 시제품을 돌려 측정 · Kafka 머리말 직접 열어 확인

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 저장에 실패한 메시지를 안전한 칸으로 옮겨 두기만 했다. 꺼내서 다시 넣는 사람이 없고, 그 칸은 30일 뒤 스스로 지워진다
- **그래서 무엇을 만드나** : 이번 이슈는 **조사**다. 되넣는 일과 집계를 다시 세는 일을 **어떤 모양으로 둘지**를 정한다. 코드를 어디까지 만들지는 8절 뒤에 정한다
- **안 하면 어떻게 되나** : 저장이 10분 넘게 막힌 구간의 신호가 30일 뒤 사라진다. 그 전까지는 **사람이 손으로** 꺼내야 하는데 그 손 절차도 아직 글로 없다

| | |
|---|---|
| 건드리는 모듈 · 파일 | 이번(조사)에는 문서만. 구현까지 가면 `ingester`(되넣는 입구 하나) · `compose.yaml`(한 번 돌고 끝나는 서비스) · `scripts/check-pipeline.sh`(깊이 보기) · `docs/kafka-reprocess/` |
| 건드리지 않는 것 | 지금 돌고 있는 소비 경로(`RawConsumer` · `RawErrorHandlerConfig`). 되넣기는 **읽는 쪽이 하나 더 생기는 일**이고 보내는 쪽은 이미 맞다(`#96`) |
| 이 이슈 범위 밖 (후속) | DLQ 가 쌓이는 것을 **알리는 경보**(탐지 몫) · 쿠버네티스 Job 매니페스트(배포 7~9단계 · monimo-deploy `#14`) · `raw` 보관 7일을 넘긴 되감기 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- ADR `#34` 가 모양을 미리 정해 뒀다 : **같은 이미지 · 쿠버네티스 Job · `ingester` 가 아닌 다른 그룹.** 고를 것이 많이 남아 있지 않다고 생각했다
- ADR `#67` 되돌림 ④ 가 **"되넣는 잡을 만들 때는 반드시 재집계를 같이 정한다"** 로 선조건을 걸어 뒀고, 그 이유를 **"기억 밖 재처리를 창도 이름표도 못 막으므로"** 로 적어 뒀다. 그래서 **기억 안이면 괜찮다**고 읽고 있었다
- `#96` 때 머리말 `x-dlq-attempt` 를 "재처리 잡이 N번 넘으면 포기를 판단할 때 쓴다" 는 용도로 미리 만들어 뒀다. 그 머리말이 **어떻게 이어지는지**는 안 재 봤다

**알고 싶었던 것**

① 되넣으면 데이터가 **실제로 돌아오나** ② 잡이 두 번 돌면 **중복**이 생기나 ③ 되넣기로 **집계까지** 고쳐지나 ④ 머리말을 **어디까지** 가져가야 하나 ⑤ 쌓인 깊이를 보는 **올바른 숫자**가 무엇인가 ⑥ 쿠버네티스가 없는 지금 **무엇이 이 잡을 돌리나**

## 2. 작업하기 전에 알아야 하는 것

### 2.1 `raw.dlq` 는 무엇이고 지금 무엇이 들어 있나

저장에 실패한 Kafka 메시지를 **원본 그대로** 옮겨 두는 토픽이다(ADR `#34` · `#51`). 파티션 1개, 보관 30일(`raw` 는 7일). 넣는 코드는 `RawErrorHandlerConfig` 의 복구 담당이고, 꺼내는 코드는 **없다.**

| 재 본 것 | 값 |
|---|---|
| 끝 오프셋 | **6** (조사 전에는 4) |
| 그 4건의 정체 | `Code: 243`(디스크 부족) · 원래 그룹 `exp-diskfull2` = **`#191` 실험이 만든 것**. 트레이스 3건 · 지표 1건 |
| 만들어진 시각 · 지워지는 시각 | 2026-10-14 05:18 → **2026-11-13 05:18** (발표 10/31 보다 **뒤**다) |
| 메시지 하나의 머리말 | **13개 · 약 6,033바이트.** 값은 406바이트다 |
| 머리말에 들어 있는 것 | 우리 둘(`x-dlq-attempt` · `x-dlq-reason`) · 스프링 열(`kafka_dlt-original-topic` · `-partition` · `-offset` · `-timestamp` · `-timestamp-type` · `-consumer-group` · `-exception-fqcn` · `-exception-cause-fqcn` · `-exception-message` · `-exception-stacktrace`) · 수집기가 붙인 `network.peer.address` |
| 읽는 컨슈머 그룹 | **0개** (`ingester` · `exp-diskfull` · `exp-diskfull2` 셋뿐이고 전부 `raw` 를 읽는다) |

**값보다 머리말이 15배 크다.** 스택 추적 한 장이 통째로 실려 있기 때문이다. 되넣을 때 이걸 그대로 가져가면 `raw` 에 스택이 흘러 들어가고, 다시 실패하면 그 위에 또 쌓인다.

### 2.2 데이터는 어디로 흐르나

```
에이전트 → 수집기 → Kafka raw(7일) → 적재 처리기 → ClickHouse 원본 셋 → MV 일곱 → 집계
                          ↑                  │
                          │                  └─ 실패 → Kafka raw.dlq(30일)
                          │                              │
                          └──────────────────────────────┘
                              되넣는 잡 (없다. 이번 조사 대상)
```

| 질문 | 답 |
|---|---|
| 실패한 데이터는 어디에 쌓이나 | Kafka `raw.dlq` 파티션 0 |
| 얼마나 보관하나 | **30일.** 지나면 Kafka 가 지운다. 그때가 진짜 유실이다 |
| 누가 꺼내나 | **아무도.** ADR `#34` 가 "적재 처리기의 관리 잡" 으로 정해 뒀고 코드는 0줄 |
| 되넣으면 어디로 가나 | `raw` 로 다시 발행한다. 키가 그대로라 같은 파티션에 들어가고, 지금 돌고 있는 `ingester` 그룹이 **평소처럼** 집어 간다. 적재 처리기에 새 코드가 필요 없다 |

### 2.3 되넣기는 중복을 만드나 (실측 : 기억이 막는다)

**두 번 돌려 봤다.** 같은 4건을 서로 다른 그룹으로 두 번 되넣었다.

| | spans | `uniqExact` | metrics_raw | transactions | heatmap_1m 합 |
|---|---|---|---|---|---|
| 되넣기 전 | 228,538 | 228,538 | 44,023 | 103,195 | 103,195 |
| **1차** 되넣기 뒤 | 228,544 (**+6**) | 228,544 | 44,026 (**+3**) | 103,198 (**+3**) | 103,198 (**+3**) |
| **2차** 되넣기 뒤 (같은 4건) | 228,544 | 228,544 | 44,026 | 103,198 | 103,198 |

- **①에 답 : 돌아온다.** 트레이스 3건(스팬 2개씩) · 지표 3줄이 실제로 들어왔고 집계까지 따라왔다
- **②에 답 : 두 번 돌려도 중복이 안 생긴다.** `#187` 이 켠 중복 제거 기억(표 열 군데 · 창 100)이 같은 블록을 버린다. 원본과 집계가 **같이** 안 늘었다
- 단, 이것은 **기억 안에 있을 때**만 참이다. 창 100은 블록 수이고 시간이 아니다. 되넣기와 원래 실패 사이에 블록 100개가 들어갔으면 못 막는다

### 2.4 되넣기는 집계를 못 고친다 (실측 : 기억이 막는 것이 문제다)

앞의 2.3이 좋은 소식이면 이쪽은 나쁜 소식이고, **같은 장치가 원인**이다.

저장이 중간에 깨지는 모양이 하나 있다 : **원본에는 들어갔고 MV 중 하나가 터져** 전체가 예외로 끝나는 경우다. `#191` 에서 실제로 본 문구가 `while pushing to view` 였다. 그러면 그 메시지는 `raw.dlq` 로 가는데 원본에는 이미 줄이 있다.

그 상태를 손으로 만들어 되넣어 봤다. 트레이스 하나(`d3de0545…`)의 집계 줄만 지우고 같은 메시지를 다시 넣었다.

| | spans | transactions |
|---|---|---|
| 집계 줄을 지운 직후 | 2 | **0** |
| 그 메시지를 되넣은 뒤 | 2 | **0** |

적재 처리기 로그는 `spans 적재: 2줄` 을 찍었다. **보냈지만 아무것도 안 들어갔다.** 원본 블록이 기억에 남아 있어 ClickHouse 가 블록을 버렸고, `deduplicate_blocks_in_dependent_materialized_views = 1` 때문에 **MV 가 아예 안 돌았다.**

- **③에 답 : 안 고쳐진다.** 되넣기는 "원본에 없는 것" 만 되살린다. 원본에 있고 집계에만 없는 구멍은 **되넣기로 영원히 안 메워진다**
- 그 구멍을 메우는 길은 **원본에서 다시 집계하는 것** 하나뿐이다. 지금은 손 절차다(`docs/kafka-reprocess/experiments/reaggregate_window.sh`, `#187` 에서 돌려 보고 적었다)
- 실제로 그 절차로 되돌렸다 : `INSERT ... SELECT` 에 `deduplicate_insert_select = 'disable'` 을 붙여 103,198 로 복구

**ADR `#67` 이 적어 둔 이유를 고쳐 읽어야 한다.** 되돌림 ④ 는 재집계가 필요한 이유를 "기억 **밖** 재처리를 못 막으므로" 로 적었다. 측정은 더 센 것을 말한다 : **기억 안에서도 재집계가 필요하다.** 기억이 되넣기의 안전장치이면서 동시에 복구를 막는 장애물이다. 결론(둘을 같이 정한다)은 그대로고 사유가 바뀐다.

**그리고 손으로 고칠 때 순서를 틀리면 다음 단이 틀어진다.** 집계 줄을 되살렸더니 `heatmap_1m` 합이 103,199(+1)가 됐다. `transactions` → `heatmap_1m` 연쇄가 한 번 더 돌았기 때문이다. `reaggregate_window.sh` 가 `heatmap_1m` → `transactions` 순으로 지우는 이유가 이것이고, 조사 중에 그 함정을 그대로 밟았다. 그 분 버킷을 지우고 다시 넣어 103,198 로 맞췄다.

### 2.5 포기 횟수를 세려면 머리말을 가져가야 한다 (실측)

되넣은 것이 **또 실패**하면 어떻게 되나. 독성 메시지(키 `logs` · 값 `0x0F`)를 머리말을 넣은 채와 뺀 채로 각각 한 번 보냈다.

| 보낸 모양 | `raw.dlq` 에 다시 들어온 것 |
|---|---|
| `x-dlq-attempt: 1` 을 **가져갔다** | `attempt=2` · `reason=poison` |
| 머리말을 **버렸다** | `attempt=1` · `reason=poison` |

- **④에 답 : `x-dlq-attempt` 는 반드시 가져가고 `kafka_dlt-*` 는 버린다.** 전자를 버리면 횟수가 매번 1로 돌아가 **영원히 도는 고리**가 된다. 후자를 가져가면 6KB 스택이 `raw` 를 타고 다닌다
- `network.peer.address`(수집기가 붙인 보낸 쪽 주소, ADR `#63`)도 가져간다. 버리면 되넣은 메시지만 `agents.ip` 가 빈칸이 된다
- 되넣은 것이 또 실패해도 **고리가 되지는 않는다** : 다시 들어가는 자리는 `raw.dlq` 의 **끝**(새 오프셋)이고 잡은 앞에서부터 읽으므로 같은 바퀴를 다시 돌지 않는다. 포기 규칙은 "무한을 막기 위해" 가 아니라 **"몇 번 뒤에 사람을 부를까"** 를 정하는 것이다

### 2.6 지금은 이 잡을 돌릴 수단이 없다

ADR `#34` 는 **쿠버네티스 Job** 으로 정했다. 그런데 쿠버네티스가 아직 없다(배포 7~9단계, monimo-deploy `#14` 가 로컬 클러스터부터 시작한다).

| 레포에 이미 있는 "한 번 돌고 끝나는" 모양 | 무엇을 하나 |
|---|---|
| `kafka-init` | 토픽을 만들고 끝난다 |
| `postgres-migrate` · `clickhouse-migrate` | 마이그레이션을 돌리고 끝난다. `infra-ready` 가 정상 종료를 기다린다 |

- **⑥에 답 : 선례가 compose 의 한 번 돌고 끝나는 서비스다.** `docker compose run --rm <이름>` 으로 손으로 부르고, 쿠버네티스가 생기면 **같은 이미지 · 같은 명령**을 Job 으로 옮긴다. `#119` 가 `clickhouse-migrate` 에 대해 같은 판단을 적어 뒀다("운영에서 무엇이 이 컨테이너를 실행하나는 배포 7~9단계에 달렸고, 같은 이미지를 쓰면 되므로 그때 정한다")
- 그룹 이름은 `ingester` 가 **아니어야** 한다. 같은 그룹을 쓰면 `raw` 를 읽는 쪽과 파티션 배분이 섞인다

### 2.7 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| `monimo.ingester.dlq` 가 DLQ 에 쌓인 양이다 | **아니다.** **그 프로세스가 보낸 수**다. 지금 지표는 2 를 말하고 토픽에는 6 건이 있다. 재시작하면 0 으로 돌아간다 |
| 그러면 끝 오프셋이 깊이다 | 그것도 아니다. **되넣은 것은 사라지지 않는다** : Kafka 는 읽어도 지우지 않고 그룹의 커밋 위치만 올라간다. 깊이 = **그 잡 그룹의 lag**(끝 오프셋 : 커밋 오프셋). 실측으로 `CURRENT 4 / END 6 / LAG 2` 를 확인했다. 즉 **잡이 생기기 전에는 깊이를 셀 수 없다** |
| 되넣기가 유실을 막는 장치다 | 유실을 막는 것은 `#96` 의 pause 쪽이다(10분까지 기다린다). 되넣기는 **그 10분을 넘긴 뒤**의 마지막 그물이다 |
| 되넣으면 집계도 같이 맞는다 | 2.4. 원본에 줄이 있으면 집계는 **안 돈다** |
| DLQ 에 든 것은 전부 되넣어야 한다 | `reason=poison` 은 데이터가 틀린 것이라 되넣으면 **그대로 또 실패**한다. 분류를 보고 걸러야 한다 |
| `raw` 보관 7일과 `raw.dlq` 30일이 같은 시계다 | 다르다. DLQ 는 30일을 들고 있지만 **같은 구간을 `raw` 에서 되감는 길은 7일에 닫힌다** |

**재현** : [`../../kafka-reprocess/experiments/dlq_replay_probe.py`](../../kafka-reprocess/experiments/dlq_replay_probe.py) (`list` · `replay <그룹>` · `one <오프셋>` · `poison <keep|strip>` 네 모드). 2.1 · 2.3 · 2.4 · 2.5 를 그대로 다시 돌릴 수 있다. **되넣는 잡이 아니다** : 포기 규칙 · 분류 걸러내기 · 재집계가 없는 조사용 시제품이다.
