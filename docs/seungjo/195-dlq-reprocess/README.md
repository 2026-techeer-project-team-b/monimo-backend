## 문제

`#96`(ADR `#51`)이 **보내는 쪽까지만** 만들었다. 적재에 실패한 메시지는 `raw.dlq` 로 가고 분류별 건수를 세지만, **꺼내는 코드가 0줄**이고 그 토픽을 읽는 컨슈머 그룹이 하나도 없었다.

| 조사 전에 재 본 것 | 값 |
|---|---|
| `raw.dlq` 끝 오프셋 | **4** (트레이스 3 · 지표 1) |
| 그 정체 | `Code: 243`(디스크 부족) · 원래 그룹 `exp-diskfull2` = **`#191` 실험이 만든 telemetrygen 데이터** |
| 지워지는 날 | **2026-11-13 05:18** (보관 30일. 발표 10/31 보다 뒤다) |
| 읽는 컨슈머 그룹 | **0개** |
| 깊이를 보는 장치 | 없다. `monimo.ingester.dlq` 는 **그 프로세스가 보낸 수**라 2 를 말하고 토픽에는 6건이 있었다 |

**무엇이 깨지나** : `10-requirements.md` 유실 허용치에 "30일이 지나면 그때는 진짜 유실이다" 로 적혀 있고, 지금 유실로 가는 경로는 이것 하나다.

## 선택지

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **가. compose 의 한 번 돌고 끝나는 서비스** | 적재와 **분리** · 다로 옮기기 쉽다 · 언제 돌렸는지 안다 | **주기 실행 없음** (사람이 부른다) |
| 나. 적재 처리기 안에 `@Scheduled` | 주기 실행이 공짜 | 적재와 **같은 프로세스** : 연결 · 실패 처리 · 그룹이 섞인다 |
| 다. 쿠버네티스 Job · CronJob (ADR `#34`) | 실행 기록 · 재시도 · 중복 실행 방지를 플랫폼이 | **지금 돌릴 클러스터가 없다** |

**조사가 뒤집은 것** : 처음에 2.6 제목을 "돌릴 수단이 없다" 로 적었는데 틀렸다. 레포에 `@Scheduled` 선례가 세 모듈(수집기 · 탐지 · 알림)에 있어서 **쿠버네티스 없이도 주기 실행이 된다.** 못 하는 것은 플랫폼이 기록 · 재시도 · 중복 실행 방지를 **대신 해 주는 쪽**뿐이다.

## 결정

**가 + 포기 3회 + 멈추면 커밋 안 함 + 재집계는 절차** (ADR `#71`)

- **고른 것** : compose 서비스 `dlq-reprocess`(적재 처리기와 **같은 이미지** · 프로필 하나만 다르다) · 그룹 `dlq-reprocess` · 머리말 셋만 · 독성은 건너뛰고 커밋 · `x-dlq-attempt` 3 에 닿으면 **멈추고 커밋 안 함**(lag 이 남아 점검이 말한다) · 한 회차는 **시작 시점의 끝까지만** · 되넣은 구간을 로그에 찍는다 · **경보는 포기한다**
- **버린 것과 이유** : 아무것도 안 함(30일 뒤 진짜 유실) · `@Scheduled`(적재와 섞인다. 주기 실행이 **지금 필요한 근거가 0번**) · 쿠버네티스 지금(클러스터 없음. 미루는 것이고 가가 전 단계) · 머리말 전부 가져가기(5KB 스택이 `raw` 를 7일 타고 다닌다) · 머리말 전부 버리기(**영원히 왕복한다**) · 독성 되넣기 · 멈출 때 커밋(**유일한 신호가 사라진다**) · 재집계 자동화(손으로 고친 횟수 0번) · DLQ 비우기(비울 수 없다)
- **되돌리는 조건** : 되넣기를 **두 번** 부르게 되면 주기 실행으로 · 집계가 어긋난 일이 **두 번** 생기면 재집계를 잡 안으로 · 포기 3회에 걸리는 것이 쌓이면 그 코드를 독성 목록에 · 놓친 경보가 문제가 되면 탐지에 과거 구간 재평가 입구 · 적재 처리기가 2대 이상이면 동시 실행 방지를 다시

## 쓰는 법

```
docker compose run --rm dlq-reprocess                                                  되넣는다
docker compose run --rm -e MONIMO_INGESTER_DLQ_REPROCESS_DRY_RUN=true dlq-reprocess    무엇을 넣을지만 본다
docker compose run --rm -e MONIMO_INGESTER_DLQ_REPROCESS_MAX_ATTEMPT=5 dlq-reprocess   포기 횟수를 올려 통과시킨다
./scripts/check-pipeline.sh                                                            깊이를 본다
```

끝나면 로그가 **되넣은 구간**을 찍는다. 그 구간을 `check-pipeline.sh` 로 대조하고 어긋나면 `docs/kafka-reprocess/experiments/reaggregate_window.sh` 를 돌린다.

## 장애가 나면

| 무엇이 죽으면 · 틀리면 | 어떻게 되나 | 어떻게 알아채나 |
|---|---|---|
| 되넣은 것이 **또 실패**한다 | `raw.dlq` 끝에 `attempt + 1` 로 붙는다. **이번 회차는 안 읽는다**(시작 시점의 끝이 경계다) | 다음 회차에서 보인다 |
| `attempt` 가 **3 에 닿는다** | 되넣지 않고 **멈춘다.** 커밋도 안 해서 lag 이 남는다. 종료코드 1 | `! raw.dlq 깊이 N건` · 로그의 오프셋 |
| 그 레코드를 통과시키고 싶다 | `MAX_ATTEMPT=5` 로 한 번 올려 돌린다. 사람의 판단이다 | : |
| **원본에는 있고 집계에만 구멍**이 있다 | **되넣기로 안 고쳐진다.** 창이 블록을 버려 MV 가 아예 안 돈다 | `check-pipeline.sh` 의 원본 ↔ 집계 대조 |
| 창에서 **밀려 나간 뒤** 되넣는다 | 중복이 들어간다. 표마다 따로 밀린다(`metrics_raw` 가 먼저 밀린다) | 같은 대조 |
| 되넣은 구간에 **경보 조건**이 있었다 | **안 울린다.** 탐지는 30초 전에 끝난 칸만 보고 과거 버킷은 무시한다 | 알아챌 장치가 **없다.** 그래서 문서에 적었다 |
| 잡을 **두 번 동시에** 돌린다 | 같은 그룹이라 뒤에 뜬 쪽이 파티션을 못 받거나 리밸런스가 난다. 막는 장치 **없음** | 되돌림 ⑤ |
| DLQ 발행이 실패한다 | `#96` 이 이미 다룬다(`setFailIfSendResultIsError`). Kafka 자체 문제라 파이프라인이 이미 멈춰 있다 | 적재가 멈춘다 |

## 이 이슈에서 배운 것 (세 줄)

- **같은 장치가 두 얼굴이다.** `#187` 의 중복 제거 기억이 되넣기를 안전하게 만들면서 동시에 집계 복구를 막는다. "막아 주는 것" 과 "고쳐 주는 것" 은 다른 일이다
- **ADR 의 결론이 맞아도 사유가 틀릴 수 있다.** `#67` 되돌림 ④ 는 결론이 맞았고 사유가 좁았다. 사유를 그대로 믿고 읽으면 "기억 안이면 괜찮다" 로 잘못 읽는다
- **돌려 보지 않으면 세 가지를 못 찾는다.** 되넣은 구간의 시각(46분 차이) · 한 회차 안의 왕복 · 창이 표마다 따로 밀리는 것. 셋 다 글로는 맞게 적혀 있었는데 돌려 보고서야 틀린 자리가 드러났다
