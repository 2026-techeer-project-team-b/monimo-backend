## 문제

- `#96` 이 **보내는 쪽까지만** 만들었다
  - 적재에 실패한 메시지는 `raw.dlq` 로 간다
  - **꺼내는 코드가 0줄**이고 그 토픽을 읽는 컨슈머 그룹이 없었다
- 보관 30일이 지나면 그때는 진짜 유실이다 (`10-requirements.md` 유실 허용치)

| 조사 전에 재 본 것 | 값 |

## 결정

- **사람이 부르는 compose 잡 하나**로 둔다
- 적재 처리기 코드는 한 줄도 안 건드렸다 (프로필로 갈라 평소에는 빈이 아예 안 생긴다)

| 무엇 | 값 |
|---|---|
| 모양 | 적재 처리기와 **같은 이미지** + 프로필 하나(`dlq-reprocess`). `docker compose run --rm dlq-reprocess` |
| 주기 실행 | **안 넣었다.** 돌릴 이유가 생긴 횟수가 0번이다 |
| 그룹 이름 | `dlq-reprocess` (`ingester` 금지) |
| 머리말 | **셋만** : `x-dlq-attempt` · `x-dlq-reason` · `network.peer.address` |
| 독성 | 건너뛰고 커밋한다 |
| 포기 | `x-dlq-attempt` 가 **3** 에 닿으면 멈추고 **커밋하지 않는다**. 종료코드 1 |
| 한 회차 | **시작 시점의 끝까지만** 읽는다 |

| 복구 | **손 절차.** 되넣은 구간을 찍어 주고 사람이 대조한다 |
| 경보 | **포기한다.** 되넣은 구간을 다시 평가하지 않는다 |

## 흐름을 시점으로 갈라 본다

### [준비할 때] 한 번

```
① compose 가 dlq-reprocess 서비스를 들고 있다 (자기 프로필 : up -d 로는 안 뜬다)
② 그 서비스는 적재 처리기와 같은 이미지다. 다른 것은 프로필 하나뿐이고
   application-dlq-reprocess.yml 이 둘을 끈다
     웹 서버   요청을 안 받는다 (포트가 적재 처리기와 겹치지 않게)
     리스너    raw 를 안 읽는다 (잡이 적재 처리기 노릇까지 하지 않게)
```

### [쓸 때마다] 사람이 한 번 부를 때

```
사람       : docker compose run --rm dlq-reprocess
잡         : raw.dlq 를 dlq-reprocess 그룹으로 구독한다
             검사 ① 미리 가진 것 = 시작 시점의 끝 오프셋 (첫 poll 에서 한 번 적어 둔다)
                                   그 그룹의 커밋 위치 (없으면 앞에서부터)
             검사 ② 방금 받은 것 = 이 레코드의 x-dlq-attempt · x-dlq-reason
레코드마다 : attempt 가 3 에 닿았나        -> 멈춘다 (커밋 안 함, 종료코드 1)
             reason 이 poison 인가         -> 건너뛴다 (커밋)
             오프셋이 ①의 끝을 넘었나      -> 이번 회차가 만든 것이라 다음 회차로
             아니면                        -> 머리말 셋만 들고 raw 로 보내고 커밋
끝나면     : 읽음 · 되넣음 · 건너뜀 과 "되넣은 구간" 을 찍는다
적재 처리기: 평소처럼 raw 에서 집어 간다 (새 코드 없음)
```

- 사고가 나는 자리는 **"보내고" 와 "커밋" 사이**다
- 보냈는데 커밋을 못 하면 다음 회차가 같은 레코드를 다시 보낸다
  - 그때는 「집계 중복은 CH 중복 제거 기억으로」 결정의 창이 막는다 (창 안에 있을 때만)

## 되넣기가 못 고치는 것 둘

### ① 원본에 줄이 있고 집계에만 구멍이 있으면 안 고쳐진다

- 그 모양이 실제로 있다 : `#191` 에서 본 `while pushing to view`
  - 원본에는 들어갔고 MV 중 하나가 터져 전체가 예외로 끝난다
  - 그 메시지는 `raw.dlq` 로 가는데 원본에는 이미 줄이 있다

| | `spans` | `transactions` |
|---|---|---|
| 집계 줄을 지운 직후 | 2 | **0** |
| 그 메시지를 되넣은 뒤 | 2 | **0** |

- 적재 로그는 `spans 적재: 2줄` 을 찍었는데 **아무것도 안 들어갔다**
- 원본 블록이 창에 남아 있어 ClickHouse 가 블록을 버렸다
- `deduplicate_blocks_in_dependent_materialized_views = 1` 때문에 **MV 가 아예 안 돌았다**
- 즉 **되넣기는 원본에 없는 것만 되살린다**

### ② 그 구간의 경보는 되살아나지 않는다

- 탐지는 `bucketEnd <= now - settleDelay`(30초)인 **완료된 칸만** 본다
- 과거 버킷은 `OUT_OF_ORDER_BUCKET` 으로 **무시한다** (`docs/alert/10-state-machine.md`)
- DLQ 에 도착하는 데만 최소 1분에서 10분이라 **구조적으로 못 이긴다**
- 되넣기가 지키는 것은 **경보가 아니라 기록**이다
  - 경보를 지키는 장치는 `#96` 의 pause 10분이다. 그 안에 살아나면 애초에 DLQ 로 안 간다

## 왜 머리말을 셋만 가져가나

```
raw (1장)  --실패-->  raw.dlq (13장 : 10장이 새로 붙는다)  --되넣기-->  raw (3장)
   31B                      6,033B                                    65B
```

| 가져가는 것 | 버리면 |
|---|---|
| `x-dlq-attempt` | 횟수가 매번 1 로 돌아가 **영원히 왕복한다** (실측 : 가져가면 `attempt=2` · 버리면 `attempt=1`) |
| `x-dlq-reason` | 독성을 걸러낼 단서가 없다 |
| `network.peer.address` | 수집기만 알던 값이라 복원할 데가 없다 (그 메시지로 **처음 등록되는 파드**만 영향) |

- 버리는 `kafka_dlt-*` 열 장은 **그때 그 실패의 기록**이다
  - 적재 처리기가 읽지 않는다
  - 다시 실패하면 스프링이 **새로 붙여 준다**
  - 안 버리면 5,144바이트 스택이 멀쩡한 `raw` 를 보관 7일 동안 타고 다닌다

## 왜 주기 실행을 안 넣었나

- 쿠버네티스가 없어서가 **아니다.** 레포에 `@Scheduled` 선례가 세 모듈에 있다 (수집기 · 탐지 · 알림)
- 돌릴 이유가 생긴 횟수가 **0번**이다 (`raw.dlq` 에 든 것이 전부 내 실험이 만든 것이었다)
- 팀이 같은 기준을 세 번 썼다
  - 「전역 설정 표는 지금 안 만든다」 결정 : 옮길 값이 하나였다
  - 「배포 순서는 손으로 · 인증서 두 묶음」 결정 ① : 순서는 손으로 시작한다
  - 「집계 중복은 CH 중복 제거 기억으로」 결정 기각 ⑥ : 주기로 돌리면 멀쩡한 집계를 매번 다시 쓴다
- 적재 처리기 안에 넣으면 연결 · 실패 처리 · 컨슈머 그룹이 **섞인다**

## 쓰는 법

```
docker compose run --rm dlq-reprocess                                                  되넣는다
docker compose run --rm -e MONIMO_INGESTER_DLQ_REPROCESS_DRY_RUN=true dlq-reprocess    무엇을 넣을지만 본다
```

- 끝나면 로그가 **되넣은 구간**을 찍는다 (원래 발행 시각 기준)
- 그 구간을 `check-pipeline.sh` 로 대조하고 어긋나면 `reaggregate_window.sh` 를 돌린다

## 내가 틀렸던 것

**ㄱ. "같은 그룹을 쓰면 파티션 배분이 섞인다"**

- 기억으로 썼고 재 보니 **안 섞인다**
- `ingester` 이름으로 `raw.dlq` 만 구독해 붙였더니 받은 것은 `raw.dlq-0` 하나였다
- 할당은 **구독한 토픽만** 따라간다
- 진짜 비용은 **리밸런스 두 번**이다 (잡이 붙을 때 · 끝날 때, 211 · 229밀리초)

**ㄴ. "되넣은 것이 또 실패해도 고리가 안 된다"**

- **두 번 틀렸다**
- 처음 : 회차를 넘으면 왕복한다는 것을 빼먹었다
- 고친 뒤 : "한 회차 안에서는 안 돈다" 로 적었는데 **구현해 돌려 보니 돌았다**
  - 잡이 빈 poll 까지 읽어서 방금 자기가 만든 실패분을 집어 갔다 (`attempt 3 → 4`)
- 한 회차의 끝 경계를 코드에 박아 고쳤다

**ㄷ. "쿠버네티스가 없어서 못 만든다"**

- 2.6 의 제목을 그렇게 적었다
- 승조가 "왜?" 라고 물어 레포를 다시 세어 보니 `@Scheduled` 선례가 **세 모듈**에 있었다
- 못 하는 것은 플랫폼이 실행 기록 · 재시도 · 중복 실행 방지를 **대신 해 주는 쪽**뿐이다

**ㄹ. "되넣은 메시지만 `agents.ip` 가 빈칸이 된다"**

- 과장이었다
- **그 메시지로 처음 등록되는 파드**만 그렇다
- `PostgresAgentRegistry.needsWrite()` 가 멀쩡한 주소를 지키게 만들어져 있다

**ㅁ. 앞 결정의 사유를 그대로 믿었다**

- 「집계 중복은 CH 중복 제거 기억으로」 결정의 되돌림 ④ 는 "기억 밖 재처리를 못 막으므로" 로 적혀 있다
- 그래서 **기억 안이면 괜찮다**고 읽고 있었다
- 재 보니 **기억 안에서도** 재집계가 필요했다
- 결론은 그대로고 사유가 바뀐다

**ㅂ. 되넣은 구간을 DLQ 레코드의 시각으로 찍었다**

- 돌려 보니 `20:18` 이 찍혔다. 데이터는 `19:32` 것이다
- DLQ 레코드의 시각은 **옮겨 적은 때**라 실패를 기다린 시간만큼 뒤에 있다 (**46분** 차이)
- 그대로 두면 사람이 **엉뚱한 분**을 재집계한다
- `kafka_dlt-original-timestamp`(8바이트 정수)를 읽는 것으로 고쳤다

**ㅅ. 손으로 집계를 고치다 `heatmap_1m` 을 +1 틀어뜨렸다**

- `transactions` 줄을 되살렸더니 연쇄가 한 번 더 돌았다
- `reaggregate_window.sh` 가 `heatmap_1m` 을 **먼저** 지우는 이유를 몸으로 밟았다
- 그 분 버킷을 다시 만들어 맞췄다 (103,198 = 103,198)

## 이 이슈에서 배운 것

- **같은 장치가 두 얼굴이다**
  - 중복 제거 기억이 되넣기를 안전하게 만들면서 동시에 집계 복구를 막는다
  - "막아 주는 것" 과 "고쳐 주는 것" 은 다른 일이다
- **결정이 맞아도 사유가 좁을 수 있다**
