# 리서치 : 샘플링 비율을 시스템 안 최댓값으로

- 날짜 2026-10-16 / 관련 이슈 [`#206`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/206) (앞 이슈 `#205` · PR `#207` 머지, ADR `#53` 보완)
- 쓴 도구: 레포 직접 읽기(`collector/sampling` · `outbound/postgres` · `#205` 마이그레이션 · seed)

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

---

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 수집기는 등록된 서비스 전부의 비율 중 가장 큰 값 하나로 모든 요청을 거른다. 서로 부르지도 않는 쇼핑몰과 우리 모듈이 한 값으로 묶인다
- **그래서 무엇을 만드나** : 가장 큰 값을 "전체에서" 가 아니라 "같은 시스템 안에서" 고른다. 쇼핑몰 요청은 쇼핑몰 서비스들 중 최댓값, 우리 모듈 요청은 우리 모듈들 중 최댓값으로 거른다
- **안 하면 어떻게 되나** : 우리 모듈 비율을 50% 로 올리는 순간 쇼핑몰도 50% 로 들어와 Kafka · ClickHouse 가 1% 기준의 50배를 받는다. 그래서 `#216` 은 "`#206` 전까지 샘플링 안 올림" 으로 막아 두었다

| | |
|---|---|
| 건드리는 모듈 · 파일 | `collector` 만. `outbound/postgres/PostgresSamplingRateSource.kt`(SQL 에 `system`) · `sampling/SamplingRateSource.kt`(`SamplingRates` 가 시스템별 값을 가짐) · `sampling/TraceSampler.kt`(스팬마다 그 서비스의 시스템 값으로 판정) · 테스트 셋 · `application.yml` 주석 |
| 건드리지 않는 것 | PG 표(`#205` 로 칸이 이미 있다) · API 서버 · 해시 공식 · 카나리 통과 · 헬스체크 거르기 · 30초 주기 · 실패 시 마지막 값 유지 (ADR `#53` 의 나머지는 그대로) |
| 이 이슈 범위 밖 (후속) | 화면 드롭다운 시스템 묶기 · 등록 폼 `system` 입력(화면) · 운영에서 우리 모듈 비율을 실제로 올리는 일(B평면) · 서비스별로 진짜 다른 비율(ADR `#53` 되돌림 ①) |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- ADR `#53` 이 최댓값을 고른 이유는 "같은 요청을 지나는 서비스끼리 다른 선을 쓰면 요청이 쪼개진다" 였다. 그 전제는 "요청이 지나는 서비스들" 의 범위가 감시 대상 전체와 같다는 것이었고, 쇼핑몰 하나일 때는 맞았다
- `#205` 로 `applications.system` 칸이 생겼다. 기본 `shop`, seed 의 우리 모듈 다섯은 `monimo`
- 지금 비율은 요청(`ExportTraceServiceRequest`) 하나에 한 값을 쓴다. 한 요청 안에 서비스가 섞일 수 있는지는 확인하지 않았다

**알고 싶었던 것**

- ① 요청 하나(한 `trace_id`)가 **시스템 경계를 넘는 경우가 정말 없나**. 쇼핑몰 에이전트 → 수집기, 화면 → API 서버, 파수꾼 → 쇼핑몰 각각
- ② `system` 을 모르는 서비스(미등록 · PG 를 아직 못 읽음)에는 **어떤 값**을 주나
- ③ 수집기가 받는 묶음 하나에 **여러 서비스 · 여러 시스템이 섞일 수 있나**. 섞이면 "전부 통과면 다시 안 만든다" 지름길을 어떻게 두나
- ④ 지금 지표(`kept` · `dropped` · `unknown_service`)와 로그를 **시스템별로 나눠야 하나**
- ⑤ ADR `#53` 을 **고쳐 쓰나, 새 번호를 다나**

## 2. 작업하기 전에 알아야 하는 것

### 2.1 샘플링 : 무엇을 어디서 거르나

- 감시 대상이 보내는 요청 기록(트레이스)을 **일부만 남기고 나머지는 버리는 것**이다. 1% 면 요청 100건 중 1건만 Kafka 로 넘긴다
- 우리는 에이전트가 아니라 **수집기**에서 거른다(ADR `#33`). 에이전트는 `always_on` 으로 전부 보낸다
- 고르는 법 : `trace_id` 뒤 8바이트를 숫자로 바꿔 `abs(hash) < 비율 × Long.MAX_VALUE` 면 남긴다(`TraceSampler.keep`). 같은 `trace_id` 면 어느 서비스의 스팬이든 같은 숫자가 나오므로 **같은 비율이면 같이 남고 같이 버려진다**
- 이 공식은 비율에 대해 **단조**다. 비율 10% 에 남은 trace 는 50% 에서도 반드시 남는다. 그래서 최댓값을 쓰면 낮은 비율을 원한 서비스의 표본을 "늘리는" 방향으로만 틀어진다
- 카나리(`trace_state` 에 `monimon=canary`)는 비율을 건너뛴다(ADR `#41`). 이번에 안 바뀐다

### 2.2 시스템 : `applications.system`

- **서로 부르는 서비스들의 묶음 이름**이다. `#205` 마이그레이션 `V202610151408__alter_applications_add_system.sql` 이 `VARCHAR(50) NOT NULL DEFAULT 'shop'` 으로 만들었다
- 지금 값은 둘 : 쇼핑몰 넷(`shop-gateway` · `shop-order` · `shop-payment` · `shop-inventory`) = `shop`, 우리 모듈 다섯(`monimo-collector` · `-ingester` · `-api-server` · `-detector` · `-notifier`) = `monimo` (`scripts/seed/postgres-applications.sql`)
- 값은 API 서버 등록(13) · 수정(8)으로만 바뀐다. 앞뒤 공백을 자르고 1~50자만 받는다(`ApplicationService.systemOf`). **대소문자는 그대로 둔다** : `Shop` 과 `shop` 은 다른 시스템이다
- 수집기 입장에서 서비스와 시스템을 잇는 끈은 **스팬의 `service.name` = `applications.name`** 하나다. 스팬에는 시스템이 안 적혀 온다

### 2.3 지금 코드 : 비율이 어떻게 흐르나

```
PG application_configs ⋈ applications (deleted_at IS NULL)
        │  30초마다 @Scheduled (scheduling-1 스레드)
        ▼
PostgresSamplingRateSource.refresh()
        │  SamplingRates.of(byService, fallback)
        │    byService = {shop-gateway: 0.01, ..., monimo-collector: 0.01, ...}
        │    applied   = byService 최댓값 (0줄이면 fallback)
        ▼
AtomicReference 스냅샷  ◀── rates() 는 이것만 준다 (요청 경로에서 PG 를 안 읽는다)
        │
OTLP 요청 ─▶ 헬스체크 거르기 ─▶ TraceSampler.sample(request)
                                     │  rates.applied >= 1.0 이면 통째로 통과 (다시 안 만든다)
                                     │  아니면 스팬마다 keep(span, rates.applied)
                                     ▼
                                 Kafka raw
```

- 비율 값이 쓰이는 곳은 `rates.applied` **한 칸**이다. 서비스별 값(`byService`)은 읽어 오지만 `registered()`(미등록 세기)와 로그에만 쓴다. `SamplingRatesTest` 에 "나중에 서비스별로 쓰게 되면 이 칸을 읽는다" 라고 적혀 있다
- 실패 규칙 셋(ADR `#53` ③) : 한 번도 못 읽었으면 yml `0.01` · 읽다가 실패하면 마지막 값 · 0줄이면 fallback 이지만 `loaded = true` 로 구분
- 미등록 서비스 스팬도 **버리지 않고** 같은 `applied` 로 거르고 `monimo.collector.sampling.unknown_service` 로 센다(ADR `#53` ④ · 기각 ⑩)

### 2.4 바꾸면 무엇이 달라지나

| 상황 | 지금 | 바꾼 뒤 |
|---|---|---|
| shop 넷 1% · monimo 다섯 1% | 모두 1% | 모두 1% (같다) |
| shop 넷 1% · monimo 하나만 50% | 쇼핑몰도 50% | 쇼핑몰 1% · monimo 다섯 50% |
| shop-order 10% · 나머지 1% | 전부 10% | shop 넷 10% · monimo 1% |
| 미등록 서비스 | 전체 최댓값 | **정해야 한다** (알고 싶었던 것 ②) |
| PG 를 한 번도 못 읽음 | yml `0.01` | yml `0.01` (같다) |

- 같은 시스템 안에서는 지금과 똑같이 최댓값이라, ADR `#53` 이 막은 "한 요청이 쪼개지는 문제" 는 **시스템 안에서는 그대로 막힌다.** 바뀌는 것은 시스템 사이뿐이다

### 2.5 요청이 시스템 경계를 넘을 수 있는 자리

- 이번 설계의 유일한 전제가 "트레이스는 시스템을 넘지 않는다" 다. 넘으면 그 요청은 두 비율로 재어져 다시 쪼개진다
- 요청 기록이 이어지는 원리 : 에이전트가 나가는 호출의 머리말(`traceparent`)에 자기 `trace_id` 를 적고, 받는 쪽 에이전트가 그 머리말을 읽어 같은 `trace_id` 를 이어 쓴다. **받는 쪽에도 에이전트가 있고, 보내는 호출이 계측될 때만** 이어진다

| 자리 | 보내는 쪽 → 받는 쪽 | 이어질 수 있나 (아직 추측, 5절에서 확인) |
|---|---|---|
| 쇼핑몰 에이전트가 수집기로 신호를 보냄 | shop → monimo-collector (gRPC 4317) | 에이전트가 자기 내보내기 호출은 계측하지 않는 것으로 안다. 이어지면 **모든 쇼핑몰 요청이 경계를 넘는다** |
| 화면이 API 서버를 부름 | 브라우저 → monimo-api-server | 브라우저에 에이전트가 없다 |
| 파수꾼 카나리가 쇼핑몰을 부름 | watchdog(Python, 에이전트 없음) → shop-gateway | 카나리는 원래 비율을 건너뛴다 |
| 우리 모듈끼리 (수집기 → Kafka → 적재 처리기) | monimo → monimo | 같은 시스템이라 상관없다 |

### 2.6 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| 서비스별 비율을 이제 따로 적용한다 | 아니다. **시스템 안에서는 여전히 최댓값 하나**다. "order 만 내렸는데 안 듣는다" 는 그대로다(AGENTS §6 화면 문구 줄) |
| `system` 은 테넌트(고객사) 칸이다 | 지금은 샘플링 묶음 축일 뿐이다. 멀티 테넌시는 비목표이고, 가면 이 칸을 승격한다(`#205` 본문) |
| 수집기가 `system` 을 스팬에서 읽는다 | 스팬에는 시스템이 없다. 수집기가 PG 에서 `name → system` 표를 읽어 `service.name` 으로 찾는다 |
| 시스템이 다르면 해시도 다르다 | 해시는 `trace_id` 만 본다. 비율(선 높이)만 시스템마다 다르다 |
| 미등록 서비스는 버려진다 | 버리지 않는다(ADR `#53` 기각 ⑩). 어떤 비율로 거를지만 정하면 된다 |
| 로컬에서 바꾼 효과가 보인다 | 로컬 seed 비율이 전부 `1.0000` 이라 지름길로 통째 통과한다. 효과를 보려면 PG 값을 직접 바꿔야 한다 |

## 3. 1차 질문 (사람 차례)

2026-10-16 대화에서 승조가 실제로 물은 순서대로 적는다. 답은 한 줄로 줄였고 근거는 2절 · 5절에 있다.

- **Q. 비율은 지표 · 트레이스 · 로그 중 무엇에 걸리나**
  - A. 트레이스 하나뿐이다. `OtlpTraceService` 만 `sampler` 를 들고 있고(`OtlpExportServices.kt:36`) 지표 · 로그는 그대로 흘러간다. 로그에 생길 하한(`#215`)은 등급 필터이지 비율이 아니다
- **Q. 아홉은 신호 종류 수인가**
  - A. 서비스 수다. `application_configs` 가 서비스 한 개 = 한 줄이고 지금 쇼핑몰 넷 + 우리 모듈 다섯이다. 설정 화면의 네 칸도 신호 넷이 아니라 쇼핑몰 서비스 네 개다
- **Q. 거르는 곳이 쇼핑몰 쪽인가 수집기 쪽인가**
  - A. 수집기 한 곳이다. 에이전트는 `always_on` 으로 전부 보낸다(ADR `#33`). 에이전트에서 거르면 비율을 바꿀 때마다 감시 대상을 재배포해야 한다
- **Q. 「선」이 무엇인가**
  - A. 남길지 버릴지 가르는 상한 하나다. `trace_id` 뒤 8바이트를 숫자로 읽고 `abs(그 숫자) < 비율 × Long.MAX_VALUE` 면 남긴다(`TraceSampler.kt:87` · `:101`)
- **Q. 다른 `trace_id` 인데 번호가 같으면 문제가 되나**
  - A. 안 된다. 번호는 식별자가 아니라 추첨 번호이고 쓰임이 「남길까 버릴까」 하나뿐이다. 묶거나 찾을 때는 `trace_id` 원래 값을 쓴다(`WHERE trace_id = …`). 1% 가 1% 가 되려면 같은 구간에 여러 트레이스가 겹치는 것이 정상이다
- **Q. `span_id` · `parent_span_id` 로 서비스를 알 수 있나**
  - A. 모른다. 서비스 이름은 스팬이 아니라 봉투 바깥 `resource` 에 한 번 적혀 온다(`TraceSampler.kt:110` 주석 · `serviceNameOf`). 부모 스팬은 다른 서비스가 **따로 보낸 봉투**에 있어서 따라갈 수도 없다
- **Q. OTLP 봉투는 어떻게 생겼고 SERVER · CLIENT 는 무슨 뜻인가**
  - A. 봉투는 `resourceSpans` → `scopeSpans` → `spans` 3겹 중첩이고, 그 안의 `spans[]` 는 **평평한 목록**이다. 부모 · 자식은 중첩이 아니라 `parent_span_id` 로 가리킨다. kind 는 SERVER = 내가 요청을 받은 구간 · CLIENT = 내가 남을 부른 구간이고, 호출 한 번이 스팬 두 개(CLIENT + SERVER)로 기록된다
- **Q. 보내는 쪽 `service.name` 이 PG `applications.name` 과 다르면 뭐가 문제인가**
  - A. 미등록이 되어 넷이 조용히 깨진다 : 비율 줄을 못 찾는다(`sampling.unknown_service`) · 적재가 `agents` 등록을 건너뛴다(`application_id` NOT NULL FK, `#66`) · 경보 대상이 안 된다 · `peer_service` 가 안 채워져 서버맵에 `EXTERNAL` 로 남는다(`#83`). 에러가 아니라 빈칸으로 나타나므로 자동 검사가 없다
- **Q. `#213` 은 무엇이고, 그것 없으면 `#206` 도 안 해도 되는 일 아닌가**
  - A. 맞다, 쇼핑몰 감시 기능에는 영향이 0 이다. 다만 `#213`(우리 모듈 다섯에 에이전트)은 ADR `#01` B평면 · FR-7 에 적힌 범위이고 앱 코드 0줄로 끝나는 작업이었다. 그것을 켜자 결함 둘이 바로 드러났다 : 우리 로그 `DEBUG` · `TRACE` 1분 3,900건(`#215`) · 비율이 한 선으로 묶임(`#206`). 둘 다 남의 앱이 붙으면 똑같이 터질 문제다
- **Q. PG 가 죽어도 파드가 안 빠지는 것은 `socketTimeout` 으로 막은 것 아닌가**
  - A. 다른 장치다. `socketTimeout` 10초(`#127` · ADR `#54`)는 주기 작업이 **영구히 멈추는 것**을 막는다. 파드가 안 빠지는 것은 결함이 아니라 결정이다(ADR `#58`, readiness 는 저장소를 안 본다 : 저장소가 흔들리면 파드가 전부 동시에 빠져 그 시간대 신호가 영구히 사라진다). 그래서 「알려 주는 몫」이 비어 있었고 그것을 B평면이 메운다
- **Q. 스팬이 섞이면 비율이 같아야 하는 것 아닌가**
  - A. 맞다. 섞이는 범위 안에서는 선이 **반드시 같아야** 한다. 그래서 섞임은 이 설계의 문제가 아니라 **통과해야 하는 관문**이다 : 섞이면 `#206` 을 못 하고 한 선으로 되돌린다
- **Q. 들어오는 양이 달라도 비율은 같아야 하는 것 아닌가**
  - A. 비율은 수단이고 목표는 **남는 건수**다. 같은 1% 면 쇼핑몰은 시간당 약 100건이 남아 충분하고 모니모는 약 1건이 남아 아무것도 못 본다. 비율을 달리해야 결과가 비슷해진다. 대가는 보정 계수가 묶음마다 달라지는 것이고 그것은 화면 몫(범위 밖)이다

---

## 4. 1차 정리

- **확실한 것** (대화로 닫혔다)
  - 비율은 **트레이스에만** 걸린다. 지표 · 로그는 이 이슈와 무관하다
  - 선을 고르는 근거는 **봉투 바깥의 `service.name`**, 남길지 정하는 근거는 **스팬 안의 `trace_id`** 다. 둘을 섞어 생각하면 안 된다
  - 그래서 선은 요청 하나에 한 번이 아니라 **`resourceSpans` 묶음마다** 골라야 한다 (알고 싶었던 것 ③ 닫힘. 한 봉투에 여러 서비스가 올 수 있다)
  - 선이 하나여야 하는 단위는 「서비스」가 아니라 **「한 트레이스가 닿는 범위」** 다. `system` 은 그 범위에 붙인 이름이다
  - 묶음 **안**은 지금과 똑같이 최댓값 하나다. ADR `#53` 이 막은 쪼개짐은 시스템 안에서 그대로 막힌다
  - 나누는 **이유는 양 차이**이고 피해가 양방향이다 : 모니모를 올리면 쇼핑몰이 같이 올라 적재가 폭증하고(26 MB/일 → 약 1.3 GB/일), 쇼핑몰에 맞춰 1% 로 두면 모니모는 표본이 하루 수십 건이라 사고 순간을 못 본다
  - `#216` 이 「`#206` 전까지 비율 안 올림」으로 묶어 둔 것이 지금 상태다 : B평면이 일을 못 하는 원인이 이 한 칸이다
- **아직 모르는 것** (5절 · 6절에서 닫는다)
  - ① **경계를 넘는가** : 이것이 전부를 가르는 관문이다. 지금 닫혀 있다고 보는 근거 둘 = 에이전트가 자기 내보내기 호출을 계측하지 않는다는 것(미확인) · 수집기 · 적재 처리기가 `OTEL_TRACES_EXPORTER=none`(`Dockerfile:55` `:63`, `#213` 이 되먹임 때문에 껐다). **5절 첫 항목으로 CH 에서 실측한다**
  - ② **미등록 서비스에 어떤 선을 주나** : 전체 최댓값 · 가장 낮은 선 · yml 기본값 · `shop` 취급 중 무엇인지
  - ④ 지표(`kept` · `dropped` · `unknown_service`)를 시스템별로 나눌지
  - ⑤ ADR `#53` 을 고쳐 쓸지 새 번호를 달지
  - (범위 밖) 보정 계수가 묶음마다 달라지는 것을 화면이 어떻게 보여줄지. `02-open-questions` 의 「1% 표본을 화면 호출 수로 쓸지」와 같은 자리

| 확인 | 값 |

| 되먹임 관측 | 수집기 트레이스를 켜자 `raw publish` PRODUCER 스팬 16건이 생기고 그것이 자기 입력으로 다시 들어왔다 → `#213` 이 끈 이유가 실제로 보인다 |

### AI 가 틀렸거나 덜 맞았던 것 (남겨 둔다)

- **인과를 뒤집어 설명했다** : 「스팬이 섞여서 문제가 생기니 비율을 분리한다」로 적었는데 반대다. **섞이지 않는 것이 분리의 전제**이고, 섞이면 분리를 못 한다. 대화에서 승조가 잡았다
- **「에이전트는 자기 내보내기 호출을 계측하지 않는다」를 사실처럼 적었다** : 에이전트 jar(`2.31.1`)를 열어 보니 전역 무시 목록은 `io.opentelemetry.javaagent.shaded.` · `.bootstrap.` 둘뿐이고(`GlobalIgnoredTypesConfigurer`) SDK · exporter 는 그 접두가 아니다(`inst/io/opentelemetry/sdk/…` · `inst/io/opentelemetry/exporter/…`). 무시 목록만으로는 못 보였으므로 미확인으로 내렸고, **실측으로 참임을 보였다**(받은 쪽 Export SERVER 스팬 17건 전부 부모 없음). 근거를 바꾼 것이다 : 「무시 목록에 있다」가 아니라 「문맥이 안 실려 온다」
- **「수집기 트레이스를 켜면 경계가 열린다」고 적었다가 실측으로 접었다** : 켜 보니 Export SERVER 스팬에 부모가 없어 섞이지 않았다. 남은 가능성은 Extension 롱폴링(`collector:8081`) 하나이고 그것은 쇼핑몰이 떠야 잰다

### 라이브러리 · 레포를 직접 열어 확인한 것

| 확인 | 결과 |
|---|---|
| 비율이 걸리는 신호 | **트레이스만**. `OtlpTraceService` 만 `sampler` 를 주입받고(`OtlpExportServices.kt:36`) 지표 · 로그 서비스는 `counter` · `producer` 만 든다 |
| 선을 만드는 자리 | `SamplingRates.of` = `byService.values.maxOrNull()` (`SamplingRateSource.kt:43`). 실제로 쓰는 칸은 `applied` **하나**이고 `byService` 는 미등록 세기 · 로그에만 쓰인다 |
| 서비스 이름을 읽는 자리 | 봉투 바깥 `resource` 의 `service.name` (`serviceNameOf`, `TraceSampler.kt:123`). 스팬에는 없다. `#206` 은 **이미 읽고 있는 이 값**을 선 고르기에 쓰는 일이다 |
| 지름길 조건 | `applied >= 1.0` 이면 요청을 다시 만들지 않는다(`TraceSampler.kt:52`). 선이 묶음마다 달라지면 이 조건도 **`resourceSpans` 마다** 봐야 한다 (알고 싶었던 것 ③) |
| 우리 모듈 트레이스 | 수집기 · 적재 처리기는 `OTEL_TRACES_EXPORTER=none`(`Dockerfile:55` · `:63`), API 서버 · 탐지 · 알림은 켬 |
| 쇼핑몰 → 모니모 호출 자리 | **둘이다** : ① 에이전트 OTLP `collector:4317` ② Extension 롱폴링 `collector:8081`(`monimo-shop/agent-extension/README.md:32`, `#122`) |
| 경계가 열릴 조건 | 처음에 「수집기 트레이스를 켜면 섞인다」로 적었다가 **실측으로 접었다**(아래 「우리 데이터로 확인한 것」). 남은 자리는 Extension 롱폴링 하나이고, 그쪽은 에이전트 exporter 가 아니라 **Extension 이 직접 거는 HTTP** 라 문맥이 실릴 수 있다 → 쇼핑몰을 띄워 재야 한다 |

### 확인 못 한 것

- **쇼핑몰 Extension 롱폴링**(`collector:8081`)이 트레이스 문맥을 싣는가 : 쇼핑몰이 떠야 잰다. 싣는다면 `shop-*` CLIENT 스팬과 `monimo-collector` SERVER 스팬이 한 `trace_id` 가 되고, **그때는 두 묶음을 한 선으로 되돌린다**(되돌림 조건)
- 쇼핑몰 실데이터로 같은 쿼리 (아래) 를 한 번 더 : 우리 모듈로 본 결과가 쇼핑몰에서도 같은지

```sql
-- 쇼핑몰 trace 에 우리 모듈 스팬이 끼어 있나 : 0 이면 경계를 안 넘는다
SELECT count()
FROM spans
WHERE service_name LIKE 'monimo-%'
  AND trace_id IN (SELECT trace_id FROM spans WHERE service_name LIKE 'shop-%');
```

- 미등록 서비스에 줄 기본값 넷 중 무엇인지 (전체 최댓값 · 가장 낮은 선 · yml 기본값 · `shop` 취급)

## 7. 2차 정리

- **좁혀진 선택지** : 5절 ② (`system` 안 최댓값) 하나. ① 은 B평면이 못 돌고, ③ 은 ADR `#53` 이 기각했고, ④ 는 성립하지 않고, ⑤ 는 핵심기능 5 를 깬다
- **결정을 가르는 기준** : 「트레이스가 시스템을 넘지 않는다」 하나였고 **실측으로 섰다** (603 trace 중 0건 · 음성 대조 1건). 남은 미확인(Extension 롱폴링)은 되돌림 조건으로 내린다
- **무엇을 정해야 하나**
  - ① **미등록 서비스에 줄 선** : 추천 = **yml 기본값**(`monimo.collector.sampling.ratio`, 운영 `0.01`)
    - 사유 셋 : 미등록은 「어느 묶음인지 모른다」는 뜻이라 특정 묶음의 값을 빌려 올 근거가 없다 · PG 를 한 번도 못 읽었을 때와 **같은 값**이라 설명이 하나로 줄어든다 · 전체 최댓값을 주면 남의 앱이 모니모 50% 를 타고 들어와 적재가 폭증한다
    - **알고 쓰는 위험** : 지금은 미등록도 전체 최댓값이라 같은 선인데, 바꾸면 **미등록 서비스가 섞인 트레이스는 쪼개질 수 있다**. 등록 전 과도기에만 생기고 `sampling.unknown_service` 로 세어져 보이므로 받아들인다 → 되돌림 ②
  - ② **ADR 번호** : 추천 = **새 번호 `#72`** + 제목에 「`#53` 보완」. 사유 = 확정 ADR 본문을 소급 수정하지 않는 선례(`#195` 는 `#67` 되돌림 사유를 **고쳐 읽는다**고만 적었다). `#53` 에는 「`#72` 가 범위를 좁혔다」 한 줄만 더한다
  - ③ **지표를 시스템별로 나눌지** : 추천 = **지금은 안 나눈다**. 묶음이 둘이고 `kept` · `dropped` 에 태그를 더하면 되돌릴 때 대시보드가 깨진다. 조건 = 묶음이 **셋 이상**이 되거나 「어느 묶음이 얼마 버렸나」를 물은 일이 생기면 `tag("system", …)` 을 더한다

### 구현 순서 (수집기 한 모듈 · 마이그레이션 0 · API 서버 0 · 화면 0)

| 순서 | 파일 | 하는 일 |
|---|---|---|
| 1 | `sampling/SamplingRateSource.kt` | `SamplingRates` 에 묶음 축을 넣는다 : 입력은 `(이름 → 비율)` 과 `(이름 → system)`, 미리 계산해 두는 것은 `system → 그 묶음 최댓값` 과 `fallback`. 꺼내는 문은 **`appliedFor(serviceName): Double`** 하나 (모르는 이름이면 `fallback`). **불변 유지** : 30초마다 참조 하나를 통째로 갈아끼운다 |
| 2 | `outbound/postgres/PostgresSamplingRateSource.kt` | SQL 에 `applications.system` 을 더해 세 칸으로 읽는다(`deleted_at IS NULL` 그대로). 로그는 묶음별 선을 찍는다 : 「shop 1% · monimo 50%」 |
| 3 | `sampling/TraceSampler.kt` | `sample()` 의 `resourceSpans` 루프에서 `serviceNameOf(resource)` → `appliedFor(이름)` 으로 **그 묶음의 선**을 꺼내고 그 아래 스팬을 그 선으로 판정한다. `keep(span, ratio)` 는 손대지 않는다 |
| 4 | 같은 파일 | **지름길을 묶음마다로 내린다** : 전에는 `applied >= 1.0` 이면 요청을 통째로 통과시켰다. 이제 「**모든** `resourceSpans` 의 선이 `>= 1.0`」일 때만 통째 통과하고, 섞여 있으면 묶음별로 거른다(로컬 seed 가 전부 `1.0` 이라 그 길이 유지된다) |
| 5 | 같은 파일 | `countUnknownServices` 는 이미 이름을 읽으므로 그대로 둔다. 선 고르기와 **두 번 읽지 않게** 묶음 루프 안에서 한 번 읽어 같이 쓴다 |
| 6 | 테스트 | `SamplingRatesTest` : 묶음별 최댓값 · 모르는 이름은 fallback · 빈 입력 · 넘긴 Map 을 나중에 고쳐도 안 바뀜. `TraceSamplerTest` : **두 묶음이 섞인 봉투**에서 각각 다른 선이 걸림 · 같은 `trace_id` 는 같은 묶음 안에서 같은 답 · 카나리는 비율을 건너뜀 · 지름길(전부 1.0) · 일부만 1.0. `PostgresSamplingRateSourceTest` : Testcontainers 로 `system` 세 칸 읽기 · `deleted_at` 제외 |
| 7 | 문서 | ADR `#72` 4요소(문제 · 채택 · 기각 · 되돌림) · `#53` 에 한 줄 · `AGENTS.md` §5 수집 파트 한 줄 · §6 「화면에는 네 칸인데 최댓값 하나」 행을 「**그 서비스가 속한 시스템 안의** 최댓값」으로 · `00-index.md` `next` |

- **건드리지 않는 것** : PG 표(`#205` 로 칸이 있다) · 해시 공식 · 카나리 통과 · 헬스체크 거르기 · 30초 주기 · 실패 시 마지막 값 유지 · `metrics_raw` · 적재 처리기
- **확인 방법** (로컬)
  - `UPDATE application_configs SET sampling_rate = 0.5 WHERE application_id IN (SELECT id FROM applications WHERE system = 'monimo')` 로 두 묶음을 다르게 둔다
  - 쇼핑몰 부하를 흘리고 `spans` 를 서비스별로 세어 **쇼핑몰은 1% · 모니모는 50%** 로 남는지 본다
  - 같은 구간에서 「서비스가 둘 이상인 trace」가 여전히 **0 건**인지 본다 (5절 쿼리 재사용)
- **되돌림**
  - ① **Extension 롱폴링이 문맥을 싣는 것이 관측되면**(쇼핑몰 `shop-*` CLIENT 와 `monimo-collector` SERVER 가 한 `trace_id`) 두 묶음을 **한 선으로** 되돌린다
  - ② **미등록 서비스가 섞인 트레이스가 실제로 쪼개지면** 미등록 기본값을 「전체 최댓값」으로 올린다
  - ③ 묶음이 **셋 이상**이 되면 지표에 `system` 태그를 더한다(②와 별개)
  - ④ 「서비스마다 진짜 다른 비율」 요구가 오면 ADR `#53` 되돌림 ① 로 올라가고, 그때 보정 계수 표시를 화면과 같이 정한다

### 여기서 나온 면접 질문

1. 트레이스 샘플링을 에이전트가 아니라 **수집기**에서 한 이유는 무엇이고, 그 대가는 무엇인가 (답 : 비율 정본이 PG 라 재배포 없이 바뀐다 · 대가는 거르기 전 신호가 네트워크를 다 타고 온다)
2. 서비스마다 다른 샘플링 비율을 쓰면 무엇이 깨지는가 (답 : 거르는 단위는 트레이스인데 설정 단위는 서비스라 같은 `trace_id` 의 위아래가 다른 선으로 재어져 고아 스팬이 생긴다. `#121` 실측 9%)
3. 「선을 묶음마다 둔다」가 안전한 조건은 무엇이고 그것을 어떻게 보였는가 (답 : 트레이스가 묶음 경계를 넘지 않는 것. 603 trace 중 0건 + 같은 `traceparent` 를 손으로 넣은 음성 대조로 측정 도구까지 검증)
4. `trace_id` 해시로 고르면 같은 번호가 겹칠 수 있는데 왜 문제가 없는가 (답 : 번호는 식별자가 아니라 추첨 번호다. 묶거나 찾는 일은 `trace_id` 원래 값으로 한다)
5. 자기 제품으로 자기를 감시할 때(도그푸딩) 무엇을 조심해야 하는가 (답 : 되먹임. 수집기 · 적재 처리기는 자기 스팬이 자기 입력으로 돌아와 `OTEL_TRACES_EXPORTER=none` 으로 끄고 지표 · 로그만 보낸다)
