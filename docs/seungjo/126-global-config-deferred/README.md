# `#126` 전역 설정 표를 지금 만들지 않는다 : 옮길 값이 하나였다

이슈 `#126` `#128` · ADR `#55` · 브랜치 `chore/126-global-config-deferred` · `#121` 이 올린 후속

**만든 것이 아니라 안 만들기로 정한 이슈다.** 코드 변경은 DB 주석 한 줄이고 나머지는 문서다.
가볍게 간다 : 이 폴더에 `research.md` · `prompts.md` · `tables.md` · `decision.md` 는 없다.

## 문제

핵심기능 5가 "재배포 없이 설정을 바꾼다" 인데, 아직 재배포해야 바뀌는 값이 남아 있었다.

```
샘플링 비율        PG 에 있다   → 화면에서 바꾼다        끝났다 (#121)
헬스체크 거를 주소   수집기 env   → 바꾸려면 재배포해야 함  남아 있다
```

헬스체크 거를 주소는 도커 · 쿠버네티스가 찌르는 `/actuator/health` 를 버리는 목록이다(`#92`). 남의 앱이 `/healthz` 를 쓰면 목록에 넣어야 하는데 이미지를 다시 배포해야 한다.

PG 로 옮기려면 둘 자리가 필요한데, 지금 설정 표(`application_configs`)는 **서비스당 한 줄**이고 이 값은 **전체 하나**다. 그래서 표를 새로 만들어야 하고, 표를 만들면 고치는 API 와 화면이 따라온다.

## 조사가 이슈 전제를 바꿨다

이슈 본문은 **옮길 값이 셋**이라고 적었다. 세어 보니 하나였다.

| 설정 | 이슈가 말한 것 | 실제 |
|---|---|---|
| 샘플링 비율 | PG `application_configs` | 맞다. 이미 옮겼다 |
| 헬스체크 거를 주소 | 수집기 env | 맞다 |
| **로그 하한** | 수집기 env | **코드에 아예 없다** |

`MIN_LOG_LEVEL` 은 레포 전체에서 문서 두 곳에만 있다. `01-decisions.md` 의 ADR `#38` ④ 와 `api-spec.md` 의 `LogsService/Export` 행이다. 수집기 `filter/` 에는 `HealthCheckFilter` 하나뿐이고 로그를 거르는 코드가 없다. **API 명세가 "하한 미만 등급은 여기서 버려짐" 이라고 적어 뒀는데 사실이 아니었다.**

`#121` 때 ERD 의 `version` 과 `updated_at` 설명이 틀렸던 것과 같은 종류다. 문서가 결정을 적어 두고 구현이 따라가지 않으면 그 문서가 거짓말이 된다.

## 결정

- **고른 것** : 전역 설정 표를 **지금 만들지 않는다.** 헬스체크 거를 주소는 수집기 전역 env 에 그대로 둔다. 로그 하한은 **폐기가 아니라 보류**로 적고 발동 조건을 둔다. `api-spec.md` 의 틀린 기술을 고친다. `application_configs.sampling_rate` 의 DB 주석(`#128`)은 새 마이그레이션 파일로 재지정한다
- **버린 것과 이유** : **줄 하나짜리 표**는 값 하나를 위해 표 · API · 화면을 만든다 · **키 · 값 표**는 값마다 타입과 검증이 다른데 전부 글자가 되어 `sampling_rate` 의 `CHECK (0 <= x <= 1)` 같은 보호가 사라진다 · **`application_configs` 에 전역용 줄 추가**는 `application_id` 가 `NOT NULL` FK 라 가짜 서비스를 만들어야 하고 `#38`("설정 단위는 앱 단위만")과 어긋난다 · **로그 하한 지금 구현**은 거를 것도 읽을 사람도 없다 · **로그 하한 폐기**는 남의 앱이 `DEBUG` 를 켜고 들어오는 경우가 진짜라 그때 처음부터 다시 정하게 된다 · **기존 마이그레이션 파일 직접 수정**은 Flyway checksum 이 어긋나 팀원 전원이 `repair` 를 돌려야 한다
- **다시 볼 조건 넷** : ① 옮길 값이 **셋 이상**이 될 때 ② 값이 안 늘어도 그 주소를 바꾸려고 **재배포한 일이 실제로 두 번** 생기면 ③ **쇼핑몰이 아닌 앱이 붙을 때** 로그 하한을 만든다 ④ **로그 검색 화면이 생길 때** 로그 하한을 만든다

### 왜 셋인가

**오늘 이미 둘이다.** 헬스체크 거를 주소와 샘플링 비율이다. 둘을 기준으로 잡으면 "지금 만들라" 가 되어 이 결정과 모순된다. 셋은 **새 요구가 실제로 하나 더 생겼다**는 뜻이다.

비용 모양도 그렇다. 처음 만들 때는 표 · 마이그레이션 · API · 화면 · 읽는 쪽으로 **네 파트가 움직이고**, 값 하나를 더 넣는 비용은 컬럼 하나다. 고정 비용은 크고 값당 비용은 거의 0 이라, 기준은 그 고정 비용을 나눠 가질 값의 수가 된다.

다만 숫자만으로는 부족해서 ② 를 같이 뒀다. 값이 둘에서 안 늘어도 불편은 커질 수 있다. 한 번 재배포는 우연이고 두 번이면 신호다.

## 전부 PG 로 옮길 수는 없다

경계가 있다.

```
env 에 있어야 하는 것    PG 주소 · Kafka 주소 · DB 비밀번호 · 내부 토큰 · JWT 키
                      (PG 주소를 PG 에 둘 수는 없다)

PG 로 옮길 수 있는 것    운영 중 사람이 화면에서 바꾸는 값
```

옮길 수 있는 값도 공짜가 아니고 비용이 넷 붙는다.

| | |
|---|---|
| 못 읽었을 때 쓸 값을 **값마다** 정해야 한다 | `#121` 은 비율 하나에 네 선택지를 비교했다(`0.01` · `1.0` · `0.0` · 기동 실패) |
| PG 장애가 번지는 범위가 넓어진다 | 지금은 비율 하나만 낡는다. 전부 PG 면 전부 낡는다 |
| 언제 적용됐는지가 흐려진다 | 30초 캐시다. 수집기가 여러 대면 그동안 서로 다른 값으로 돈다 |
| 로컬과 테스트에 seed 가 필요해진다 | `#121` 때 팀원 전원이 `docker compose down -v` 를 돌려야 했다 |

## 어떻게 확인했나

로그 하한을 보류한 근거는 전부 실측이다.

```
ClickHouse 로그 등급    INFO 51,336 · ERROR 2,643 · WARN 578 · WARNING 7
                      DEBUG · TRACE 0건 (쇼핑몰 앱이 INFO 아래를 안 만든다)

저장 비중              spans 99.47 MiB (1,405,331줄)
                      logs   3.14 MiB (   54,564줄)   전체의 3%
                      metrics 344 KiB

로그 보관 기간          97일
로그 조회 API          0개 (query 아래: agent · error · health · servermap · support · trace · transaction)
api-server 에서 level 을 쓰는 코드   0건
```

**거를 것도 없고, 아껴야 할 이유도 없고, 로그를 읽는 사람도 없다.**

`MIN_LOG_LEVEL` 이 없다는 것은 레포 전체 검색으로 확인했다. 문서 두 곳에만 있고 코드에는 없다.

## 범위 밖으로 남긴 것

`WARN` 578건과 `WARNING` 7건이 **같은 뜻인데 따로 세어진다.** 적재 처리기 `LogTranslator` 가 `severity_text` 를 대문자로만 바꾸고 표준 이름으로 맞추지 않는다. 하한과 무관하게 틀린 숫자이지만, 고치면 ClickHouse 에 저장되는 값이 바뀌는 동작 변경이라 이 결정 범위 밖으로 뒀다. (후속 `#144` · ADR `#59` 에서 해소했다. 거기서 **이 7건이 가짜 데이터가 낼 수 없는 값이라 진짜 생산자의 것이었다**는 것과, 그 뒤 볼륨이 새로 만들어져 지금 표에는 없다는 것도 밝혀졌다.) `AGENTS.md` §6 에 올렸다.
