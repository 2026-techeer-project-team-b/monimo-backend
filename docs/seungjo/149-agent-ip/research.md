# `#149` `agents.ip` 를 채운다 : 조사와 결정

> - 9단계 틀
> - ③ · ⑥ · ⑧ 은 사람(승조) 차례다
> - 2 와 5 는 처음 보는 사람 눈높이로 쓴다
> - 파일 이름 · 라이브러리 이름 · 설정 키는 9절에서만 쓴다

## 1. 어떤 이슈인지

### 지금 무엇이 잘못됐나

- 파드 명단 표에 **주소 칸이 있는데 전부 비어 있다**
  - 표를 만들 때 "수집기가 연결 통로에서 알아내 메시지에 붙이고 적재 처리기가 채운다" 고 적어 뒀다
  - 그런데 수집기 쪽 코드가 한 줄도 없다
- 화면은 이미 그 칸을 그린다
  - 파드 상세 머리와 파드 목록이 주소를 보여 준다
  - 지금은 전부 빈칸이다
- 적재 처리기는 파드를 처음 볼 때 호스트 이름 · JVM 버전 · 에이전트 버전은 채운다
  - 주소만 빼 놓았다
  - 그 자리에 "수집기가 붙여 줘야 하는데 아직 없다" 는 주석이 남아 있다
  - 파드 등록을 만든 작업 `#66` 때 미룬 것

### 그래서 무엇을 하나

- 에이전트가 신호를 보낼 때 **그 에이전트의 주소**를 알아낸다
  - 적재 처리기까지 전달한다
  - 파드 명단에 적는다
- 세 가지를 정한다
  - **어디서 얻을지** : 수집기가 연결에서 읽나, 에이전트가 스스로 적어 보내나
  - **어떻게 전달할지** : 메시지 겉봉에 붙이나, 안에 끼워 넣나
  - **바뀌면 어떻게 할지**

### 안 하면 어떻게 되나

- 화면 영향만 있다
  - 수집 · 적재 · 경보는 이 칸을 안 쓴다
- 같은 서비스의 파드가 여럿일 때 어느 파드가 어느 주소인지 구분할 단서가 없다
- 스레드 덤프 명령은 이 주소로 가지 않는다(수집기 팬아웃으로 간다)
  - 그래서 틀려도 동작은 안 깨진다
  - 그런데 화면에 **틀린 주소**를 보여 주는 것은 빈칸보다 나쁘다
  - 정확히 못 채우면 비워 두는 쪽이 맞다

## 2. 작업하기 전에 알아야 하는 것

- 꼭 알아야 하는 것 다섯 개다
- 이 다섯이 선택지를 가른다

### 2.1 주소를 얻는 길은 둘이고, 에이전트는 기본으로 자기 주소를 안 보낸다

| 길 | 누가 아나 | 어떻게 |
|---|---|---|
| **연결에서 읽기** | 수집기 | 에이전트가 수집기에 연결하면 수집기 쪽에 "상대 주소" 가 남는다. gRPC 가 그 값을 꺼내는 공식 방법을 준다. 연결 하나에 값 하나고, 그 연결로 오는 모든 요청이 같은 값을 본다 |
| **에이전트가 적어 보내기** | 에이전트 | 에이전트가 신호마다 붙이는 "나는 누구" 꼬리표(resource)에 주소를 넣는다. 에이전트 기본값에는 **호스트 이름과 CPU 종류만 있고 주소는 없다**(공식 소스 확인). 넣으려면 기동 설정 한 줄로 직접 적어야 한다. 쿠버네티스는 파드 자기 IP 를 환경변수로 내려 주는 기능(Downward API)이 있어 그 한 줄이 가능하다. 지금 파드 이름표(`service.instance.id`)를 넣는 것과 같은 방식이다 |

- 조사가 "에이전트 쪽으로는 길이 없다" 로 결론 냈는데 **반만 맞다**
  - 자동으로는 없고, 설정으로는 있다
  - 둘째 길은 쇼핑몰 배포 설정(compose · 매니페스트)을 고치는 일이 따라온다
  - 에이전트 코드는 안 고치므로 비침습 원칙은 지킨다
- 실측(로컬) : 지금 쇼핑몰 에이전트가 보내는 꼬리표에 주소는 없고 호스트 이름만 있다
  - 그 호스트 이름은 컨테이너 ID 12자리(`75869dbf1bd1` 꼴)라 사람이 봐도 뜻이 없다

### 2.2 연결에서 읽은 주소는 "누가 보냈나" 이고, 환경마다 다르게 보인다

| 환경 | 수집기가 보는 상대 주소 | 근거 |
|---|---|---|
| 로컬 compose | **에이전트 컨테이너의 네트워크 안 주소**(172.19.0.11 ~ 14). 다만 IPv6 겉모양(`::ffff:172.19.0.11`)으로 보인다 | 실측 2026-10-11 : 수집기 컨테이너의 4317 연결 8개가 쇼핑몰 네 컨테이너 주소와 정확히 일치. 재시작하면 주소가 바뀔 수 있다 |
| 쿠버네티스 안 (에이전트 파드 → 수집기 Service) | **에이전트 파드 IP 그대로.** 클러스터 안 트래픽은 출발 주소를 바꾸지 않는다 | 공식 문서 「Using Source IP」. EKS 는 파드에 VPC 주소를 직접 주고 VPC 안에서는 바꾸지 않는다 |
| 바깥 로드밸런서를 거칠 때 | **로드밸런서 주소**로 덮인다. 보존하려면 따로 켜야 한다(NLB 는 Proxy Protocol, ALB 는 헤더) | 공식 문서. 우리 수집기는 클러스터 안 에이전트만 받으므로 지금은 해당 없음 |

- 그래서 연결에서 읽는 길은 **지금 우리 두 환경(compose · EKS 안)에서 둘 다 파드 주소가 맞게 나온다**
  - 바깥에서 들어오는 에이전트가 생기면 그때 틀린 주소가 적힐 수 있다는 것을 알아 둔다
- **그 경우 2.1 의 두 길이 서로 다른 값을 준다**
  - 에이전트가 적어 보낸 주소는 진짜 파드 주소(맞음)
  - 수집기가 연결에서 읽은 주소는 로드밸런서 주소(틀림)
  - 지금은 두 길이 같은 값을 주지만 그때는 에이전트 쪽이 더 정확해진다
  - (나) · (다) 로 옮겨 갈 근거가 이것이다
- IPv6 겉모양은 떼서 저장해야 한다
  - **저장이 실패해서가 아니라 조용히 들어가기 때문이다** (2.5 실측)

### 2.3 수집기 → 적재 처리기로 넘길 때, 겉봉에 붙이는 길과 안에 끼우는 길이 있다

- 수집기는 받은 데이터를 **한 글자도 안 풀고 바이트 그대로** Kafka 에 넣는다
  - 그게 지금 약속이다(키 = 신호 이름, 값 = 받은 바이트)
  - 적재 처리기가 풀어서 읽는다
- **겉봉(헤더)**
  - Kafka 메시지에는 값과 따로 "이름 = 값" 꼬리표를 붙일 자리가 있다(0.11 부터)
  - 수집기가 `agent.ip = 172.19.0.11` 같은 꼬리표를 붙인다
  - 적재 처리기가 꺼내 등록 재료에 합친다
  - 데이터 바이트는 그대로다
- **안(바이트)**
  - 받은 데이터를 풀어 꼬리표(resource)에 주소를 끼워 넣고 다시 바이트로 만든다
  - 약속("받은 그대로")이 깨진다
  - 요청마다 풀고 다시 조립하는 비용이 생긴다
  - 대신 적재 처리기는 다른 꼬리표(호스트 이름 등)와 똑같이 읽으면 된다
- **한 메시지 = 한 연결의 한 요청 = 에이전트 하나**
  - 요청 안에 꼬리표 묶음(resource)이 여러 개 있어도 전부 같은 에이전트의 것이라 겉봉 하나로 충분하다
  - 그런데 중간에 다른 수집기(OTel Collector 등)를 끼우면 깨지는 전제다
  - 우리는 끼우지 않는다(에이전트 → 우리 수집기 직결)

### 2.4 지금 등록은 "처음 한 번만 적고 그 뒤로는 안 건드린다" 라 주소가 바뀌면 안 따라간다

- 적재 처리기는 파드를 처음 볼 때 한 줄 넣는다
  - 이미 있으면 아무것도 안 한다(이름 충돌이면 무시)
  - 그래서 호스트 이름 · 버전은 처음 값이 영구히 남는다
  - 메모리 캐시도 "이미 아는 파드" 를 기억해 PG 를 다시 안 친다
- 주소는 그 칸들과 성격이 다르다 : **바뀐다**
  - 다만 "재시작" 이 두 가지 다른 일을 가리켜서 갈라 적는다

| 무슨 일 | 주소는 | 명부는 |
|---|---|---|
| **안의 프로세스만** 죽었다 다시 뜸 (컨테이너 · 파드는 그대로. 쿠버네티스가 컨테이너만 다시 띄우는 경우) | **그대로** | 문제 없다 |
| **컨테이너 · 파드 자체가** 없어지고 새로 만들어짐 (배포 교체 · 이미지 다시 빌드 · 노드 이동) | **새로 받는다** | 이름표가 같아 같은 줄로 보고 안 고친다 → **옛 주소가 남는다** |

- **실측 (2026-10-12, 로컬 도커)**
  - 컨테이너 재시작은 `172.19.0.3` → `172.19.0.3` 그대로
  - 지우고 **생성 순서를 뒤집어** 다시 만들면 같은 이름의 컨테이너가 `172.19.0.3` → `172.19.0.4` 로 바뀐다
  - 반대로 혼자 지우고 바로 다시 만들면 비어 있던 그 주소를 다시 받기도 한다
    - 도커가 가장 낮은 빈 주소를 준다
- 그래서 정확한 말은 "항상 바뀐다" 가 아니라 **"유지된다는 보장도, 바뀐다는 보장도 없다"** 다
  - ① 을 고르면 화면에 **때로는 맞고 때로는 틀린** 값이 남는다
  - 언제 틀린지 알 방법이 없다
  - 늘 틀리면 "이 칸은 못 믿는다" 가 되는데 가끔 맞으면 믿게 되므로 더 나쁘다
- **이름표에 무엇을 넣느냐로 안정성이 3단이고, 그에 따라 이 칸의 운명이 갈린다**

| 이름표에 넣는 값 | 컨테이너만 다시 뜸 | 파드 · 컨테이너 재생성 | 명부는 | 주소 칸은 |
|---|---|---|---|---|
| 아무것도 안 넣음 (에이전트가 무작위 ID 생성) | **바뀐다** | 바뀐다 | 뜰 때마다 줄이 쌓인다. **못 쓴다** | 새 줄에 새 주소라 맞다 |
| 쿠버네티스 파드 이름 | 유지 | **바뀐다**(무작위 꼬리) | 배포마다 새 줄 | 새 줄에 새 주소라 **늘 맞다** |
| 손으로 고정한 이름 (**지금 로컬 쇼핑몰**) | 유지 | 유지 | 줄 하나로 유지 | **옛 주소가 남는다** |

- 우리가 고친 것은 첫째 줄 → **셋째 줄**이다(쇼핑몰 `#30`)
  - 둘째 줄로 간 것이 아니다
  - 첫째 줄이 문제였던 이유는 명부가 "지금 파드 목록" 이 아니라 "지금까지 떴던 횟수" 가 되기 때문이다
- **쿠버네티스에서 이름표에 무엇을 넣을지는 아직 안 정했다**
  - `AGENTS.md` §6 : "값을 정할 때 같이 확인"
  - 파드 이름이 유력 후보다
- **그래서 결정 3 이 이름표 선택에 묶인다**
  - 파드 이름을 쓰면 갱신 장치가 거의 필요 없다
  - 고정 이름을 쓰면 필요하다
- 그런데 **로컬은 이미 셋째 줄로 확정**이고 쿠버네티스 값은 미정이다
  - ② 를 넣으면 이름표를 어느 쪽으로 정해도 주소가 맞다
  - ① 로 두면 두 결정이 서로 묶인다
    - 나중에 이름표를 고정 이름으로 정하는 순간 주소가 조용히 틀려진다
  - **결정을 서로 묶지 않는 쪽**을 고른다
- 이름표 고정 자체는 좋은 결정이었다
  - 다만 그 결정이 이 칸에서는 "틀린 값이 남는다" 로 나타난다
  - 빈칸이면 눈치채는데 옛 주소는 믿게 된다
- 선택
  - ① 처음 값만(지금 방식 그대로, 주소도 처음 것)
  - ② 바뀌면 갱신
    - 메시지마다 PG 를 치면 안 되므로 "캐시에 기억한 주소와 다를 때만 UPDATE" 같은 장치가 필요하다
- 비슷한 자리가 하나 있다 : 파드 상태(UP · DOWN)는 탐지가 갱신한다
  - 주소 갱신을 넣으면 적재 처리기가 이 표를 **갱신**하는 첫 사례가 된다(지금은 넣기만)

### 2.5 주소 칸이 주소 전용 타입이고, 군더더기는 실패하지 않고 조용히 들어간다

- PG 의 주소 칸은 글자가 아니라 **주소 전용 타입(INET)** 이다
  - 우리가 검사하는 것이 아니라 DB 가 거른다
- **실측 (2026-10-12, 로컬 PG)** : 아무 글자나 거르는 것은 맞지만 **2.2 의 군더더기 붙은 모양은 거르지 않는다**

```
'not-an-ip'          → ERROR: invalid input syntax for type inet   (실패)
'::ffff:172.19.0.11' → 저장됨. 꺼내면 '::ffff:172.19.0.11', 주소 종류는 IPv6(6)
'172.19.0.11'        → 저장됨. 꺼내면 '172.19.0.11', 주소 종류는 IPv4(4)
```

- **처음에 "틀린 모양이면 넣기가 실패한다" 고 적었는데 이 경우에는 틀렸다**
  - 실패하면 바로 알아채는데 조용히 들어가는 쪽이 더 나쁘다
- 그래서 군더더기를 떼는 이유는 저장 실패를 막으려는 것이 아니다
  - **화면에 `::ffff:172.19.0.11` 이 그대로 보이는 것과 주소 종류가 IPv6 로 잘못 기록되는 것을 막으려는 것**이다
  - 떼는 일은 선택이 아니라 필수다
- 적재 처리기의 등록 SQL 은 이미 직접 쓴 SQL 이다
  - 주소 글자를 그 타입으로 바꿔 넣는 한 줄을 더하면 된다
- 표 대조용 클래스에는 그 칸이 빠져 있다
  - "채우는 코드가 생길 때 넣는다" 고 적혀 있다
- API 서버는 이미 그 칸을 글자로 바꿔 읽는다(`host()` 함수)
- 화면은 `10.42.17.64` 모양의 글자를 기대한다

### 2.6 추가로 알아 둘 것

- 스레드 덤프 명령은 이 주소를 쓰지 않는다
  - 수집기가 들고 있는 명령 통로로 간다
  - 주소가 틀려도 명령은 안 깨진다
- 수집기를 여러 대 띄워도 겉봉은 메시지에 붙어 따라간다
  - 그래서 어느 수집기가 받았든 상관없다
  - 적재 처리기가 여러 대여도 같다
- 주소 하나로 파드를 특정할 수는 없다
  - 파드가 죽고 새 파드가 같은 주소를 받을 수 있다
  - 식별자는 여전히 이름표(agent_key)다
  - 주소는 **사람이 보는 단서**다
- 에이전트가 적어 보내는 길(2.1 둘째)을 고르면 compose 에서는 컨테이너 자기 주소를 알 방법이 마땅치 않다
  - 쿠버네티스 Downward API 같은 것이 없다
  - 로컬은 빈칸, 운영만 채워지는 모양이 된다

### 2.7 측정 흐름

- 로컬 : 쇼핑몰 네 컨테이너를 띄운 뒤 PG 명단에서 네 줄의 주소가 `172.19.0.x` 네 개와 같은지 본다
  - 한 컨테이너를 재시작해 주소가 바뀌었을 때 명단이 어떻게 되는지 본다
  - ①이면 옛 주소, ②면 새 주소
- 겉봉이 없는 메시지(옛 수집기가 넣은 것 · 점검 스크립트 telemetrygen)도 적재가 깨지지 않고 주소만 빈칸인지 본다
- IPv6 겉모양 입력에 대해 `172.19.0.11` 로 저장되는지 단위 시험

### 2.8 자주 헷갈리는 것

- "에이전트 IP" 는 **에이전트가 붙은 앱(파드)의 주소**다
  - 에이전트는 앱 안에서 돈다
  - 노드(서버) 주소가 아니다
- 호스트 이름 칸에 들어 있는 12자리 글자는 사람이 지은 이름이 아니라 컨테이너 ID 다
  - 쿠버네티스에서는 파드 이름이 들어온다
- 로컬 compose 의 `172.x` 는 내 컴퓨터 안 가상 네트워크 주소라 바깥에서 접속할 수 없다
  - 화면에 보여도 "로컬 주소" 라는 것만 알면 된다

### 출처

- OTel Java Agent 리소스 속성 : opentelemetry-java-instrumentation `instrumentation/resources/library` 의 HostResource(호스트 이름 · CPU 종류만) · semconv `host.ip` 정의(문자열 배열, 기본 제공 아님)
- gRPC 원격 주소 : grpc-java javadoc `Grpc.TRANSPORT_ATTR_REMOTE_ADDR`(실험 API 표시) · `ServerCall.getAttributes()` · `Contexts.interceptCall` · grpc-java 이슈 5489
- 쿠버네티스 출발 주소 : kubernetes.io 「Using Source IP」 · EKS 「Enable outbound internet access for Pods」(VPC 안 SNAT 없음)
- Kafka 헤더 : KIP-82(0.11) · Spring Kafka 「Sending Messages」
- 표준 속성 이름 : semantic-conventions 레포 `docs/registry/attributes/network.md`(`network.peer.address`, Stable) · `client.md`(`client.address`, Stable, 프록시 뒤 원 클라이언트를 뜻함) · `source.md`(`source.address`, Development)

## 3. 1차 질문 (사람 차례)

1. **주소를 어디서 얻나**
   - (가) 수집기가 연결에서 읽는다
   - (나) 에이전트가 기동 설정으로 자기 파드 IP 를 적어 보낸다
   - (다) 둘 다 : 에이전트가 적어 보낸 것이 있으면 그것을, 없으면 연결 주소
   - ERD 는 (가)로 적었다
2. **주소가 바뀌면**
   - ① 처음 값만 남긴다(지금 방식)
   - ② 바뀌면 갱신한다
     - ②면 적재 처리기가 이 표를 갱신하는 첫 사례가 된다
3. **로컬 compose 의 `172.x` 주소도 그대로 적나** : 적는다 / 로컬은 비워 둔다
   - 화면에 보여도 되는가가 기준
4. **바깥 로드밸런서를 거쳐 들어오는 에이전트** 는 지금 없다
   - 그 경우 틀린 주소(LB 주소)가 적히는 것을 지금 막아 둘 것인가
   - 안 한다 / 사설 주소 대역이 아니면 비워 둔다
5. 조사가 빠뜨린 것이 있나

## 4. 1차 정리

- 사용자 확정 2026-10-12
- 다섯 개를 다 받았다

| 물은 것 | 정한 것 | 사용자가 말한 사유 |
|---|---|---|
| 주소를 어디서 얻나 | **(가) 수집기가 연결에서 읽는다** | 수집기가 에이전트와 연결돼 있으니 그 주소를 적으면 그만이다 · 아직 우리 서비스 안에 주소를 바꿀 로드밸런서 같은 것이 없다 |
| (나) 를 버린 이유 | | **로컬에서 테스트할 수 없다는 것이 가장 큰 단점** |
| (다) 를 버린 이유 | | 데이터의 출처를 적는 기능치고 **너무 과하다** |
| 전달 방법 | **(A) Kafka 봉투 메모(헤더)** | |
| 주소가 바뀌면 | **(②) 고친다** | 파드가 재생성되면 다른 주소를 가지는데 화면에 옛 주소가 보이니 그걸 고치려면 ② 여야 한다 |
| 로드밸런서 대비 | **안 한다** | 지금 그런 경로가 없다. 생기면 되돌림 조건으로 |
| 로컬 `172.x` 주소 | **적는다** | |

### 왜 그렇게 정했는지 (사유 보강)

- **(가)**
  - 쇼핑몰 레포를 한 글자도 안 고친다
  - 감시 대상이 감시 도구에 맞춰 바뀌지 않는다는 원칙이다
  - 포트 결정(`#148`)에서도 같은 이유로 그쪽을 골랐다
  - 로컬에서도 채워지는 것이 덤이다
- **(A)**
  - 이 작업 하나 때문에 "받은 바이트 그대로 넘긴다" 약속을 깰 가치가 없다
  - 수집기는 지금 메트릭 · 로그를 아예 열지 않는다
    - 그래서 (B) 는 그 둘에 새 비용을 만든다
- **(②)**
  - ① 로 두면 화면에 때로는 맞고 때로는 틀린 값이 남는다(2.4 실측)
  - 쿠버네티스 이름표 값이 미정인데, ② 면 그 결정이 어느 쪽으로 가도 주소가 맞다
  - **두 결정을 서로 묶지 않는 쪽**이다
- **로컬도 적는다**
  - 로컬인지 판별할 방법이 없다
  - 사설 대역으로 가르면 쿠버네티스 파드 주소(보통 `10.x`)까지 같이 비워진다
  - 프로필로 가르면 환경마다 다르게 도는 코드가 되어 로컬 시험의 뜻이 사라진다
  - 로컬 명부와 운영 명부는 **다른 DB** 라 로컬 주소가 운영 화면에 보일 일이 없다

### 같이 물어서 기각한 안 : "주소 칸을 아예 지운다"

- 사용자가 "주소 쓸모가 그렇게 좁으면 칸을 없애면 되는 거 아니냐" 고 물었다
- 셈해 보니 **치우는 쪽이 더 비싸다**

| | 채우기 | 지우기 |
|---|---|---|
| PG | 손 안 댐 (칸이 이미 있다) | 마이그레이션 하나 (올라간 파일은 못 고쳐서 새 파일, 「PG 마이그레이션은 db/postgres 한 곳 + Flyway」 결정) |
| 수집기 · 적재 처리기 | **코드 다섯 자리 + 시험** | 손 안 댐 |
| 조회 API | 손 안 댐 (이미 그 칸을 읽는다) | 응답에서 칸 빼기 |
| 화면 | 손 안 댐 (이미 그린다) | 표시 · 타입 · 가짜 데이터 · 계약 시험 기대 목록 네 곳 |
| 노션 명세 | 손 안 댐 | ERD · API 명세 두 페이지 (팀 정본) |
| 움직이는 파트 | **수집 하나** | **넷** (수집 · 조회 · 인증 설정 · 화면 공동) + 팀 합의 |

- **기각 사유** : 화면 칸 하나를 없애려고 네 파트를 움직이는 것이 배보다 배꼽이 크다
  - `#126`(전역 설정 표)에서 "만들면 네 파트가 움직인다" 를 사유로 **안 만들기**를 택했다
  - 이번은 방향이 뒤집혀 **만드는 쪽이 한 파트 · 없애는 쪽이 넷**이다
  - 같은 기준을 쓰면 만드는 쪽이다
- **세 번째 안("칸은 남기고 화면에서만 숨긴다")도 기각**
  - 명세는 약속하고 코드는 안 지키는 **지금 상태가 그대로 남는다**
  - 그게 가장 나쁘다
  - 실제로 `AGENTS.md` 막힌 것 목록 첫 줄에 계속 올라와 있었다
- **이 작업의 근거는 "주소가 꼭 필요해서" 가 아니다**
  - 쓸모는 좁다(2.6)
  - 근거는 **치우는 값이 채우는 값보다 비싸다**는 것뿐이다
  - 이것을 ADR 에 그대로 적는다
- **되돌림** : 명세 · 화면에서 이 칸을 빼기로 팀이 정하면 채우는 코드도 같이 뺀다

### 주소가 혼자만 할 수 있는 일 (쓸모를 좁혀 확정한 것)

- 조사 중에 "주소가 왜 필요한가" 를 여러 번 되물어 쓸모를 셋으로 좁혔다
- 이것이 이 칸의 전부다

| 쓸모 | 왜 이름표로는 안 되나 |
|---|---|
| **바깥 네트워크 기록과 맞춰 보기** | AWS 흐름 기록 · 로드밸런서 기록은 **주소로만 적힌다.** 우리 이름표를 모른다. 우리 명부와 그 기록을 잇는 유일한 열쇠다 |
| **죽은 파드가 그때 어디 있었나 되짚기** | 쿠버네티스는 죽은 파드 정보를 안 들고 있다. 이름표는 "누구" 까지만 알려 주고 "어디" 는 담고 있지 않다 |
| **가짜 신호 출처 좁히기** | 이름표 · 호스트 이름은 보낸 쪽이 마음대로 적는다. **주소만 우리가 연결에서 직접 읽으므로 속일 수 없다.** 신호 받는 문에 아직 인증이 없어(「OWLBY 벤치마크 4가지 반영」 결정 미구현) 이것이 유일한 단서다 |

- 반대로 **노드를 짐작하는 것은 확실한 쓸모가 아니다**
  - 노드마다 주소 대역이 갈리는 구성일 때만 된다
  - 여러 노드가 같은 대역을 쓰면 안 된다
- 주소로 **하지 않는 것**
  - 파드 식별(겹친다)
  - 스레드 덤프 보내기(수집기 팬아웃)
  - 경보(주소 보는 규칙 0개)
  - 차트와 조회(코드가 안 읽는다)

### 조사가 바로잡힌 것 둘 (지우지 않는다)

- **"에이전트 쪽으로는 길이 없다" 는 반만 맞았다**
  - 자동으로는 없고 기동 설정으로는 있다(2.1)
  - 이 구분을 못 했으면 (나) · (다) 를 선택지에 올리지도 못했다
- **A 의 단점 하나를 내가 과장했다**
  - "실패분 재처리 코드가 키와 값만 옮긴다" 고 적었다
  - 실제로는 스프링이 만든 부품을 쓰고 그 부품이 원본 헤더를 복사하는 것으로 문서화돼 있다
  - "고쳐야 한다" 가 아니라 **"시험으로 확인한다"** 다
- **2.5 의 "틀린 모양이면 넣기가 실패한다" 도 틀렸다**
  - 군더더기 붙은 주소는 실패하지 않고 조용히 들어간다(실측)
  - 떼는 이유가 저장 실패 방지가 아니라 화면에 괴상한 값이 보이는 것 방지로 바뀌었다

## 5. 구현을 위한 선택지 정리

- 큰 것 다섯은 4절에서 정했다
- 남은 것은 짓는 방법 쪽이고 다섯 묶음이다

### 묶음 1. 봉투 메모의 이름을 무엇으로 할까

- 메모는 "이름 = 값" 한 쌍이라 이름을 정해야 한다
- 값은 주소 글자다

| 안 | 설명 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| **우리 말로 짓기** | 우리가 보기 좋은 이름을 그냥 정한다 | 뜻이 바로 읽힌다 | 남이 보면 우리만의 규칙이다 |
| **규약 이름 따르기** | 계측 표준에 "상대 쪽 주소" 를 가리키는 정해진 이름이 있다. 그것을 쓴다 | 나중에 다른 도구가 끼어도 뜻이 통한다 · 이름을 고민할 일이 없다 | 그 이름이 우리가 담는 뜻과 정확히 같은지 확인해야 한다 |
| **지금 쓰는 꼴 따르기** | 실패분을 옮길 때 쓰는 메모 두 개가 이미 있다. 그 작명 꼴을 그대로 쓴다 | 한 레포 안에서 모양이 하나다 | 그 둘은 우리 내부 사정을 담는 메모라 성격이 조금 다르다 |

### 묶음 2. 주소를 못 읽었을 때 어떻게 할까

- 연결에서 주소를 꺼내는 일이 늘 되는 것은 아니다
  - 꺼내는 기능이 "실험 단계" 로 표시돼 있다
  - 연결 방식이 바뀌면 빈손이 될 수 있다

| 안 | 설명 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| **메모를 아예 안 붙인다** | 못 읽으면 조용히 넘어간다. 적재 처리기는 "주소 없음" 으로 보고 칸을 안 건드린다 | 가장 단순하다 · 옛 메시지와 같은 모양이라 처리 경로가 하나다 | 왜 비었는지 모른다 |
| **못 읽은 횟수를 센다** | 위와 같은데 세는 눈금을 하나 둔다 | 조용히 비는 일을 알아챌 수 있다 | 눈금 하나가 늘어난다 |
| **신호 받기를 거절한다** | 주소를 못 읽으면 에이전트에게 실패를 돌려준다 | 빈칸이 안 생긴다 | **절대 안 된다.** 화면 칸 하나 때문에 신호를 버리는 것이다 |

### 묶음 3. 군더더기를 어디서 떼나

- 주소가 `::ffff:` 가 앞에 붙은 모양으로 온다
- 떼는 자리가 둘이다

| 안 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **수집기에서 떼고 깨끗한 글자를 보낸다** | 메모에 들어가는 값이 이미 사람이 읽는 모양이다 · 적재 처리기는 받은 대로 쓴다 | 수집기가 주소 모양까지 신경 쓴다 |
| **적재 처리기에서 뗀다** | 수집기는 읽은 것을 그대로 넘긴다 | 메모 안의 값과 명부에 들어가는 값이 달라서, 중간에서 보면 헷갈린다 · 명부에 넣는 쪽에 손질 코드가 모인다 |

### 묶음 4. 수정 시각 칸을 같이 건드릴까

- 명부에는 "마지막으로 고친 시각" 칸이 따로 있다
- 화면도 그 값을 받아 간다

| 안 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **같이 고친다** | 파드 살았나 칸을 고치는 쪽(탐지)이 이미 그렇게 한다. 모양이 하나다 | 주소가 바뀔 때마다 그 시각이 움직인다 |
| **안 건드린다** | 주소만 조용히 바뀐다 | 명부 안에서 고치는 방식이 두 가지가 된다 |

### 묶음 5. 세 신호 중 어디에 메모를 붙일까

| 안 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **셋 다 (트레이스 · 지표 · 로그)** | 어느 신호가 먼저 와도 주소가 들어간다 | 붙이는 자리가 세 군데다 |
| **지표와 로그만** | 트레이스는 골라내기로 통째로 버려질 수 있어 믿을 수 없는 길이다. 지표는 늘 온다 | 트레이스만 보내는 앱이 붙으면 빈칸이다 |

### 딸려 오는 것 둘

- 명부 표를 코드와 대조하는 자리에 주소 칸이 **빠져 있다**
  - "채우는 코드가 생길 때 넣는다" 는 메모가 달려 있어서 이번에 넣는다
  - 안 넣으면 표와 코드가 어긋난 채로 남는다
- 적재 처리기가 기억하는 목록이 "이름표만" 에서 "이름표와 주소 짝" 으로 바뀐다
  - 상한(만 개)과 넘치면 비우는 규칙은 그대로 둔다

## 6. 2차 질문 (사람 차례)

1. **묶음 1 메모 이름** : 우리 말로 짓기 / 규약 이름 따르기 / 지금 쓰는 꼴 따르기
2. **묶음 2 주소를 못 읽었을 때** : 메모를 안 붙인다 / 거기에 세는 눈금까지 둔다
   - 거절은 뺀다
3. **묶음 3 군더더기 떼는 자리** : 수집기 / 적재 처리기
4. **묶음 4 수정 시각 칸** : 같이 고친다 / 안 건드린다
5. **묶음 5 어느 신호에** : 셋 다 / 지표와 로그만
6. 빠진 선택지가 있나

## 7. 2차 정리

- 사용자 확정 2026-10-12
- 다섯 묶음 중 넷을 받았다
- 수정 시각 칸은 선례가 뚜렷해 묻지 않고 맞췄다

| 물은 것 | 정한 것 |
|---|---|
| 묶음 1 봉투 메모 이름 | **계측 규약의 표준 이름을 쓴다** |
| 묶음 2 주소를 못 읽었을 때 | **메모를 안 붙이고, 못 읽은 횟수를 세는 눈금을 둔다** |
| 묶음 3 군더더기 떼는 자리 | **수집기에서 뗀다** |
| 묶음 4 수정 시각 칸 | **같이 고친다** (묻지 않았다. 파드 살았나 칸을 고치는 쪽이 이미 그 칸을 같이 고치고 있어 모양을 하나로 맞췄다) |
| 묶음 5 어느 신호에 | **셋 다** (트레이스 · 지표 · 로그) |

### 이 선택이 만드는 것

- **표준 이름 = `network.peer.address`** (조사로 확정, 2026-10-12)
  - 후보가 둘이었다
  - 프록시가 중간에 있을 때 뜻이 갈린다
  - 우리는 프록시가 없어 **두 값이 결과적으로 같아지지만 이름이 약속하는 뜻이 다르다**

| 이름 | 공식 정의 | 프록시가 있으면 | 안정성 |
|---|---|---|---|
| `client.address` | "Client address : domain name if available without reverse DNS lookup; otherwise, IP address or UNIX domain socket name." 주석에 "When observed from the server side, and when communicating through an intermediary, `client.address` SHOULD represent the client address behind any intermediaries" | **프록시 뒤의 원 클라이언트**를 뜻하려 한다. 헤더를 파싱해 복원하는 것이 전제다 | Stable |
| **`network.peer.address`** | "Peer address of the network connection : IP address or UNIX domain socket name." | **방금 연결한 그 상대(프록시 자신)** 를 뜻한다. 소켓 수준의 값이다 | Stable |

- **고른 이유**
  - 우리는 소켓에서 직접 읽고 헤더를 파싱하지 않는다
  - `client.address` 를 쓰면 **"프록시 뒤 원 클라이언트" 라고 약속해 놓고 실제로는 직전 홉을 담는** 거짓 약속이 된다
  - 로드밸런서가 생기는 날 그 거짓이 드러난다
  - `network.peer.address` 는 정의가 우리가 하는 일과 정확히 같다
- 세 번째 후보 `source.address` 도 확인했다
  - 안정성이 Development 라 뺐다
- 짝 속성 `network.peer.port`(int, Stable)가 있지만 **포트는 담지 않는다**
  - 명부에 포트 칸이 없고 쓸 데도 없다
- 출처 : semantic-conventions 레포 `docs/registry/attributes/network.md` · `client.md` · `source.md`
- **세는 눈금** : 수집기에 "주소를 못 읽은 횟수" 눈금 하나가 늘어난다
  - 관리 포트의 눈금 목록에 들어간다
  - 그래서 관통 점검 스크립트가 보는 자리와 같다
- **수집기에서 떼기** : 메모에 들어가는 값이 이미 `172.19.0.13` 모양이다
  - 적재 처리기는 받은 글자를 손질 없이 주소 칸에 넣는다
  - 손질 코드가 한 자리에만 있다
- **셋 다** : 붙이는 자리가 세 군데다
  - 트레이스는 골라내기를 지난 뒤 Kafka 로 가므로 **전부 버려지면 메모도 안 간다**
  - 그때는 지표 · 로그가 받쳐 준다(둘은 안 거른다)
- **수정 시각 같이 고치기** : 고치는 문장 하나가 칸 둘을 건드린다

### 바꾸는 것

| 어디 | 무엇 |
|---|---|
| 수집기 | 연결에서 상대 주소를 읽는 가로채기 · 그 값을 요청 처리까지 넘기는 통로 · 군더더기 떼기 · Kafka 에 넣을 때 메모 붙이기(세 신호) · 못 읽은 횟수 눈금 |
| 적재 처리기 | 메모에서 주소 꺼내기 · 목격 기록에 주소 더하기 · 기억 목록을 "이름표 → 주소" 짝으로 · 넣는 문장에 주소 칸 · **고치는 문장 신설**(주소가 다를 때만, 수정 시각 같이) · 표 대조용 코드에 주소 칸 |
| 명부 표 | **안 바꾼다.** 칸이 이미 있다 |
| 조회 API · 화면 | **안 바꾼다.** 이미 그 칸을 읽고 그린다 |

### 안 바꾸는 것 (범위 밖)

- **이름표는 안 건드린다**
  - 이미 돌아간다
  - 쿠버네티스에서 이름표에 무엇을 넣을지는 배포 단계 몫
- **ClickHouse 에 안 넣는다**
  - 주소는 신호의 성질이 아니라 파드의 성질이다
- 로드밸런서를 거친 주소 보정(프록시 규약 등)
  - 지금 그 경로가 없다
- 에이전트가 자기 주소를 적어 보내게 하는 길(2.1 의 (나))
  - 기각했고 되돌림 조건으로만 남긴다

### 남은 것 · 안 한 것

- **쿠버네티스에서 이름표에 무엇을 넣을지는 여전히 미정**이다(`AGENTS.md` §6)
  - ② 를 고른 덕에 어느 쪽으로 정해도 주소가 맞다
  - 2.4 표의 둘째 줄(파드 이름)로 가면 갱신이 거의 안 돈다
  - 셋째 줄(고정 이름)로 가면 계속 돈다
- **로드밸런서 경유 보정은 안 했다**
  - 그 경로가 생기면 수집기가 읽는 값이 LB 주소가 된다
  - 「파드 주소는 수집기가 읽어 Kafka 헤더로」 결정 되돌림 ②
- **포트는 담지 않았다**(`network.peer.port`)
  - 명부에 칸이 없다
