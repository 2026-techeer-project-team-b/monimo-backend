# `#149` 파드 명부의 주소 칸을 채운다 : 수집기가 연결에서 읽어 봉투 메모로 넘긴다

이슈 `#149` · ADR `#63` · 브랜치 `feat/149-agent-ip` · `AGENTS.md` §6 첫 줄(2026-09-29 등재)을 지운다

조사는 [`research.md`](research.md) 9단계에 있다. 이 글은 그 요약과 확인 결과다.

## 문제

`agents` 표에 **주소 칸이 있는데 전부 비어 있다.**

```
#66 (파드 등록)  칸은 만들고 "수집기가 붙여 줘야 하는데 아직 없다" 는 주석만 남겼다
화면            파드 상세 머리 · 파드 목록이 그 칸을 이미 그린다  -> 빈칸
조회 API        그 칸을 host() 로 글자로 바꿔 이미 내보낸다      -> null
ERD(노션 정본)   "수집기가 연결 통로에서 알아내 메시지에 붙이고 적재 처리기가 채운다"
수집기 코드      0줄
```

명세와 화면은 약속하고 코드는 안 지키는 상태가 2주 넘게 남아 있었다.

### 왜 적재 처리기가 혼자서는 못 하나

**주소는 데이터 안에 없다.** 에이전트(OTel Java Agent 2.x)가 신호마다 붙이는 꼬리표에는 호스트 이름과 CPU 종류만 있고 주소는 없다(공식 소스 확인, 실측도 같다). 즉 주소는 **데이터의 성질이 아니라 연결의 성질**이다.

```
에이전트 --- gRPC 연결 ---> 수집기 --- Kafka ---> 적재 처리기 ---> PG 명부
            연결이 있다            연결이 없다
            상대 주소를 안다        원리적으로 알 수 없다
```

그래서 수집기만 알 수 있고, 수집기가 적재 처리기까지 옮겨 줘야 한다.

## 선택지

큰 결정이 셋이었다. 전체 표와 버린 이유는 [`research.md`](research.md) 4절 · 5절에 있다.

| 무엇 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 주소를 어디서 얻나 | **수집기가 gRPC 연결에서 읽는다** | 에이전트가 기동 설정(쿠버네티스 Downward API)으로 적어 보내기 : compose 에 그 장치가 없어 **로컬에서 시험할 수 없다** / 둘 다 쓰기 : 출처를 적는 기능치고 과하다 |
| 어떻게 넘기나 | **Kafka 봉투 메모(헤더)** `network.peer.address` | 데이터 안(resource)에 끼워 넣기 : "받은 바이트 그대로" 약속(`#16`)이 깨지고, 수집기가 지금 지표 · 로그를 아예 열지 않아 그 둘에 풀고 다시 조립하는 비용이 새로 생긴다 |
| 주소가 바뀌면 | **고친다** (캐시한 주소와 다를 때만) | 처음 값만 남기기 : 재생성 때 주소는 "유지된다는 보장도, 바뀐다는 보장도 없다"(실측). 화면에 **때로는 맞고 때로는 틀린** 값이 남는다. 늘 틀리면 못 믿는 칸이 되는데 가끔 맞으면 믿게 되므로 더 나쁘다 |

### 헤더 이름을 `client.address` 로 하지 않은 이유

둘 다 OTel 규약의 Stable 속성이고 지금은 **같은 값**이 들어간다. 다른 것은 이름이 약속하는 뜻이다.

| 이름 | 규약이 말하는 것 | 프록시가 생기면 |
|---|---|---|
| `client.address` | "서버 쪽에서 볼 때, 중간 경유가 있으면 **그 뒤에 숨은 원래 클라이언트**를 가리켜야 한다" | 헤더를 파싱해 복원해야 그 약속을 지킨다. 우리는 안 한다 |
| **`network.peer.address`** | "네트워크 연결의 **상대 주소**" (소켓 수준) | 직전 홉을 담는다. 우리가 하는 일과 정의가 같다 |

소켓에서 직접 읽으면서 `client.address` 라고 적으면 **지키지 못할 약속**이 되고, 로드밸런서가 생기는 날 조용히 거짓이 된다. `source.address` 는 안정성이 Development 라 뺐다.

## 결정

ADR `#63` 에 4요소로 있다. 바꾼 것은 **수집 파트 두 모듈뿐**이다.

| 어디 | 무엇 |
|---|---|
| `collector` | gRPC 가로채기 신설(서버에 한 번 건다 → 세 신호 전부) · 주소 글자 다듬기 · 못 읽은 횟수 눈금 · 발행 때 헤더 붙이기 |
| `ingester` | 헤더에서 주소 꺼내기 · 목격 기록에 칸 추가 · `INSERT` 에 `CAST(:ip AS inet)` · **`UPDATE` 신설** · 캐시를 "이름표 → 마지막으로 본 주소" 짝으로 · 표 대조 클래스에 칸 |
| `common` | 헤더 이름 약속 한 줄 (붙이는 쪽과 꺼내는 쪽이 다른 모듈이라 글자가 어긋나면 조용히 빈칸이 된다) |
| PG · 조회 API · 화면 | **안 바꿨다.** 칸이 이미 있고, 이미 읽고 그린다 |

### 이 작업의 근거는 "주소가 꼭 필요해서" 가 아니다

조사 중에 "그럼 칸을 없애면 되는 거 아니냐" 는 질문을 받았다. 세어 보니 **치우는 쪽이 더 비쌌다.**

| | 채우기 | 지우기 |
|---|---|---|
| 움직이는 파트 | **수집 하나** | **넷** : 수집(마이그레이션) · 조회(응답) · 화면(표시 · 타입 · 가짜 데이터 · 계약 시험) · 노션 정본 두 페이지 + 팀 합의 |

`#126`(전역 설정 표)에서 **"만들면 네 파트가 움직인다"** 를 사유로 **안 만들기**를 택했는데, 이번은 방향이 뒤집혀 만드는 쪽이 한 파트다. 같은 기준을 쓰면 만드는 쪽이다. ADR 채택 사유에 그대로 적었다.

주소의 쓸모는 좁다. 셋뿐이다 : 바깥 네트워크 기록(AWS 흐름 기록 · 로드밸런서 기록은 주소로만 적힌다)과 맞춰 보기 · 죽은 파드가 그때 어디 있었나 되짚기 · 가짜 신호 출처 좁히기(보낸 쪽이 마음대로 적는 이름표와 달리 **주소만 우리가 연결에서 직접 읽으므로 속일 수 없다**). 파드 식별 · 스레드 덤프 · 경보 · 차트는 이 칸을 안 쓴다.

## 장애가 나면

| 무슨 일 | 어떻게 되나 |
|---|---|
| 주소를 못 읽는다 (전송 수단이 바뀜 · 실험 API 가 값을 안 줌) | 메모를 안 붙이고 눈금만 오른다. **신호는 그대로 받는다.** 화면 칸 하나 때문에 데이터를 버리지 않는다 |
| 메모가 없는 메시지가 섞인다 (옛 수집기 · 점검 스크립트 telemetrygen) | 적재와 등록은 그대로 돌고 주소 칸만 빈다. 이미 채워진 칸을 **비우지는 않는다** |
| PG 가 죽는다 | 등록 · 갱신이 실패로 세어지고(`outcome=failed`) ClickHouse 적재는 그대로 간다. 다음 메시지에서 다시 시도된다 |
| 주소가 자꾸 바뀐다 | `outcome=ip_updated` 가 계속 오른다. 파드가 쉴 새 없이 교체되고 있다는 신호다 (ADR `#63` 되돌림 ④) |
| 메시지가 `raw.dlq` 로 간다 | 주소 메모가 그대로 따라간다. 재처리 잡(범위 밖)이 주소를 잃지 않는다 |
| 바깥 로드밸런서가 생긴다 | 그때부터 **로드밸런서 주소**가 적힌다. 지금 그런 경로가 없어 막지 않았고 되돌림 조건으로 남겼다 |

## 어떻게 확인했나

### 관통 (로컬 compose, 2026-10-12)

쇼핑몰 네 서비스를 띄우고 주문을 흘렸다. `#148` 뒤라 포트 우회 없이 그냥 떴다.

```
명부에 적힌 주소                      docker inspect 실제 주소
shop-gateway-local-1    172.19.0.14   172.19.0.14
shop-order-local-1      172.19.0.13   172.19.0.13
shop-payment-local-1    172.19.0.11   172.19.0.11
shop-inventory-local-1  172.19.0.12   172.19.0.12
```

- 네 줄이 정확히 일치. PG `family(ip)` 가 **전부 4(IPv4)** 다 : `::ffff:` 를 안 뗐으면 6 이 된다
- 수집기 눈금 `peer_address.unknown` = **0**
- 첫 실행에서 `registered` 0 · `ip_updated` 4 였다. 네 줄이 이미 있고 주소만 `NULL` 이었기 때문이다. **`=` 대신 `IS DISTINCT FROM` 을 쓴 이유가 여기서 드러났다** : `NULL <> '172.19.0.11'` 은 참이 아니라 `NULL` 이라 `=` 꼴로 썼으면 옛 줄은 영원히 비어 있었다
- `shop-inventory` 를 지우고 빈 주소를 다른 컨테이너가 먼저 잡게 한 뒤 다시 만들었다 : `172.19.0.12` → `172.19.0.15`, **줄 수 4 그대로**, 그 줄만 `updated_at` 이 움직이고 `ip_updated` 가 하나 올랐다
- 적재 처리기를 재시작해 캐시를 비우고 주문 12건을 흘렸다 : `updated_at` 네 줄 전부 그대로(diff 차이 없음) · `ip_updated` 0 · `failed` 0. **실제 쓰기가 0** 이다
- `check-pipeline.sh`(telemetrygen) · `check-wiring.sh` 통과

자세한 숫자는 [`research.md`](research.md) 9절에 있다.

### 시험

| 무엇 | 어디 |
|---|---|
| 주소 글자 다듬기 (IPv4 · `::ffff:` 꼴 · 영역 꼬리 · 좁히기 실패 · 값 없음) | `collector` `PeerAddressTest` |
| 가로채기가 Context 에 담는다 · 못 읽으면 null 이고 눈금만 오른다 | `collector` `PeerAddressInterceptorTest` |
| gRPC 로 보내면 Kafka 메시지에 메모가 붙고 **값 바이트는 그대로** | `collector` `OtlpGrpcReceiverTest` (세 신호 전부) |
| 메모 읽기 (있음 · 없음 · 빈 값 · 같은 이름 둘) | `ingester` `RawPeerAddressHeaderTest` |
| 처음 등록에 주소 들어감 · 다른 주소면 고쳐짐 · 같은 주소면 쓰기 0줄 · 메모 없으면 칸 유지 · 모르는 서비스는 주소가 있어도 등록 안 됨 | `ingester` `PostgresAgentRegistryTest` |
| 적재와 함께 주소가 명부에 들어간다 (Kafka → PG 관통) | `ingester` `RawConsumerTest` |
| `raw.dlq` 로 갈 때 주소 메모가 따라간다 | `ingester` `RawErrorHandlerTest` |

시험 수 : 수집기 **110건** · 적재 처리기 **148건** · 공통 1건, 실패 0 (2026-10-12).

DLQ 건은 **조사가 틀렸던 것을 바로잡은 자리**다. 처음에 "실패분 재처리 코드가 키와 값만 옮긴다" 고 적어 A안의 단점으로 올렸는데, 코드를 읽어 보니 스프링이 만든 부품(`DeadLetterPublishingRecoverer`)을 쓰고 그 부품이 원본 헤더를 복사한다고 문서화돼 있었다. "고쳐야 한다" 가 아니라 **"우리가 확인한 적이 없다"** 였고, 그래서 시험으로 고정했다.

### 조사가 바로잡힌 것 셋 (지우지 않는다)

1. **"에이전트 쪽으로는 길이 없다" 는 반만 맞았다.** 자동으로는 없고 기동 설정으로는 있다. 이 구분을 못 했으면 선택지 둘을 아예 올리지도 못했다
2. **A안의 단점 하나를 과장했다.** 위의 DLQ 건
3. **"주소 모양이 틀리면 넣기가 실패한다" 가 틀렸다.** PG `inet` 은 `'not-an-ip'` 는 거절하지만 `'::ffff:172.19.0.11'` 은 **조용히 받아** 주소 종류를 IPv6 로 기록한다(실측). 실패하면 바로 알아채는데 조용히 들어가는 쪽이 더 나쁘다. 군더더기를 떼는 이유가 "저장 실패 방지" 에서 "화면에 괴상한 값과 틀린 주소 종류가 남는 것 방지" 로 바뀌었다
