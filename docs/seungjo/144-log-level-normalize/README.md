# `#144` 로그 등급을 숫자 기준 여섯 이름으로 고정한다 : 자유 문자열을 믿고 있었다

> **이 작업의 기술 설계 문서 한 장.** 문제 → 선택지 → 결정 → 장애가 나면 순서로 읽으면 끝난다.
> 결정 정본은 [`../../design/01-decisions.md`](../../design/01-decisions.md) 의 ADR `#59` 이고, 여기는 그 한 건을 한 장으로 펼친 것이다.
> **라이트로 간 건**이다. 조사 9단계를 안 돌렸다 : 고칠 자리가 함수 하나이고 결정도 "정본을 무엇으로 두나" 하나였다.

- 2026-10-11 / 승조(`@SeungJo-02`) / 결정 ADR `#59` / 이슈 [`#144`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/144)
- 유저 플로우에서 어디: 쇼핑몰 앱 → 에이전트 → 수집기 → Kafka → **적재 처리기가 등급을 정하는 자리** → ClickHouse `logs.level` → (아직 없는) 로그 검색 화면. 코드 한 함수만 바뀐다

## 문제

적재 처리기가 로그 등급을 **앱이 보낸 글자를 대문자로만 바꿔** 그대로 넣고 있었다.

```kotlin
// 전
if (record.severityText.isNotBlank()) return record.severityText.trim().uppercase()
return when (record.severityNumberValue) { in 13..16 -> "WARN" ... }   // 글자가 있으면 여기 안 온다
```

**OTel 규약이 그 두 값을 다르게 정의한다.**

| 값 | 규약이 정한 성격 |
|---|---|
| `severity_text` | **"출처가 부르는 이름 그대로"** 인 자유 문자열 |
| `severity_number` | 1~24 를 여섯 구간으로 나눈 **비교 가능한 정규화 값** |

우리는 정본을 버리고 자유 문자열을 썼다. 로깅 도구마다 이름이 다르다.

| 도구 | 경고 | 오류 |
|---|---|---|
| Logback · Log4j2 · SLF4J | `WARN` | `ERROR` |
| java.util.logging | **`WARNING`** | **`SEVERE`** |
| Python | **`WARNING`** | `ERROR` · **`CRITICAL`** |

**자기 약속도 깨고 있었다** : `LogRow.level` 주석이 이미 여섯 이름으로 적혀 있고, ClickHouse `logs.level` 은 값의 종류가 적다는 전제로 고른 `LowCardinality(String)` 이다.

### 지금 영향은 0 이다. 다만 처음에 쓴 근거는 틀렸다 (실측 2026-10-11)

처음에는 **"표에 표준 아닌 등급이 0건이다"** 를 근거로 삼았다. 리뷰가 그 줄들의 출처를 물어 다시 재니 **번역기를 지나온 줄이 아니었다.**

| 52,264줄을 가르면 | 값 | 어떻게 가렸나 |
|---|---|---|
| **가짜 데이터**(`scripts/seed/`)가 넣은 줄 | **52,255** | 꼬리표가 `http.route` 하나뿐인 모양. SQL 이 `'INFO'` · `'WARN'` · `'ERROR'` 글자를 직접 넣는다 |
| telemetrygen 이 넣은 줄 | 9 | 가짜 데이터가 쓰지 않는 `service_name` 으로 가렸다. 전부 `INFO` |
| **Logback 앱이 넣은 줄** | **0** | 꼬리표에 `thread.name` 이 있는 줄이 0. 그 꼬리표를 붙이는 것은 번역기가 아니라 **OTel Java 에이전트의 Logback 붙임쇠**다 (번역기는 온 것을 옮기기만 한다) |

**그래서 "표준 아닌 등급 0건" 은 SQL 글자 상수를 센 동어반복이었다.** 번역기의 동작을 전혀 재지 않았고, "쇼핑몰이 전부 Logback 이라 늘 `WARN` 이 온다" 도 이 표로는 잴 수 없다. 쇼핑몰은 지금 떠 있지도 않다.

**다시 세운 근거는 둘이다.**

| 잰 것 | 값 |
|---|---|
| `level` 을 읽거나 거르는 코드 | **0줄** (api-server · detector 전체. 유일한 소비처는 아직 구현 전인 문 35) |
| 표에서 번역기를 지나온 줄 | **9줄**. 백필할 것이 사실상 없다 (가짜 데이터는 다시 넣으면 된다) |

## 선택지

| 묶음 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 무엇을 정본으로 | **숫자(`severity_number`)** | **글자를 정본으로 두고 별칭 표만 붙이기** = 표가 영원히 안 끝난다. 모르는 이름이 오면 그대로 통과해 값 범위가 다시 열린다. 숫자는 규약이 1~24 로 닫아 둬서 빠짐이 없다 |
| 모르는 글자 | **빈 글자로 둔다** | **그대로 넣기** = 거르는 칸의 값 범위가 열려 조회 쪽이 고를 목록을 만들 수 없다. 본문은 그대로 남으므로 내용이 사라지지는 않는다 |
| 원래 글자 보존 | **안 한다** | **`attributes` 에 넣기** = 그 칸의 뜻이 "앱이 붙인 꼬리표" 다. 우리 키를 끼우면 조회 응답에 섞여 나가고 앱 것과 구분이 안 된다. 보존 요구가 생기면 컬럼을 따로 만든다 |
| 몇 개로 접나 | **여섯** | **네 단 그대로 남기기**(`WARN2` 등) = 거르는 칸이라 여섯으로 충분하고 화면 필터 목록이 24개가 된다 |
| 언제 | **지금** | **조회 파트가 문 35 만들 때 같이** = 그 사이 쌓인 줄을 고치는 일이 생기고, 문 35 를 만드는 사람이 값 범위를 모르는 채로 필터를 짜게 된다 |

## 결정

- **고른 것**: 숫자가 1~24 면 그 구간의 여섯 이름 중 하나. 숫자가 없으면(0 이거나 규약 밖) 글자를 **별칭 표로 여섯에 맞춘다**. 표에 없으면 빈 글자. **글자와 숫자가 어긋나면 숫자가 이긴다**
- **별칭 표에 넣은 것**: **규약 부록 B(출처별 예시 매핑)의 일곱 열에 실제로 있는 이름만** 넣었다. 표준 여섯 + java.util.logging(`FINEST` · `FINER` · `FINE` · `CONFIG` · `WARNING` · `SEVERE`) + syslog(`EMERGENCY` · `EMERG` · `ALERT` · `ERR` · `NOTICE`) + Windows 이벤트 로그 · ETW · .NET(`VERBOSE` · `INFORMATION` · `INFORMATIONAL`) + zap(`PANIC` · `DPANIC`) + `CRITICAL`. **완전한 목록이 아니라고 주석에 적었다**
- **되돌리는 조건**: 원래 글자를 봐야 하는 요구가 생기면 컬럼을 하나 더한다 · 네 단 구분이 필요해지면 숫자를 그대로 저장하는 컬럼을 더한다 · 표에 없는 글자가 실제로 들어오는 것이 관측되면 그 이름을 표에 더한다 (빈 글자로 들어간 줄은 `message` 가 남아 사후 확인이 된다)

## 어떻게 확인했나

- `LogTranslatorTest` **21건 통과** (전 7건 + 이번 14건)
    - 같은 뜻 다른 글자(`WARN` · `WARNING`)가 **같은 값**이 되는 것
    - 글자와 숫자가 어긋날 때 **숫자가 이기는 것** (글자 `WARN` · 숫자 17 → `ERROR`)
    - 별칭 표, 특히 **이름만 보고 짐작하면 틀리는 다섯 자리** : `FINER` → `DEBUG` · `ALERT` → `ERROR` · `VERBOSE` → `DEBUG` · `PANIC` → `ERROR` · `CRITICAL` → `FATAL`
    - 대소문자와 앞뒤 공백 무시
    - 여섯 구간 **경계값 12개** (1 · 4 · 5 · 8 · 9 · 12 · 13 · 16 · 17 · 20 · 21 · 24)
    - 숫자 0 과 규약 밖(99)에 모르는 글자면 **빈 글자**
    - **숫자를 못 알아볼 때 글자 쪽으로 넘어가는 것** (숫자 99 에 글자 `WARNING` → `WARN`, 숫자 0 에 `SEVERE` → `ERROR`). 리뷰가 "숫자만 두고 빈 글자를 기대하는 시험은 글자 쪽 길이 지워져도 통과한다" 를 잡아 줘서 더했다
    - 변별력 확인 : 번역 함수의 글자 쪽을 일부러 지우면 **21건 중 9건이 깨진다**
- 전체 `./gradlew test --rerun-tasks` **576건 실패 0**

## 안 한 것

- **과거 줄 백필.** 표에서 번역기를 지나온 줄이 9줄뿐이고 나머지는 다시 넣으면 되는 가짜 데이터라 할 것이 없다
- **문 35 구현.** 조회 파트 몫이다. `level` 필터 목록이 여섯 + 빈 글자라고 전달했다
- **원래 글자 보존.** 요구가 생기면 컬럼을 따로 만든다
- **로그 하한**(`MIN_LOG_LEVEL`)은 `#126` 에서 보류로 확정됐다 (ADR `#55`). 이 건과 무관하다

## 리뷰가 잡은 것

**별칭 표의 다섯 개가 틀렸다.** 처음 쓴 표에서 **이름의 뜻으로 구간을 짐작한 것**이 전부 틀렸고, 규약 부록 B 를 직접 떠서 대조하니 갈렸다.

| 내가 쓴 것 | 실제 | 왜 |
|---|---|---|
| `FINER` → `TRACE` | **`DEBUG`** | java.util.logging 에서 `TRACE` 구간은 `FINEST` 하나뿐이다. `FINER` · `FINE` · `CONFIG` 는 셋 다 `DEBUG` 구간(5 · 6 · 7) |
| `ALERT` → `FATAL` | **`ERROR`** | syslog 는 숫자가 작을수록 심각하다. `Emergency`(0)만 `FATAL`(21) 이고 `Alert`(1) · `Critical`(2) · `Error`(3)는 셋 다 `ERROR` 구간(19 · 18 · 17) |
| `CRIT` → `FATAL` | 같은 이유로 틀림 | 짧은 표기는 부록에 없어 **표에서 뺐다** |
| `VERBOSE` → `TRACE` | **`DEBUG`** | Windows 이벤트 로그 · ETW 둘 다 5 다 |
| `PANIC` → `FATAL` | **`ERROR`** | Go 의 zap 에서 `Panic` 은 19, `Dpanic` 은 18. `FATAL` 은 `Fatal` 하나뿐 |

그리고 `WARNINGS` 처럼 **출처 없이 지어낸 항목 하나**도 처음 표에 있었다.

**교훈** : 별칭 표는 이름의 뜻으로 짐작하면 안 되고 **출처가 배정받은 숫자**를 봐야 한다.

### 같이 밝혀진 것 둘

- **규약이 "숫자가 이긴다" 를 정해 두지는 않았다.** 둘이 어긋날 때 소비자가 무엇을 할지 지시하는 문장이 없고, 가장 가까운 것은 "크기를 비교하는 자리에서는 숫자를 쓰라" 한 줄이다. **그 문장을 근거로 우리가 고른 것**이고 규약의 명령이 아니다. 부록 B 자신도 제목이 "example mappings" 로 규범이 아니다
- **글자를 버리는 선택에는 반대 선례가 있다.** OTel Collector 의 파일 로그 수신기는 매핑에 걸리지 않으면 **숫자를 0 으로 남기고 글자는 원문 그대로 둔다.** 우리가 다른 이유는 칸이 하나라서다 : OTLP 는 두 필드를 다 들고 가지만 우리는 `level` 한 칸으로 접었다. 보존 요구가 생기면 컬럼을 더한다

## 내가 틀렸던 것

지우지 않고 남긴다. **이 건에서 내가 한 실수가 두 겹이다.**

**① 남이 쟀다는 숫자를 다시 재지 않고 받아썼다** (`#119` 에 이어 두 번째)

- `AGENTS.md` §6 과 `#126` 기록이 "`WARN` 578건 · `WARNING` 7건으로 갈려 있다" 로 적고 있었다
- 그걸 그대로 옮겨 **"등급으로 세는 순간 숫자가 틀린다" 를 지금 일어나는 일처럼** 승조에게 말했다

**② 다시 쟀을 때 무엇을 재고 있는지 확인하지 않았다** (이게 더 나쁘다)

- `WARNING` 이 0건인 것을 보고 **"그 7건이 어떻게 생겼는지 확인할 수 없어 근거로 쓰지 않는다"** 로 적었다
- 그리고 이 작업의 사유를 "지금 틀리고 있다" 에서 "영향이 0 이라 싸다" 로 내렸다
- **리뷰가 그 판단을 뒤집었다.** 가짜 데이터는 `'INFO'` · `'WARN'` · `'ERROR'` 세 글자만 넣으므로 **`WARNING` 7줄은 가짜 데이터에서 나올 수 없다**
- 그 줄들은 **번역기를 지나온 진짜 생산자**의 것이다. `WARNING` 은 `java.util.logging` · Python · `.NET` · syslog 가 다 쓰는 글자인데, **Spring Boot 앱 안에서 그 글자가 나올 경로는 `java.util.logging`** 이다(Logback 은 `WARN` 을 보낸다). **이번 별칭 표가 그걸 받는다**
- 사라진 이유도 장부로 날짜가 잡힌다 : 스키마 생성 행이 `2026-10-09 13:16:46` 이라 그 전의 모든 줄이 함께 지워졌다. 보관 기간 97일은 애초에 관계가 없었다(가장 오래된 줄이 `2026-10-09` 다)
- **즉 이 결함은 실제로 한 번 관측됐다.** 지금 안 보이는 것은 볼륨을 새로 만든 뒤 쇼핑몰이 돌지 않았기 때문이다
- 재측정이 오히려 **틀린 결론을 뒷받침하는 데** 쓰였다. 숫자를 다시 재는 것만으로는 부족하고 **그 숫자가 무엇을 재고 있는지**를 봐야 한다

## 장애가 나면

| 보이는 것 | 원인 | 보는 곳 |
|---|---|---|
| 로그 등급이 빈 글자로 들어온다 | 보낸 쪽이 숫자를 안 채웠고 글자도 별칭 표에 없다 | 같은 줄의 `message` 와 `logger`. 이름을 확인해 표에 더한다 |
| 앱은 `WARNING` 이라고 찍었는데 표에는 `WARN` 이다 | **의도한 동작이다.** 여섯으로 모은다 | ADR `#59` 채택 ① |
| 앱 로그와 등급이 다르다 | 글자와 숫자가 어긋났고 숫자가 이겼다 | 보낸 쪽 설정. **우리가 숫자를 정본으로 고른 것**이라(규약이 명령한 것은 아니다) 우리 쪽은 안 고친다 |
| 로그 검색 필터에 없는 등급이 보인다 | `#144` 이전에 적재된 줄이다. 그 줄들은 안 고쳤다 | 적재 시각으로 가른다. 지금 표에서 번역기를 지나온 줄은 9줄(telemetrygen, 전부 `INFO`)뿐이다 |
