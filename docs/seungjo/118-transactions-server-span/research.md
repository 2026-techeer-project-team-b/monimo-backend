# 리서치 : `transactions` 를 서비스가 받은 요청 기준으로

- 2026-10-07 시작 / 관련 이슈 [`#118`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/118)
- 쓴 도구: 로컬 compose 실데이터 측정 · 레포 DDL · 조회 코드 직접 확인 · 조회 파트 이슈 글

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

> 이 이슈는 **다른 파트가 발견해서 넘어온 첫 건**이다. 조회 파트(현영)가 스캐터를 만들다 찾아 개인 스크럼에 적었고, `db/clickhouse/` 가 파트를 넘는 공용 영역이라 수집 쪽이 가져왔다.

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 스캐터 차트가 **맨 앞 서비스에서만** 점을 보여준다. 주문 · 결제 · 재고를 고르면 비어 있다
- **그래서 무엇을 만드나** : 그 차트가 읽는 표를 **"각 서비스가 받은 요청" 기준으로** 채우게 바꾼다
- **안 하면 어떻게 되나** : "어느 서비스가 느린가" 를 보려고 만든 화면인데 **느린 서비스를 고를 수가 없다.** 결제가 느려도 결제 화면은 비어 있고, 맨 앞 서비스의 느린 점을 하나씩 눌러 안을 들여다봐야 한다

| | |
|---|---|
| 건드리는 모듈 · 파일 | `db/clickhouse/004_create_materialized_views.sql`(MV 조건) · 필요하면 `003_create_rollup_tables.sql`(컬럼) · `docs/design/web-v2/erd.md` · 노션 「ERD」 · `docs/design/01-decisions.md`(ADR 신설) · `AGENTS.md` §5 · §6 |
| 건드리지 않는 것 | **수집기 · 적재 처리기 코드 0줄.** 이 표를 읽지도 쓰지도 않는다. **조회 코드도 0줄** : `ScatterRepository` 가 `service_name` 과 시간 범위로만 읽어서 줄이 들어오면 그대로 동작한다. `scripts/seed-clickhouse.sh` 도 표 이름만 쓰므로 그대로다 |
| 이 이슈 범위 밖 (후속) | `GET /traces/transactions`(요청 목록)과 `GET /traces/heatmap` 구현은 조회 파트 몫이다. S3 cold 계층(ADR `#34`)도 배포 단계 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- `transactions` 는 ClickHouse 표이고, `spans` 에 줄이 들어오는 순간 MV 가 자동으로 채운다. 내가 `#10` 에서 만들었다
- MV 조건이 `parent_span_id = ''` 인 것은 ERD 에 "트랜잭션(루트 스팬)" 으로 적혀 있어서 그대로 옮긴 것이다. **그 기준이 화면과 맞는지는 확인하지 않았다**
- `#92` 를 하면서 "자식 없는 헬스체크 SERVER 스팬이 루트로 분류돼 히트맵에 쌓인다" 는 것을 봤다. 그때는 헬스체크만 문제로 봤고 **기준 자체를 의심하지 않았다**

**알고 싶었던 것**

① 다른 APM 은 「트랜잭션」을 무엇으로 세나. 루트 기준인가 서비스 기준인가, 둘을 다 쓰는 곳이 있나
② 한 표로 두 기준(서비스별 · 고객 요청별)을 담는 방법이 `is_root` 컬럼 말고 또 있나
③ 줄이 3.4배로 늘면 조회 속도와 저장 크기에 실제로 어떤 영향인가. 지금 `ORDER BY` 로 괜찮은가
④ 운영에서 MV 조건을 바꾸는 안전한 절차는 무엇인가. `down -v` 가 없는 환경에서 집계가 비는 구간을 줄일 수 있나
⑤ `span_id` 를 넣으면 스캐터 · 요청 목록 화면이 실제로 무엇을 더 할 수 있나

## 2. 작업하기 전에 알아야 하는 것

### 2.1 스캐터 차트가 무엇인가

**요청 하나를 점 하나로 찍은 그림**이다. 가로축이 시각, 세로축이 걸린 시간이다.

```
걸린 시간
  ↑
3s│              ·        ← 느린 요청 하나
  │        ·
1s│   ·  ·     ·    ·
  │ ······················  ← 대부분은 빠르다
  └────────────────────▶ 시각
```

쓰는 법은 **느린 점을 드래그로 긁어서 그 요청 목록을 보는 것**이다. 핵심 기능 4번(히트맵 · 스캐터)이 그것이고, 점을 누르면 트레이스 상세로 간다. 그래서 점 하나가 **실제 요청 하나**여야 한다.

**히트맵은 같은 데이터를 칸으로 센 것**이다. 1분 × 50ms 칸마다 건수를 세어 색으로 보여준다. 점이 너무 많을 때 전체 모양을 보는 용도다.

| | 스캐터 | 히트맵 |
|---|---|---|
| 점 하나 | 요청 하나 | 칸 하나의 **건수** |
| 읽는 표 | `transactions` | `heatmap_1m` |
| 눌러서 | 트레이스 상세로 간다 | 건수만 안다 |

둘이 같은 뿌리에서 나오므로 뿌리를 바꾸면 **같이 바뀐다.**

### 2.2 `transactions` 표는 무엇을 담나

ClickHouse 표다. PG 가 아니다. `db/clickhouse/003_create_rollup_tables.sql` 에 있다.

| 컬럼 | 형 | 무엇 |
|---|---|---|
| `trace_id` | String | 점을 눌러 트레이스 상세로 갈 때 쓰는 열쇠 |
| `start_time` | DateTime64(3) | 스캐터 가로축 |
| `duration_ms` | UInt32 | 스캐터 세로축 |
| `service_name` | LowCardinality | 화면에서 고르는 기준 |
| `agent_id` | LowCardinality | 어느 파드 |
| `span_name` | LowCardinality | 요청 이름 |
| `is_error` | UInt8 | 점 색 |
| `http_status` | UInt16 | 상태 코드 |

`span_id` 가 **없다.** 지금은 트레이스 하나에 줄 하나라 필요가 없었다.

| 항목 | 값 |
|---|---|
| 엔진 | `MergeTree` |
| `ORDER BY` | `(service_name, start_time)` |
| `PARTITION BY` | `toDate(start_time)` |
| TTL | 93일 뒤 삭제 |
| 채우는 것 | `mv_transactions`(MV). 사람도 코드도 직접 넣지 않는다 |
| 읽는 것 | 조회 API 뿐. 수집기 · 적재 처리기는 안 본다 |

### 2.3 MV 가 무엇이고 언제 도나

**MV**(Materialized View)는 **원본 표에 INSERT 가 들어오는 순간 조건을 통과한 줄만 다른 표에 넣어 주는 문**이다. 우리가 `#10` 에서 7개를 만들었다.

중요한 성질이 둘이다.

- **들어올 때 한 번만 본다.** 조건을 바꾸면 **그 뒤에 들어오는 줄부터** 새 규칙이 적용된다. 이미 들어간 줄은 다시 계산하지 않는다
- **조회가 나중에 못 고친다.** 틀린 값이 들어가면 그 분(minute)은 영원히 틀린 채 남는다. `#83`(`peer_service`)과 `#92`(헬스체크)가 같은 이유로 **적재 전**에 처리해야 했다

MV 는 정의 자체를 바꿀 때도 걸림돌이 있다. `db/clickhouse/*.sql` 은 **데이터가 비어 있을 때만** 실행된다(`compose.yaml:90`). 그래서 로컬은 `docker compose down -v` 로 볼륨을 지우고 다시 켜야 새 MV 가 생긴다. 운영에는 그 수단이 없다.

### 2.4 루트 스팬과 SERVER 스팬은 어떻게 다른가

둘 다 "요청을 받은 기록" 인데 **범위가 다르다.**

```
SERVER  gateway   POST /api/orders     parent 없음  ← 루트이면서 SERVER
└─ CLIENT   gateway   → order
   └─ SERVER   order    POST /orders    parent 있음  ← SERVER 이지만 루트 아님
      └─ CLIENT   order    → payment
         └─ SERVER   payment  POST /pay  parent 있음  ← SERVER 이지만 루트 아님
```

- **루트 스팬** : 그 요청의 **맨 처음** 구간. 트레이스마다 하나다. 조건은 `parent_span_id = ''`
- **SERVER 스팬** : 어느 서비스든 **요청을 받았다**는 기록. 서비스를 지날 때마다 하나씩 생긴다. 조건은 `span_kind = 'SERVER'`

**루트는 SERVER 의 부분집합이다.** 그래서 조건을 SERVER 로 넓히면 루트도 그대로 들어온다. 잃는 것이 없다.

다른 집계표는 이미 SERVER 기준이다. **`transactions` 만 기준이 달랐다.**

| 표 | 조건 |
|---|---|
| `service_health_1m` | `span_kind = 'SERVER'` |
| `url_stats_1m` | `span_kind = 'SERVER'` |
| `server_map_1m` | `span_kind = 'CLIENT'` |
| **`transactions`** | **`parent_span_id = ''`** |

### 2.5 데이터는 어디로 흐르나

```
쇼핑몰 ─OTLP─▶ 수집기 ─▶ Kafka raw ─▶ 적재 처리기 ─▶ ClickHouse spans
                                                            │
                                      mv_transactions       │  (조건 : 지금은 루트만)
                                                            ▼
                                                      transactions
                                                      │         │
                                       mv_heatmap_1m  │         │  스캐터 · 요청 목록이 읽는다
                                                      ▼         ▼
                                                  heatmap_1m   조회 API
                                                      │
                                                   히트맵이 읽는다
```

| 질문 | 답 |
|---|---|
| 누가 채우나 | ClickHouse 안의 MV. 코드가 넣지 않는다 |
| 누가 읽나 | 조회 API 세 개. 수집 쪽은 읽지도 쓰지도 않는다 |
| 얼마나 보관하나 | `transactions` 93일 · `heatmap_1m` 120일 |
| 가짜 데이터는 어디로 들어가나 | `spans` 에만 넣는다(`db/clickhouse/seed/001_fake_signals.sql`). `transactions` 는 MV 가 채운다 |

`spans` 에는 네 서비스 스팬이 **전부 있다.** 문이 좁은 것이다.

| 서비스 | SERVER 스팬 | 그중 루트 | `transactions` 줄 | 스캐터 |
|---|---|---|---|---|
| `shop-gateway` | 30,148 | 30,148 | 30,148 | 보인다 |
| `shop-order` | 30,144 | **23** | 23 | 거의 빈다 |
| `shop-payment` | 21,228 | **21** | 21 | 거의 빈다 |
| `shop-inventory` | 21,083 | **0** | 0 | 빈다 |

**조회 파트는 order 를 0건으로 봤는데 내 로컬에는 23줄이 있었다. 그 23줄의 정체가 중요하다.**

| 서비스 | 요청 이름 | 줄 |

`#92` 기록에 "자식 없는 헬스체크 SERVER 스팬이 루트로 분류돼 히트맵에 쌓였다" 고 적어 뒀는데, **그 문장이 이 이슈의 증거가 됐다.**

줄 수는 이렇게 변한다.

| | 지금 (루트만) | 바꾼 뒤 (SERVER) | 배수 |
|---|---|---|---|
| 합계 | 30,214 | **102,625** | **약 3.4배** |

`heatmap_1m` 도 같은 비율로 늘고, 지금 `transactions` 와 똑같은 서비스 분포를 보인다(측정 확인).

### 2.7 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| MV 설정이 안 돼 있어서 비는 것이다 | **아니다.** MV 는 잘 설정돼 있고 **설계대로 동작했다.** ERD 에도 "트랜잭션(루트 스팬)" 으로 적혀 있다. 표의 기준과 화면의 기준이 어긋난 것이다 |
| 데이터가 없어서 안 나온다 | **원인과 결과가 뒤집혔다.** 조건이 안 통과시켜서 데이터가 없는 것이다. `spans` 에는 네 서비스가 다 있다 |
| 스팬이 "도착지 · 목적지 아이디" 를 들고 있다 | 들고 있는 것은 **자기 번호(`span_id`)와 부모 번호(`parent_span_id`)** 다. 방향은 번호가 아니라 `span_kind` 가 말한다 |
| 번호를 `span_kind` 에서 가져온다 | **서로 무관한 별개 칸**이다. 모든 스팬이 자기 `span_id` 를 갖고, `parent_span_id` 는 나를 부른 스팬의 번호다 |
| 바꾸면 CLIENT 스팬도 들어온다 | **안 들어온다.** 조건이 `span_kind = 'SERVER'` 다 |
| 조회 코드를 고쳐야 한다 | **안 고친다.** `ScatterRepository` 가 `service_name` 과 시간 범위로만 읽는다 |
| 스캐터만 영향받는다 | **표 2개 · API 3개가 걸린다.** `heatmap_1m` 이 `transactions` 에서 파생된다 |
| 미리 표를 비우고 `down -v` 한다 | **미리 비울 필요가 없다.** `down -v` 가 볼륨을 지우니 그게 곧 비우기다. 순서는 파일 수정 → `down -v` → 켜기 → seed |
| `down -v` 가 필요한 이유는 옛 줄 때문이다 | **MV 정의 때문이다.** DDL 이 빈 DB 에서만 돌아서, 그냥 켜면 옛 조건의 MV 가 그대로 남는다 |
| ERD 의 TTL 설명대로 S3 로 간다 | ERD 는 "3일 디스크 → 90일 S3 → 93일 삭제" 라고 적지만 **로컬 DDL 은 93일 삭제 한 단**이다. S3 는 배포 단계(ADR `#34`)이고 `#96` 에서도 같은 차이를 확인했다 |

## 3. 1차 질문 (사람 차례)

> **이 이슈는 질문이 2절보다 먼저 왔다.** 조회 파트 글을 읽은 2026-10-06 에 열일곱 번을 주고받았고,
> 그 기록이 노션 「스캐터가 gateway 에서만 나오는 문제」 에 먼저 들어갔다.
> 2절은 그 대화에서 드러난 구멍을 메우려고 **뒤에** 쓴 것이다. 그래서 1차 질문이 2절을 읽고 나온 질문이 아니다.

### 첫 바퀴 : 표가 어디 있고 누가 건드리나

**Q1.** `transactions` 는 CH 인지 PG 인지 확인, 이 안에 컬럼이 어떤 것들이 있고 수집 쪽에서 수정이 필요한지

> **ClickHouse** 다. `db/clickhouse/003_create_rollup_tables.sql`. 컬럼 8개이고 `span_id` 는 없다(2.2 절 표).
> **수집 쪽 수정은 없다.** 수집기 · 적재 처리기는 이 표를 읽지도 쓰지도 않는다. 채우는 것은 DB 안의 MV, 읽는 것은 조회 API 뿐이다.
> 내 쪽에 걸리는 것은 둘이다 : `db/clickhouse/` 는 CODEOWNERS 기본 리뷰어가 수집이라 리뷰가 자동으로 온다. 그리고 `scripts/seed-clickhouse.sh` 가 이 표를 비우는 목록에 넣고 있지만 이름만 쓰므로 규칙이 바뀌어도 그대로 돈다.

**Q2.** 표를 채우는 규칙을 수정하면 스캐터가 비는 이슈가 해결된다는 부분이 이해가 안 된다

> **지금은 표에 줄이 아예 안 들어간다.** 조회 코드도 조립도 멀쩡하다.
> ```
> spans 에는 SERVER 스팬 4개가 다 있다
>   ① gateway    parent 없음   ← transactions 에 들어간다
>   ② order      parent = ①   ← 안 들어간다
>   ③ payment    parent = ②   ← 안 들어간다
>   ④ inventory  parent = ②   ← 안 들어간다
> ```
> MV 조건이 `WHERE parent_span_id = ''` 라서 ① 만 통과한다. order 를 고르면 **읽을 줄이 0개**다.

**Q3.** `transactions` 테이블을 한글로 바꾼다면

> 실제 표 이름은 영어로 둔다. ClickHouse 식별자이고 쿼리 · 코드 · ERD 가 전부 걸려 바꿀 이득이 없다.
> 문서에서 부르는 말만 바꾸면 되는데, **A 안이 통과하면 지금 이름이 뜻과 안 맞게 된다** : 지금은 「요청 첫 구간」, 바꾼 뒤는 「서비스별 받은 요청」 이다. ERD 의 "트랜잭션(루트 스팬)" 을 고쳐야 하는 이유가 그것이다.

**Q4.** seed 스크립트가 `transactions` 를 비우는 목록에 넣고 있는 것 설명

> 스크립트는 표 11개를 TRUNCATE 한 뒤 다시 채운다. 가짜 데이터는 **`spans` 에만** 넣고(`seed/001_fake_signals.sql`) `transactions` 는 MV 가 채운다.
> 그래서 MV 조건을 바꾸면 **다음 seed 실행부터** 새 규칙대로 채워지고 스크립트는 고칠 데가 없다. 단 이미 들어 있는 줄은 안 바뀐다.

### 둘째 바퀴 : 스팬의 번호와 kind

**Q5.** 지금 `transactions` 에 gateway 만 들어가고 나머지는 안 들어가는 상태이고, 이유는 표 안에 데이터가 없어서인가

> **원인과 결과가 뒤집혔다.** 데이터가 없어서 안 나오는 게 아니라 **조건이 안 통과시켜서 데이터가 없는 것**이다.
> ```
> MV 조건이 좁다              ← 원인
>       ▼
> transactions 에 gateway 만   ← 결과
>       ▼
> order 스캐터가 0건           ← 증상
> ```

**Q6.** 스팬은 자기 번호랑 부모 번호를 가지고 있는데 그게 각각 SERVER · CLIENT kind 에서 가져오는 건가

> **서로 무관한 별개 칸이다.** 번호를 kind 에서 가져오지 않는다. 스팬 하나가 네 가지를 따로 들고 있다 : `span_id`(내 번호) · `parent_span_id`(나를 부른 스팬의 번호) · `span_kind`(받았나 보냈나) · `trace_id`(호출 전체 번호).
> 번호는 **누가 누구 밑인가**를, kind 는 **받았나 보냈나**를 말한다. 다른 질문에 답한다.

**Q7.** 요청을 보내는 쪽 스팬이 부모 스팬이고 받는 스팬이 도착지 스팬인가

> "받는 쪽 = 도착지" 는 맞고 **"보내는 쪽 = 부모" 는 축이 다르다.** CLIENT 와 SERVER 는 한 쌍일 때 CLIENT 가 부모, SERVER 가 자식이다. 그런데 부모·자식은 kind 와 별개라 **SERVER 도 부모가 될 수 있다.** 그래서 SERVER 를 지우면 고아 스팬이 생긴다.

**Q8.** CLIENT 안에 여러 SERVER 가 생기나. 예시를 보면 SERVER 안에 CLIENT 가 많은데

> 번갈아 나온다. **CLIENT 밑에는 SERVER 가 하나**(한 번 보내면 받는 쪽도 하나), **SERVER 밑에는 CLIENT 가 여러 개**(받아서 일하면서 몇 번이든 부를 수 있다). SERVER 밑에 CLIENT 가 없을 수도 있다 : 헬스체크가 그렇다.

### 셋째 바퀴 : `span_id` 와 영향 범위

**Q9.** `transactions` 에 `span_id` 를 추가하는 건데 이 `span_id` 는 SERVER · CLIENT 에서 가져오는 자기 번호인가. 하나의 트레이스 ID 로 상세 조회 해야 하는 거 아닌가. 아니면 그냥 추가하면 더 좋은 건가

> 그 줄이 된 스팬 **자기 번호**다. 그리고 **A 로 가면 `transactions` 에 들어가는 것은 SERVER 스팬만**이다. CLIENT 는 안 들어간다. 조건이 `span_kind = 'SERVER'` 이니까.
> **상세 조회는 `trace_id` 로 맞다.** 그건 그대로다. `span_id` 가 필요한 상황은 더 좁다 : 같은 트레이스에서 같은 서비스가 두 번 호출되면 `trace_id` 와 `service_name` 이 같은 줄이 둘 생기고, 그때 "이 점이 둘 중 어느 구간인가" 를 집으려면 있어야 한다.

**Q10.** 즉 `span_id` 는 같은 트레이스에서 같은 서비스가 호출됐을 때 각각 어느 스팬에서 왔는지 확인하려고 붙이는 것이고, 굳이 넣을 필요는 없지만 `spans` 표에서 확인하면 되니까

> 맞다. 안 넣어도 `trace_id` 로 상세를 열면 `spans` 에서 전부 보인다. 다만 "상세를 열어 눈으로 찾는다" 와 "그 구간으로 바로 간다" 는 다르니, **요청 목록 화면을 어떻게 만들지에 달렸다.**

**Q11.** 히트맵도 같이 바뀐다는 것은 스캐터에 사용되는 테이블이 3개라는 말인가

> **표는 2개, 화면과 API 는 3개다.** 스캐터가 직접 읽는 표는 `transactions` 하나이고, `heatmap_1m` 이 거기서 파생된다.
> ```
> spans ──▶ transactions ──▶ heatmap_1m
>             │                  │
>      스캐터 · 요청 목록        히트맵
> ```

**Q12.** ERD 수정은 들어올 때 규칙이랑 컬럼 추가 때문인 것 같고

> 맞고 **셋이다.** MV 조건(사본 304줄) · 표 설명 "트랜잭션(루트 스팬)"(294줄) · `span_id` 를 넣기로 하면 컬럼.
> 하나 더 있다 : `spans.parent_span_id` 설명(194줄)이 "비어 있으면 루트라 `transactions` 가 이 조건으로 골라낸다" 고 적는데 그 조건이 사라진다.

**Q13.** 「뜻이 바뀐다」 의 해결법

> 셋이다. **문서로 못 박기**(비용 0, 막을 장치 없음) · **다른 데서 센다**(`spans` 직접 조회, 느리다) · **`is_root` 컬럼 하나 넣기**.
> 셋째를 제안한다. `toUInt8(parent_span_id = '') AS is_root` 한 줄이면 **한 표로 두 질문에 답한다** : 서비스별은 `service_name` 으로, 고객 요청 수는 `is_root = 1` 로. 지금 조건은 "루트였다" 는 정보를 통째로 버리는데 그걸 조건에서 컬럼으로 옮기는 셈이다.

### 넷째 바퀴 : MV 와 볼륨

**Q14.** 어떤 테이블에 MV 조건을 세우면 그 조건에 맞게 테이블이 채워지는 건가

> 맞다. 원본에 INSERT 가 들어오는 **그 순간** 조건을 통과한 줄만 목적지 표에 넣는다. 조건을 바꾸면 **그 뒤에 들어오는 줄부터** 적용된다.

**Q15.** 「이미 들어 있는 줄은 안 바뀐다, `down -v` 로 다시 만들어야 한다」 쉽게 설명

> **내 앞선 설명이 두 가지를 섞었다.** `down -v` 가 필요한 진짜 이유는 옛 줄이 아니라 **MV 정의**다. `db/clickhouse/*.sql` 은 데이터가 비어 있을 때만 실행되므로(`compose.yaml:90`) 그냥 켜면 옛 조건의 MV 가 남는다.
> 데이터를 다시 채우는 것은 seed 스크립트만으로 된다(TRUNCATE 하고 다시 넣는다).

**Q16.** 그럼 데이터 다 지우고 `down -v` 해서 스키마 수정하고 데이터를 다시 채운다?

> 순서가 하나 뒤집혔다. **미리 지울 필요가 없다** : `down -v` 가 볼륨을 삭제하니 그게 곧 지우기다.
> 그리고 "스키마 수정" 도 정확히는 아니다. 컬럼은 그대로이고(`span_id` 를 넣기로 하면 그때는 바뀐다) 바뀌는 것은 **채우는 규칙** 한 줄이다.
> ```
> 1. 004_create_materialized_views.sql 의 조건을 고친다
> 2. docker compose down -v
> 3. docker compose up -d --wait   ← 빈 DB 라 DDL 이 돌아 새 MV 가 생긴다
> 4. ./scripts/seed-clickhouse.sh
> ```
> `down -v` 는 PostgreSQL 볼륨까지 지우니 seed 를 꼭 다시 돌려야 한다. 그 스크립트가 PG 의 감시 대상 서비스 4줄도 같이 채운다.

**Q17.** 볼륨이라는 게 데이터를 저장하는 역할인가. K8s 의 볼륨은 무엇인가

> 컨테이너 밖에 데이터를 두는 저장 공간이다. 컨테이너를 지우고 새로 띄워도 남는다. 우리 `compose.yaml` 끝에 `clickhouse-data` · `postgres-data` 둘이 있고, **Kafka 는 볼륨이 없어서** 컨테이너를 내리면 메시지가 사라진다.
> K8s 는 파드에 붙인다 : `emptyDir`(파드와 같이 죽는다) · `PersistentVolumeClaim`(파드보다 오래 산다, compose 볼륨에 해당) · `configMap`·`secret`(설정 주입이고 저장이 아니다). 지금 `monimo-deploy` 에 PVC 가 없어서 배포 단계 할 일에 들어간다.

### 다섯째 바퀴 : 2절을 쓴 뒤 (2026-10-07)

**Q18.** 1절의 세 줄을 예시로 설명해 달라

> 결제가 느려진 상황으로 보면 이렇다.
> ```
> 지금 : ① shop-payment 고름   → 점 0개 (내 로컬은 헬스체크 21개만)
>        ② shop-gateway 고름   → 점 30,148개. 느린 점이 위에 깔려 있다
>        ③ 느린 점 하나 누름    → 트레이스 상세
>        ④ 안을 읽는다          → gateway 50ms · order 80ms · payment 3,000ms
>        ⑤ ③④ 를 몇 번 반복     → "결제가 늘 느리다" 고 말할 수 있다
>
> 바꾼 뒤 : ① shop-payment 고름 → 점 21,228개. 느린 점이 바로 보인다
>          ② 느린 구간 드래그   → 느린 결제 요청 목록
> ```
> 다섯 단계가 두 단계가 되고, **서비스를 번갈아 골라 비교**할 수 있다. 지금은 gateway 의 느린 점이 결제 탓인지 재고 탓인지도 모른다.

**Q19.** 스캐터가 보여주는 느린 요청은 메트릭 · 트레이스 · 로그 중 무엇인가

> **트레이스다.** 점 하나 = 스팬 하나(SERVER 스팬)이고, 세로축 `duration_ms` 도 스팬이 들고 있는 값이다. 점을 눌러 열리는 상세도 `spans` 를 읽는다. 메트릭과 로그는 관여하지 않는다.
> 구분하면 : 메트릭은 "결제 CPU 80%", 로그는 "결제 실패 메시지", 트레이스는 "이 요청이 결제에서 3초 걸렸다" 다.

**Q20.** 스캐터가 gateway 에서만 나오는 문제는 이미 해결한 것이 아닌가

> **문서만 끝났고 코드 · DB 는 그대로다.** 지금도 조건이 `WHERE parent_span_id = ''` 다(`004_create_materialized_views.sql:23`).
> `#110` 이 머지된 것은 **스캐터 API 를 만든 것**이고 표 기준은 손대지 않았다. 그래서 코드는 멀쩡한데 읽을 줄이 없는 상태다.

### 이 절에서 바로잡힌 것 (다섯 건)

- **"MV 설정이 안 되어 있어서" 가 아니다.** MV 는 잘 설정돼 있고 설계대로 돌았다. 표의 기준과 화면의 기준이 어긋난 것이다
- **"데이터가 없어서" 는 결과다.** 원인은 조건이 좁은 것이다
- **번호와 kind 는 별개 축이다.** 번호를 kind 에서 가져오지 않는다
- **`down -v` 가 필요한 이유는 옛 줄이 아니라 MV 정의다.** 내가 처음에 두 가지를 섞어 설명했다
- **표는 2개, API 는 3개다.** "스캐터에 쓰는 표가 3개" 가 아니다

### AI 가 먼저 틀린 것

- 내가 "조립할 때 중복을 하나로 친다" 고 답했는데 **코드를 열어 보니 자리가 달랐다.** 중복 제거는 `TraceRepository` 의 ClickHouse 쿼리에 있는 `LIMIT 1 BY span_id` 가 한다. `SpanTree` 는 중복 제거를 하지 않는다
- 내가 "order · payment 는 0건" 이라고 조회 파트 숫자를 그대로 옮겼는데, **실측은 23 · 21줄이고 헬스체크 39 + 앱 시작 DDL 5**였다. 직접 세어 보고 나서야 알았다

## 4. 1차 정리

질문 스무 번이 끝난 뒤의 상태다.

**확실한 것**

- `transactions` 는 ClickHouse 표이고 **MV 가 채우고 조회 API 만 읽는다.** 수집기 · 적재 처리기 코드는 0줄 바뀐다
- 비는 원인은 **MV 조건이 루트 스팬만 통과시키는 것**이다. `spans` 에는 네 서비스 스팬이 다 있다
- **루트는 SERVER 의 부분집합**이라 조건을 SERVER 로 넓히면 잃는 것이 없다. 다른 집계표 셋은 이미 SERVER 또는 CLIENT 기준이고 `transactions` 만 달랐다
- 조회 코드는 안 고친다. `ScatterRepository` 가 `service_name` 과 시간 범위로만 읽는다
- 영향은 **표 2개 · API 3개**다. `heatmap_1m` 이 파생이라 같이 바뀐다
- 바꾸면 **「트랜잭션」의 뜻이 바뀐다.** 고객 요청 하나가 1줄에서 4줄이 되고, 이 표로 전체 요청 수를 세면 부풀려진다
- 줄 수는 30,214 → 102,625 (**약 3.4배**, 실측)
- 로컬 적용은 **파일 수정 → `down -v` → 켜기 → seed** 순서다. `down -v` 가 필요한 이유는 DDL 이 빈 DB 에서만 돌기 때문이다
- 헬스체크는 **`#92` 가 이미 발행 전에 버린다.** 조건을 SERVER 로 넓혀도 안 섞인다

**아직 모르는 것** (5절이 답한다)

- 다른 APM 은 트랜잭션을 루트 기준으로 세나 서비스 기준으로 세나. 둘을 다 쓰는 곳이 있나 (①)
- 한 표로 두 기준을 담는 방법이 `is_root` 말고 또 있나 (②)
- 3.4배가 조회 속도와 저장에 실제로 어떤 영향인가. 지금 `ORDER BY (service_name, start_time)` 로 괜찮은가 (③)
- 운영에서 `down -v` 없이 MV 조건을 바꾸는 안전한 절차는 무엇인가. 집계가 비는 구간을 줄일 수 있나 (④)
- `span_id` 를 넣으면 화면이 실제로 무엇을 더 할 수 있나 (⑤)

## 5. 선택지와 설명

### 조사 프롬프트

두 갈래로 나눠 서브에이전트 2개에 동시에 보냈다. A = 다른 APM 이 트랜잭션을 무엇으로 세나, B = ClickHouse MV 교체 절차와 3.4배의 영향. 원문은 같은 폴더의 [`prompts.md`](prompts.md) 에.

### 5.1 무엇을 조건으로 하나 : 선택지가 셋이다 (①)

조사 전에는 `span_kind = 'SERVER'` 한 줄이라고 생각했다. **조사가 그것을 셋으로 늘렸다.**

| | 조건 | 줄 수 (로컬 측정) |
|---|---|---|
| **지금** | `parent_span_id = ''` | 30,572 |
| **①** | `span_kind = 'SERVER'` | 103,699 |
| **②** | `span_kind IN ('SERVER','CONSUMER')` | 103,699 (**CONSUMER 가 0건이라 ① 과 같다**) |
| **③** | `span_kind IN ('SERVER','CONSUMER') OR parent_span_id = ''` | 103,755 (**+56**) |

**업계는 전부 ③ 꼴이다.** `SERVER` 단독을 쓰는 곳이 하나뿐이고 그마저 문서가 경고를 붙인다.

| 제품 | 진입 판별 조건 | 근거 |
|---|---|---|
| **Elastic APM** | `root \|\| SERVER \|\| CONSUMER` | `apm-data` 의 `input/otlp/traces.go` 소스 한 줄 |
| **Datadog** | root + `span.kind:server` + `span.kind:consumer` | OTel 매핑 공식 문서 |
| **Pinpoint** (OTLP 경로) | `SERVER \|\| CONSUMER \|\| parent 없음` | `OtlpTraceMapper.initRootAndChild()` |
| **New Relic** | 프로세스(서비스)마다 Transaction 1건 | 공식 문서 (판별 규칙은 미공개) |
| **SigNoz** | 둘 다 제공. 진입은 **`service.name` 이 바뀌는 지점** | `query_builder.go` + `sub_root_operations` MV |
| **Jaeger SPM** | **`span.kind = server` 단독** | 공식 문서. **다만 "unspecified 나 client kind 스팬은 안 보인다" 고 바로 경고한다** |

**Pinpoint 는 이미 우리가 가려는 기준이다.** 컬렉터의 `HbaseTraceService.insertSpan` 이 들어온 모든 Span 에 대해 스캐터 인덱스를 **조건 없이** 넣고, 행키에 `applicationName` 이 들어간다. 그래서 서비스를 골라 보는 것이 자연스럽고 중간 서비스에도 점이 찍힌다. 우리가 참고하는 제품이 그렇게 하고 있었다.

**OTel 쪽에 "진입 스팬" 표준 용어는 없다.** 스펙은 `root span` 만 정의한다. 대신 구현체 이름에 흔적이 있다 : `opentelemetry-java-instrumentation` 의 `ServerSpan` 이 **`LocalRootSpan`** 으로 개명됐고, 이유가 "SERVER 라는 이름은 CONSUMER 와 스케줄 잡 INTERNAL 까지 담기에 좁다" 였다([issue #5857](https://github.com/open-telemetry/opentelemetry-java-instrumentation/issues/5857)). **생태계가 스스로 SERVER 단독이 좁다고 판단한 것이다.**

프로토콜에는 더 정확한 신호가 생겼다. OTLP v1.2.0 부터 `Span.flags` 에 **부모 컨텍스트가 remote 인지** 알리는 비트가 있다([OTEP 182](https://github.com/open-telemetry/oteps/pull/182)). 원칙적으로 가장 정확한 진입 판별은 `부모 없음 OR 부모가 remote` 다. 다만 옛 에이전트는 안 채우므로 `unknown` 이 섞인다.

**우리에게 ② 와 ③ 의 차이는 그 56줄이다.** 내용을 열어 봤다.

```
telemetrygen    lets-go                        22
shop-inventory  CLIENT                         10
shop-order      CREATE TABLE shop.orders        7
shop-inventory  HELLO · INSERT · CREATE TABLE  14
shop-gateway    lets-go                         3
```

전부 `span_kind = 'CLIENT'` 인 루트다. 앱이 시작할 때 스키마를 만드는 DDL 과 시험 도구가 넣은 것이다. **③ 을 고르면 이것들이 스캐터 점으로 찍힌다.** ② 를 고르면 깨끗하지만, 나중에 배치나 스케줄 잡이 생기면 그 루트가 INTERNAL 이라 안 잡혀서 다시 고쳐야 한다.

### 5.2 두 기준을 한 표에 담는 방법 (②)

**표를 둘로 나눈 사례는 하나도 없었다.** 넓게 담고 플래그나 토글로 거르는 것이 주류다. 네 변형이 확인됐다.

| 방식 | 어디서 | 어떻게 |
|---|---|---|
| **플래그 컬럼** | **Elastic APM** | 집계 지표에 `transaction.root` **boolean** 필드. 설명이 "루트 트랜잭션 지표를 식별한다. 트레이스 단위 지표 계산에 쓸 수 있다" |
| 스팬 위의 플래그 | Datadog | 에이전트가 `_dd.top_level` 을 찍어 보낸다. 판별은 "루트이거나 부모와 서비스가 다르면" |
| 작은 사전 표 + 큰 팩트 표 필터 | SigNoz | `(serviceName, name)` 사전을 MV 둘로 채워 스코프 필터에 쓴다. 자기조인 MV 비용을 진다 |
| 읽는 쪽 토글 | Grafana Traces Drilldown | Root / Server / Consumer / All 을 버튼으로 고른다 |

**첫 번째가 우리 `is_root` 제안과 1:1 로 같다.** 제안이 업계 선례를 가진 셈이다.

Grafana 문서가 트레이드오프까지 적어 둔 것이 유용하다. All spans 의 단점으로 **"Skewed RED metrics"** 를 든다. 필터 없이 전체 스팬을 집계하면 지연과 에러율이 사용자가 체감하는 것과 어긋난다는 것이고, **우리가 걱정하는 "4배 부풀려짐" 과 같은 지적이다.** SigNoz 도 FAQ 에서 "Services 대시보드는 진입 오퍼레이션만 세고, `signoz_calls_total` 직접 조회는 모든 스팬을 센다" 고 해명한다.

### 5.3 MV 를 어떻게 바꾸나 (④)

조사 B 가 **샌드박스 DB 를 만들어 여섯 방법을 실제로 돌려 봤다.** 우리 ClickHouse 는 `26.8.10.6` 이고 복제 표가 아니다.

| 방법 | 집계가 비나 | 중복이 생기나 | 쓸 수 있나 |
|---|---|---|---|
| `DROP VIEW` + `CREATE` | **빈다.** 그 사이 INSERT 는 영구 유실 | 안 생김 | **운영 금지** |
| **`ALTER TABLE ... MODIFY QUERY`** | **안 빈다** | 안 생김 | **이것을 쓴다** |
| `CREATE OR REPLACE MATERIALIZED VIEW ... TO` | 안 빈다 | 안 생김 | 26.5 부터. 얻는 게 없다 |
| 새 이름 MV 를 만들고 둘을 같이 돌리기 | 안 빈다 | **생긴다.** 겹친 기간만큼 정확히 2배 | **금지** |
| `EXCHANGE TABLES` · `RENAME` 으로 MV 교체 | 안 빈다 | **생긴다.** 이름만 바뀌고 둘 다 계속 돈다 | **금지** |
| `INSERT INTO ... SELECT` (과거 백필) | 안 빈다 | **생긴다, 두 군데서** | 조건부 (5.8) |

**`DROP VIEW` + `CREATE` 가 조용히 구멍을 낸다.** MV 를 지우고 4줄 넣고 다시 만들었더니 타깃에 **0줄**이 들어갔다. 에러도 경고도 없다. 로컬은 `down -v` 로 리셋하니 안 보이지만, 운영에서는 그 구간 그래프가 영구히 0 이 된다.

**`MODIFY QUERY` 가 유일한 답이다.** 공식 문서가 "without interrupting ingestion process" 라고 쓰고, `TO [db.]name` 으로 만든 MV 를 노린 명령이라 우리 경우에 정확히 맞는다. 26.8 에서 실험용 설정 없이 바로 됐다.

**다만 함정이 있다. `MODIFY QUERY` 는 타깃 표 스키마를 검사하지 않는다.** 실험으로 확인한 것 : SELECT 에서 **컬럼을 빠뜨려도 에러 없이 통과**하고 그 컬럼이 타입 기본값으로 채워진다. 우리 경우로 치면 `service_name` 을 빠뜨리면 **그 뒤 모든 줄의 서비스 이름이 빈 문자열**이 되고 아무도 모른다. 타깃에 없는 컬럼을 넣어도 조용히 무시되고, 타입이 달라도 암묵 캐스팅된다. **바꾼 뒤 각 컬럼에 값이 들어오는지 확인하는 단계가 절차에 반드시 들어가야 한다.**

### 5.4 운영에는 마이그레이션 수단이 아예 없다 (조사가 찾은 범위 밖 문제)

조사 B 가 **이번 변경의 최대 미결 항목**으로 꼽은 것이고, 확인해 보니 맞았다.

| | 수단 | 운영에서 DDL 을 바꿀 수 있나 |
|---|---|---|
| PostgreSQL | `postgres-migrate` 컨테이너 (Flyway) | **된다** |
| ClickHouse | `docker-entrypoint-initdb.d` 마운트 뿐 | **안 된다** |

`db/clickhouse/*.sql` 은 **빈 DB 에서만** 실행되고(`compose.yaml:92`), 게다가 전부 `CREATE ... IF NOT EXISTS` 다. 그래서 **004 파일을 고쳐도 이미 떠 있는 ClickHouse 에서는 조용히 건너뛴다.** 로컬은 `down -v` 가 가려 주고 있었다.

이번 이슈가 처음 그 바닥을 건드린다. `ALTER ... MODIFY QUERY` 를 담은 파일(`005_` 같은)을 두는 것과, **그 파일을 운영에서 무엇이 실행하는지**를 정해야 한다. 후자는 이 이슈 범위를 넘는다.

### 5.6 `is_root` 컬럼의 실제 비용 (②)

조사 B 가 wide part 로 강제해 컬럼별로 쟀다.

| 컬럼 | 디스크 | 줄당 |
|---|---|---|
| `trace_id` (String) | 3,308,597 B | **31.9 B (표 전체의 78%)** |
| `start_time` | 461,668 B | 4.45 B |
| `duration_ms` | 297,118 B | 2.87 B |
| **`is_root` (UInt8)** | **985 B** | **0.009 B** |

**`is_root` 는 985 바이트다.** 비압축 103,697 바이트가 985 로 줄어 105:1 압축이다. 표 전체로는 **+0.04%**. 비용 논의가 성립하지 않는다.

**조회는 오히려 빨라진다.** `WHERE is_root = 1` 은 정렬 키에 없어서 granule 을 건너뛰지 못하지만, ClickHouse 가 자동으로 `PREWHERE` 로 옮긴다(`optimize_move_to_prewhere` 기본 1, 우리도 1).

| | 읽은 줄 | 읽은 바이트 | 시간 |
|---|---|---|---|
| `is_root` 조건 없음 | 33,880 | 430 KiB | 3.0 ms |
| `is_root = 1` 추가 | 33,880 | **147 KiB** | **2.0 ms** |

읽는 줄은 같은데 바이트가 1/3 이다. 0.009 B/줄 짜리 플래그를 먼저 읽고 안 맞는 줄은 `trace_id` 를 아예 안 읽는다. **손으로 `PREWHERE` 를 쓸 필요도 없다.**

**정렬 키와 스키핑 인덱스는 건드리지 말라는 것이 조사 결론이다.** 첫 칸에 넣으면 지금의 binary search 가 깨지고, 마지막 칸은 효과가 없다. 정렬 키는 표를 만들 때만 정할 수 있어 바꾸려면 표를 다시 만들어야 한다. 스키핑 인덱스는 `is_root` 가 29.4% 라 거의 모든 블록에 1 이 섞여 있어 공식 문서가 "쓸모없이 비용만 든다" 고 경고하는 경우에 해당한다.

### 5.7 `ORDER BY` 는 지금 그대로 맞다 (③)

공식 가이드가 꼽는 첫 기준이 "조회 필터에 자주 쓰이는 컬럼" 이고, 대표 예시가 **종류 8개짜리 저카디널리티 컬럼을 첫 칸에 두는 것**이다. 우리 `service_name`(5종류 · `LowCardinality`)이 같은 패턴이다.

`EXPLAIN indexes=1` 로 실제 동작을 봤다. 파티션 pruning · minmax · primary key 세 단계가 다 돌고 **binary search** 를 쓴다. granule 16개 중 2개만 읽는다.

**유의할 것 하나** : `service_name` 을 `WHERE` 에 **안 주는** 쿼리는 primary key 로 못 거른다. 지금 조회는 항상 주므로 괜찮지만, "전체 서비스 합계" 화면이 생기면 다시 봐야 한다.

파티션은 93개로 권장 범위(100~1,000 미만) 안이고, 하루 4 MiB 는 ClickHouse 기준으로 매우 작다. 조사가 **덤으로 `ttl_only_drop_parts = 1`** 을 제안했다. 지금 기본값 0 이라 93일 TTL 이 mutation 으로 줄 단위 삭제를 하는데, 파티션이 TTL 단위(일)와 이미 정렬돼 있으니 켜면 part 를 통째로 버려 훨씬 싸다. 이번 변경과 독립적이다.

**규모 감각** : 공식 primary key 가이드의 입문 예제가 한 표 5,982만 줄이다. 우리 930만 줄은 **튜닝 없이 단일 노드에서 도는 급**이다. 그래서 이 결정의 기준은 성능이 아니라 **"어떤 기준이 맞는 숫자를 주는가"** 다.

### 5.8 결정 전에 봐야 하는 함정

1. **`MODIFY QUERY` 가 스키마를 검사하지 않는다.** 컬럼을 빠뜨리면 조용히 빈 값이 채워진다. 바꾼 뒤 검증 쿼리를 돌려야 한다
2. **`is_root` 를 추가하는 순서가 정해져 있다.** `ADD COLUMN` → MV 수정 → (백필) 이다. **거꾸로 하면 조용히 깨진다** : 타깃에 없는 컬럼을 MV SELECT 에 넣으면 에러 없이 무시되므로, MV 를 먼저 고치면 그 사이 들어온 줄의 `is_root` 가 버려진다. 되돌릴 때는 순서가 반대다(`DROP COLUMN` 은 MV 가 참조하는 컬럼을 거부한다)
3. **`is_root` 가 과거 구간에서 거꾸로 거짓이 된다.** `ADD COLUMN` 의 기본값이 0 인데, 지금 들어 있는 30,572줄은 `parent_span_id = ''` 조건으로 들어온 것이라 **사실은 전부 루트**다. 백필하지 않으면 "믿을 수 있는 시점" 경계를 문서나 화면에 둬야 한다
4. **백필이 `heatmap_1m` 을 이중 집계할 수 있다.** 조사가 실험으로 확인했다 : `transactions` 에 **직접** INSERT 해도 `mv_heatmap_1m` 이 돈다(cascade). `heatmap_1m` 은 `SummingMergeTree` 라 `cnt` 가 **조용히 합산**되고 **줄 수가 늘지 않아 눈으로 안 보인다.** 반드시 "heatmap 해당 파티션 비우기 → transactions 백필" 순서여야 한다
5. **백필을 두 번 돌리면 그대로 두 배다.** `non_replicated_deduplication_window = 0`(기본값)이고 복제 표가 아니라 `insert_deduplicate` 가 효과가 없다. 되돌릴 수단은 `DROP PARTITION` 하나뿐이라 **날짜 파티션 단위로** 하고 어디까지 했는지 기록해야 한다
6. **93일을 한 번에 못 넣는다.** `max_partitions_per_insert_block = 100`(기본값)이라 하루 파티션이 100개를 넘으면 예외가 난다. 공식 권고도 쪼개는 쪽이다
7. **`CONSUMER` 가 그 자체로 진입을 보장하지 않는다.** 폴링 루프 안에서 메시지를 소비하면 CONSUMER 스팬이 다른 스팬의 자식이다. Elastic 이 [apm-server #7001](https://github.com/elastic/apm-server/issues/7001) 로 이 오분류를 인정했고 **아직 미해결**이다. 보수적으로 가려면 `kind IN ('SERVER','CONSUMER') AND (parent_span_id = '' OR is_remote)` 가 더 정확하다
8. **한 서비스에 SERVER 스팬이 여러 개일 수 있다.** OTel Java 자동계측은 중첩 SERVER 를 기본 억제하지만 **스펙 보장이 아니다.** 수동 계측 · 서비스 메시 사이드카 · 내부 프록시가 있으면 한 요청에 둘 이상 생겨 중복 계수된다
9. **kind 미지정(`unspecified`)이면 어떤 kind 필터에도 안 걸린다.** Jaeger SPM 문서가 명시적으로 지적하는 실패 모드다

### 5.9 AI 가 틀렸거나 덜 맞았던 것 (남겨 둔다)

### 확인 못 한 것

- **`MODIFY QUERY` 의 원자성** : 공식 문구는 "ingestion 을 끊지 않는다" 까지다. "중간에 걸친 블록이 옛 쿼리와 새 쿼리 중 정확히 하나로만 간다" 는 **미확인**이고 3rd-party 블로그에만 있다
- **동시 INSERT 중에 `MODIFY QUERY` 를 돌리는 실험** : 조사는 insert 가 멈춘 상태에서만 했다. 초당 수천 건이 들어오는 중에도 한 줄도 안 빠지는지 미확인
- **클러스터 전체 보증** : K8s 로 가서 ClickHouse 를 여러 노드로 두면 다시 확인해야 한다
- **직접 INSERT 가 하위 MV 를 트리거하는가** : 실험은 "돈다" 인데 공식 문서 요약은 반대였다. **백필 전에 반드시 재현**해야 한다
- **운영에서 CH DDL 을 무엇이 실행하나** : 수단이 없다는 것까지 확인했고 무엇을 쓸지는 안 정했다. 이 이슈 범위 밖
- **56줄(CLIENT 루트)이 운영에서도 나오나** : 로컬에서는 앱 시작 DDL 과 시험 도구였다. 운영 분포는 측정 못 했다
- **`heatmap_1m` 2.74배가 운영에서도 유지되나** : 로컬 가짜 데이터 분포에 달린 값이다. 서비스가 늘거나 지연 분산이 커지면 3.4배에 가까워질 수 있다
- **New Relic · Pinpoint 네이티브 에이전트의 진입 판별 규칙** : 결과 서술만 있고 조건이 공개돼 있지 않다
- **Datadog `_dd.top_level` 의 공식 문서** : 못 찾았다. 근거가 dd-trace-go 이슈와 PR 이다
- **Jaeger 스캐터의 `duration` 이 루트 스팬 것인지 트레이스 전체 범위인지** : 미확인
- **Uptrace · HyperDX 등 다른 ClickHouse 기반 OSS** : 조사 범위에 못 넣었다. SigNoz 외의 선례는 없다
- **`ttl_only_drop_parts = 1` 의 실제 이득** : 공식 권고와 설정값 확인까지만 했다
- **`is_root` 가 들어오면 어느 화면이 "서비스별" 이고 어느 화면이 "고객 요청 전체" 인지** : 조회 파트와 정해야 한다

## 7. 2차 정리

> 5 를 읽은 뒤의 상태다. **아직 결정이 아니다.** 결정은 8 에서 승조가 내린다.

### 조사가 바꾼 것

조사 전에는 "조건 한 줄을 고치고 `is_root` 를 넣는다" 였다. 조사가 **셋을 바꿨다.**

| | 조사 전 | 조사 뒤 |
|---|---|---|
| 조건 | `span_kind = 'SERVER'` | **선택지 셋.** 업계는 전부 CONSUMER 와 루트를 함께 넣는다 |
| 어떻게 바꾸나 | 파일 고치고 `down -v` | **`ALTER ... MODIFY QUERY`** 를 써야 한다. `DROP`+`CREATE` 는 조용히 구멍을 낸다 |
| `is_root` | "넣으면 좋다" | **Elastic 에 같은 패턴이 있다.** 비용 985 바이트이고 조회가 오히려 빨라진다 |

그리고 **범위 밖 문제 하나**가 드러났다. 운영에 ClickHouse 마이그레이션 수단이 없다.

### 좁혀진 선택지

**조건** (고르는 것은 이것 하나다)

| | 조건 | 얻는 것 | 포기하는 것 |
|---|---|---|---|
| ① | `SERVER` | 가장 단순 | 업계와 다르다. 메시지 큐가 들어오면 다시 고친다 |
| **②** | `SERVER` + `CONSUMER` | **지금 비용 0**(CONSUMER 0건). 메시지 큐 대비가 끝난다 | 배치 · 스케줄 잡 루트는 여전히 안 잡힌다 |
| ③ | `SERVER` + `CONSUMER` + 루트 | **업계 표준.** 배치 진입까지 잡는다 | DDL · 시험 도구 잡음 56줄이 점으로 찍힌다 |

**정할 것이 없는 것 (그냥 한다)**

- **`ALTER ... MODIFY QUERY` 를 쓴다.** 집계가 비지도 중복이 생기지도 않는 유일한 방법이다
- **바꾼 뒤 검증 쿼리를 돌린다.** `MODIFY QUERY` 가 스키마를 안 보기 때문이다
- **`DROP VIEW`+`CREATE` · 둘 같이 돌리기 · `EXCHANGE` 는 안 쓴다**
- **정렬 키와 스키핑 인덱스는 건드리지 않는다**

### 결정을 가르는 기준

| 기준 | ① | ② | ③ |
|---|---|---|---|
| 지금 드는 비용 | 없음 | **없음** | DDL 잡음 56줄 |
| 다시 고칠 일 | 메시지 큐 들어오면 | 배치 생기면 | **거의 없음** |
| 업계와 같은가 | 아니오 | 절반 | **예** |

**세 기준이 맞물린다.** ② 는 "공짜로 살 수 있는 미래만 사고 잡음은 안 들인다", ③ 은 "지금 잡음을 받아들이고 다시 안 고친다" 다.

### 무엇을 정해야 하나

| | 정할 것 | 어떤 컬럼인가 | 안 정하면 |
|---|---|---|---|
| 1 | **조건을 ① · ② · ③ 중 무엇으로** | 컬럼이 아니라 MV 의 `WHERE` 한 줄이다 | 이 이슈의 본체다 |
| 2 | **`is_root` 컬럼을 넣을지** | `UInt8`(0 또는 1). **이 줄이 그 요청이 시작된 지점이었나**를 적는다. `toUInt8(parent_span_id = '')` 로 MV 안에서 계산한다 | 이 표로 고객 요청 수를 세면 4배 부풀려진다 |
| 3 | **`span_id` 컬럼을 넣을지** | `String`. **그 줄이 된 스팬 자기 번호**다. `trace_id` 가 요청 전체 번호이고 이것은 그 안의 구간 번호다 | 같은 트레이스에 같은 서비스가 두 번 나올 때 점을 못 구분한다. 조회 파트의 화면 계획에 달렸다 |
| 4 | **과거 구간을 백필할지** | 해당 없음 | `is_root` 가 과거에서 거꾸로 거짓이 된다. 백필하면 `heatmap_1m` 이중 집계 위험을 진다 |
| 5 | **`005_` 마이그레이션 파일을 이 이슈에서 둘지** | 해당 없음 | 004 를 고쳐도 운영에서는 안 바뀐다. 실행 수단까지는 범위 밖이다 |

#### 2 번 `is_root` : 고객 요청과 그 요청이 지나간 경로를 가른다

조건을 넓히면 한 요청이 여러 줄이 되는데 **표만 보고는 구분할 방법이 없다.**

```
trace_id   service_name   duration_ms   is_root
T1         gateway        240           1      ← 고객이 실제로 기다린 시간
T1         order          180           0
T1         payment         90           0
T1         inventory       40           0
```

`duration_ms` 를 보면 왜 섞으면 안 되는지 드러난다. 240 이 고객이 기다린 시간이고 나머지는 **그 안의 부분**이다. 네 줄을 합친 550 은 아무 뜻이 없는 숫자다.

| 보려는 것 | 어떻게 |
|---|---|
| 결제 서비스 스캐터 | `WHERE service_name = 'shop-payment'` |
| 고객 요청이 몇 건이었나 | `WHERE is_root = 1` |

**지금은 조건이 그 역할을 하고 있다.** 들어온 줄이 전부 루트라 따로 표시할 필요가 없었다. 조건을 넓히면 그 정보가 사라지므로 **조건에서 컬럼으로 옮기는 것**이다.

#### 3 번 `span_id` : 같은 서비스를 두 번 지날 때 점을 집는다

```
transactions  (trace_id = T1)
  T1  inventory   ← 재고를 두 번 불렀다
  T1  inventory
```

두 줄이 `trace_id` 도 `service_name` 도 같다. 스캐터에 점이 둘 찍히는데 **어느 구간인지 집을 열쇠가 없다.**

| 하려는 것 | 필요한가 |
|---|---|
| 점을 눌러 **트레이스 상세**를 연다 | **`trace_id` 로 충분하다.** 상세는 `spans` 를 직접 읽어 조립한다 |
| 요청 목록에서 줄을 눌러 **그 구간으로 바로 간다** | `span_id` 가 있어야 한다 |

측정상 겹치는 키는 **한 키당 최대 2줄**이고 평균 1.00줄이라 드물다. 안 넣어도 상세를 열면 `spans` 에서 전부 보인다. 다만 `trace_id String` 이 이미 디스크의 78% 를 먹고 있어 **같은 급의 컬럼을 하나 더 넣는 비용**은 `is_root` 와 비교할 수 없다.

### 범위 밖인 것

- **운영에서 CH DDL 을 실행하는 수단** : 수단이 없다는 것이 이번에 드러났다. 별 이슈로 올려야 한다
- **`ttl_only_drop_parts = 1`** : 독립적인 개선이다
- **`trace_id` 가 저장의 78%** : 줄이려면 따로 봐야 한다
- **요청 목록 · 히트맵 API 구현** : 조회 파트 몫이다

### 여기서 나온 면접 질문

1. 집계 표가 설계대로 동작했는데도 화면이 비어 보였다. 무엇이 어긋났던 것인가
2. 다른 APM 들은 "서비스가 받은 요청" 을 어떻게 판별하나. `span_kind = SERVER` 만으로는 왜 모자란가
3. 한 표를 두 기준으로 쓰려면 무엇을 바꾸겠나. 업계에 선례가 있나
4. 운영 중인 집계 뷰의 정의를 바꿀 때 집계가 비거나 중복되지 않게 하려면 어떻게 하나
5. 플래그 컬럼 하나를 추가하면 조회가 느려질 것 같은데 왜 빨라졌나
6. 집계가 두 단계로 파생될 때 과거 데이터를 다시 채우면 무엇이 위험한가
7. 로컬에서는 보이지 않다가 운영에서만 드러날 문제를 이번에 하나 찾았다. 무엇인가

mv_transactions 의 조건을 parent_span_id = '' 에서
span_kind IN ('SERVER','CONSUMER') 으로 바꾼다.

조건을 바꾸는 이유는 세 가지다. 첫째로 지금 비어 있는 게 데이터가 없어서가 아니라 조건이
좁아서인데, spans 에는 네 서비스 SERVER 스팬이 다 있고(gateway 30478 · order 30356
· inventory 21447 · payment 21396) 그중 루트는 gateway 것뿐이라 거기만 점이 찍힌다.
루트는 SERVER의 부분집합이라 조건을 넓혀도 지금 들어오던 건 그대로 들어온다.

둘째로 우리 레포 안에서 이 표만 기준이 다르다. mv_url_stats_1m 이랑
mv_service_health_1m 이 이미 span_kind = 'SERVER' 인데 mv_transactions 만
parent_span_id 를 본다. 한 DB 안에 두 기준이 섞여 있는 거라 맞추는 쪽이 맞다.

셋째로 조회 코드를 안 고친다. ScatterRepository 가 service_name 과 시간 범위로만 읽어서
줄이 들어오면 그대로 돈다. 화면이 서비스를 골라 보는 구조로 이미 만들어져 있으니까 표가
화면을 따라가는 게 맞다.

CONSUMER 를 같이 넣는 이유는 일이 서비스로 들어오는 방법이 HTTP 하나가 아니라서다.
큐에 쌓인 메시지를 받으면 그 스팬이 SERVER 가 아니라 CONSUMER 인데, SERVER 만 조건으로
걸면 그 서비스 스캐터가 또 빈다. 지금 문제와 똑같은 일이 작은 규모로 생기는 거다.
우리 쇼핑몰은 ADR #25에서 동기 MVC로 못 박아서 CONSUMER 가 0건이고, 그래서 지금은
SERVER 만 걸든 CONSUMER 를 같이 걸든 결과가 완전히 같다. 비용이 0이라는 뜻이다.

그런데도 넣는 이유는 쇼핑몰이 감시 대상의 전부가 아니기 때문이다. 우리 제품 전제가
에이전트만 붙이면 쓸 수 있다는 거니까 남의 앱이 들어올 수 있고, 그 앱이 Kafka 를 쓰면
그 서비스 화면이 빈다. 쇼핑몰은 시험 대상일 뿐이다. 토큰 하나 더 쓰는 거라 틀릴 일도 없다.

조건에 OR parent_span_id = '' 까지 넣는 건 지금 안 한다. Elastic 이랑 Datadog,
Pinpoint 는 그걸 다 넣는데 그러면 아무도 안 불렀는데 서비스가 스스로 시작한 일까지
잡힌다. 배치나 스케줄 잡이 거기 들어가니까 언젠가는 필요한데, 지금 우리 데이터에서
거기 걸리는 건 56줄이고 전부 앱 켜질 때 도는 CREATE TABLE 이랑 telemetrygen 이 넣은
시험 데이터다. 운영에서도 파드가 뜰 때마다 생기는 거라 로컬 잡음만이 아니고, 어느
서비스가 느린지 보려는 화면에 CREATE TABLE 점이 찍히는 건 도움이 안 된다. 진짜 배치를
만들 때 넓히는 걸 되돌림 조건에 적어 두자.

B 방식, 조회가 spans 를 직접 읽는 건 안 한다. 원본 표라 느리고 히트맵이 heatmap_1m 을
못 쓰게 되는데 그러면 집계표를 만든 이유가 없어진다.

C 방식, 지금대로 두고 중간 서비스는 안내 문구를 띄우는 것도 안 한다. 스캐터를 만든 이유가
어느 서비스가 느린지 보려는 건데 느린 서비스를 못 고르면 기능이 반쪽이다.

is_root 컬럼을 같이 넣자. toUInt8(parent_span_id = '') 한 줄이면 된다.

이게 필요한 이유는 조건을 넓히면 고객 요청 하나가 여러 줄이 되는데 표만 보고 구분할
방법이 없어지기 때문이다. 요청 하나가 서비스 4개를 지나면 4줄이 되고 count() 가 4를
준다. duration_ms 를 보면 더 분명한데 루트 줄의 240ms 가 고객이 기다린 시간이고 나머지
180 90 40 은 그 안의 부분이라 네 개를 합친 550 은 아무 뜻이 없는 숫자다. 지금은 조건이
그 구분을 해 주고 있는데 조건을 넓히면 사라지니까 조건에서 컬럼으로 옮기는 거다.

문서에 이 표로 요청 수를 세지 마라고 적어 두는 방법도 있는데 그건 막을 장치가 없고
규칙을 모르는 사람이 count() 를 쓰면 틀린 숫자가 화면에 나간다. 컬럼을 두면
service_name 으로 서비스별, is_root = 1 로 고객 요청 수를 한 표에서 다 본다.
조사해 보니 Elastic APM 에 transaction.root 라는 boolean 이 똑같은 용도로 있었다.
설명이 루트 트랜잭션 지표를 식별한다, 트레이스 단위 지표 계산에 쓸 수 있다고 적혀 있다.
표를 둘로 나눈 사례는 하나도 없고 넓게 담고 플래그로 거르는 게 업계 방식이다.

비용도 재 봤는데 985바이트다. 표 전체의 0.04퍼센트고 0과 1 두 가지뿐이라 105대 1로
압축된다. 그리고 조회가 오히려 빨라진다. is_root 는 정렬 키에 없어서 granule 을 건너뛰진
못하는데 ClickHouse 가 자동으로 PREWHERE 로 옮겨서 0.009바이트짜리 플래그를 먼저 읽고
안 맞는 줄은 trace_id 를 아예 안 읽는다. 읽는 바이트가 430KiB 에서 147KiB 로 줄고
3.0ms 가 2.0ms 가 됐다. 손으로 PREWHERE 쓸 필요도 없다.

정렬 키랑 스키핑 인덱스는 건드리지 않는다. 첫 칸에 넣으면 지금 service_name 등호로
걸리는 binary search 가 깨지고 마지막 칸은 효과가 없다. 정렬 키는 표 만들 때만 정할 수
있어서 바꾸려면 표를 다시 만들어야 한다. 스키핑 인덱스는 is_root 가 29퍼센트라 거의 모든
블록에 1이 섞여 있어서 공식 문서가 쓸모없이 비용만 든다고 경고하는 경우에 해당한다.

span_id 는 조회 쪽에 물어보고 정하자. 같은 트레이스에서 같은 서비스가 두 번 호출되면
trace_id 랑 service_name 이 같은 줄이 둘 생기는데 그때 점 하나를 그 구간으로 집으려면
필요하다. 트레이스 상세를 여는 것까지는 trace_id 로 충분하니까 요청 목록에서 줄을 눌러
해당 구간으로 바로 가는 화면을 만들 거면 넣고 아니면 안 넣는다. 재 보니까 겹치는 키가
한 키당 최대 2줄이고 평균 1.00줄이라 드물다. 그리고 trace_id String 이 이미 디스크의
78퍼센트를 먹고 있어서 같은 급 컬럼을 하나 더 넣는 건 is_root 랑 비교할 비용이 아니다.
넣기로 하면 is_root 랑 같이 넣어서 ERD 수정을 한 번에 끝낸다.

MV 를 바꾸는 방법은 ALTER TABLE ... MODIFY QUERY 를 쓴다.

조사가 샌드박스 DB 를 만들어서 여섯 방법을 직접 돌려 봤는데 집계가 비지도 중복이 생기지도
않는 게 이것뿐이었다. DROP VIEW 하고 CREATE 하는 건 운영에서 쓰면 안 된다. MV 를 지우고
4줄 넣고 다시 만들었더니 타깃에 0줄이 들어갔고 에러도 경고도 없었다. 로컬은 down -v 로
리셋하니까 안 보이는데 운영에서는 그 구간 그래프가 영구히 0이 된다. 새 이름으로 MV 를
만들어서 둘을 같이 돌리는 것도 안 된다. 소스 4줄에 타깃 8줄이 들어가서 겹친 기간만큼
정확히 두 배가 되고 우리 transactions 는 평범한 MergeTree 라 되돌릴 방법이 파티션 통째로
버리는 것밖에 없다. EXCHANGE TABLES 는 교환한 뒤에도 두 MV 가 둘 다 계속 돌아서 교체
수단이 아니다.

MODIFY QUERY 쓸 때 조심할 게 하나 있는데 이게 타깃 표 스키마를 검사하지 않는다.
SELECT 에서 컬럼을 빠뜨려도 에러 없이 통과하고 그 컬럼이 타입 기본값으로 채워진다.
service_name 을 빠뜨리면 그 뒤 모든 줄의 서비스 이름이 빈 문자열이 되는데 아무도 모른다.
타깃에 없는 컬럼을 넣어도 조용히 무시되고 타입이 달라도 암묵 캐스팅된다. 그래서 바꾼 뒤에
각 컬럼에 값이 실제로 들어오는지 확인하는 쿼리를 돌리는 단계를 절차에 넣자. 최소한 빈
문자열이나 0이 아닌지 세는 것 하나랑, 서비스가 고르게 나오는지 보는 것 하나다. gateway 만
나오면 안 바뀐 거다.

is_root 를 넣는 순서도 정해져 있다. ADD COLUMN 을 먼저 하고 그 다음에 MV 를 고친다.
거꾸로 하면 조용히 깨진다. 타깃에 없는 컬럼을 MV SELECT 에 넣으면 에러 없이 무시되니까
MV 를 먼저 고치면 그 사이 들어온 줄의 is_root 가 버려진다. 되돌릴 때는 순서가 반대인데
DROP COLUMN 이 MV 가 참조하는 컬럼을 거부하니까 MV 를 먼저 고쳐야 한다.

과거 구간 백필은 안 한다.

ADD COLUMN 의 기본값이 0이라서 지금 들어 있는 3만 줄의 is_root 가 전부 0으로 보이는데
그 줄들은 parent_span_id = '' 조건으로 들어온 거라 사실은 전부 루트다. 즉 과거 구간에서
is_root 가 정확히 거꾸로 거짓이 된다. 그런데도 백필을 안 하는 이유는 지금 배포 전이고
쌓인 게 전부 가짜 데이터라 얻을 게 없는데 위험은 크기 때문이다.

위험이 두 가지인데 하나는 heatmap_1m 이 조용히 두 배가 되는 거다. transactions 에 직접
INSERT 해도 mv_heatmap_1m 이 따라 도는 걸 조사가 실험으로 확인했고, heatmap_1m 은
SummingMergeTree 라서 같은 칸에 들어온 cnt 를 더한다. 원래 100이던 칸이 200이 되는데
줄 수가 안 늘어나니까 눈으로 안 보인다. 중복 제거가 아니라 합산이라서 그렇다.

다른 하나는 두 번 돌리면 그대로 두 배라는 거다. non_replicated_deduplication_window 가
0이고 우리는 복제 표가 아니라서 insert_deduplicate 가 효과가 없다. 되돌릴 수단은
DROP PARTITION 하나뿐이라 줄 단위로 못 지운다.

그래서 백필 대신 이 시각부터 기준이 바뀌었다를 ADR 이랑 ERD 에 적고, is_root 를 믿을 수
있는 시점 경계를 조회 쪽에 알려 주자. 로컬은 down -v 로 다 지우니까 경계가 안 생긴다.
나중에 운영 데이터가 생긴 뒤에 백필이 필요해지면 공식 문서가 권하는 별 표에 채우고
MOVE PARTITION 하는 방식으로 하고, 그 전에 직접 INSERT 가 하위 MV 를 돌리는지 샌드박스에서
한 번 더 재현하자. 조사가 공식 문서 요약과 자기 실험 결과가 반대였는데 원문을 못 봤다고
밝혀 뒀다.

적용 순서는 로컬에서 파일 고치고 down -v 하고 다시 켜고 seed 돌리는 거다. down -v 가
필요한 이유는 옛 줄 때문이 아니라 db/clickhouse/*.sql 이 빈 DB 에서만 돌아서 그냥 켜면
옛 조건 MV 가 그대로 남기 때문이다. PG 볼륨도 같이 지워지니까 seed 를 꼭 다시 돌려야
화면에 뭐가 보인다. 팀원들도 각자 해야 하니까 PR 본문이랑 AGENTS.md 에 적어 두자.

운영 마이그레이션은 별 이슈로 올리자. 조사하다 알게 된 건데 우리 운영에 ClickHouse DDL 을
바꿀 수단이 아예 없다. PG 는 postgres-migrate 컨테이너가 Flyway 로 도는데 CH 는
docker-entrypoint-initdb.d 마운트뿐이고 그게 빈 DB 에서만 돈다. 게다가 우리 파일이 전부
CREATE ... IF NOT EXISTS 라서 004 를 고쳐도 이미 떠 있는 CH 에서는 조용히 건너뛴다.
로컬에서 down -v 가 그걸 가려 주고 있었던 거다.

이번 이슈에서 005_ 파일을 만들어 둘 수도 있는데 그러면 파일은 있는데 그걸 실행할 수단이
없는 상태가 돼서 더 헷갈린다. 수단을 정하는 게 이 이슈보다 큰 일이니까 따로 올리고
AGENTS.md §6 에 적어 두자. 이번에는 004 를 고치고 로컬은 down -v 로 적용한다.

ERD 도 같이 고친다. 레포 사본 docs/design/web-v2/erd.md 의 294줄 트랜잭션(루트 스팬) 과
304줄 MV 조건, 그리고 194줄 spans.parent_span_id 설명에 비어 있으면 루트라 transactions
가 이 조건으로 골라낸다고 적혀 있는데 그 조건이 사라지니까 셋 다 바꾼다. is_root 를
넣으니까 컬럼 목록도 늘어난다. 노션이 정본이라 거기도 같이 간다.

ADR 로 남긴다. 트랜잭션의 뜻이 바뀌는 거라 4요소로 적어야 한다.

되돌리는 조건은 네 가지다. 배치나 스케줄 잡을 만들어서 부모 없는 INTERNAL 루트가 생기면
조건에 OR parent_span_id = '' 를 넣어 넓힌다. 이 표로 전체 요청 수를 세는 화면이 생기고
is_root 로 안 풀리면 표를 둘로 나눈다. 줄이 3.4배로 늘어서 스캐터 조회가 눈에 띄게
느려지면 ORDER BY 를 다시 보거나 격자로 접는 기준인 limit 5000 을 내린다. 한 서비스에
SERVER 스팬이 여러 개 생기는 구성이 들어오면, 서비스 메시 사이드카 같은 게 그런데,
중복 계수가 되니까 그때 다시 본다.

요청 목록 GET /traces/transactions 과 히트맵 GET /traces/heatmap 구현은 조회 파트 몫이라
이번 범위 밖이다. 우리는 표가 채워지게 하는 것까지 한다. ttl_only_drop_parts 를 1로
켜는 것도 조사가 덤으로 제안했는데 이번 변경과 독립적이라 따로 보자.

그러니 그렇게 구현해줘.
```

**이 프롬프트가 결정의 4요소를 그대로 담고 있다.** 채택(조건 ② + `is_root` + `MODIFY QUERY`)과 기각 넷(① 이 좁다 · ③ 은 DDL 잡음 · B 는 느리다 · C 는 기능이 반쪽)이 각각 사유와 함께 있고, 뒤쪽 문단이 되돌리는 조건 넷이다. 그래서 이 글이 곧 ADR 이고 구현은 이 글을 코드로 옮기는 것이다.

### 결정이 선택지 어디에 닿았나

| 7절에서 정할 것 | 결정 |
|---|---|
