- 2026-10-07
- 조사 서브에이전트 2개(opus)를 동시에 돌렸다. A = 다른 APM 의 트랜잭션 기준, B = ClickHouse MV 교체와 성능

## 이 이슈의 시작은 프롬프트가 아니었다

다른 이슈와 다르다. **조회 파트(현영)가 스캐터를 만들다 찾아 개인 스크럼에 올린 글**이 출발점이다. 그 글을 읽고 2026-10-06 에 질문 열일곱 번을 주고받은 것이 사실상 리서치 3절 · 6절 역할을 했고, 그 기록이 노션 「스캐터가 gateway 에서만 나오는 문제」 에 먼저 들어갔다.

그래서 순서가 이렇게 됐다.

```
현영의 글 → 질문 17번(노션에 기록) → 레포 리서치 1 · 2절 → 질문 3번 → 조사 2개 → 5 · 7절
```

리서치 1 · 2절이 **질문보다 뒤에** 쓰였다. 3절 머리에 그 사실을 적어 뒀다.

## 조사 A : 다른 APM 은 트랜잭션을 무엇으로 세나

**한 번에 됐나** : 됐다. 되묻지 않았다.

**무엇이 나왔나** : 조건을 `span_kind = 'SERVER'` 한 줄로 단정했던 것이 **셋으로 늘었다.** 여섯 제품 중 SERVER 단독을 쓰는 곳이 하나뿐이고 그마저 문서가 경고를 붙인다는 것, 그리고 Elastic APM 에 `transaction.root` boolean 이 실제로 있다는 것이 결정을 바꿨다.

```
APM 제품들이 "트랜잭션" 또는 스캐터 차트의 점을 **무엇 기준으로 세는지** 조사해 달라. 우리 팀이 ClickHouse 집계표의 기준을 바꿀지 결정하는 근거로 쓴다.

## 배경 (우리 상황)

- 자체 APM 을 만들고 있다. OTel 에이전트 → 우리 수집기 → Kafka → 적재 처리기 → ClickHouse
- `spans` 표에 스팬이 평면으로 쌓인다. 거기서 Materialized View 가 `transactions` 표를 채운다
- 지금 조건: `WHERE parent_span_id = ''` (부모 없는 루트 스팬만 = 고객 요청 하나당 1줄)
- 스캐터 차트(가로 시각 · 세로 응답시간 · 점 하나 = 요청 하나)가 이 표를 읽는다
- 문제: 화면이 "서비스를 골라서 본다" 구조인데, 루트만 모으니 **맨 앞 서비스(gateway)에만 점이 있다.** 중간 서비스(order · payment · inventory)는 0건
- 검토 중인 변경: `WHERE span_kind = 'SERVER'` (각 서비스가 받은 요청마다 1줄). 줄이 약 3.4배로 늘어난다

## 조사해 줄 것

**① 각 제품이 무엇을 "트랜잭션" 또는 스캐터의 점 하나로 세나**

다음을 각각 확인해 달라. 가능하면 공식 문서나 소스 코드를 근거로.

- **Pinpoint** (우리가 참고하는 제품이다. 스캐터 차트가 핵심 기능)
- **SigNoz** (ClickHouse 기반이라 우리와 구조가 가장 비슷하다)
- **Jaeger**
- **Elastic APM** (transaction 과 span 을 명시적으로 나눈다고 알고 있다)
- **Datadog APM** 또는 **New Relic** (둘 중 자료가 확실한 쪽)
- **Grafana Tempo / Pyroscope** 같은 OSS 중 스캐터 비슷한 화면이 있는 것

각 제품에 대해:
- 점 하나 또는 "트랜잭션" 한 건이 **루트 스팬 기준인가, 서비스가 받은 요청(진입 스팬) 기준인가, 둘 다인가**
- 서비스별로 보는 화면이 있나. 있다면 그 화면은 무엇을 읽나
- 용어를 어떻게 쓰나 (transaction · trace · entry span · service-level 등)

**② 한 표에 두 기준을 같이 담는 패턴이 있나**

우리는 "서비스별" 과 "고객 요청 전체" 두 기준이 다 필요할 수 있다. 바꾸면 "전체 요청 수" 를 세는 용도로는 못 쓰게 된다(4배 부풀려짐).

- `is_root` 같은 플래그 컬럼을 두는 패턴이 실제 제품/오픈소스에 있나
- Elastic APM 의 `transaction.type` · `parent.id` 유무, OTel 의 진입 스팬 판별 관행 등
- 아니면 표를 두 개로 나누는 쪽이 일반적인가

**③ OTel 규약에 "진입 스팬(entry span)" 개념이 있나**

- OpenTelemetry semantic conventions 나 spec 에 "서비스의 진입 지점" 을 가리키는 표준 용어나 속성이 있나
- Pinpoint 는 entry span 이라는 말을 쓴다고 알고 있는데 OTel 쪽 대응물이 있나
- `span_kind = SERVER` 로 진입 스팬을 판별하는 것이 관행적으로 맞나. 틀릴 수 있는 경우(CONSUMER 스팬, 비동기 진입 등)는 무엇인가
```

## 조사 B : ClickHouse MV 교체 절차와 3.4배의 영향

**한 번에 됐나** : 됐다. 되묻지 않았다.

**무엇이 나왔나** : 조사가 **샌드박스 DB 를 만들어 여섯 방법을 직접 돌려 봤고**, 그 실험이 세 가지를 바꿨다. `DROP VIEW`+`CREATE` 가 조용히 구멍을 낸다는 것, `MODIFY QUERY` 가 타깃 스키마를 검사하지 않는다는 것, 백필이 `heatmap_1m` 을 이중 집계한다는 것이다. 그리고 **운영에 CH 마이그레이션 수단이 아예 없다**는 범위 밖 문제를 찾아냈다.

```
ClickHouse Materialized View 의 **정의를 운영 중에 바꾸는 안전한 절차**와 **대상 표의 줄 수가 3.4배로 늘 때의 영향**을 조사해 달라. 우리 팀이 집계표 기준을 바꿀지 결정하는 근거로 쓴다.

## 배경 (우리 구성, 전부 확인된 사실)

(mv_transactions · transactions · mv_heatmap_1m · heatmap_1m 의 DDL 원문을 그대로 붙였다)

- 로컬 개발은 docker compose 이고 `db/clickhouse/*.sql` 이 **빈 DB 에서만** 실행된다. 그래서 로컬은 `docker compose down -v` 로 볼륨을 지우고 다시 켠다
- 운영은 아직 배포 전이지만 K8s 로 갈 예정이다. **운영에는 `down -v` 가 없다**
- 측정값: 조건을 바꾸면 `transactions` 가 30,214줄 → 102,625줄 (약 3.4배). `heatmap_1m` 도 비슷한 비율로 늘 것으로 예상
- 조회 패턴은 `WHERE service_name = ? AND start_time >= ? AND start_time < ?` 가 전부다. 거기에 `argMax(...)` 로 격자별 대표를 뽑는 쿼리가 하나 있다

## 조사해 줄 것

**① 운영 중 MV 정의를 바꾸는 방법과 각각의 위험**

ClickHouse 에서 MV 의 SELECT 를 바꾸는 방법들을 비교해 달라.

- `DROP VIEW` + `CREATE MATERIALIZED VIEW` : 그 사이에 들어온 INSERT 는 어떻게 되나. 정확히 무엇을 잃나
- `ALTER TABLE ... MODIFY QUERY` : 어느 버전부터 되나, 제약은 무엇인가, 원자적인가
- `CREATE MATERIALIZED VIEW` 를 새 이름으로 만들고 둘을 같이 돌린 뒤 옛것을 떼는 방법 : 중복이 생기나
- `EXCHANGE TABLES` 나 `RENAME` 을 쓰는 패턴이 있나
- 대상 표에 **이미 쌓인 과거 줄**을 새 기준으로 다시 채우는 방법 (`INSERT INTO ... SELECT` 백필). 주의할 점은 무엇인가. MV 가 동시에 돌면 이중 집계가 생기나

각 방법에 대해 **"집계가 비는 구간이 생기나"** 와 **"중복이 생기나"** 를 분명히 말해 달라. 우리가 가장 두려워하는 것이 그 둘이다.

**② 줄 수가 3.4배로 늘 때의 실제 영향**

- `ORDER BY (service_name, start_time)` 가 위 조회 패턴에 맞나. `service_name` 이 `LowCardinality` 이고 종류가 5개 정도일 때 정렬 키 첫 칸으로 두는 것이 적절한가
- 같은 `(service_name, start_time)` 을 가진 줄이 여러 개 생긴다. `MergeTree` 에서 정렬 키 중복이 문제가 되나
- `PARTITION BY toDate(start_time)` 에 하루 10만 줄 수준이면 파티션 크기가 적절한가
- 3.4배가 저장 크기와 조회 지연에 실제로 어느 정도 영향인가. ClickHouse 에서 이 규모(하루 수십만 줄)는 어떤 급인가

**③ `is_root` 같은 플래그 컬럼을 추가하는 비용**

우리는 `toUInt8(parent_span_id = '') AS is_root` 를 컬럼으로 추가할지 검토 중이다. "서비스별" 과 "고객 요청 전체" 두 기준을 한 표로 보려는 것이다.

- `UInt8` 컬럼 하나를 추가하는 비용 (저장 · 압축)
- `WHERE is_root = 1` 로 거르는 쿼리가 정렬 키에 없는 컬럼이라 느릴 수 있나. 그렇다면 정렬 키에 넣어야 하나, 아니면 `PREWHERE` 나 데이터 스키핑 인덱스가 나은가
- 기존 표에 컬럼을 추가할 때 `ALTER TABLE ADD COLUMN` 의 비용과 MV 를 같이 고쳐야 하는 순서
```

## 조사를 시킬 때 넣은 것

두 프롬프트에 공통으로 둔 장치가 셋이다. `#92` · `#96` 에서 효과를 본 것들이다.

- **배경에 우리 DDL · 설정값 원문을 그대로 붙였다.** 일반론이 아니라 우리 구성에 대한 답이 나오게

## 구현 프롬프트

**한 번에 됐나** : 이 글이 곧 설계다. 조사 2건과 질문 스무 번을 거친 뒤 2026-10-07 에 썼다.

같은 원문이 [`research.md`](research.md) 8절과 ADR 안에도 있다. 세 곳이 글자 단위로 같다.

```
A로 가되 조건은 SERVER 하나가 아니라 CONSUMER까지 넣는 방향으로 가자.

mv_transactions 의 조건을 parent_span_id = '' 에서
span_kind IN ('SERVER','CONSUMER') 으로 바꾼다.

조건을 바꾸는 이유는 세 가지다. 첫째로 지금 비어 있는 게 데이터가 없어서가 아니라 조건이
좁아서인데, spans 에는 네 서비스 SERVER 스팬이 다 있고(gateway 30478 · order 30356
· inventory 21447 · payment 21396) 그중 루트는 gateway 것뿐이라 거기만 점이 찍힌다.
루트는 SERVER의 부분집합이라 조건을 넓혀도 지금 들어오던 건 그대로 들어온다.

둘째로 우리 레포 안에서 이 표만 기준이 다르다. mv_url_stats_1m 이랑
mv_service_health_1m 이 이미 span_kind = 'SERVER' 인데 mv_transactions 만
parent_span_id 를 본다. 한 DB 안에 두 기준이 섞여 있는 거라 맞추는 쪽이 맞다.

셋째로 조회 코드를 안 고친다. ScatterRepository 가 service_name 과 시간 범위로만 읽어서
줄이 들어오면 그대로 돈다. 화면이 서비스를 골라 보는 구조로 이미 만들어져 있으니까 표가
화면을 따라가는 게 맞다.

CONSUMER 를 같이 넣는 이유는 일이 서비스로 들어오는 방법이 HTTP 하나가 아니라서다.
큐에 쌓인 메시지를 받으면 그 스팬이 SERVER 가 아니라 CONSUMER 인데, SERVER 만 조건으로
걸면 그 서비스 스캐터가 또 빈다. 지금 문제와 똑같은 일이 작은 규모로 생기는 거다.
우리 쇼핑몰은 ADR #25에서 동기 MVC로 못 박아서 CONSUMER 가 0건이고, 그래서 지금은
SERVER 만 걸든 CONSUMER 를 같이 걸든 결과가 완전히 같다. 비용이 0이라는 뜻이다.

그런데도 넣는 이유는 쇼핑몰이 감시 대상의 전부가 아니기 때문이다. 우리 제품 전제가
에이전트만 붙이면 쓸 수 있다는 거니까 남의 앱이 들어올 수 있고, 그 앱이 Kafka 를 쓰면
그 서비스 화면이 빈다. 쇼핑몰은 시험 대상일 뿐이다. 토큰 하나 더 쓰는 거라 틀릴 일도 없다.

조건에 OR parent_span_id = '' 까지 넣는 건 지금 안 한다. Elastic 이랑 Datadog,
Pinpoint 는 그걸 다 넣는데 그러면 아무도 안 불렀는데 서비스가 스스로 시작한 일까지
잡힌다. 배치나 스케줄 잡이 거기 들어가니까 언젠가는 필요한데, 지금 우리 데이터에서
거기 걸리는 건 56줄이고 전부 앱 켜질 때 도는 CREATE TABLE 이랑 telemetrygen 이 넣은
시험 데이터다. 운영에서도 파드가 뜰 때마다 생기는 거라 로컬 잡음만이 아니고, 어느
서비스가 느린지 보려는 화면에 CREATE TABLE 점이 찍히는 건 도움이 안 된다. 진짜 배치를
만들 때 넓히는 걸 되돌림 조건에 적어 두자.

B 방식, 조회가 spans 를 직접 읽는 건 안 한다. 원본 표라 느리고 히트맵이 heatmap_1m 을
못 쓰게 되는데 그러면 집계표를 만든 이유가 없어진다.

C 방식, 지금대로 두고 중간 서비스는 안내 문구를 띄우는 것도 안 한다. 스캐터를 만든 이유가
어느 서비스가 느린지 보려는 건데 느린 서비스를 못 고르면 기능이 반쪽이다.

is_root 컬럼을 같이 넣자. toUInt8(parent_span_id = '') 한 줄이면 된다.

이게 필요한 이유는 조건을 넓히면 고객 요청 하나가 여러 줄이 되는데 표만 보고 구분할
방법이 없어지기 때문이다. 요청 하나가 서비스 4개를 지나면 4줄이 되고 count() 가 4를
준다. duration_ms 를 보면 더 분명한데 루트 줄의 240ms 가 고객이 기다린 시간이고 나머지
180 90 40 은 그 안의 부분이라 네 개를 합친 550 은 아무 뜻이 없는 숫자다. 지금은 조건이
그 구분을 해 주고 있는데 조건을 넓히면 사라지니까 조건에서 컬럼으로 옮기는 거다.

문서에 이 표로 요청 수를 세지 마라고 적어 두는 방법도 있는데 그건 막을 장치가 없고
규칙을 모르는 사람이 count() 를 쓰면 틀린 숫자가 화면에 나간다. 컬럼을 두면
service_name 으로 서비스별, is_root = 1 로 고객 요청 수를 한 표에서 다 본다.
조사해 보니 Elastic APM 에 transaction.root 라는 boolean 이 똑같은 용도로 있었다.
설명이 루트 트랜잭션 지표를 식별한다, 트레이스 단위 지표 계산에 쓸 수 있다고 적혀 있다.
표를 둘로 나눈 사례는 하나도 없고 넓게 담고 플래그로 거르는 게 업계 방식이다.

비용도 재 봤는데 985바이트다. 표 전체의 0.04퍼센트고 0과 1 두 가지뿐이라 105대 1로
압축된다. 그리고 조회가 오히려 빨라진다. is_root 는 정렬 키에 없어서 granule 을 건너뛰진
못하는데 ClickHouse 가 자동으로 PREWHERE 로 옮겨서 0.009바이트짜리 플래그를 먼저 읽고
안 맞는 줄은 trace_id 를 아예 안 읽는다. 읽는 바이트가 430KiB 에서 147KiB 로 줄고
3.0ms 가 2.0ms 가 됐다. 손으로 PREWHERE 쓸 필요도 없다.

정렬 키랑 스키핑 인덱스는 건드리지 않는다. 첫 칸에 넣으면 지금 service_name 등호로
걸리는 binary search 가 깨지고 마지막 칸은 효과가 없다. 정렬 키는 표 만들 때만 정할 수
있어서 바꾸려면 표를 다시 만들어야 한다. 스키핑 인덱스는 is_root 가 29퍼센트라 거의 모든
블록에 1이 섞여 있어서 공식 문서가 쓸모없이 비용만 든다고 경고하는 경우에 해당한다.

span_id 는 조회 쪽에 물어보고 정하자. 같은 트레이스에서 같은 서비스가 두 번 호출되면
trace_id 랑 service_name 이 같은 줄이 둘 생기는데 그때 점 하나를 그 구간으로 집으려면
필요하다. 트레이스 상세를 여는 것까지는 trace_id 로 충분하니까 요청 목록에서 줄을 눌러
해당 구간으로 바로 가는 화면을 만들 거면 넣고 아니면 안 넣는다. 재 보니까 겹치는 키가
한 키당 최대 2줄이고 평균 1.00줄이라 드물다. 그리고 trace_id String 이 이미 디스크의
78퍼센트를 먹고 있어서 같은 급 컬럼을 하나 더 넣는 건 is_root 랑 비교할 비용이 아니다.
넣기로 하면 is_root 랑 같이 넣어서 ERD 수정을 한 번에 끝낸다.

MV 를 바꾸는 방법은 ALTER TABLE ... MODIFY QUERY 를 쓴다.

조사가 샌드박스 DB 를 만들어서 여섯 방법을 직접 돌려 봤는데 집계가 비지도 중복이 생기지도
않는 게 이것뿐이었다. DROP VIEW 하고 CREATE 하는 건 운영에서 쓰면 안 된다. MV 를 지우고
4줄 넣고 다시 만들었더니 타깃에 0줄이 들어갔고 에러도 경고도 없었다. 로컬은 down -v 로
리셋하니까 안 보이는데 운영에서는 그 구간 그래프가 영구히 0이 된다. 새 이름으로 MV 를
만들어서 둘을 같이 돌리는 것도 안 된다. 소스 4줄에 타깃 8줄이 들어가서 겹친 기간만큼
정확히 두 배가 되고 우리 transactions 는 평범한 MergeTree 라 되돌릴 방법이 파티션 통째로
버리는 것밖에 없다. EXCHANGE TABLES 는 교환한 뒤에도 두 MV 가 둘 다 계속 돌아서 교체
수단이 아니다.

MODIFY QUERY 쓸 때 조심할 게 하나 있는데 이게 타깃 표 스키마를 검사하지 않는다.
SELECT 에서 컬럼을 빠뜨려도 에러 없이 통과하고 그 컬럼이 타입 기본값으로 채워진다.
service_name 을 빠뜨리면 그 뒤 모든 줄의 서비스 이름이 빈 문자열이 되는데 아무도 모른다.
타깃에 없는 컬럼을 넣어도 조용히 무시되고 타입이 달라도 암묵 캐스팅된다. 그래서 바꾼 뒤에
각 컬럼에 값이 실제로 들어오는지 확인하는 쿼리를 돌리는 단계를 절차에 넣자. 최소한 빈
문자열이나 0이 아닌지 세는 것 하나랑, 서비스가 고르게 나오는지 보는 것 하나다. gateway 만
나오면 안 바뀐 거다.

is_root 를 넣는 순서도 정해져 있다. ADD COLUMN 을 먼저 하고 그 다음에 MV 를 고친다.
거꾸로 하면 조용히 깨진다. 타깃에 없는 컬럼을 MV SELECT 에 넣으면 에러 없이 무시되니까
MV 를 먼저 고치면 그 사이 들어온 줄의 is_root 가 버려진다. 되돌릴 때는 순서가 반대인데
DROP COLUMN 이 MV 가 참조하는 컬럼을 거부하니까 MV 를 먼저 고쳐야 한다.

과거 구간 백필은 안 한다.

ADD COLUMN 의 기본값이 0이라서 지금 들어 있는 3만 줄의 is_root 가 전부 0으로 보이는데
그 줄들은 parent_span_id = '' 조건으로 들어온 거라 사실은 전부 루트다. 즉 과거 구간에서
is_root 가 정확히 거꾸로 거짓이 된다. 그런데도 백필을 안 하는 이유는 지금 배포 전이고
쌓인 게 전부 가짜 데이터라 얻을 게 없는데 위험은 크기 때문이다.

위험이 두 가지인데 하나는 heatmap_1m 이 조용히 두 배가 되는 거다. transactions 에 직접
INSERT 해도 mv_heatmap_1m 이 따라 도는 걸 조사가 실험으로 확인했고, heatmap_1m 은
SummingMergeTree 라서 같은 칸에 들어온 cnt 를 더한다. 원래 100이던 칸이 200이 되는데
줄 수가 안 늘어나니까 눈으로 안 보인다. 중복 제거가 아니라 합산이라서 그렇다.

다른 하나는 두 번 돌리면 그대로 두 배라는 거다. non_replicated_deduplication_window 가
0이고 우리는 복제 표가 아니라서 insert_deduplicate 가 효과가 없다. 되돌릴 수단은
DROP PARTITION 하나뿐이라 줄 단위로 못 지운다.

그래서 백필 대신 이 시각부터 기준이 바뀌었다를 ADR 이랑 ERD 에 적고, is_root 를 믿을 수
있는 시점 경계를 조회 쪽에 알려 주자. 로컬은 down -v 로 다 지우니까 경계가 안 생긴다.
나중에 운영 데이터가 생긴 뒤에 백필이 필요해지면 공식 문서가 권하는 별 표에 채우고
MOVE PARTITION 하는 방식으로 하고, 그 전에 직접 INSERT 가 하위 MV 를 돌리는지 샌드박스에서
한 번 더 재현하자. 조사가 공식 문서 요약과 자기 실험 결과가 반대였는데 원문을 못 봤다고
밝혀 뒀다.

적용 순서는 로컬에서 파일 고치고 down -v 하고 다시 켜고 seed 돌리는 거다. down -v 가
필요한 이유는 옛 줄 때문이 아니라 db/clickhouse/*.sql 이 빈 DB 에서만 돌아서 그냥 켜면
옛 조건 MV 가 그대로 남기 때문이다. PG 볼륨도 같이 지워지니까 seed 를 꼭 다시 돌려야
화면에 뭐가 보인다. 팀원들도 각자 해야 하니까 PR 본문이랑 AGENTS.md 에 적어 두자.

운영 마이그레이션은 별 이슈로 올리자. 조사하다 알게 된 건데 우리 운영에 ClickHouse DDL 을
바꿀 수단이 아예 없다. PG 는 postgres-migrate 컨테이너가 Flyway 로 도는데 CH 는
docker-entrypoint-initdb.d 마운트뿐이고 그게 빈 DB 에서만 돈다. 게다가 우리 파일이 전부
CREATE ... IF NOT EXISTS 라서 004 를 고쳐도 이미 떠 있는 CH 에서는 조용히 건너뛴다.
로컬에서 down -v 가 그걸 가려 주고 있었던 거다.

이번 이슈에서 005_ 파일을 만들어 둘 수도 있는데 그러면 파일은 있는데 그걸 실행할 수단이
없는 상태가 돼서 더 헷갈린다. 수단을 정하는 게 이 이슈보다 큰 일이니까 따로 올리고
AGENTS.md §6 에 적어 두자. 이번에는 004 를 고치고 로컬은 down -v 로 적용한다.

ERD 도 같이 고친다. 레포 사본 docs/design/web-v2/erd.md 의 294줄 트랜잭션(루트 스팬) 과
304줄 MV 조건, 그리고 194줄 spans.parent_span_id 설명에 비어 있으면 루트라 transactions
가 이 조건으로 골라낸다고 적혀 있는데 그 조건이 사라지니까 셋 다 바꾼다. is_root 를
넣으니까 컬럼 목록도 늘어난다. 노션이 정본이라 거기도 같이 간다.

ADR 로 남긴다. 트랜잭션의 뜻이 바뀌는 거라 4요소로 적어야 한다.

되돌리는 조건은 네 가지다. 배치나 스케줄 잡을 만들어서 부모 없는 INTERNAL 루트가 생기면
조건에 OR parent_span_id = '' 를 넣어 넓힌다. 이 표로 전체 요청 수를 세는 화면이 생기고
is_root 로 안 풀리면 표를 둘로 나눈다. 줄이 3.4배로 늘어서 스캐터 조회가 눈에 띄게
느려지면 ORDER BY 를 다시 보거나 격자로 접는 기준인 limit 5000 을 내린다. 한 서비스에
SERVER 스팬이 여러 개 생기는 구성이 들어오면, 서비스 메시 사이드카 같은 게 그런데,
중복 계수가 되니까 그때 다시 본다.

요청 목록 GET /traces/transactions 과 히트맵 GET /traces/heatmap 구현은 조회 파트 몫이라
이번 범위 밖이다. 우리는 표가 채워지게 하는 것까지 한다. ttl_only_drop_parts 를 1로
켜는 것도 조사가 덤으로 제안했는데 이번 변경과 독립적이라 따로 보자.
```
