## 1. 무엇을 하려는 것인가

**배포 7~9단계에 들어가면 바로 막히는 것 셋을 미리 정한다.** 셋 다 "쿠버네티스에서 수집 쪽을 어떻게 올리나" 라서 한 조사로 묶었다.

| 묶음 | 막는 자리 | 지금 상태 |
|---|---|---|
| ㄱ 파드 이름표 | 파드 매니페스트의 환경변수 | **ADR 이 없다.** 쇼핑몰 README 에 예시만 있고 지금 값은 에이전트가 만든 UUID 다 |
| ㄴ 마이그레이션 실행 주체 | 배포 동기화 순서 | **방향만 정해져 있다.** ADR `#49` 가 "쿠버네티스 Job", ADR `#57` 이 "실행 주체는 배포 단계에서" |
| ㄷ 인증서 주입 | Secret 과 볼륨 | **읽는 쪽만 정해져 있다.** ADR `#64` 가 파일 셋을 읽는 것까지, ADR `#62` ⑦ 이 비밀값 경로를 |

### 지금 무엇이 잘못됐나

```
ㄱ  파드가 재시작되면 명부에 새 줄이 하나 생긴다
    배포 교체와 크래시 재시작이 화면에서 똑같이 보인다 ("옛 키 끊김 + 새 키")
    실측 2026-10-05 : shop-order 컨테이너를 재시작하니 agent_id 가 새 UUID 로 바뀜

ㄴ  운영에서 표 정의를 바꿀 수단은 만들었는데(#119) 그것을 돌릴 주체가 없다
    지금 그 일을 하는 것은 compose 의 일회성 컨테이너 둘뿐이다

ㄷ  수집기는 파일 셋을 읽을 준비가 됐는데(#159) 운영에서 그 파일을 어디서 받을지 없다
    로컬은 compose 가 certs/ 에 만든다. 클러스터에는 그 컨테이너가 없다
```

### 이미 정해져 있는 것 (다시 정하지 않는다)

- 마이그레이션 SQL 은 **한 곳**이고 실행은 서비스가 아니라 **전용 컨테이너 한 번**이다 (ADR `#49`). 1b 에서 배포 레포로 옮기고 쿠버네티스 Job 으로 바꾸는 것까지 적혀 있다
- 비밀값은 **Secrets Manager + External Secrets** 다 (ADR `#62` ⑦). Secrets Store CSI 는 "파일 마운트라 Spring 환경변수로 쓰려면 한 단계 더" 라서 기각됐다
- 수집기는 파일 셋 셋(자기 신분증 · 자기 열쇠 · 기관 인증서)을 **기동 때 한 번** 읽고 못 읽으면 기동을 멈춘다. 갱신은 파일을 바꾸고 재시작이다 (ADR `#64`)
- 명부(`agents`)의 주인은 **적재 처리기**다 (ADR `#39`). 파드 식별자는 `service.instance.id` → `k8s.pod.name` → `host.name` 순서로 고른다 (`#58`)

## 2. 꼭 알아야 하는 것 다섯

### 2.1 이름표는 "같은 파드인가" 를 판정하는 유일한 열쇠다

명부에 줄이 하나 생기는 기준이 이 값이다. 그래서 값이 바뀌면 **다른 파드가 새로 떴다**는 뜻이 된다.

```
[기동할 때]
파드 ──▶ 에이전트 : 이름표 값 (환경변수로 주면 그 값, 안 주면 에이전트가 UUID 를 만든다)

[신호를 보낼 때마다]
에이전트 ──[ resource 에 이름표 ]──▶ 수집기 ──▶ 적재 처리기

적재 처리기 검사 ① 미리 가진 명부에서  -> 이 이름표가 이미 있나
적재 처리기 검사 ② 방금 받은 이름표로  -> 없으면 새 줄, 있으면 본 시각만 고친다

없으면 줄이 하나 늘어난다
```

- 지금은 ②가 늘 "없다" 로 떨어진다. 에이전트가 기동마다 새 UUID 를 만들기 때문이다
- 쿠버네티스는 파드 이름을 환경변수로 내려 주는 장치가 있다. 쇼핑몰 README 에 그 예시가 이미 있고, 순서를 틀리면 글자 그대로 들어가며 **경고도 없다**
- 주의 : **컨테이너 재시작과 파드 재생성은 다르다.** 컨테이너만 다시 뜨면 파드 이름이 유지되고, 배포로 파드가 새로 뜨면 새 이름이다. 즉 이름표를 파드 이름으로 맞추면 "크래시 재시작은 같은 줄 · 배포 교체는 새 줄" 이 된다. 그것이 우리가 원하는 구분인지가 ㄱ 의 핵심 질문이다
- `AGENT_DOWN` 경보는 **서비스 단위**로 설계돼 있다. 파드 키가 재시작마다 바뀌어도 서비스에 살아 있는 키가 하나라도 있으면 위반이 아니다. 그래서 이름표를 고쳐도 경보 쪽은 안 깨진다

### 2.2 마이그레이션은 "앱보다 먼저, 한 번만, 실패하면 멈춤" 셋을 동시에 지켜야 한다

compose 는 이 셋을 표시등 하나로 지킨다. 토픽 만들기와 마이그레이션 둘이 끝나야 그 표시등이 켜지고, 앱은 그 뒤에 뜬다.

- 쿠버네티스에는 그런 표시등이 없다. 파드는 서로를 기다리지 않고 동시에 뜬다
- 표 정의가 안 바뀐 상태로 새 코드가 뜨면 **기동이 실패한다** : 우리 서비스는 표와 코드가 다르면 안 뜨게 해 뒀다(검증 모드)
- 반대로 마이그레이션이 **여러 번** 돌면 Flyway 가 "이미 돌렸다" 로 넘기므로 중복 자체는 안전하다. 문제는 여러 개가 **같은 순간에** 돌 때다
- 그리고 **실패를 알아야 한다** : compose 는 종료 코드로 알려 주고 그 뒤 단계가 서지만, 클러스터에서는 실패한 Job 이 조용히 남아 있을 수 있다

### 2.3 인증서는 "비밀값" 과 "파일" 두 성질을 같이 갖는다

열쇠는 비밀값이라 Secrets Manager 에 두는 것이 맞고, 수집기는 그것을 **파일로** 읽는다.

- 그래서 비밀값 경로(ADR `#62` ⑦)를 그대로 쓰면서 마지막 한 걸음만 더하면 된다 : 운영자가 만든 Secret 을 파드에 **파일로 걸어 주는** 것
- ADR `#62` ⑦ 이 Secrets Store CSI 를 기각한 사유("파일 마운트라 환경변수로 쓰려면 한 단계 더")는 **인증서에는 해당하지 않는다.** 인증서는 애초에 파일이 필요하다. 다만 이미 고른 쪽으로도 파일을 줄 수 있어서 도구를 하나 더 들일 이유는 없다
- 요구 수준(`none` · `optional` · `require`)은 **비밀값이 아니다.** 그 값은 설정이고, 두 단계 전환이 그 값 하나를 바꾸는 일이라 비밀값과 다른 자리에 두는 것이 자연스럽다
- 갱신은 자동이 아니다 : 파일을 바꾸고 **재시작**이다. 쿠버네티스는 Secret 이 바뀌면 파일을 갈아 주지만 수집기는 기동 때 한 번만 읽으므로 파드를 다시 떠야 한다

### 2.4 "손으로 만들기" 를 고른 이유가 클러스터에서 반쯤 사라진다

ADR `#64` 는 인증서를 손으로 만들기로 했다. 그때 기각한 쪽이 **클러스터 자동 발급**인데, 기각 사유가 "클러스터가 아직 없다" 였다.

- 클러스터가 생기면 그 사유가 없어진다. 그래서 ㄷ 은 "지금 손으로 넣고 넘어갈까" 와 "이 기회에 자동으로 바꿀까" 의 선택이 된다
- 비교 기준은 둘이다 : 발표까지 남은 일수와, 인증서 기간이 5년이라 **발표 전에 만료가 올 일이 없다**는 사실
- 자동 발급을 들이면 입구 인증서(웹 · API 의 HTTPS)와 **같은 도구**가 된다. 입구 쪽은 이미 그 도구를 쓰기로 정해져 있다(ADR `#62` ⑤)

### 2.5 셋은 서로 거의 독립이지만 한 자리에서 만난다

| | 바뀌는 레포 | 코드 | 다른 둘과 엉키나 |
|---|---|---|---|
| ㄱ 파드 이름표 | 배포(매니페스트) · 쇼핑몰(문서) | 0줄 | 안 엉킨다. 적재 처리기는 이미 그 칸을 읽는다 |
| ㄴ 마이그레이션 | 배포(Job · 동기화 순서) | 0줄 | 앱보다 먼저 떠야 한다는 점만 ㄷ 과 같다 |
| ㄷ 인증서 | 배포(Secret · 볼륨) · 수집기(설정 경로) | 0줄 | 요구 수준을 올리는 시점이 쇼핑몰 파드와 묶인다 |

- 셋 다 **우리 코드는 0줄**이다. 바뀌는 것은 배포 레포의 매니페스트와 문서다
- 그래서 이 조사의 결과물은 "무엇을 적을지" 가 아니라 **"어떤 모양으로 적을지"** 다
