## 1. 무엇을 하려는 것인가

- **배포 7~9단계에 들어가면 바로 막히는 것을 미리 정한다**
- 둘 다 "쿠버네티스에서 수집 쪽을 어떻게 올리나" 라서 한 조사로 묶었다

| 묶음 | 막는 자리 | 지금 상태 |
|---|---|---|
| ㄱ 마이그레이션 실행 주체 | 배포 동기화 순서 | **Job 이라는 것과 둘 자리까지 정해져 있다.** 「PG 마이그레이션은 db/postgres 한 곳 + Flyway」 결정 가 "쿠버네티스 Job", 배포 레포가 `schema/` 를 그 자리로 적어 뒀고 조사 문답에도 "스키마 Job" 이 나온다. 「ClickHouse 마이그레이션도 Flyway」 결정 이 "실행 주체는 배포 단계에서" 로 넘긴 것은 **무엇이 그 Job 을 띄우나**다 |
| ㄴ 인증서 주입 | Secret 과 볼륨 | **읽는 쪽과 비밀값 경로가 정해져 있고 도구도 이미 들어온다.** 「에이전트 인증은 수집기 포트 mTLS」 결정 가 파일 셋을 읽는 것까지, 「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑦ 이 비밀값 경로를, ⑤ 가 입구 인증서용으로 cert-manager 를 이미 채택했다. 열린 것은 **손님 · 서버 인증서를 누가 만들어 어떻게 파드에 넣나**다 |

### 지금 무엇이 잘못됐나

```
ㄱ  운영에서 표 정의를 바꿀 수단은 만들었는데(#119) 그것을 돌릴 주체가 없다
    지금 그 일을 하는 것은 compose 의 일회성 컨테이너 둘뿐이다

ㄴ  수집기는 파일 셋을 읽을 준비가 됐는데(#159) 운영에서 그 파일을 어디서 받을지 없다
    로컬은 compose 가 certs/ 에 만든다. 클러스터에는 그 컨테이너가 없다
```

### 이미 정해져 있는 것 (다시 정하지 않는다)

- **파드 이름표는 쇼핑몰 `#30`(2026-10-05)에서 끝났다**
  - 이름은 **파드 이름 그대로**다
  - 환경변수로 넣고, 쿠버네티스는 Downward API 다
  - 네임스페이스를 붙이는 꼴은 그때 기각했다(한 네임스페이스 안의 파드 이름은 이미 유일하다)
  - 결정 기록은 `monimo-shop` `docs/seungjo/30-service-instance-id/`
- 마이그레이션 SQL 은 **한 곳**이다 (「PG 마이그레이션은 db/postgres 한 곳 + Flyway」 결정)
  - 실행은 서비스가 아니라 **전용 컨테이너 한 번**이다
  - 1b 에서 배포 레포로 옮기고 쿠버네티스 Job 으로 바꾸는 것까지 적혀 있다
- 비밀값은 **Secrets Manager + External Secrets** 다 (「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑦)
  - Secrets Store CSI 는 "파일 마운트라 Spring 환경변수로 쓰려면 한 단계 더" 라서 기각됐다
- 수집기는 파일 셋(자기 신분증 · 자기 열쇠 · 기관 인증서)을 **기동 때 한 번** 읽는다 (「에이전트 인증은 수집기 포트 mTLS」 결정)
  - 못 읽으면 기동을 멈춘다
  - 갱신은 파일을 바꾸고 재시작이다
- 명부(`agents`)의 주인은 **적재 처리기**다 (「규칙 · 채널 API 주인은 API 서버, 탐지는 읽기만」 결정)
  - 파드 식별자는 `service.instance.id` → `k8s.pod.name` → `host.name` 순서로 고른다 (`#58`)
- 마이그레이션 파일이 **배포 레포 `schema/` 로 옮겨 간다**(1b 부터)
  - 배포 레포 문서 둘이 그 폴더를 "ClickHouse DDL · PG 마이그레이션" 으로 적어 뒀다
- **cert-manager 가 이미 클러스터에 들어온다**(「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑤, 배포 레포 `infra/`)
  - 입구 인증서(웹 · API 의 HTTPS)를 공개 도메인 검증으로 받는 쓰임이다

## 2. 꼭 알아야 하는 것 다섯

### 2.1 마이그레이션은 "앱보다 먼저, 한 번만, 실패하면 멈춤" 셋을 동시에 지켜야 한다

- **이미 Flyway 로 되어 있다**
  - 빠진 것은 도구가 아니라 **그 도구를 켜는 손**이다
  - 순서대로 적용 · 이미 한 것 건너뛰기 · 바뀐 파일 막기는 Flyway 가 한다
  - 지금 그 Flyway 를 돌려 주는 것은 compose 이고 클러스터에는 그 역할이 비어 있다
- **Job 이 무엇인가** : 쿠버네티스에서 "한 번 돌고 끝나는 일" 을 맡는 물건이다
  - 평소 파드는 계속 살려 두는 것(죽으면 다시 띄운다)이다
  - Job 은 끝까지 돌아 성공하면 더 안 띄운다
  - 우리 compose 에 이미 같은 성격이 **넷** 있다 : 토픽 만들기 · PG 마이그레이션 · ClickHouse 마이그레이션 · 인증서 만들기
    - 전부 `restart: "no"` 다
  - 그 넷을 쿠버네티스로 옮긴 이름이 Job 이다
    - 그래서 "모양은 정해졌다" 는 **그 컨테이너 정의를 그대로 옮기면 된다**는 뜻이다
- 정해진 것은 그 모양과 **파일을 둘 자리**까지다
  - 열린 것은 그 Job 을 **무엇이 언제 띄우나**다
  - 배포 쪽 조사에도 동기화 훅 · 웨이브를 다룬 줄이 하나도 없다(확인 완료)
- compose 는 이 셋을 표시등 하나로 지킨다
  - 네 Job 이 **성공으로 끝나야** 그 표시등이 켜지고, 앱은 그 뒤에 뜬다
- 쿠버네티스에는 그런 표시등이 없다
  - 파드는 서로를 기다리지 않고 동시에 뜬다
- 표 정의가 안 바뀐 상태로 새 코드가 뜨면 **기동이 실패한다**
  - 우리 서비스는 표와 코드가 다르면 안 뜨게 해 뒀다(검증 모드)
- 반대로 마이그레이션이 **여러 번** 돌면 Flyway 가 "이미 돌렸다" 로 넘긴다
  - 그래서 중복 자체는 안전하다
  - 문제는 여러 개가 **같은 순간에** 돌 때다
- 그리고 **실패를 알아야 한다**
  - compose 는 종료 코드로 알려 주고 그 뒤 단계가 선다
  - 그런데 클러스터에서는 실패한 Job 이 조용히 남아 있을 수 있다

### 2.2 인증서는 "비밀값" 과 "파일" 두 성질을 같이 갖는다

- `#159`(수집기 mTLS : 손님 신분증 검사) 가 이미 한 것과 비어 있는 것을 먼저 갈라야 한다
  - 빈 것은 **클러스터 쪽 절반**이다

```
[로컬에서 준비할 때 (한 번)]
인증서 Job ──▶ 내 컴퓨터 폴더 ./certs : 기관 1 · 서버 1 · 손님 5 를 만든다
compose  ──▶ 수집기에 그 폴더를 /certs 로 걸어 준다
compose  ──▶ 쇼핑몰 넷에도 같은 폴더를 /certs 로 걸어 준다

[클러스터에서는]
만드는 쪽 : 그 Job 이 없다
거는 쪽   : 그 폴더가 없다
읽는 쪽   : 그대로 쓴다 (경로만 주면 된다)
```

- **파일 넷은 이미 만들었다**
  - 남은 일은 새로 만드는 것이 아니라 **이미 만든 것을 옮기는 것**이다
- 그런데 **compose 가 공짜로 준 전제 둘이 깨진다**
  - 그것이 이 묶음의 알맹이다
- **폴더 하나를 모두가 같이 본다**
  - 클러스터에는 그런 폴더가 없다
  - 수집기와 쇼핑몰은 다른 파드이고 서로의 디스크를 못 본다
- **그 폴더가 내 컴퓨터에 남아 있다**
  - 파드 안에서 만들면 파드가 다시 뜰 때 사라진다
  - 그러면 **기관이 매번 새로 생겨** 어제 심은 손님 신분증이 전부 못 붙는다
- 열쇠는 비밀값이라 Secrets Manager 에 두는 것이 맞다
  - 레포는 다섯 개가 전부 공개다
  - 수집기는 그것을 **파일로** 읽는다
- 그래서 비밀값 경로(「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑦)를 그대로 쓰면서 마지막 한 걸음만 더하면 된다
  - 만들어진 Secret 을 파드에 **파일로 걸어 주는** 것
- 「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑦ 이 Secrets Store CSI 를 기각한 사유("파일 마운트라 환경변수로 쓰려면 한 단계 더")는 **인증서에는 해당하지 않는다**
  - 인증서는 애초에 파일이 필요하다
  - 다만 이미 고른 쪽으로도 파일을 줄 수 있어서 도구를 하나 더 들일 이유는 없다
- 요구 수준(`none` · `optional` · `require`)은 **비밀값이 아니다**
  - 그 값은 설정이다
  - 두 단계 전환이 그 값 하나를 바꾸는 일이라 비밀값과 다른 자리에 두는 것이 자연스럽다
- 갱신은 자동이 아니다 : 파일을 바꾸고 **재시작**이다
  - 쿠버네티스는 Secret 이 바뀌면 파일을 갈아 준다
  - 그런데 수집기는 기동 때 한 번만 읽으므로 파드를 다시 떠야 한다
- **개수가 는다**
  - 지금 셈은 비밀 5개(월 약 $2)다
  - 인증서는 기관 1 · 서버 1 · 손님 서비스마다 1 이다
  - 배포 조사가 "경로 접두사로 묶으면 한 번에 가져와 호출 수가 준다" 를 적어 뒀다
  - 그래서 **한 비밀에 파일 여럿을 담는 모양**이 자연스럽다

### 2.3 "손으로 만들기" 를 고른 이유가 클러스터에서 반쯤 사라진다

- 「에이전트 인증은 수집기 포트 mTLS」 결정 는 인증서를 손으로 만들기로 했다
  - 그때 기각한 쪽이 **클러스터 자동 발급**이다
  - 기각 사유가 "클러스터가 아직 없다" 였다
- 클러스터가 생기면 그 사유가 없어진다
  - 그래서 ㄴ 은 "지금 손으로 넣고 넘어갈까" 와 "이 기회에 자동으로 바꿀까" 의 선택이 된다
- 비교 기준은 둘이다
  - 발표까지 남은 일수
  - 인증서 기간이 5년이라 **발표 전에 만료가 올 일이 없다**는 사실
- 자동 발급을 들이는 것이 **도구를 새로 들이는 일이 아니다**
  - 그 도구(cert-manager)는 입구 인증서 때문에 이미 클러스터에 들어온다(「EKS 배포 기반 : Spot · NAT · Traefik」 결정 ⑤ · 배포 레포 `infra/`)
- 다만 **쓰임이 다르다**
  - 입구 쪽은 공개 도메인을 검증해 공개 기관 인증서를 받는 길이고, 손님 신분증은 그 길로 못 만든다
  - 우리 기관을 클러스터 안에 두고(사설 발급자) 거기서 찍는 쓰임이라 설정이 따로다
  - 같은 도구를 두 가지로 쓰는 셈이다

### 2.4 둘은 서로 거의 독립이고 우리 코드는 0줄이다

| | 바뀌는 레포 | 코드 | 다른 하나와 엉키나 |
|---|---|---|---|
| ㄱ 마이그레이션 | 배포(Job · 동기화 순서) | 0줄 | 앱보다 먼저 떠야 한다는 점만 같다 |
| ㄴ 인증서 | 배포(Secret · 볼륨) · 수집기(설정 경로만) | 0줄 | 요구 수준을 올리는 시점이 쇼핑몰 파드와 묶인다 |

- 바뀌는 것은 배포 레포의 매니페스트와 문서다
  - 그래서 이 조사의 결과물은 "무엇을 적을지" 가 아니라 **"어떤 모양으로 적을지"** 다

### 2.5 파드 이름표는 이미 끝났다 : 끝난 것과 남은 것을 가른다

- 처음에 이것을 열린 결정으로 적었는데 틀렸다

| | 상태 |
|---|---|
| 값을 무엇으로 할까 | **끝났다.** 파드 이름 그대로 (쇼핑몰 `#30`) |
| 어떻게 넣을까 | **끝났다.** 환경변수, 쿠버네티스는 Downward API. 순서를 틀리면 글자 그대로 들어가고 경고가 없다는 함정까지 쇼핑몰 README 에 적혀 있다 |
| 네임스페이스를 붙일까 | **끝났다.** 안 붙인다. 두 네임스페이스가 같은 백엔드로 들어오면 그때 붙인다 |
| 남은 것 | 매니페스트에 **그대로 옮겨 적는 일**뿐이다. 배포 단계의 손일이고 결정이 아니다 |

- 그리고 **백엔드 메모가 낡았다**
  - `AGENTS.md` 의 실측 메모가 "파드 이름으로 채우면 키가 유지된다 : 값을 정할 때 같이 확인" 으로 끝난다
  - 그 메모는 2026-10-05 알림 파트가 적은 것이고 쇼핑몰 `#30` 이 **같은 날 늦게** 머지됐다
  - 이 PR 에서 그 한 줄을 고친다
- 받아들인 것 하나 : 파드 이름을 쓰면 **배포 교체마다 명부 줄이 는다**
  - 컨테이너만 재시작하면 같은 줄이고 파드가 새로 뜨면 새 줄이다
  - `AGENT_DOWN` 이 서비스 단위라 경보는 안 깨진다

   - 내가 **ADR 유무로 결정 유무를 판정**한 것이 틀렸다
   - 승조가 "이건 이미 끝낸 거 아니였나" 라고 되물어 드러났고, 묶음이 셋에서 둘로 줄었다
   - 찾아보니 백엔드 메모 한 줄이 낡아 있던 것이 내가 헷갈린 원인이기도 하다
3. **2절 다섯 개를 "열린 것" 처럼 적었는데 셋은 이미 된 것이었다**
   - 승조가 하나씩 되물어 드러났다
     - ① 마이그레이션은 **Flyway 로 이미 되어 있다**(빠진 것은 그것을 켜는 손)
     - ② 인증서를 파일로 읽는 것은 `#159` 에서 **했다**(금고에는 아무것도 안 넣었고 AWS 계정 자체가 없다)
     - ③ 손님 신분증 넷도 **이미 만들었다**(내 컴퓨터 폴더에 있고 클러스터에 없을 뿐이다)
   - 그리고 ④ 자동 발급은 **안 하기로** 했다(토이 프로젝트 · 기간 5년)
   - 그래서 열린 것이 **순서 장치 하나와 옮기기 하나**로 줄었다
   - 내가 "정해진 것" 과 "해 본 것" 을 같은 칸에 적어서 둘 다 안 된 것처럼 보였다
2. **ㄴ 과 ㄷ 의 "정해진 정도" 도 과소평가했다**
   - 승조가 "ㄴ하고 ㄷ도 확인해 줘" 라고 해서 뒤져 보니 조각이 하나씩 더 있었다
     - 마이그레이션은 **둘 자리(`schema/`)까지** 정해져 있고 "스키마 Job" 이라는 말이 조사 문답에 이미 있다
     - 인증서는 **발급 도구(cert-manager)가 입구 때문에 이미 클러스터에 들어온다**
   - 둘 다 열린 것은 맞지만 열린 폭이 내가 적은 것보다 좁았다
   - 반대로 **동기화 훅 · 웨이브는 양쪽 레포에 한 줄도 없어** ㄱ 의 핵심은 진짜로 비어 있다

## 5. 선택지 정리

### 5.0 순서가 왜 필요한가 (이유 셋)

- 승조 질문 : "결국 마이그레이션 이후에 서버가 떠야 해서 그런 거지?"
  - 맞다
  - 다만 걸리는 자리가 셋이다

| 먼저 끝나야 하는 것 | 안 끝나면 | 근거 |
|---|---|---|
| PG · ClickHouse 마이그레이션 | 앱이 **기동 실패**한다. 표와 코드가 다르면 안 뜨게 해 뒀다(`ddl-auto: validate`, 다섯 모듈 전부) | 「PG 접근은 JPA」 결정 가드레일 · 「PG 마이그레이션은 db/postgres 한 곳 + Flyway」 결정 |
| Kafka 토픽 만들기 | 수집기는 뜨지만 **발행이 실패**한다. 토픽 자동 생성을 꺼 뒀다(`KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"`). 에이전트에 `UNAVAILABLE` 로 돌려보내므로 유실은 아니고 수집이 안 되는 상태 | `compose.yaml` · 「DLQ 는 Kafka 토픽 · S3 는 ClickHouse cold 계층」 결정 |
| 인증서 (요구 수준을 켠 뒤) | 수집기가 **기동 실패**한다. 파일을 못 읽으면 평문으로 대신 뜨지 않게 했다 | 「에이전트 인증은 수집기 포트 mTLS」 결정 ⑨ |

- **중요한 단서 하나** : 순서 장치가 없어도 쿠버네티스는 죽은 파드를 계속 다시 띄우므로 **결국은 뜬다**
  - 그래서 이 장치의 값은 "뜨는가" 가 아니라 셋이다
- 배포가 **성공했다고 착각하지 않는 것**
  - 실패한 Job 이 조용히 남는 것을 막는다
- 재시작 루프 동안 **에이전트 버퍼가 버티는 시간**을 낭비하지 않는 것
  - 넘치면 그때는 사라진다
- 사람이 **원인을 빨리 아는 것**
  - "기동 실패 반복" 이 아니라 "마이그레이션 실패" 로 보이게

### 5.1 순서 장치 네 갈래

| 갈래 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **A 손으로** | Job 을 먼저 돌려 끝난 것을 보고 앱을 올린다 | 도구 0개 · 지금 당장 된다 · 실패가 종료 코드로 눈앞에 보인다 · 발표까지 배포 횟수가 적다 | 사람이 빠뜨리면 조용히 어긋난다 · **자동 배포와 어긋난다** : 배포 도구는 git 에 새 매니페스트가 들어오면 사람을 기다리지 않는다 · 재현이 기억에 의존 |
| **B 배포 도구 훅** | 동기화할 때 앱보다 먼저 Job 을 돌리고 실패하면 동기화를 멈춘다 | 자동 · git 에 적혀 재현된다 · 실패가 **배포 실패로** 보인다 · 앱보다 먼저를 도구가 보장 | 그 도구(Argo CD)를 먼저 세워야 쓴다(일정 10/25~27) · 훅 문법과 끝난 Job 치우는 규칙을 배운다 · 로컬 쿠버네티스 구간(10/18~21)에 그 도구를 안 올리면 그때는 못 쓴다 |
| **C 차트 훅** | 차트를 깔 때 먼저 돌린다 | 배포 도구 없이도 된다(차트만으로) · 앱과 한 묶음으로 관리 | 배포 도구와 같이 쓰면 **훅이 두 겹**이 된다(두 도구가 같은 일을 각자 방식으로 한다, **미확인** : 겹칠 때 거동을 확인해야 한다) · 실패 때 되돌리는 규칙이 헷갈린다 |
| **D 기다리는 초기 컨테이너** | 앱 파드 앞에 작은 컨테이너를 두고 "장부가 N 번까지 적용됐나" 를 확인해 아니면 기다린다 | 앱이 **스스로** 기다려 도구와 무관 · 로컬과 운영이 같은 방식 | 서비스마다 같은 것이 붙는다 · 마이그레이션이 영원히 안 오면 영원히 기다린다(한도 필요) · 「PG 마이그레이션은 db/postgres 한 곳 + Flyway」 결정와 경계가 가깝다(돌리는 것이 아니라 기다리는 것이라 위반은 아니다) |

- A 와 B 는 **배타가 아니다**
  - 로컬 쿠버네티스 구간은 A, 배포 도구가 서면 B 로 옮기는 길이 있다
- D 는 A · B · C 중 무엇을 골라도 **덧붙일 수 있다**
  - 다만 지금 표가 바뀌는 일이 드물어 값이 작다

### 5.2 인증서 옮기기 세 갈래 (주고받는 것)

- 전제 : **새로 만들지 않는다**
  - 이미 만든 파일을 금고에 올려 파드에 파일로 걸 뿐이다
  - 자동 발급은 안 한다(2.3)

| 갈래 | 금고에 두는 모양 | 장점 | 단점 |
|---|---|---|---|
| **ㄱ 한 묶음** | 비밀 하나에 기관 · 서버 · 손님 전부 | 이름 하나 · 꺼내는 호출 1회 · 매니페스트가 가장 짧다 | **쇼핑몰 파드가 수집기 열쇠까지 받는다**(최소 권한이 깨진다) · 하나를 갈면 전부 재시작 · 손님 하나가 샜을 때 범위 판단이 섞인다 |
| **ㄴ 두 묶음** | 수집기용(기관 · 서버 · 서버 열쇠) · 쇼핑몰용(기관 · 손님 넷) | **서버 열쇠를 손님에게 안 준다**(최소 권한의 핵심) · 한쪽을 갈면 그쪽만 재시작 · 이름 둘이라 관리가 가볍다 | 쇼핑몰 넷이 서로의 신분증을 본다(같은 레포 · 같은 배포라 신뢰 경계가 같다) |
| **ㄷ 역할마다** | 기관 · 서버 · 손님 서비스마다 하나 (여섯) | 유출 범위가 가장 좁다 · 한 파드만 재시작 | 이름 여섯 · ESO 설정과 매니페스트가 여섯 벌 · 지금 쇼핑몰 넷은 신뢰 경계가 같아 **얻는 것이 적다** |

- **비용은 결정자가 아니다**
  - 비밀 하나에 월 약 $0.40 이라 둘이면 $0.8, 여섯이면 $2.4 다
  - 예산 월 $167 ~ 220 에서 차이가 안 난다
- 결정자는 둘이다
  - **서버 열쇠를 손님 파드에 주느냐**
  - **하나 갈 때 몇이 재시작되느냐**
- 요구 수준(`none` · `optional` · `require`)은 비밀이 아니라 설정이라 **금고가 아닌 자리**에 둔다
  - 두 단계 전환이 그 한 줄을 바꾸는 일이다

| 무엇 | 정한 것 | 사유 |
|---|---|---|
| 순서 장치 | **손으로 시작** (Job 넷을 먼저 돌려 성공을 보고 앱을 올린다) | 로컬 구간에 배포 도구가 없다 · 도구 0개 · 실패가 종료 코드로 바로 보인다 |

| 인증서 묶음 | **둘** : 수집기용 · 쇼핑몰용 | 서버 열쇠를 손님 파드에 주지 않는 선을 지키면서 이름이 둘뿐이다 |
| 요구 수준 | **금고 밖** (설정) | 비밀이 아니다. 두 단계 전환이 그 한 줄을 바꾸는 일이다 |

### 이 선택이 만드는 것

- **발표 전 구간에서는 사람이 순서 장치다**
  - 순서 장치의 값이 "결국 뜨는가" 가 아니라 "배포 실패를 알아채는 것" 이다
  - 사람이 지켜보는 동안은 사람이 그 역할을 한다
- **옮기는 비용을 미리 낮춰 둔다**
  - Job 정의를 compose 컨테이너 모양 그대로 두면 나중에 훅 표시만 더하면 된다
  - A 에서 B 로 가는 길에 다시 설계할 것이 없다
- **금고에 들어가는 것이 정해진다**
  - 수집기 묶음 : 기관 인증서 · 서버 신분증 · 서버 열쇠
  - 쇼핑몰 묶음 : 기관 인증서 · 손님 신분증 넷 · 손님 열쇠 넷
  - 점검용과 만료 시험용 벌은 로컬 전용이라 안 넣는다
- **기관 열쇠는 보관만 한다**
  - 금고에 두되 어떤 파드에도 걸지 않는다
  - 찍는 데만 쓰고 클러스터는 쓸 일이 없다
  - 넣는 이유는 분실 대비 하나다

### 안 바꾸는 것 (범위 밖)

- **매니페스트와 차트를 쓰지 않는다**
  - 배포 레포 몫이고 이 이슈는 정하는 것까지다
- **우리 코드 0줄**
  - 수집기는 파일 경로만 받으면 되고 그 설정은 이미 있다
- **인증서를 새로 만들지 않는다**
  - 로컬에서 이미 만든 것을 올린다
- **자동 발급을 들이지 않는다**
  - 되돌림 조건으로만 남긴다
