# 리서치 : 샘플링 비율을 PG 에서 읽는다

- 2026-10-08 / 관련 이슈 `#121` / ADR `#33` · `#37`(Q23) · `#38` · `#41` 이 이미 정해 둔 것을 코드로 옮기는 일
- 쓴 도구: 레포 직접 읽기(수집기 · 적재 처리기 · API 서버 · DDL · compose) · 로컬 PG 실조회

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

---

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 100건 중 몇 건을 남길지 정하는 숫자가 **수집기 이미지 안에 박혀 있다.** 바꾸려면 파일을 고치고 빌드하고 다시 배포해야 한다.
- **그래서 무엇을 만드나** : 수집기가 그 숫자를 **PostgreSQL 에서 30초마다 읽어** 쓰게 한다. 화면에서 숫자를 바꾸면 30초 안에 반영된다.
- **안 하면 어떻게 되나** : 운영 중에 트래픽이 늘어 수집기가 버거울 때 비율을 내리는 방법이 **재배포뿐**이다. 팀이 정한 핵심기능 5("재배포 없이 샘플링률과 경보 임계값을 바꾼다")의 절반이 안 된 상태로 남는다.

| | |
|---|---|
| 건드리는 모듈 · 파일 | `collector/` : `sampling/SamplingProperties.kt` · `sampling/TraceSampler.kt` · 새 PG 읽기 어댑터 1개 · `application.yml` · `application-local.yml` · `TraceSamplerTest` |
| 같이 볼 것 | `scripts/seed/postgres-applications.sql`(로컬 비율) · `compose.yaml`(수집기 환경변수) |
| 건드리지 않는 것 | 고르는 방식 자체(trace_id 해시) · 카나리 예외(ADR `#41`) · 헬스체크 거르기와의 순서 · 메트릭 · 로그 · `application_configs` 표 구조 · API 서버의 설정 수정 API |
| 이 이슈 범위 밖 (후속) | 로그 등급 하한을 PG 로 옮기기(지금은 수집기 전역 env, ADR `#38`) · 헬스체크 거를 주소를 PG 로 옮기기(ADR `#50` 기각 ④ : "K(샘플링 비율을 PG 로)가 길을 뚫으면 그때 옮길 수 있다") · 수집기 여러 대일 때의 설정 동기화 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- 샘플링은 에이전트가 아니라 **수집기**가 한다. 에이전트는 100% 보내고 수집기가 1% 만 남긴다 (ADR `#33`).
- 그 1% 라는 숫자는 지금 `application.yml` 에 있고, 로컬에서는 전부 통과하도록 1.0 으로 덮어써 둔 것을 기억한다.
- 설정을 재배포 없이 바꾸는 것이 핵심기능 5 라는 것은 알았지만, 샘플링률이 그 안에 들어간다는 것은 잊고 있었다.

**알고 싶었던 것**

① 왜 하필 `trace_id` 로 고르나. 주사위를 굴리면 안 되나
② "PG 에서 읽는다" 가 정확히 무엇을 읽는다는 것인가. 표에 그 칸이 이미 있나
③ 비율이 서비스마다 다르면 어떻게 되나
④ PG 가 죽으면 수집이 멈추나
⑤ 로컬에서는 전부 통과로 쓰고 있는데 PG 를 읽기 시작하면 그게 어떻게 되나

## 2. 작업하기 전에 알아야 하는 것

### 2.1 샘플링 : 왜 버리나, 왜 수집기에서 버리나

쇼핑몰 요청 하나가 들어오면 OTel 에이전트가 **그 요청이 지나간 구간마다 스팬 한 개**를 만든다. 요청이 gateway → order → payment 를 지나면 스팬이 대여섯 개 생긴다. 이걸 전부 저장하면 요청 수의 몇 배가 ClickHouse 에 쌓인다. 그래서 **일부만 남기고 버린다.** 그 비율이 샘플링 비율이다.

버리는 자리는 세 군데가 가능했다.

| 어디서 버리나 | 우리는 | 왜 |
|---|---|---|
| 에이전트 (헤드 샘플링) | **안 쓴다** | 쇼핑몰 4곳 설정을 건드려야 하고, "에이전트만 붙이면 된다" 는 제품 전제가 깨진다 |
| **수집기** | **여기서 한다** | 우리 코드라 비율을 우리가 쥔다. ADR `#33` |
| 적재 처리기 · ClickHouse | 안 쓴다 | 이미 Kafka 와 네트워크를 다 쓴 뒤라 아끼는 효과가 없다 |

에이전트는 `always_on`(100% 전송)이고 고르는 일은 전부 수집기 몫이다. 코드는 `collector/.../sampling/TraceSampler.kt` 한 파일이다.

### 2.2 주사위가 아니라 `trace_id` 해시인 이유 (①)

**핵심은 수집기가 트레이스를 모아 보지 않는다는 점이다.** 스팬은 서비스마다 따로, 에이전트 배치 주기(기본 5초)에 맞춰 **따로따로** 도착한다.

```
요청 1건 (trace_id = abc)
  shop-gateway 의 스팬  ──▶ 수집기        (따로 도착)
  shop-order 의 스팬    ──▶ 수집기        (5초 뒤일 수도 있다)
  shop-payment 의 스팬  ──▶ 수집기        (또 따로)
```

여기서 **주사위를 굴려** 1% 를 고르면 gateway 스팬만 당첨되고 나머지는 꽝이 되어, 머리만 있고 몸통이 없는 기록이 남는다. 쓸모가 없다.

그래서 주사위를 쓰지 않고 **`trace_id` 를 숫자로 바꿔 경계선과 비교**한다. `trace_id` 는 그 요청의 모든 스팬이 **똑같이 들고 있는 번호**다.

```kotlin
// TraceSampler.kt:69
return abs(hashOf(span.traceId)) < upperBound
```

```
trace_id abc 를 숫자로 → 5
경계선(비율 1%) → 1
5 > 1 → 버린다

gateway 스팬  : abc → 5 → 버림
order 스팬    : abc → 5 → 버림     (똑같이)
payment 스팬  : abc → 5 → 버림     (똑같이)
```

**스팬이 언제 어디서 도착해도 판정이 같다.** 한 트레이스는 전부 남거나 전부 버려진다. 모아 볼 필요가 없다. `span_id` 도, 도착 시각도, 무작위도 안 본다. `trace_id` 하나만 본다.

숫자로 바꾸는 방법은 `trace_id` 16바이트 중 **뒤 8바이트를 그대로 정수로 읽는 것**이다(`TraceSampler.kt:78`). `trace_id` 가 무작위라 그 숫자도 고르게 퍼진다. OTel 의 비율 샘플러와 같은 방식이라, 나중에 에이전트 쪽 샘플링으로 되돌려도 기준이 같다.

**이 방식이 성립하는 조건은 경계선이 같다는 것이다.** 비율이 서비스마다 다르면 경계선이 달라지고, 같은 숫자 5 가 gateway 에서는 밖 · order 에서는 안이 된다. 2.9 와 5절에서 다시 본다.

예외는 하나, **카나리**다. `trace_state` 에 `monimon=canary` 가 있으면 비율을 건너뛰고 무조건 남긴다. 파수꾼이 보낸 것이라 버리면 장애 판정 자체가 불가능하다 (ADR `#41`).

### 2.3 그 숫자가 지금 어디에 있나 (세 군데다)

비율 하나를 정하는 자리가 지금 셋이고, 아래가 위를 덮는다.

| 순위 | 어디 | 값 | 누가 쓰나 |
|---|---|---|---|
| 1 | `collector/src/main/resources/application.yml:31` | `0.01` | 운영 기본값 |
| 2 | `application-local.yml:19` | `1.0` | `./gradlew :collector:bootRun --args='--spring.profiles.active=local'` |
| 3 | `compose.yaml:179` `MONIMO_COLLECTOR_SAMPLING_RATIO` | `${COLLECTOR_SAMPLING_RATIO:-1.0}` | 컨테이너로 띄운 수집기. `.env` 로 바꾼다 |

세 값이 전부 **전역 하나**다. 서비스를 가리지 않는다. `SamplingProperties` 가 `ratio: Double` 한 칸뿐이다.

그리고 세 자리 모두 **이미지 또는 레포 파일**이다. 운영에서 바꾸려면 배포가 필요하다. 이것이 이 이슈가 메우려는 틈이다.

### 2.4 PG 쪽은 이미 다 준비돼 있다 (②)

읽을 칸은 `application_configs.sampling_rate` 다. `db/postgres/config/V202609271938__create_application_configs.sql` :

```sql
application_id   BIGINT       NOT NULL UNIQUE REFERENCES applications (id),
sampling_rate    NUMERIC(5,4) NOT NULL CHECK (sampling_rate >= 0 AND sampling_rate <= 1),
version          INT          NOT NULL DEFAULT 1,
```

- `UNIQUE` 라 **서비스당 한 줄**이다 (ADR `#38` : 설정 단위는 앱 단위만, 파드별 오버라이드 없음).
- `NUMERIC(5,4)` 라 소수 넷째 자리까지다. `0.0100` = 100건 중 1건.
- 줄은 **서비스를 등록할 때 같이 생긴다.** 기본값은 `ApplicationConfig.DEFAULT_SAMPLING_RATE = 0.0100`.
- 고치는 API 도 있다 : `ApplicationConfigService.update`. `expected_version` 을 받아 다르면 `409 CONFIG_VERSION_CONFLICT`. 두 사람이 동시에 고쳐 한쪽이 묻히는 것을 막는다.
- 그 DDL 주석 첫 줄에 이미 적혀 있다 : **"소유: API 서버 (ADR #36), 수집기가 30초 캐시로 읽는다 (ADR #37)"**. 이 이슈를 예상해 둔 자리다.

즉 **표도 API 도 기본값도 다 있고, 수집기가 그 칸을 읽는 코드만 없다.**

### 2.5 데이터는 어디로 흐르나

```
                                    ┌──────────────────────────┐
                                    │ PG application_configs   │
                                    │  shop-gateway   0.0100   │
                                    │  shop-order     0.0100   │
                                    └────────────┬─────────────┘
                                   30초마다 읽기 │ (이 선이 지금 없다)
                                                 ▼
에이전트 100% ──▶ 수집기 :4317 ──▶ 헬스체크 거르기 ──▶ 샘플링 ──▶ Kafka raw ──▶ 적재 ──▶ CH
                                                        ▲
                                         지금은 application.yml 값 하나

사람이 바꾸는 길 :  화면 ──▶ API 서버 PUT /applications/{uuid}/config ──▶ PG
```

| 질문 | 답 |
|---|---|
| 왜 API 서버를 거치지 않고 PG 를 직접 읽나 | **API 서버 장애가 수집기 샘플링까지 번지기 때문이다.** 수집 경로 가용성 목표는 99.9%, 조회는 99.5% 다. 수집이 조회에 매달리면 더 낮은 쪽으로 끌려 내려간다 (ADR `#37` Q23 기각 사유) |
| 수집기가 PG 에 쓰나 | **안 쓴다. 읽기만 한다.** 표 주인은 API 서버다 (ADR `#20` · `#36`) |
| 버려진 스팬은 어디 남나 | **아무 데도 안 남는다.** Kafka 에 들어가기 전에 버린다. 그게 아끼는 이유다 |
| 바꾼 값이 언제 듣나 | 최대 30초 뒤 (캐시 주기) |
| PG 가 죽으면 (④) | **마지막으로 읽은 값을 그대로 쓴다.** 수집은 계속 돈다 (ADR `#37` Q23) |

### 2.6 `service.name` 은 스팬에 없다

"서비스별 비율" 로 가려면 스팬을 보고 **어느 서비스 것인지** 알아야 한다. 그런데 OTLP 는 세 겹이고 서비스 이름은 맨 바깥에 **한 번만** 붙는다.

```
ExportTraceServiceRequest
└─ ResourceSpans          ← resource 속성에 service.name = "shop-order"
   └─ ScopeSpans
      └─ Span             ← trace_id · span_kind · parent_span_id 는 여기
```

같은 서비스의 스팬 수백 개가 `ResourceSpans` 하나에 묶여 오므로 이름을 중복해 담지 않는 것이다. 지금 함수는 스팬만 받는다.

```kotlin
fun keep(span: Span): Boolean          // 지금. 서비스를 모른다
```

`sample()` 은 이미 세 겹을 다 돌고 있으니(`TraceSampler.kt:46`) 바깥 겹에서 이름을 한 번 읽어 안쪽 판정에 내려 주면 된다. 다만 **`keep()` 의 서명이 바뀌고 `TraceSamplerTest` 의 `keep(span)` 호출 7군데가 같이 바뀐다.**

`agent_id`(파드 식별자)를 고를 때 적재 처리기가 쓰는 순서(`service.instance.id` → `k8s.pod.name` → `host.name`)와 같은 자리에서 `service.name` 을 읽는다.

### 2.7 "30초 캐시" 가 무슨 뜻인가, 그리고 베낄 선례

스팬 하나 판정할 때마다 PG 를 치면 초당 수천 번이 된다. 그래서 **값을 한 번 읽어 들고 있다가 30초 지나면 다시 읽는다.** 이것이 캐시다.

적재 처리기가 **똑같은 일**을 이미 하고 있다. `ingester/.../outbound/postgres/PostgresServiceCatalog.kt` 는 `applications` 의 이름 목록을 30초 캐시로 읽는다.

```kotlin
private val snapshot = AtomicReference(Snapshot(emptySet(), Instant.EPOCH))

override fun activeNames(): Set<String> {
    val current = snapshot.get()
    if (Duration.between(current.loadedAt, now) < ttl) return current.names   // 아직 안 지났다

    val fresh = runCatching { load() }.getOrElse { error ->
        log.warn("서비스 목록 갱신 실패 : 이전 목록 {}개 유지", current.names.size)
        snapshot.set(Snapshot(current.names, now))   // 실패 시각으로 갱신 : 매번 PG 를 다시 치지 않게
        return current.names
    }
    snapshot.set(Snapshot(fresh, now))
    return fresh
}
private fun load() = jdbc.queryForList("SELECT name FROM applications WHERE deleted_at IS NULL", ...)
```

가져올 것 다섯 가지.

| | 무엇 | 왜 |
|---|---|---|
| 1 | **Entity 를 만들지 않는다.** `JdbcTemplate` 으로 SQL 한 줄 | 표 주인은 API 서버다. 수집기에 Entity 를 두면 표 주인 규칙이 흐려진다 |
| 2 | `AtomicReference` 스냅샷을 통째로 갈아끼운다 | 여러 스레드가 동시에 읽는다. 값 하나만 바꾸면 잠금이 필요 없다 |
| 3 | **실패하면 이전 값을 그대로 쓴다** | ADR `#37` Q23 "PG 장애 시 마지막 값 유지" 가 이 줄이다 |
| 4 | 실패해도 **시각은 갱신한다** | 안 하면 PG 가 죽은 동안 스팬마다 PG 를 다시 친다 |
| 5 | TTL 을 `@Value("...ttl:30s")` 로 뺀다 | 테스트에서 30초를 기다릴 수 없다 |

그 파일 짝인 `ServiceCatalog.kt` 주석에 이렇게 적혀 있다 : **"표 주인은 API 서버지만 읽기만 한다 : 수집기가 샘플링 비율을 읽는 것과 같은 성격 (ADR #20)"**. 이 이슈를 가리키고 있는 문장이다.

수집기는 **PG 연결이 이미 있다.** `collector/build.gradle.kts` 에 `bundles.postgres`, `application-local.yml` 에 datasource, `compose.yaml` 에 `POSTGRES_HOST` 가 들어간다. 새 의존성은 0 이다.

### 2.8 우리 로컬의 실제 값 (⑤)

2026-10-08 로컬 PG 직접 조회.

```
      name      | sampling_rate | version
----------------+---------------+---------
 shop-gateway   |        0.0100 |       1
 shop-inventory |        0.0100 |       1
 shop-order     |        0.0100 |       1
 shop-payment   |        0.0100 |       1
```

넷 다 **1%** 다. `scripts/seed/postgres-applications.sql:17` 이 `0.0100` 으로 넣는다.

그런데 지금 로컬 수집기는 **1.0(전부 통과)** 으로 돈다. `application-local.yml` 이든 `compose.yaml` 의 환경변수든 1.0 이다. 이유는 그 주석에 적혀 있다 : "로컬에서는 보낸 것이 그대로 보여야 흐름을 확인할 수 있으므로".

**PG 를 읽기 시작하면 로컬이 1% 로 떨어져 화면이 거의 빈다.** 손님 100명을 넣어도 점 한 개다. 그러면 팀원 전원이 "데이터가 안 보인다" 고 한다. 머지 전에 정해야 하는 일이다.

### 2.9 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| 샘플링은 스팬 단위로 고른다 | **트레이스 단위다.** 한 트레이스는 전부 남거나 전부 버려진다. 재료가 `trace_id` 뿐이라 저절로 그렇게 된다 |
| 수집기가 트레이스를 모아 두고 판정한다 | **모으지 않는다.** 스팬 하나하나 따로 판정하는데 답이 같아진다. 모으면 버퍼 비용이 든다 |
| `application.yml` 을 새로 만드는 일이다 | **반대다.** yml 은 이미 있다. 그 값을 yml **밖으로** 꺼내 PG 로 옮긴다. yml 값은 "PG 를 못 읽을 때 쓰는 비상용 기본값" 으로 남는다 |
| PG 를 읽으면 PG 가 죽을 때 수집도 멈춘다 | **안 멈춘다.** 마지막 값을 쓴다. 다만 **첫 조회부터 실패하면** 들고 있을 값이 없어 yml 기본값으로 가야 한다 |
| 비율을 서비스마다 다르게 두면 그 서비스만 덜 쌓인다 | **그 서비스를 지나는 트레이스가 반쪽 난다.** 2.2 의 전제가 깨져 부모 없는 고아 스팬이 생긴다 (`#92` · `#118` 의 `(누락된 구간)`) |
| 비율을 바꾸면 즉시 듣는다 | **최대 30초** 걸린다. 수집기가 여러 대면 그 30초 동안 서로 다른 비율로 돈다 |
| 메트릭 · 로그도 샘플링된다 | **트레이스만이다.** `OtlpMetricsService` · `OtlpLogsService` 는 샘플러를 거치지 않는다 |
| 카나리도 비율을 따른다 | **안 따른다.** 무조건 통과 (ADR `#41`). 1% 면 카나리의 99% 가 사라져 파수꾼 판정이 불가능해진다 |
| 버려진 스팬은 DLQ 에 남는다 | **아무 데도 안 남는다.** Kafka 전에 버린다. `raw.dlq`(ADR `#34`)는 적재 실패용이라 다른 이야기다 |

## 3. 1차 질문 (사람 차례)

> 승조가 2 를 읽고 모르는 것을 여기에 적는다. 답은 바로 아래에 붙인다.
> **아래 세 개는 2절을 쓰기 전에 이미 물은 것이라 그 자리에 그대로 옮겼다.** (`#118` 처럼 질문이 2절보다 먼저 왔다)

- **Q1. "5. 가장 중요한 함정: 트레이스가 반쪽 난다 ... 해시 방식이 왜 좋았냐면, 같은 trace_id 는 어느 서비스에서 와도 같은 판정이 나와서 콜트리가 안 끊겼습니다. 비율이 서비스마다 다르면 그 전제가 깨집니다." 이게 무슨 말이지?**
  - A. 스팬은 서비스마다 따로 도착하는데, 주사위를 굴려 고르면 gateway 스팬만 남고 그 아래가 없어진다. 그래서 `trace_id` 를 숫자로 바꿔 경계선과 비교한다. `trace_id` 는 그 요청의 모든 스팬이 똑같이 들고 있으니 **어디서 판정해도 답이 같다.** 조건은 경계선(비율)이 같다는 것. gateway 1% · order 10% 면 해시값 5 가 gateway 에서는 경계선 1 보다 커서 버려지고 order 에서는 경계선 10 보다 작아서 남는다. 남은 order 스팬은 부모가 버려졌으므로 **고아 스팬**이 되고, 트레이스 상세에서 `(누락된 구간)` 아래에 매달리고 `transactions` 에 `is_root = 0` 줄로 들어간다. 2.2 와 2.9 에 넣었다.

- **Q2. 정리하면 샘플링을 위한 `application.yml` 을 만든다인가?**
  - A. 반대다. `application.yml` 은 이미 있고 지금 거기서 읽고 있다. 이 이슈는 그 값을 **yml 에서 빼서 PG 로 옮기는** 일이다. yml 값은 PG 를 못 읽을 때 쓰는 비상용 기본값으로 남는다. 옮기는 이유는 yml 이 이미지 안에 구워져 있어서 바꾸려면 배포해야 하기 때문이고, ADR `#33` 이 "비율의 정본은 PG" 라고 이미 정해 뒀다. 2.3 과 2.9 에 넣었다.

- **Q3. 즉 샘플링을 할 때 `trace_id` 를 가지고 트레이스에서 모두 선택 혹은 모두 실패로 한다는 건가?**
  - A. 맞다. 트레이스 단위로 전부 남기거나 전부 버린다. 중요한 점은 **수집기가 트레이스를 모아 보지 않는다**는 것이다. 스팬 하나하나를 따로 받아 따로 판정하는데 재료가 `trace_id` 뿐이라 결과가 저절로 같아진다. `span_id` 도 도착 시각도 무작위도 안 본다. 예외는 카나리 하나뿐이다. 2.2 와 2.9 에 넣었다.

- **Q4. `NUMERIC(5,4)` 가 왜 소수 넷째 자리까지인가. 그걸로 충분한가?**
  - A. `(5,4)` 는 전체 5자리 · 소수점 아래 4자리, 즉 `0.0000` ~ `1.0000` 이다(위쪽은 `CHECK` 가 막는다). 넷째 자리 `0.0001` 은 **1만 건에 1건**이라 지금 쓰는 1%(`0.0100`) 보다 두 자리 더 잘게 쪼갤 여지가 남는다. 충분하다 : 쇼핑몰 4개가 초당 수백~수천 스팬을 보내는 규모에서 1만 건에 1건보다 더 잘게 나누면 표본이 너무 적어 화면 숫자가 뜻을 잃는다. API 서버가 받을 때 `setScale(4, HALF_UP)` 으로 미리 맞춰 보낸 값과 돌려주는 값이 달라지지 않게 해 둔다 (`ApplicationConfigService.samplingRateOf`).

- **Q5. `expected_version` 낙관적 락이 왜 필요한가?**
  - A. 두 사람이 같은 서비스의 설정 화면을 동시에 열면 **늦게 저장한 쪽이 먼저 저장한 쪽을 덮어쓰고 아무도 그 사실을 모른다**(lost update). 한 명은 1% 로 내렸다고 믿는데 실제로는 50% 로 돈다. 그래서 "내가 본 건 version 3 이었다" 를 같이 보내고 DB 가 그새 4 가 됐으면 `409 CONFIG_VERSION_CONFLICT` 로 거절한다. 샘플링 비율은 저장소 비용과 데이터량에 직결되는 값이라 조용히 묻히면 안 된다.

- **Q6. `AtomicReference` 스냅샷이 왜 잠금보다 나은가?**
  - A. 읽기와 쓰기 횟수가 극단적으로 다르다. 읽기는 스팬마다(초당 수천 번), 쓰기는 30초에 한 번이다. 잠금을 걸면 그 수천 번마다 잠금 비용을 내고 갱신하는 동안 읽기가 멈춘다. `AtomicReference` 는 참조 하나를 통째로 갈아끼우므로 읽는 쪽은 잠금 없이 "옛 스냅샷" 또는 "새 스냅샷" 중 하나를 보는데 **둘 다 완성된 값이라 반쯤 바뀐 중간 상태를 보는 일이 없다.** 조건 하나 : 스냅샷 안이 **불변**이어야 한다. 비율은 서비스별이라 `Map` 이 들어갈 텐데 그 `Map` 을 나중에 꺼내 수정하면 이 보장이 깨진다. 매번 새 `Map` 을 만들어 갈아끼워야 한다.

- **Q7. 수집기가 여러 대일 때 30초 동안 비율이 엇갈리는 것이 실제로 얼마나 문제인가?**
  - A. **사람이 비율을 바꾸는 순간에만, 최대 30초** 생기고 저절로 복구된다. 지금 수집기는 로컬도 운영 계획도 1대라 아직 발생하지 않는다. 생기면 증상은 Q1 의 고아 스팬이다 : 1% → 10% 로 올리는 중이면 새 비율을 읽은 수집기 A 가 남긴 order 스팬의 부모가 아직 옛 비율인 수집기 B 에서 버려질 수 있다. 받아들일 만하다 : 없애려면 수집기끼리 설정을 맞추는 장치(브로드캐스트 · 공유 캐시)가 필요한데 ADR `#31` 이 Redis 를 폐기한 이유와 같은 크기의 비용이다. 다만 **"일시적이고 자동 복구된다" 를 ADR 에 명시**해야 나중에 누가 이걸 버그로 보고하지 않는다.

- **Q8. "첫 조회부터 실패" 와 "읽다가 실패" 를 왜 다르게 다뤄야 하는가?**
  - A. **들고 있는 값이 있느냐 없느냐**다. 읽다가 실패하면 마지막 값이 있으니 그걸 쓴다(ADR `#37` Q23 그대로). 첫 조회부터 실패하면 쓸 값이 없다. 그때 빈 값을 그대로 쓰면 비율이 `0`(전부 버림, 데이터 유실) 또는 `1`(전부 통과, 저장소 폭발)이 되는데 **둘 다 사고**라 yml 기본값 `0.01` 로 떨어져야 한다. `PostgresServiceCatalog` 는 빈 집합으로 시작해도 괜찮았다 : "모르는 주소는 `EXTERNAL` 로 둔다" 가 틀려도 안전한 쪽이었다. **샘플링은 안전한 쪽이 없다.** 선례를 그대로 베끼면 안 되는 유일한 지점이다.

ADR `#38` 이 "설정 단위는 앱 단위만" 으로 정할 때, **그 단위가 샘플링에 적용되면 트레이스가 조각난다는 점을 아무도 적지 않았다.** 로그 등급이나 경보 임계값은 앱별로 둬도 서로 간섭하지 않지만, 샘플링은 **한 요청이 여러 앱을 지나므로** 앱별 설정이 요청 하나를 쪼갠다. 설정 단위를 정할 때 "이 설정이 요청 경계를 넘나드나" 를 묻지 않은 것이다.

그래서 이 이슈는 ADR `#33` 의 문구를 그냥 구현하면 끝나는 일이 아니다. **"앱별 비율" 의 뜻을 여기서 정해야 한다.**

### 5.1 앱별 비율을 어떻게 다룰까 (①)

문제는 2.2 의 전제다. 해시 샘플링이 콜트리를 안 끊는 이유는 **경계선이 같아서**인데, 앱별 비율은 경계선을 다르게 만든다.

```
trace_id abc 의 해시 = 5   (어디서 계산해도 5다)

shop-gateway 비율 1%   → 경계선 1   → 5 > 1  → 버림
shop-order   비율 10%  → 경계선 10  → 5 < 10 → 남김
```

#### 깨지는 방향은 둘인데 성격이 전혀 다르다

조사하고 나서야 본 것이다. 우리 공식 `abs(hash) < ratio * Long.MAX_VALUE` 는 **비율에 대해 단조**다. 비율이 커지면 남기는 범위가 넓어지기만 한다. 그래서 비율이 달라도 **아무렇게나 조각나지 않고 방향이 정해진다.**

| 어느 쪽이 큰가 | 무슨 일이 생기나 | 화면에서 |
|---|---|---|
| **하류 비율이 더 크다** (gateway 1% < order 10%) | 부모가 버려지고 자식이 남는다 : **고아 스팬** | 트레이스 상세에 `(누락된 구간)`, `transactions` 에 `is_root = 0` 줄, 히트맵에 반쪽 요청 |
| **상류 비율이 더 크다** (gateway 10% > order 1%) | 부모가 남고 자식이 빠진다 : **꼬리 잘림.** 루트는 항상 있다 | 트레이스가 짧게 보인다. 고아는 **구조적으로 0** |

증명은 한 줄이다. `r_상류 >= r_하류` 이면 하류가 남긴 트레이스(`hash < r_하류 * MAX`)는 `r_하류 * MAX <= r_상류 * MAX` 이므로 상류에서도 반드시 남는다. 부모 없는 자식이 **생길 수 없다.**

OTel Collector `probabilistic_sampler` 가 이것을 **"consistent probability sampling"** 이라는 이름으로 문서화해 두었다.

> "Consistent probability samplers can be safely used with a mixture of probabilities and preserve sub-trace completeness, provided that child spans and log records are sampled with probability greater than or equal to the parent context." (README:65-68)
>
> "A three-tier system could be configured with 1% sampling in the first tier, 10% sampling in the second tier, and 50% sampling in the bottom tier. In this configuration, 1% of traces will be complete, 10% of traces will be sub-trace complete at the second tier." (README:70-78)

**단 OTel 의 권장 방향은 우리와 반대다.** OTel 은 `자식 >= 부모`(고아를 허용하고 꼬리 잘림을 막는다)를 권한다. 우리 화면이 싫어하는 것은 `#92` · `#118` 에서 본 그 고아 쪽이라, 우리가 단조성을 쓰려면 **`상류 >= 하류`** 로 **반대 방향**을 강제해야 한다. "루트 보존을 위해 상류를 크게" 라고 적힌 공식 문서는 찾지 못했다(추론이다).

#### 선택지 일곱

| 방법 | 한 줄 설명 | 얻는 것 | 포기하는 것 | 크기 |
|---|---|---|---|---|
| **A. 루트 기준** | 비율을 "그 서비스가 **시작한** 트레이스" 에만 적용한다 | 조각남이 **구조적으로 0.** 업계 전원의 뜻과 같다 | 수집기가 스팬만 보고 루트 서비스를 모른다. 진입이 아닌 서비스의 비율 칸은 **안 쓰이는 칸**이 된다 | 크다 (버퍼 또는 다른 재료가 필요) |
| **B. 서비스별 독립 + 조각남 수용** | 지금 생각대로 하고 쪼개짐을 사양으로 선언한다 | 가장 싸다. `keep()` 에 서비스 이름만 넘기면 된다 | 고아 스팬. 증상이 샘플링 때문이라고 아무도 못 알아본다 | 가장 작다 |
| **C. 단조성 강제** | 서비스별로 두되 **상류 >= 하류**를 PG · API 가 검증한다 | 고아 **0**, 서비스별의 뜻도 산다. 꼬리만 짧아진다 | 호출 그래프를 알아야 한다(쇼핑몰은 고정이지만 일반해가 아니다). 검증 코드는 API 서버 몫 | 중간 (다른 파트 일) |
| **D. 최댓값 하나** | 앱별로 받되 쓸 때는 `max()` | C 의 특수 경우라 고아 0. 코드가 한 줄 | 내릴 때가 이상하다 : 한 서비스를 내려도 다른 서비스가 높으면 그대로 높다 | 작다 |
| **E. 전역 한 줄을 PG 에** | 앱별 칸을 안 쓰고 전역 설정을 따로 둔다 | 뜻이 가장 정직하다. 샘플링은 애초에 트레이스 단위 = 전역 | 새 칸 · 새 API · 화면 수정. 이미 만든 앱별 칸이 논다 | 중간 (다른 파트 일) |
| **F. 트레이스를 모아 루트 기준 판정** | tail 샘플링을 만든다 | 뜻과 온전성을 둘 다 얻는다 | 수집기가 **상태를 갖는다**(ADR `#33` 과 충돌). 2대 이상이면 앞에 trace_id 로드밸런서 필요 | 가장 크다 |
| **G. 샘플링을 에이전트로 되돌린다** | OTel `ParentBased` 전파를 쓴다 | 업계 방식 그대로. 수집기가 가벼워진다 | ADR `#33` 되돌림 (b) 를 발동하는 일이고 **그 조건(수집기 한계 실측)이 충족되지 않았다.** Extension 범위도 넓어진다 | 범위 밖 |

**결정을 가르는 축**

| 방법 | 고아 스팬 | 「앱별」 의 뜻 | 다른 파트 일 | ADR 과 충돌 | 되돌리기 |
|---|---|---|---|---|---|
| A. 루트 기준 | **0** | 살지만 좁다 | 없다 | 없다 | 쉽다 |
| B. 독립 + 수용 | **생긴다** | 완전히 산다 | 없다 | 없다 | 쉽다 |
| **C. 단조성 강제** | **0** | 산다 | 생긴다 (검증) | 없다 | 쉽다 |
| **D. 최댓값** | **0** | 약하다 | 없다 | 없다 | 쉽다 |
| E. 전역 한 줄 | 0 | 없어진다 | 생긴다 (표 · 화면) | 없다 | 어렵다 |
| F. tail | 0 | 완전히 산다 | 없다 | **`#33`** | 코드를 버린다 |
| G. 에이전트 | 0 | 완전히 산다 | 쇼핑몰 쪽 | **`#33` 되돌림 미충족** | 어렵다 |

**A** 는 Jaeger · Datadog · Elastic · Pinpoint · AWS X-Ray **전원의 뜻**이다. Elastic 문구가 가장 선명하다 : "Each subsequent service respects the initial service's sampling decision, regardless of its configured sample rate." 대가는 **"진입이 아닌 서비스의 비율 칸이 안 쓰인다"** 는 혼란인데, X-Ray 가 그것을 `Common Pitfall` 로 문서화해 뒀다 : "If you create a strict sampling rule for Service B, but Service B is always called by Service A, your rule for Service B will likely never be applied." 구현 난점은 우리 수집기가 **스팬만 보고 그 트레이스의 루트 서비스를 알 수 없다**는 점이다. `#118` 의 `is_root` 판정과 같은 재료(`parent_span_id` 가 빈 스팬)가 필요한데, 그 스팬이 가장 늦게 올 수도 있다(`#50`).

**B** 는 Apache SkyWalking 이 **우리와 정확히 같은 구조로 하고 있다.** 백엔드(OAP)에서 세그먼트별로 독립 판정하고, 재료는 `trace_id` 해시, 비율은 그 세그먼트의 서비스 이름으로 조회한다. 심지어 `AtomicReference` 보관까지 같다. 그리고 **문서가 쪼개짐을 인정한다** : "the backend would make its best effort not to split the traces", 인스턴스 A=35 · B=55 예시로 "some trace segments may be missed, as they are reported to Backend-Instance A and ignored". 즉 **선례가 있고 그 선례의 결론은 "온전성을 포기하고 문서에 적는다"** 다. 우리도 갈 수 있지만 `(누락된 구간)` 과 `is_root = 0` 이 늘어나는 것을 버그가 아니라 사양으로 선언해야 한다.

**C** 가 이번 조사로 **새로 생긴 선택지**다. 위의 단조성 증명 덕에 고아가 0 이면서 서비스별 비율이 산다. 쇼핑몰 호출 그래프는 `gateway → order → payment · inventory` 로 고정이라 "gateway >= order >= payment · inventory" 를 검증하면 된다. 문제는 ① 검증을 어디서 하나(PG `CHECK` 로는 서비스 간 비교가 안 되고 API 서버 쪽 코드가 필요하다) ② 호출 그래프가 바뀌면 검증 규칙도 바뀐다 ③ 화면이 "이 값은 상류보다 작아야 합니다" 를 설명해야 한다.

**D** 는 C 의 특수 경우다(모두 같게 두면 단조성 자동 만족). 가장 싸게 고아를 0 으로 만든다. 대신 뜻이 "이 서비스의 비율" 이 아니라 "전체 비율 후보 중 하나" 가 된다. **지금 네 서비스가 전부 `0.0100` 으로 같다**는 점에서(2.8), 실제로 다르게 둘 상황이 있는지부터 물어야 한다.

**E** 는 뜻이 가장 정직하다. 어긋남의 뿌리가 "트레이스 단위 설정을 앱별 칸에 담은 것" 이기 때문이다. 하지만 표 · API · 화면이 이미 만들어졌다. `#118` 에서 조회 파트의 발견이 수집으로 넘어온 것처럼, 이번에는 수집의 발견이 조회 · 인증 설정으로 넘어간다.

**F** 는 OTel Collector `tail_sampling` 이 하는 일이다. `decision_wait` 기본 30초 · `num_traces` 기본 50000 으로 메모리에 모으고, README 가 대문자로 못 박는다 : "**All spans for a given trace MUST be received by the same collector instance.**" 수집기를 2대로 늘리는 순간 앞에 `routing_key: traceID` 로드밸런서가 필요하다. ADR `#33` 이 수집기 샘플링을 고른 이유("가볍다")를 정면으로 깬다.

**G** 는 업계 방식을 그대로 쓰는 길이고 사실 가장 정석이다. 다만 ADR `#33` 이 그것을 **되돌림 조건 (b)** 로 못 박았다 : "수집기 샘플링 때문에 에이전트 → 수집기 트래픽이 수집기 CPU · 네트워크 한계를 넘는 것이 실측되면". **그 실측이 없다.** 조건이 충족되지 않았으므로 이 이슈에서 발동할 수 없다.

### 5.2 로컬에서 전부 통과를 어떻게 유지할까 (③)

지금 로컬은 `1.0`(전부 통과)이고 PG seed 는 `0.0100` 이다(2.8). PG 를 읽기 시작하면 로컬 화면이 거의 빈다.

| 방법 | 얻는 것 | 포기하는 것 | 구현 크기 |
|---|---|---|---|
| **A. seed 를 `1.0000` 으로 바꾼다** | 코드에 분기가 없다. "정본은 PG" 가 로컬에서도 그대로 성립한다 | 로컬 PG 가 운영과 다른 값을 들고 있다. `seed-clickhouse.sh` 를 다시 돌려야 한다 | 1줄 |
| **B. 로컬 프로필에서는 PG 조회를 끈다** | 로컬이 지금과 똑같이 돈다 | 로컬에서 **PG 읽는 길 자체가 안 돌아** 그 코드가 시험되지 않는다 | 작다 (조건 하나) |
| **C. 환경변수를 "PG 무시" 스위치로 남긴다** | 로컬 · 운영 양쪽에서 급할 때 끌 수 있다 | "정본은 PG" 가 흐려진다. 운영에서 누가 켜 두면 화면 조작이 조용히 안 듣는다 | 작다 |
| D. 아무것도 안 하고 로컬도 1% 로 둔다 | 운영과 똑같다 | 손님 100명을 넣어도 점 한 개다. 개발이 거의 불가능하다 | 0 |

**A** 가 가장 단순하고 **B** 가 가장 안전해 보이지만 B 는 함정이 있다. **로컬에서 안 돌면 그 코드는 CI 와 운영에서 처음 돈다.** `#118` 에서 MV 조건을 바꾼 뒤 로컬 실데이터로 확인한 것이 리뷰를 통과시킨 근거였는데, B 를 고르면 그런 확인을 할 자리가 없다.

**C** 는 지금 `compose.yaml:179` 에 이미 있는 `MONIMO_COLLECTOR_SAMPLING_RATIO` 를 살리는 길이다(5.4 와 같은 결정이다).

### 5.3 첫 조회 실패 · 미등록 서비스는 어떻게 할까 (④ · ⑤)

Q8 에서 본 대로, 선례(`PostgresServiceCatalog`)를 그대로 베끼면 안 되는 자리다. 빈 값은 비율 `0`(전부 버림) 또는 `1`(전부 통과)이 되고 **둘 다 사고**다.

| 상황 | 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|---|
| 첫 조회 실패 | **A. yml 기본값 `0.01`** | 운영에서 쓰던 값과 같다. 아무 일도 안 일어난 것처럼 돈다 | PG 가 사실은 다른 값이었으면 조용히 어긋난다 |
| | B. `1.0` 전부 통과 | 데이터를 안 잃는다 | 1% 를 전제로 잡은 저장소 · Kafka 가 100배를 받는다. **이쪽이 더 큰 사고다** |
| | C. `0.0` 전부 버림 | 저장소가 안전하다 | PG 가 늦게 뜨는 동안 신호가 통째로 사라진다. 그 사실이 조용하다 |
| | D. 수집기 기동 실패 | 어긋남이 없다 | PG 가 1분 늦게 뜨면 수집기가 안 뜬다. 수집 경로 가용성 99.9% 를 PG 에 묶는다 |
| 미등록 서비스 | **A. yml 기본값** | 단순하다. 신호를 일단 받는다 | 등록 안 한 서비스의 데이터가 Kafka 에 들어간다 |
| | B. 전부 버린다 | 등록이 곧 감시 시작이라는 설계(ADR `#36`)와 맞는다 | 등록 직후 30초 동안 그 서비스 신호가 사라진다. 적재 처리기는 버리면서 카운터로 센다(`unknown_service`) |

첫 조회 실패에서 **A 와 D 가 갈리는 축은 "조용한 어긋남" 과 "큰 실패" 중 무엇을 고르느냐**다. 우리 레포는 지금까지 큰 실패 쪽을 골라 왔다 : 적재 처리기는 Flyway 이름 규칙이 어긋나면 조용히 무시하지 않고 **실행 전체를 실패**시킨다(ADR `#49`). 다만 거기는 기동 시점의 마이그레이션이고 여기는 **수집 경로의 가용성**이라 성격이 다르다.

미등록 서비스는 **적재 처리기와 다르게 다뤄도 된다.** 적재 처리기는 `agents` 표에 FK 를 넣어야 해서 건너뛸 수밖에 없었지만(`#66`), 수집기는 Kafka 에 넣기만 하면 되고 거르는 판단을 뒤에서 또 한다.

### 5.4 환경변수를 남길까 (④)

`compose.yaml:179` 가 지금 `MONIMO_COLLECTOR_SAMPLING_RATIO` 를 넣고 있고 주석에 "샘플링을 눈으로 시험하려면 `.env` 에 `COLLECTOR_SAMPLING_RATIO=0.1` 처럼 넣는다" 가 적혀 있다.

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **A. 기본값 자리로만 남긴다** (PG 가 있으면 PG 가 이긴다) | "정본은 PG" 가 분명하다. 첫 조회 실패 때 쓸 값이 생긴다 (5.3 A) | 운영에서 PG 를 못 고치는 상황에 끌 수단이 없다 |
| B. "PG 무시" 스위치로 남긴다 (설정하면 env 가 이긴다) | 급할 때 PG 와 무관하게 끈다. 로컬도 해결된다 (5.2 C) | 운영에 켜 둔 것을 잊으면 **화면 조작이 조용히 안 듣는다.** 가장 찾기 어려운 버그 |
| C. 없앤다 | 길이 하나뿐이라 헷갈릴 일이 없다 | 로컬 · CI 에서 비율을 조절할 수단이 사라진다 |

B 의 위험은 실제로 겪은 종류다 : `#118` 에서 **파일을 고쳐도 조용히 안 듣는** 상황(ClickHouse initdb)이 가장 오래 사람을 헷갈리게 했다. 같은 모양의 함정이다.

### 남이 어떻게 하나

#### 비율 판정을 어디서 하나 (①)

**조사한 일곱 제품 중 여섯이 루트에서만 판정하고 전파한다.** 그래서 그 제품들의 "서비스별 비율" 은 전부 **"그 서비스가 시작한 트레이스의 비율"** 이다. 예외는 SkyWalking 하나이고, 그것이 우리와 같은 구조다.

| 제품 | 어디서 판정 | 근거 |
|---|---|---|
| Jaeger | **루트만** | 원격 부모가 있으면 `samplingState.setFinal()` 로 확정되어 샘플러를 아예 호출하지 않는다 (`tracer.go:297-301` · `323-326`). 코드 주석 : "joining a trace is not possible, because sampling decision inherited from upstream is final" (`tracer.go:421`) |
| OTel `JaegerRemoteSampler` | **루트만** | 세 전략 분기를 **전부** `Sampler.parentBased(...)` 로 감싼다 (`JaegerRemoteSampler.java:157-177`). 초기 샘플러도 `parentBased(traceIdRatioBased(0.001))` |
| Datadog | **루트만** | "The decision to keep or drop a trace is made at the start of the root span and then propagated to other services as part of their request context." 에이전트가 서비스별 비율을 돌려주지만 **"to apply at the root of traces"** |
| Elastic APM | **루트만** | "Each subsequent service respects the initial service's sampling decision, **regardless of its configured sample rate**; the result is a sampling percentage that matches the initiating service." tail 정책도 **"which service initiated the distributed trace"** 기준 |
| AWS X-Ray | **루트만** | "X-Ray sampling is Parent-based ... it will honor that decision regardless of any of its own matching sampling rules." + `Common Pitfall` 경고 |
| Pinpoint | **루트만** | `isContinueSampled()` 가 조건 없이 `true` (`BasicTraceSampler.java:110-113`). 호출부 주석 : "always set true because the decision of sampling has been made on previous nodes" |
| **Apache SkyWalking** | **서비스마다 독립** | OAP 백엔드가 세그먼트별로 `Math.abs(traceId.hashCode()) % 10000` 과 서비스별 정책을 비교 (`TraceSegmentSampler.java:33-37`). **우리와 같은 구조** |

#### 우리와 같은 구조(모으지 않고 수집 단에서 고름)로 서비스별 비율을 쓰는 곳

**SkyWalking 하나다. 그리고 온전성을 포기하고 문서에 적었다.**

| 확인 | 내용 |
|---|---|
| 판정 공식 | `Math.abs(traceId.hashCode()) % 10000` : 우리 `abs(hash) < ratio * MAX` 와 **구조가 같다** |
| 설정 보관 | `AtomicReference<SamplingPolicySettings>` : **우리 계획(Q6)과 같다** |
| 못 읽었을 때 | `new SamplingPolicy(10000, -1)` = **전부 통과** (`SamplingPolicySettings.java:38-41`) |
| 쪼개짐 | 문서가 인정 : "the backend would make its best effort **not to split the traces**", 비율 35 vs 55 예시로 "some trace segments **may be missed**" |
| 비율을 다르게 두는 것 | 금지하지 않고 권하지 않는다 : "although we **recommend** that you set the values to be the same" |
| Zipkin 리시버 쪽 공식 | "Because the boundary is derived from the trace ID, **every span of a given trace is kept or dropped together**" : 우리 2.2 와 같은 문장 |

반대로 **온전성을 지키는 쪽은 전부 트레이스를 모은다** : OTel Collector `tail_sampling`(`decision_wait` 30초 · `num_traces` 50000 · "All spans for a given trace MUST be received by the same collector instance"), Elastic APM tail-based(APM Server 로컬 스토리지, 루트 트랜잭션이 끝날 때 결정, 루트가 안 오면 "silently drop all associated trace events").

Datadog 의 수집 단 probabilistic sampler 는 **전역 비율 하나뿐이고 서비스별이 없다**(`DD_APM_PROBABILISTIC_SAMPLER_SAMPLING_PERCENTAGE`).

#### OTel Collector `probabilistic_sampler` (③)

| 질문 | 답 |
|---|---|
| `trace_id` 해시인가 | 기본 모드(`hash_seed`)는 그렇다. FNV 해시를 trace ID 에 적용해 임계값과 비교 |
| **서비스별 비율 지원** | **없다.** 설정은 `sampling_percentage` 하나다. 속성별 비율 요청(Issue #33449)은 **"Closed as not planned"** |
| 인스턴스마다 같아야 하는 것 | **비율이 아니라 `hash_seed`** : "all collectors for a given tier (e.g. behind the same load balancer) must have the same `hash_seed`" |
| 비율이 티어마다 다를 때 | **금지하지 않고 규칙을 준다** : `자식 >= 부모` 면 sub-trace completeness 가 보존된다. 1% / 10% / 50% 3계층 예시까지 문서에 있다 |
| 랜덤성을 못 구하면 | 기본 거부 (`fail_closed` 기본 `true`) |
| 문서 모순 | README:133 은 `hash_seed` 가 기본이라 하고 README:175 는 `proportional` 이 기본이라 한다. **코드는 `hash_seed`** |

#### 사양으로 푸는 길 (`tracestate` 의 `th`)

OTel 에 이 문제를 사양으로 푸는 길이 있고 **아직 실험 단계다.**

- 상태 : `**Status**: [Development]` (`tracestate-probability-sampling.md:8`). OTEP 235 는 스펙 레포로 이전됨
- 방식 : 56비트 랜덤값 `R` 과 56비트 거부 임계값 `T` 를 `tracestate` 의 `ot` 구역에 싣는다 (25% = `ot=th:c`). `R >= T` 면 남긴다
- 우리 자리에 대한 규정 : "**Downstream samplers are able to raise the applied threshold, but they cannot lower.**" 즉 하류는 비율을 **내릴 수만** 있다. 올리면 통계 오류가 된다
- Collector 의 `tracestate` 연동은 **알파 feature gate 이고 기본 꺼짐** (`processor.tailsamplingprocessor.usetracestate`)
- 우리 에이전트는 `always_on` 으로 보내므로 **받을 `th` 가 없다.** 우리가 심어야 하고, 심을 자리는 에이전트(= ADR `#33` 되돌림)다

**우리 해시가 사양과 1바이트 다르다.** 우리는 `trace_id` **뒤 8바이트 + `abs()`**(`TraceSampler.kt:69` · `78`), 사양의 랜덤성은 **뒤 7바이트(56비트)** 다. W3C `random` trace flag 도 "at least the right-most 7 bytes" 다. 나중에 `th` · `rv` 와 호환시키려면 7바이트로 바꿔야 한다.

**우리 30초는 Elastic APM Server 의 기본값과 정확히 같다.** 업계 범위(2초 ~ 5분) 한가운데다. "실패하면 마지막 값 유지" 는 Jaeger · OTel · Elastic · SkyWalking **전원의 공통 동작**이라 ADR `#37` Q23 은 표준을 따른 것이다.

**첫 조회 실패는 제품마다 갈린다** : Jaeger · OTel 은 **0.001(보수적)**, Datadog · SkyWalking 은 **전부 통과(공격적)**. 갈리는 이유는 자리다. Jaeger · OTel 은 **보내는 쪽**이라 많이 보내는 것이 위험하고, Datadog 은 **백엔드가 비율을 돌려주는** 구조라 못 받았으면 아직 판단할 재료가 없다는 뜻이다. 우리는 뒤에 Kafka 와 ClickHouse 가 있고 그 용량을 1% 전제로 잡았으니 Jaeger · OTel 쪽이다.

#### 인스턴스 사이에 설정이 엇갈리는 구간 (⑤ · Q7)

| 제품 | 다루나 | 내용 |
|---|---|---|
| **SkyWalking** | **정면으로 다룬다** | "we recommend that you set the values to be the same" + A=35 · B=55 숫자 예시로 유실을 설명 |
| OTel `probabilistic_sampler` | 비율 차이는 경고하지 않고 규칙을 준다 | 대신 **`hash_seed` 일치**를 요구 |
| **Datadog** | 코드가 완화 장치를 둔다 | 비율이 올라갈 때 **직전 값의 2배까지만**, 그 상승도 `rampUpInterval = 1s` 당 한 번. 주석 : "This prevents a spike in sampled traces when the agent restarts and temporarily reports rate=1.0 for all services" |
| Jaeger · OTel · Elastic · Pinpoint · X-Ray | 애초에 문제가 아니다 | 루트가 정하고 전파하므로 하류가 옛 설정을 들고 있어도 쓰이지 않는다 |

**Q7 의 결론("일시적이고 자동 복구된다, 받아들인다")에 인용할 선례가 생겼다** : SkyWalking 이 같은 구조에서 같은 결론을 내리고 "같게 두기를 권한다" 를 문서에 적었다. 그리고 **Datadog 의 2배 상한은 우리도 싸게 베낄 수 있다** : PG 에서 읽은 새 비율이 직전보다 크면 한 번에 2배까지만 올린다. 비율 상향 중의 고아 급증이 완화된다(대가는 수렴이 느려지는 것).

### AI 가 틀렸거나 덜 맞았던 것 (남겨 둔다)

- 처음에 "수집기가 PG 를 읽는 선을 하나 잇는 작은 일" 로 요약했다. **앱별 비율이 트레이스를 쪼갠다는 것을 2절을 쓰면서야 봤다.** 그 전까지는 ADR 문구를 그대로 구현하면 끝나는 일로 설명했다.
- 선례(`PostgresServiceCatalog`)를 "그대로 베끼면 된다" 고 다섯 가지로 정리했는데, **첫 조회 실패 처리는 베끼면 안 되는 자리**였다(Q8). 적재 처리기는 빈 집합이 안전한 쪽이었고 샘플링은 안전한 쪽이 없다.
- **가장 큰 것** : "비율이 다르면 트레이스가 조각난다" 고만 말하고 **깨지는 방향이 둘이고 성격이 다르다는 것을 놓쳤다.** 우리 공식이 비율에 대해 단조라서 `상류 >= 하류` 면 고아 스팬이 **구조적으로 생길 수 없다.** 선택지 C(단조성 강제)가 조사 뒤에야 나왔고, 그게 없었으면 "안전한 길은 최댓값뿐" 이라는 틀린 전제로 결정했을 것이다. OTel 이 이걸 `consistent probability sampling` 으로 이미 문서화해 두었다.
- 5.1 D("루트 서비스 비율")를 처음 적을 때 "업계 방식과 같다(추정)" 로 달았는데, 맞지만 **비용이 전혀 다르다.** 업계는 루트에서 판정하고 **전파**하니 공짜이고, 우리는 전파가 없어 같은 뜻을 구현하면 버퍼가 붙는다. 그래서 선택지를 A(루트 기준)와 F(트레이스 모으기)로 쪼갰다.
- 조사 보조 에이전트 한 쪽이 Jaeger collector 의 전략 reload 기본값을 "60초" 로 가정해 물었는데, 실제 기본값은 **0(reload 안 함)** 이었다. 질문 안에 틀린 전제를 넣었던 것이다.

| 확인 | 결과 |

### 확인 못 한 것

우리 쪽 (이것이 선택을 가른다)

- **서비스별 비율을 실제로 다르게 둘 상황이 있나.** 지금 넷 다 같고, 다르게 둘 이유(한 서비스만 트래픽이 폭증 · 한 서비스만 자세히 보고 싶다)가 실제 요구인지 아니면 표를 만들 때 "앱별이니까" 로 따라온 것인지 확인하지 못했다. **5.1 의 선택이 여기에 달려 있다.**
- **수집기가 운영에서 몇 대로 뜨나.** `monimo-deploy` 의 K8s 매니페스트를 확인하지 않았다. 1대면 Q7 의 엇갈림은 아예 안 생긴다.
- 조회 파트 화면(`monimo-web`)이 샘플링 비율 입력을 **서비스별로 받고 있나**, 아니면 아직 안 만들었나. 5.1 C · E 의 비용이 여기에 달려 있다.
- 30초이라는 주기가 어디서 왔나. ADR `#37` Q23 이 숫자를 정했지만 근거 수치가 없다. **업계값(Elastic 서버 30초 · Jaeger 60초)과 맞다는 것은 확인했지만 그때 그 근거로 정한 것은 아니다.**

조사 쪽

- **"루트를 보존하려면 상류 비율을 더 크게 둬야 한다"** 는 OTel 인용문에서 유도한 결론이고 그렇게 적힌 공식 문서는 없다. OTel 공식 권장은 **반대 방향**(`자식 >= 부모`)이다.
- 우리 `abs(뒤 8바이트)` 가 사양의 7바이트(56비트) 대비 분포에서 실제로 치우치는지 **측정하지 않았다.**
- OTel `probabilistic_sampler` 의 속성별 비율 요청(Issue #33449) 기각 사유 본문을 읽지 못했다. 라벨("Closed as not planned" · Stale)만 확인했다.
- SkyWalking 에이전트 쪽(`agent.sample_n_per_3_secs`)이 `sw8` 헤더로 결정을 전파하는지. 서버 쪽만 확인했다.
- Pinpoint 의 비율을 중앙에서 내려주는 수단과 주기. `profiler.sampling.rate` 가 에이전트 로컬 설정이라는 전제로만 봤다.
- Elastic APM tail-based 의 인스턴스 간 동기화 주기. 검색 결과 수준으로만 보았다.
- Jaeger 서버 `--sampling.strategies-reload-interval` 의 플래그 기본값이 선언된 자리. `> 0` 일 때만 켜진다는 것만 코드로 확인했다.

## 6. 2차 질문 (사람 차례)

> 승조가 5 를 읽고 모르는 것을 여기에 적는다. 답은 바로 아래에 붙인다.

- **Q9. (깨지는 방향 표를 가리키며) 이거 쉽게 설명해줘**
  - A. `trace_id` 를 숫자로 바꾸면 그 요청의 **번호표**가 된다. 비율은 "몇 번까지 남길까" 하는 **선**이다. 번호표는 그 요청의 모든 스팬이 똑같이 들고 있으니, 선이 같으면 전부 남거나 전부 버려진다. 선이 다르면 같은 번호표가 한쪽에선 통과하고 한쪽에선 걸린다. 번호표 5번 요청에서 `gateway 1%`(1번까지) · `order 10%`(10번까지)면 gateway 는 버리고 order 는 남긴다. 반대로 `gateway 10%` · `order 1%` 면 gateway 가 남고 order 가 빠진다. 전자가 고아, 후자가 꼬리 잘림이다.

- **Q10. `gateway 1%` · `order 10%` 이거도 각각 설정인가?**
  - A. 그렇다. `application_configs` 가 `application_id` 에 `UNIQUE` 라 **서비스당 한 줄**이고, 그 줄마다 `sampling_rate` 칸이 있다. 지금 넷 다 `0.0100` 이고 수집기가 이 표를 안 읽으니 **아무 효력이 없다.** 고치는 길(화면 → `PUT /applications/{uuid}/config` → PG)은 이미 열려 있다. 이 이슈가 그 칸들을 깨우는 일이라, 깨울 때 "다르게 넣으면 어떻게 할지" 를 정해 놓지 않으면 사고가 열린다.

- **Q11. `gateway 1%` · `order 10%` 의 뜻이 전체 트레이스의 1% 를 뽑고 order 는 10% 를 뽑는다는 소리인가? 근데 gateway 안에 order 가 있는 거 아니야?**
  - A. 둘 다 맞게 짚었다. 비율이 재는 것은 "트레이스" 가 아니라 **"그 서비스가 보낸 스팬"** 이다. 트리에서는 order 가 gateway 안에 있지만 **수집기는 트리를 못 본다** : 스팬이 서비스마다 따로 도착하고 각 스팬에는 `service.name` 만 적혀 있다. 그래서 같은 트리의 위아래가 서로 다른 선으로 재어진다. **샘플링이 다루는 단위(트레이스)와 설정이 적용되는 단위(서비스)가 어긋난 것**이 문제의 뿌리다. 로그 등급이나 경보 임계값은 서비스 안에서 끝나므로 이런 일이 없다. 샘플링만 요청 경계를 넘는다.

- **Q12. 적재할 때도 어쩔 수 없이 짤린 상태로 적재되기도 하니까, 각각 다른 % 로 해도 각각 다른 % 의 조회가 된다? 그리고 「수용」 과 「전역 한 줄」 은 뭐지? 「네 줄」 은 뭐지?**
  - A. **「네 줄」** 은 `application_configs` 의 서비스 네 개 줄이다. **「수용」(B)** 은 아무 장치도 안 넣고 깨지는 것을 사양으로 선언하는 것(SkyWalking 방식), **「전역 한 줄」(E)** 은 앱별 칸을 안 쓰고 전역 설정 자리를 새로 하나 만드는 것이다.
  - **"짤린 상태로 적재되기도 한다" 는 맞지만 그것이 근거가 되지는 않는다** : 지금도 고아가 생긴다(`#50` : 요청 직후 조회 · 적재 실패 · 에이전트 버퍼 초과). 다만 그것은 **사고일 때만 드물게** 생기고, 샘플링이 만드는 것은 **상시 · 비율 차이에 비례**한다(1% 대 10% 면 전체의 9%). 지금 `(누락된 구간)` 은 "뭔가 유실됐다" 는 경고 신호인데, 상시로 뜨면 그 신호가 죽는다.
  - **"각각 다른 % 의 조회가 된다" 는 절반 맞다.** 서비스 하나만 보는 화면(스캐터 · 히트맵 · URL 통계 · 서비스 건강)은 **괜찮다.** 표본 밀도만 달라지고 틀리지 않는다. 깨지는 것은 **서비스를 잇는 화면** 셋이다.

- **Q13. 「깨지는 화면」 의 의미는?**
  - A. 화면이 에러를 내는 것이 아니라 **아무 경고 없이 틀린 숫자와 틀린 관계를 보여준다.** ① 트레이스 상세 : 부모 줄이 없어 `(누락된 구간)` 이라는 가짜 루트 아래에 매달린다. "gateway 가 order 를 불렀다" 는 관계와 전체 소요 시간이 사라진다 ② 고객 요청 수 : 같은 요청의 줄들이 쌍으로 안 들어와 숫자 비가 깨진다 ③ 서버맵 : 화살표는 부른 쪽(CLIENT) 스팬, 동그라미는 받은 쪽(SERVER) 스팬이라 **서로 다른 비율로 뽑혀** "들어온 것보다 처리한 것이 많은" 그림이 된다.

- **Q14. 「고객 요청 수(`is_root`)」 예시가 무슨 말이지? `shop-gateway` 인 트레이스 트리 전체를 가져온다는 건가, 게이트웨이 속 order 스팬들이 아니라?**
  - A. **트리를 가져오는 것이 아니다.** `is_root` 는 줄 하나에 붙은 표시(0 또는 1)일 뿐이다. 핵심은 `transactions` 가 **트레이스당 한 줄이 아니라 "서비스가 받은 요청" 당 한 줄**이라는 것이다(`#118`). 요청 하나가 서비스 셋을 지나면 **세 줄**이 생기고, 그중 부모가 없는 줄(gateway)에만 `is_root = 1` 이 붙는다. 그래서 `count(*)` 는 "서비스들이 처리한 일의 수", `count(is_root = 1)` 은 "고객 요청 수" 다. 트리 조립은 트레이스 상세 화면에서 API 서버가 따로 한다(`SpanTree.assemble`).

- **Q15. 고객 요청 수를 뽑는 거니까 gateway 만 뽑는다? 근데 샘플링 수가 다르면 order 랑 gateway 가 짝이 안 되니까, 즉 개수가 안 맞으니까 문제가 된다?**
  - A. 둘 다 맞다. 한 가지만 정확히 하면 `is_root = 1` 은 "gateway 를 뽑는다" 가 아니라 **"그 요청이 시작된 줄을 뽑는다"** 다. 지금은 진입이 gateway 하나뿐이라 결과적으로 gateway 만 나오지만, 큐에서 order 가 직접 꺼내 처리하면(CONSUMER) 그 줄도 `is_root = 1` 이 된다. `#118` 에서 조건을 `SERVER · CONSUMER` 로 넓힌 이유다. 그리고 짝이 안 맞는 것이 **숫자 모순과 고아 스팬 둘로** 나타난다 : 같은 원인이 숫자로도 트리로도 드러난다.

- **Q16. C 의 경우는 자식 스팬이 사라질 수 있는 거 아닌가?**
  - A. **맞다. AI 가 "C : 고아 0" 이라고만 적어 대가를 흐릿하게 뒀다.** C 는 "잃지 않는다" 가 아니라 **"안전한 방향으로 잃는다"** 다. 자식이 사라지지만 **CLIENT 스팬은 남는다**(부른 쪽이 상류라 상류 비율을 따른다). 그래서 "order 를 불렀고 95ms 걸렸다" 는 보이고 "order 가 안에서 뭘 했나" 만 안 보인다. 고아 쪽은 정반대로 **"누가 불렀나 · 전체가 몇 ms 였나 · 어디서 시작됐나"** 를 잃는다. 꼬리 잘림이 덜 나쁜 이유 둘 : ① 하위 서비스에 에이전트가 없을 때도 똑같이 생기는 **정상적인 짧은 트레이스**라 화면이 이미 다룬다 ② `is_root` 가 살아 있어 고객 요청으로 세어진다.
  - **그리고 C 가 안 고치는 것이 있다** : **숫자 비 모순은 C 에서도 남는다.** 방향만 뒤집힌다(고객 요청 1,000 · order 처리 100). 서버맵도 화살표가 노드보다 많아진다. **숫자 비까지 맞는 것은 선이 하나인 D 와 E 뿐이다.**

- **Q17. (제외한 선택지 표에서) ADR `#33` 이 뭐야?**
  - A. "에이전트를 직접 만들지 말고 OTel 기성품을 쓰고, 샘플링은 수집기가 한다" 는 결정이다(2026-09-13 팀 결정, 에이전트 방향 네 번째 결정). **이 이슈의 양쪽 끝이 여기서 나온다** : "비율의 정본은 PG 라 재배포 없이 바뀐다" 가 `#121` 을 해야 하는 이유이고, "에이전트는 100% 보내고 수집기가 고른다" 가 A · F · G 가 막히는 이유다. 되돌림 (b)("수집기 CPU · 네트워크 한계를 넘는 것이 실측되면 에이전트 헤드 샘플링으로 전환")가 선택지 G 를 발동시키는 조건인데 **그 실측이 없다.**

- **Q18. 「전역 한 줄」(E) 은 무슨 방법이지? 전용 테이블을 만들어야 한다는 거지?**
  - A. 그렇다. **전역 설정 표가 지금 없다**(`db/postgres/` 에 `config` · `alert` · `ingest` 뿐). 그래서 E 는 **줄 하나짜리 표를 새로 만드는 일**이고, 그 주인은 API 서버이며(ADR `#36`) API 와 화면이 따라온다. `application_configs.sampling_rate` 는 `enabled_modules` · `log_level` 이 폐기된 뒤 **그 표의 유일한 쓸모 있는 칸**이라, 빼면 표가 거의 빈 표가 된다. 다만 E 가 틀린 선택은 아니다 : 지금 전역 설정이 셋(헬스체크 주소 · 로그 하한 · 샘플링 비율) 다 env 에 흩어져 있고, ADR `#50` 이 "K(샘플링 비율을 PG 로)가 길을 뚫으면 그때 옮길 수 있다" 고 적어 뒀다. **전역 설정 표를 만드는 것 자체가 결정거리**(무엇이 들어가나 · 캐시 주기를 공유하나 · 화면 어디에)라 이 이슈에 끼우기에는 크다. `#119` 처럼 별 이슈가 맞다.

- **Q19. (스스로 정리해 보며) 현재 문제가 기존 샘플링이 yml 파일로 있어서 샘플링할 때마다 재빌드가 필요해서 PG 에서 샘플링 규칙을 읽고 샘플링을 하게 하려고 하는 건데, 문제가 수집하는 건 트레이스고 비교하는 건 PG 속 스팬들의 종류로 비교하게 되니까 각각의 스팬마다 샘플링 비율이 달라지게 되었는데, 이게 문제가 `gateway 1% < order 10%` 라면 고아 스팬이 생기고 `gateway 10% > order 1%` 라면 스팬 일부가 빠지는 현상이 일어나고, `trace_id` 를 통해서 요청 개수를 셀 때 스팬들 개수와 루트 스팬의 개수가 불일치하는 문제가 발생하고, 서버맵에서도 다른 비율로 CLIENT 랑 SERVER 가 채워지니까 맵 자체가 이상하게 되는 문제가 생겨서. 이게 맞나?**
  - A. 대체로 맞다. **두 군데를 고친다.**
  - **① "스팬들의 종류" 가 아니라 「서비스 이름」 이다.** 샘플링이 보는 것은 `resource` 의 `service.name` 하나이고 `span_kind`(SERVER · CLIENT · CONSUMER)는 **안 본다.** PG 표가 서비스당 한 줄이고 그 이름으로 줄을 찾는다. 그래서 "스팬마다 비율이 달라진다" 가 아니라 **"서비스마다 달라진다"** 다. 같은 서비스의 스팬은 종류가 달라도 같은 비율을 쓴다. **서버맵 문제는 결과가 종류별로 드러나는 것**이다 : 간선은 `gateway` 가 보낸 CLIENT 스팬 · 노드는 `order` 가 보낸 SERVER 스팬이라 **서비스가 달라서** 비율이 갈린다. 종류 때문이 아니다.
  - **② 요청 수는 `trace_id` 가 아니라 `is_root` 로 센다.** `distinct trace_id` 를 세지 않고 `transactions` 의 줄에 붙은 표시를 센다. `count(*)` 는 "서비스들이 처리한 일의 수", `count(is_root = 1)` 은 "고객 요청 수" 다. 어긋나는 것은 그 두 숫자의 **비**다.
  - 그리고 "재빌드" 는 **"비율을 바꿀 때마다"** 다. 샘플링 자체는 지금도 돌고 있다.

- **Q20. 즉 A 는 gateway 에서의 요청이면 order 도 gateway 의 샘플링 % 랑 같아지는 건데, order 같은 경우에는 부모 스팬을 찾을 수 없어서 문제가 생기는 거고, 이걸 해결하기 위해서는 스팬을 메모리에 모아 두는 방식(F)을 사용해야 하고, 이 방식을 구현하려면 수집기가 스팬들의 데이터를 기억해야 하는 상태를 가지게 되고 수집기가 2개 이상이 되면 LB 도 필요하고 병목 현상도 발생한다? 이건가?**
  - A. 맞다. 한 군데만 더 정확히 하면 **"부모 스팬을 찾을 수 없어서" 가 아니라 "부모가 누군지 알려면 기억해야 해서"** 다. order 스팬은 `parent_span_id` 는 들고 있다. 모르는 것은 **그 부모가 어느 서비스 것인지**이고, 그걸 알려면 부모 스팬 자체를 들고 있어야 한다. 부모 스팬은 아직 안 왔거나(에이전트 배치 5초) 이미 처리해 흘려보냈다.
  - 나머지는 그대로다 : 모아 두면 수집기가 상태를 갖고, 2대 이상이면 같은 트레이스 스팬이 같은 수집기로 가야 해서 `trace_id` 로드밸런서가 필요하고, OTel 기본값 기준 30초 대기 · 5만 트레이스 메모리가 병목이 된다.
  - **한 문장으로** : A 의 뜻은 맞지만, 우리는 **에이전트가 입구에서 정해 전파하는 길(G)을 안 쓰기로 했기 때문에**(ADR `#33`), 그 뜻을 수집기에서 구현하려면 기억(F)이 필요하고 그게 비싸다.

## 7. 2차 정리

> 승조가 Q19 · Q20 으로 스스로 정리한 것을 뼈대로 쓰고, 그 자리에서 고친 두 군데를 반영했다.

### 지금 무엇이 문제인가 (둘)

**문제 1 : 비율이 이미지 안에 있다.** 비율을 **바꿀 때마다** 파일을 고쳐 빌드하고 다시 배포해야 한다. 그래서 PG 에서 읽게 바꾸려 한다. ADR `#33` 이 "정본은 PG 라 재배포 없이 바뀐다" 로 이미 정했는데 코드가 안 따라갔다.

**문제 2 : 거르는 단위와 설정 단위가 다르다.** 거르는 것은 **트레이스**(요청 하나)인데 PG 의 설정은 **서비스**당 한 줄이다. 수집기는 스팬에 적힌 `service.name` 으로 줄을 찾으므로, 비율이 서비스마다 달라진다.

여기서 두 가지를 분명히 해 둔다.

| 헷갈린 것 | 실제 |
|---|---|
| "스팬 종류(SERVER · CLIENT)로 비율을 찾는다" | **`service.name` 하나만 본다.** `span_kind` 는 샘플링과 무관하다. 같은 서비스의 스팬은 종류가 달라도 같은 비율을 쓴다 |
| "스팬마다 비율이 달라진다" | **서비스마다 달라진다** |
| "요청 수를 `trace_id` 로 센다" | **`is_root` 표시를 센다.** `count(*)` 가 "서비스들이 처리한 일", `count(is_root = 1)` 이 "고객 요청 수" |

### 서비스마다 비율이 다르면 깨지는 것 셋

| | 어떻게 깨지나 |
|---|---|
| **트레이스** | `gateway 1% < order 10%` 면 부모가 버려지고 자식만 남는다 : **고아 스팬.** 반대로 `gateway 10% > order 1%` 면 자식이 빠진다 : **꼬리 잘림.** 루트는 남아 트리가 거짓말을 하지 않는다 |
| **고객 요청 수** | 같은 요청의 줄들이 쌍으로 안 들어와 `count(*)` 와 `count(is_root = 1)` 의 **비가 어긋난다.** 모든 요청이 두 서비스를 다 지나는데 숫자가 10배 벌어진다 |
| **서버맵** | 간선은 `gateway` 가 보낸 CLIENT 스팬 · 노드는 `order` 가 보낸 SERVER 스팬이라 **서비스가 달라 비율이 갈린다.** "들어온 것보다 처리한 것이 많은" 그림이 된다 |

깨지는 셋의 공통점은 **두 서비스의 기록을 맞춰 봐야 하는 화면**이라는 것이다. 한 서비스 안에서 끝나는 화면(스캐터 · 히트맵 · URL 통계 · 서비스 건강)은 표본 밀도만 달라지고 **틀리지 않는다.**

그리고 "깨진다" 는 **에러가 나는 것이 아니다.** 경고 없이 틀린 숫자와 틀린 관계를 보여준다. 그래서 진단이 가장 어렵다.

### 업계 방식(A)이 우리에게 비싼 이유

업계 일곱 중 여섯은 "서비스별 비율" 의 뜻을 **"그 서비스가 입구인 트레이스의 비율"** 로 둔다(A). 그러면 트레이스 하나에 선이 하나만 적용되어 쪼개질 수 없다. gateway 가 부른 요청이면 order 스팬도 **gateway 의 비율을 따른다.**

우리 수집기는 그걸 할 수 없다. order 스팬이 도착했을 때 **그 트레이스의 입구가 누군지 모른다.**

```
order SERVER 스팬이 들고 있는 것
  trace_id       = abc
  parent_span_id = s1      ← 부모 번호는 있다
  service.name   = order   ← 자기 이름만 있다

"s1 이 어느 서비스 것이냐" 는 적혀 있지 않다
```

부모 스팬을 찾을 수 없는 것이 아니라 **그 부모가 누군지 알려면 기억해야 한다.** 부모 스팬은 아직 안 왔거나(에이전트 배치 5초) 이미 처리해 흘려보냈다.

그래서 사슬이 이렇게 이어진다.

```
A 를 하려면      →  입구가 누군지 알아야 하고
알려면           →  스팬을 모아 둬야 하고 (F)
모아 두면        →  수집기가 상태를 갖고 (ADR #33 "가볍다" 위반)
                 →  2대 이상이면 trace_id 로드밸런서가 필요하고
                 →  30초 대기 · 5만 트레이스 메모리가 병목이 된다
```

업계는 F 가 필요 없다. **에이전트가 입구에서 판정하고 `traceparent` 헤더로 전파**해서 하류는 헤더만 보고 따른다. 기억할 것이 없다. 그 길로 가려면 에이전트가 샘플링해야 하고 그것이 **G** 인데, ADR `#33` 이 그것을 **되돌림 (b)** 로 예약해 뒀다 : "수집기 CPU · 네트워크 한계를 넘는 것이 실측되면". **그 실측이 없다.**

> **한 문장** : A 의 뜻은 맞지만, 우리는 에이전트가 입구에서 정해 전파하는 길(G)을 안 쓰기로 했기 때문에, 그 뜻을 수집기에서 구현하려면 기억(F)이 필요하고 그게 비싸다.

### 그래서 D 로 간다

**네 줄을 다 읽고 가장 큰 값 하나만 쓴다.** 선이 하나면 입구를 몰라도 되고, 트레이스가 쪼개질 수 없다.

| | 장점 | 단점 |
|---|---|---|
| **D** | 선이 하나라 **깨질 수 없다.** 숫자 비도 맞는다. 코드 한 줄. 표 · API · 화면 안 고친다 | 내릴 때 안 듣는다. 화면 입력칸이 네 개인데 하나만 듣는다 : 설명이 필요 |

**고른 이유 넷**

| | 기준 | 어디로 |
|---|---|---|
| 1 | 서비스별로 다르게 둘 **실제 요구가 있나** | 넷 다 `0.0100` 이고 누가 고친 적이 없다 → **없다** |
| 2 | 다른 파트를 움직일 만한 일인가 | 이 이슈의 목표는 "재배포 없이" 고 D 로도 완전히 된다 → **아니다** |
| 3 | 마음이 바뀌면 어디로 가기 쉬운가 | D → C 는 검증 추가만. E → D 는 표를 되살려야 한다 → **D** |
| 4 | 숫자 보정 문제를 같이 풀 준비가 됐나 | `AGENTS.md` §6 미해결이 아직이다. C 는 그걸 같이 풀어야 한다 → **아니다** |

**D 는 C 의 특수 경우**다. 다 같게 두면 `상류 >= 하류` 가 자동으로 만족되므로, C 로 올라갈 때 버리는 코드가 없다.

| | 왜 |

| B 수용 | 고아가 **상시**로 생긴다. 1% 대 10% 면 전체 요청의 9%. 트레이스 추적은 핵심기능 1번이다 |

```

### 여기서 나온 면접 질문

1. 왜 샘플링을 에이전트가 아니라 수집기에서 하나. 그 선택의 대가는 무엇인가

4. 비율이 달라 트레이스가 깨질 때 두 방향 중 어느 쪽이 덜 나쁜가. 왜인가
5. 업계는 서비스별 비율을 쓰는데 왜 우리는 그 방식을 그대로 못 쓰나
6. PG 를 못 읽었을 때 "전부 통과" 와 "전부 버림" 중 무엇도 고르지 않은 이유는
7. 설정 캐시가 30초인데 수집기가 여러 대면 그 사이에 무슨 일이 생기나. 왜 고치지 않았나

## 8. 구현 프롬프트 (사람 차례)

> 7 을 읽고 승조가 결정을 글로 내린 것. **이 글이 곧 설계다.**
> 같은 원문이 [`prompts.md`](prompts.md) 와 ADR `#53` 안에도 있다.
> 2026-10-08 작성. 조사 1건과 질문 스무 번을 거친 뒤에 쓴 글이다.

```
D로 가자. 서비스별 네 줄 다 읽고 그중 가장 큰 값 하나만 쓴다.

즉 지금 문제가 샘플링 비율이 yml에 박혀 있어서 바꿀 때마다 재빌드랑 재배포가 필요한 거고
그래서 PG에서 읽게 하려는 건데, PG 설정은 서비스당 한 줄이고 샘플링은 트레이스 단위라
단위가 어긋나는 게 문제다. 수집기는 스팬에 적힌 service.name으로 줄을 찾으니까 결과적으로
서비스마다 비율이 달라진다. span_kind는 안 본다.

서비스마다 비율이 달라지면 깨지는 게 셋이다.
트레이스에서는 gateway 1% < order 10%면 부모가 버려지고 자식만 남아서 고아 스팬이 되고,
gateway 10% > order 1%면 자식 스팬이 빠지는데 이건 루트가 남아서 트리가 거짓말은 안 한다.
고객 요청 수에서는 gateway 줄과 order 줄이 쌍으로 안 들어와서 count(*)랑
count(is_root = 1)의 비가 깨진다. 모든 요청이 두 서비스를 다 지나는데 숫자가 10배 벌어진다.
서버맵에서는 간선이 gateway의 CLIENT 스팬이고 노드가 order의 SERVER 스팬이라 서비스가
달라서 비율이 갈리고, 들어온 것보다 처리한 게 많은 그림이 나온다.

깨지는 셋이 전부 두 서비스 기록을 맞춰 봐야 하는 화면이다. 한 서비스 안에서 끝나는
스캐터나 히트맵, URL 통계, 서비스 건강은 표본 밀도만 달라지고 안 틀린다.

선을 하나로 만들면 이게 다 사라진다. 우리 공식이 abs(hash) < ratio * Long.MAX_VALUE라서
비율이 같으면 한 트레이스가 전부 남거나 전부 버려지니까 그렇다.

그리고 지금 서비스별로 다르게 둘 이유가 확인이 안 된다. 네 줄이 전부 0.0100이고 seed가
넣은 뒤로 아무도 고친 적이 없다. 이 이슈에 필요한 건 서비스마다 다르게가 아니라 재배포
없이 바꾸는 거고 그건 D로도 다 된다.

B, 서비스별 비율 그대로 쓰고 깨지는 걸 받아들이는 건 안 한다.

양이 계산되는데 gateway 1%에 order 10%면 전체 요청의 9%가 고아가 된다. 그리고 에러가
나는 게 아니라 경고 없이 틀린 숫자가 뜨는 거라 증상이 샘플링 때문이라고 떠올릴 사람이
없다. 트레이스 추적은 핵심기능 1번이다. SkyWalking이 우리랑 똑같은 구조로 이 길을 가면서
비율 35 대 55 예시로 일부 세그먼트가 유실될 수 있다고 문서에 적어 놨는데 우리는 안 고른다.

C, 단조성 강제는 안 하고 되돌림에 적어 두자.

조사하다 알게 된 건데 우리 공식이 비율에 대해 단조라서 깨지는 방향이 정해져 있다. 상류
비율이 하류보다 크거나 같으면 하류가 남긴 번호표는 상류에서도 반드시 남으니까 고아가
구조적으로 생길 수가 없다. 자식만 빠지는 꼬리 잘림이 되는데 그건 하위 서비스에 에이전트가
없을 때도 생기는 거라 화면이 이미 다룬다. OTel probabilistic_sampler가 이걸 consistent
probability sampling으로 문서화해 뒀다. 다만 OTel 권장 방향은 자식 >= 부모로 우리랑
반대인데 그쪽은 하위 세부를 더 보려는 목적이고 우리는 루트가 빠지는 게 더 아프니까
반대로 가는 거다. 이건 ADR에 적어 두자.

근데 C는 고아만 막고 숫자 비 모순은 그대로 남는다. 방향만 뒤집혀서 고객 요청 1,000에
order 처리 100이 된다. 표본을 보정할지 표본이라고 표시할지는 아직 팀이 안 정한 거라 같이 풀어야 한다. 검증
코드도 API 서버 몫이라 다른 파트 일이 생기고, 호출 그래프를 코드가 알아야 해서 감시 대상이
늘면 깨진다. D가 C의 특수 경우라 다 같게 두면 조건이 자동으로 만족되니까, 서비스별로
다르게 둘 요구가 나오면 max() 떼고 검증 붙이면 된다. 버릴 코드가 없다.

E, 전역 설정 표를 새로 만드는 것도 안 한다. 참고로 이건 CH가 아니라 PG다.

뜻으로는 그게 제일 정직하다. 샘플링은 애초에 트레이스 단위라 전역 설정인데 그걸 서비스별
칸에 담은 게 어긋남의 뿌리다. 근데 PG에 전역 설정 표가 없어서 줄 하나짜리 표를 새로
만들어야 하고 주인이 API 서버라 API랑 화면이 따라온다. sampling_rate는 enabled_modules랑
log_level이 폐기된 뒤로 application_configs의 유일한 쓸모 있는 칸이라 빼면 표가 거의 빈다.
전역 설정 표 만드는 것 자체가 결정거리라 이 이슈에 끼우기엔 크다. 지금 전역 설정이 셋인데
헬스체크 주소랑 로그 하한이랑 이번 비율이고 다 env에 흩어져 있으니까 따로 올리자.
헬스체크 주소를 env에 둘 때도 샘플링 비율이 PG로 길을 뚫으면 그때 옮기자고 적어 뒀었다.

A, 루트 기준은 하고 싶어도 못 한다.

A가 gateway에서 시작한 요청이면 order 스팬도 gateway 비율을 따르게 하는 거다. 트레이스
하나에 선이 하나만 걸리니까 쪼개질 수가 없다. 조사해 보니 업계 일곱 중 여섯이 이렇게 한다.
Jaeger랑 OTel JaegerRemoteSampler, Datadog, Elastic APM, X-Ray, Pinpoint 전부 비율을 그
서비스가 입구인 트레이스에만 적용하고 하류는 전파된 결정을 따른다. Elastic 문구가 제일
선명한데 하류 서비스는 자기 비율과 무관하게 최초 서비스의 결정을 따른다고 적혀 있다.
X-Ray는 B에 규칙을 걸어도 B가 항상 A에게 불린다면 그 규칙은 영원히 적용되지 않는다고
Common Pitfall로 경고까지 해 뒀다.

못 하는 이유는 order 스팬이 왔을 때 그 트레이스의 입구가 누군지 모르기 때문이다. 스팬에
parent_span_id는 있는데 그 부모가 어느 서비스 건지는 안 적혀 있다. 부모를 못 찾는 게
아니라 부모가 누군지 알려면 기억을 해야 하는 거다. 부모 스팬은 아직 안 왔거나 에이전트
배치가 5초라 늦게 오거나 이미 처리해서 흘려보냈다. 업계가 공짜인 건 에이전트가 입구에서
판정하고 traceparent 헤더로 전파해서 하류는 헤더만 보면 되기 때문인데, 우리는 ADR #33으로
에이전트를 always_on으로 뒀으니까 그 헤더가 없다. 그래서 우리 구조에서 A는 F가 된다.

F, 스팬을 메모리에 모아 두는 것도 안 한다. 병목이 심해진다.

수집기가 스팬 데이터를 기억하는 상태를 갖게 되는데 ADR #33이 수집기 샘플링을 고른 이유가
가볍다는 거였다. 그리고 수집기가 2개 이상이 되면 LB도 필요해진다. OTel tail_sampling
README가 같은 트레이스 스팬은 전부 같은 collector 인스턴스가 받아야 한다고 대문자로 못 박아
놨다. 기본값도 30초 대기에 5만 트레이스 메모리다.

G, 수집기가 무거워지면 샘플링을 에이전트로 옮기는 건데 지금 차례가 아니다.

그게 업계 정석이고 A를 공짜로 얻는 길이긴 하다. 근데 ADR #33이 이걸 이미 되돌리는 조건으로
예약해 뒀다. 수집기 CPU랑 네트워크가 한계를 넘는 게 실측되면 에이전트 헤드 샘플링으로
전환한다고 적혀 있는데 그 실측이 없다. 틀린 방법이 아니라 아직 조건이 안 된 방법이다. 그리고 #33이 자체 Extension을
스레드 덤프 받는 것 하나로 한정해 뒀다.

읽는 방법은 ADR #37에서 이미 정해 놨다. PG를 직접 보고 30초 캐시, 실패하면 마지막 값 유지다.

적재 처리기의 PostgresServiceCatalog를 그대로 베끼면 된다. Entity 없이 JdbcTemplate으로
SQL 한 줄 치고 AtomicReference 스냅샷을 통째로 갈아끼우고, 실패하면 이전 값을 쓰면서 실패
시각은 갱신해서 매 스팬마다 PG를 다시 안 치게 하고 TTL은 설정으로 뺀다. 그 파일 짝인
ServiceCatalog.kt 주석에 수집기가 샘플링 비율을 읽는 것과 같은 성격이라고 미리 적혀 있다.
비율은 Map이 들어가니까 스냅샷 안이 불변이어야 한다. 꺼내서 수정하면 보장이 깨진다.

API 서버 경유는 #37이 이미 기각했다. 조회 장애가 수집 경로로 번지는데 수집은 99.9%,
조회는 99.5%다. 조사해 보니 실패하면 마지막 값 유지는 Jaeger랑 OTel, Elastic, SkyWalking
전원의 공통 동작이고 30초는 Elastic APM Server 기본값하고 똑같다. Jaeger랑 OTel은 60초다.

못 읽을 때 쓸 값은 두 경우로 나눈다. 읽다가 실패하면 마지막 값, 첫 조회부터 실패하면
application.yml의 0.01이다.

들고 있는 값이 있느냐 없느냐가 다르다. 첫 조회 실패에는 쓸 값이 없는데 빈 값을 그냥 쓰면
비율이 0이나 1이 되고 둘 다 사고다. PostgresServiceCatalog는 빈 집합으로 시작해도
괜찮았는데 모르는 주소는 EXTERNAL로 둔다가 틀려도 안전한 쪽이었기 때문이다. 샘플링은
안전한 쪽이 없어서 선례를 그대로 베끼면 안 되는 유일한 자리다.

1.0으로 전부 통과시키는 건 안 한다. 1% 전제로 잡은 Kafka랑 ClickHouse가 100배를 받는다.
Datadog랑 SkyWalking이 이쪽인데 그들은 보내는 쪽이 아니라 백엔드가 비율을 돌려주는 쪽이라
못 받았으면 아직 판단 재료가 없다는 뜻이다. 우리는 뒤에 저장소가 있으니까 Jaeger랑 OTel
쪽이 맞고 둘 다 0.001로 보수적으로 깐다. 0.0으로 전부 버리는 것도 안 한다. PG가 늦게 뜨는
동안 신호가 통째로 사라지고 그게 조용하다. 수집기 기동 실패도 안 한다. 수집 가용성 99.9%를
PG에 묶는 거다. Flyway 이름 규칙이 어긋나면 실행 전체를 실패시키게 해 뒀지만
거긴 기동 시점 마이그레이션이고 여긴 수집 경로라 성격이 다르다.

applications에 없는 서비스도 기본값을 주고 그 수를 카운터로 센다.

확인해 봤는데 적재 처리기가 스팬은 안 거른다. RawConsumer가 activeNames()를 peer_service
분류에만 쓰고 등록 여부랑 무관하게 다 저장한다. agents 표 등록만 건너뛰는데 그것도
application_id가 NOT NULL FK라서 못 넣는 거다. 즉 미등록 서비스를 막는 문은 수집기뿐이고
지금 열려 있다. 여기서 버리면 지금 들어오던 게 안 들어오는 동작 변경이 되고 telemetrygen이
안 보이고 서비스 등록 직후 30초 동안 그 서비스 신호가 사라진다. 이 이슈는 비율을 어디서
읽나를 바꾸는 일이라 범위를 안 넓힌다. 그리고 4317이 평문이라서 누구나 가짜 스팬을 넣을 수
있는 게 더 큰 구멍이니까, 누구를 들여보낼지는 에이전트 mTLS 할 때 한 번에 정하자.

환경변수는 기본값 자리로만 남긴다. MONIMO_COLLECTOR_SAMPLING_RATIO를 유지하되 PG를 읽는
데 성공하면 PG가 이긴다.

PG 무시 스위치로 두는 건 안 한다. 설정하면 env가 이기게 하면 운영에 켜 둔 걸 잊었을 때
화면 조작이 조용히 안 듣는다. #118에서 파일을 고쳐도 조용히 안 듣는 상황이 제일 오래
사람을 헷갈리게 했는데 같은 모양의 함정이다. Elastic도 중앙 설정이 지워지면 로컬 설정으로
돌아가는 쪽이다.

로컬 seed를 1.0000으로 바꾸자. scripts/seed/postgres-applications.sql의 0.0100을 고친다.

지금 로컬이 1.0으로 도는데 PG를 읽기 시작하면 seed 값인 1%가 적용돼서 손님 100명을 넣어도
점 한 개가 된다. 로컬 프로필에서 PG 조회를 끄는 방법도 있는데 그러면 PG 읽는 코드가
로컬에서 안 돌고 CI랑 운영에서 처음 돈다. #118에서 리뷰를 통과시킨 근거가 로컬 실데이터
확인이었으니까 그 자리를 없애지 말자.

30초 엇갈림은 안 고친다.

수집기가 여러 대면 비율을 바꾼 뒤 30초 동안 한쪽은 새 비율 한쪽은 옛 비율로 돈다. 사람이
바꿀 때만 생기고 저절로 복구되고 지금 수집기는 1대다. 없애려면 수집기끼리 설정을 맞추는
장치가 필요한데 전에 Redis를 폐기한 이유랑 같은 크기의 비용이다. SkyWalking이 같은
구조에서 값을 같게 두기를 권한다고 문서에 적어 뒀다. 버그가 아니라는 걸 ADR에 적어 둬야
나중에 누가 이걸 올리지 않는다. Datadog는 비율 상향을 직전 값의 2배까지로 제한해서 급증을
막는데 우리는 1대라 효과가 없으니까 수집기를 늘릴 때 넣는 걸로 되돌림에 적자.

해시를 뒤 7바이트로 바꾸는 것도 안 한다. OTel의 consistent sampling 사양이랑 W3C random
trace flag는 뒤 7바이트 56비트인데 우리는 8바이트에 abs()다. 아직 확정된 사양이 아니고 우리
에이전트가 그 값을 안 보내니까 이번 범위 밖이라고 적어 두자.

구현할 때 조심할 게 하나 있다. upperBound를 지금 생성자에서 한 번 계산하는데 비율이
30초마다 바뀌니까 읽을 때 계산으로 옮겨야 한다. 안 옮기면 PG를 읽어도 판정이 안 바뀌는데
로그에는 새 비율이 찍혀서 찾기 어렵다. TraceSamplerTest가 keep(span)을 7군데서 직접
부르니까 비율 공급자를 테스트에서 갈아끼울 수 있게 만들자.

확인은 PG 한 줄을 0.1로 바꾸고 30초 안에 kept랑 dropped 카운터가 바뀌는지, 네 줄이 다를 때
max()가 쓰이는지, PG 컨테이너를 멈춰도 수집이 계속 도는지, PG를 멈춘 채로 수집기를 띄워서
0.01로 가는지, 없는 서비스 이름으로 telemetrygen을 보내도 안 죽는지, down -v하고 seed
돌려서 로컬에 점이 보이는지를 본다. 적용 비율을 로그에 찍어 두면 나중에도 쓸모 있다.

조회 파트에 알릴 게 하나 있다. 코드는 안 고치는데 입력칸이 서비스별로 네 개인데 실제로는
가장 큰 값 하나만 듣는다. 화면에 한 줄 설명이 없으면 order만 내렸는데 안 듣는다는 문의가
온다. ERD의 application_configs 설명도 같이 고친다.

ADR로 남긴다. 되돌리는 조건은 네 가지다. 서비스별로 다른 비율을 쓸 요구가 나오면 C로
올라가고 그때 화면 호출 수 보정을 같이 정한다. 수집기 한계가 실측되면 ADR #33을 되돌려서
G로 가는데 그러면 전파가 생겨서 이 문제 자체가 사라진다. 외부에 OTLP 문을 열 때
미등록 서비스를 막는 걸 mTLS와 같이 정한다. 수집기를 2대 이상으로 늘릴 때 Datadog 식 2배
상한을 넣는다.

### 결정이 선택지 어디에 닿았나

| 7절 선택지 | 결정 |
|---|---|
| A 루트 기준 | 기각. 우리 구조에서 F 가 된다 |
| B 수용 | 기각. 고아가 상시로 생긴다 |
| C 단조성 강제 | **되돌림 ① 로 미룬다.** D 가 C 의 특수 경우다 |
| **D 최댓값** | **채택** |
| E 전역 한 줄 | 기각. 별 이슈로 올린다 |
| F 트레이스 모으기 | 기각. 수집기가 상태를 갖는다 |
| G 에이전트로 되돌리기 | **되돌림 ② 로 미룬다.** 조건이 아직 아니다 |
| 읽는 방법 | ADR `#37` 그대로 (PG 직접 · 30초 캐시 · 실패 시 마지막 값) |
| 못 읽을 때 | 첫 조회 실패는 yml 기본값, 읽다 실패는 마지막 값 |
| 미등록 서비스 | 기본값 + 카운터. 차단은 mTLS 와 같이 |
| 환경변수 | 기본값 자리로만 |
| 로컬 | seed 를 `1.0000` 으로 |
