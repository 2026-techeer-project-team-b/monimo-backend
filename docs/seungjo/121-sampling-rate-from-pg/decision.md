정본은 [`../../design/01-decisions.md`](../../design/01-decisions.md) 의 `#53`. 여기는 요약과 길 안내만.

## 4요소

| **채택** | ① 수집기가 `application_configs.sampling_rate` 를 서비스별로 다 읽고 **그중 최댓값 하나**를 모든 트레이스에 쓴다. 서비스별로 따로 적용하지 않는다 ② 읽는 방법은 ADR `#37` Q23 그대로 : PG 직접 조회 · 30초 캐시 · 실패 시 마지막 값 유지. | **기각 ④** 루트 기준 : "그 서비스가 입구인 트레이스의 비율" (A) | 사유: 업계 일곱 중 여섯의 뜻이지만(Jaeger · OTel `JaegerRemoteSampler` · Datadog · Elastic APM · AWS X-Ray · Pinpoint) 그들은 에이전트가 입구에서 판정하고 `traceparent` 로 전파해서 공짜다. 우리는 ADR `#33` 으로 에이전트를 `always_on` 으로 둬 전파가 없고, 수집기가 스팬을 받았을 때 `parent_span_id` 는 있어도 그 부모가 어느 서비스 건지는 적혀 있지 않다. **알려면 기억해야 하므로 우리 구조에서 ④ 는 ⑤ 가 된다** |

| **기각 ⑥** 샘플링을 에이전트로 되돌리기 (G) | 사유: ADR `#33` **되돌림 (b)** 가 "수집기 CPU · 네트워크 한계를 넘는 것이 실측되면" 으로 예약해 둔 것이고 **그 실측이 없다.** ADR `#33` 이 자체 Extension 을 스레드 덤프 수신 1건으로 한정했다 |
| **기각 ⑦** 첫 조회 실패에 `1.0`(전부 통과) | 사유: 1% 를 전제로 잡은 Kafka 와 ClickHouse 가 **100배**를 받는다. Datadog · SkyWalking 이 이쪽이지만 그들은 보내는 쪽이 아니라 백엔드가 비율을 돌려주는 쪽이라 못 받았으면 아직 판단 재료가 없다는 뜻이다. 우리는 뒤에 저장소가 있어 Jaeger · OTel 쪽(`0.001`, 보수적)이 맞다 |
| **기각 ⑧** 첫 조회 실패에 `0.0`(전부 버림) | 사유: PG 가 늦게 뜨는 동안 신호가 통째로 사라지고 그 사실이 조용하다 |
| **기각 ⑨** 첫 조회 실패에 수집기 기동 실패 | 사유: 수집 경로 가용성 99.9% 를 PG 에 묶는다. Flyway 이름 규칙에서 "큰 실패" 쪽을 고른 것(ADR `#49`)과 달리 거긴 기동 시점 마이그레이션이고 여긴 수집 경로다 |
| **기각 ⑩** 미등록 서비스를 버린다 | 사유: 적재 처리기는 `agents` 표 FK 때문에 등록만 건너뛰고 **스팬 자체는 ClickHouse 에 전부 저장한다**(`RawConsumer` 가 `activeNames()` 를 `peer_service` 분류에만 쓴다). 즉 미등록 서비스를 막는 문은 수집기뿐이고 지금 열려 있는데, 여기서 버리면 지금 들어오던 것이 안 들어오는 **동작 변경**이 되고 시험 도구(`telemetrygen`)가 안 보이고 서비스 등록 직후 30초 동안 그 서비스 신호가 사라진다. 4317 이 평문이라는 더 큰 구멍과 함께 에이전트 mTLS 에서 한 번에 정한다 |
| **기각 ⑪** 환경변수를 "PG 무시 스위치" 로 두기 | 사유: 운영에 켜 둔 것을 잊으면 **화면 조작이 조용히 안 듣는다.** `#118` 에서 파일을 고쳐도 조용히 안 듣는 상황(ClickHouse initdb)이 가장 오래 사람을 헷갈리게 했다. Elastic APM 도 중앙 설정이 지워지면 로컬 설정으로 폴백하는 쪽이다 |
| **기각 ⑫** 로컬 프로필에서 PG 조회를 끄기 | 사유: PG 읽는 코드가 **로컬에서 안 돌고 CI 와 운영에서 처음 돈다.** `#118` 에서 리뷰를 통과시킨 근거가 로컬 실데이터 확인이었다 |
| **기각 ⑬** Datadog 식 2배 상한 (비율 상향 시 한 번에 2배까지) | 사유: 수집기가 1대라 효과가 없다. 되돌림 ④ 로 미룬다 |
| **기각 ⑭** 해시를 뒤 7바이트로 바꾸기 | 사유: OTel 의 consistent sampling 사양(`tracestate` 의 `th` · `rv`)과 W3C `random` trace flag 는 뒤 7바이트(56비트)이고 우리는 8바이트 + `abs()` 인데, 아직 확정된 사양이 아니고 우리 에이전트가 `th` 를 안 보낸다. 범위 밖 |
| **되돌림** | ① 서비스별로 다른 비율을 쓸 **실제 요구가 나오면** 기각 ②(단조성 강제)로 올라간다. 최댓값은 ② 의 특수 경우라(다 같으면 `상류 >= 하류` 자동 만족) `max()` 를 떼고 검증을 붙이면 되고 버리는 코드가 없다. 그때 화면의 호출 수 보정을 같이 정해야 한다 ② 수집기 CPU · 네트워크 한계를 넘는 것이 **실측되면** ADR `#33` 되돌림 (b)를 발동해 샘플링을 에이전트로 옮긴다. 전파가 생기므로 이 ADR 이 다루는 단위 어긋남 자체가 사라진다 ③ **외부에 OTLP 문을 열 때** 미등록 서비스를 버리는 쪽으로 바꾼다. 에이전트 mTLS 와 함께 정한다 ④ **수집기를 2대 이상으로 늘릴 때** Datadog 식 2배 상한을 넣는다 |

**고의로 안 고친 것** : 수집기가 여러 대일 때 30초 동안 비율이 엇갈리는 구간은 버그가 아니다. 사람이 비율을 바꿀 때만 생기고 저절로 복구되며 지금 수집기는 1대다. 없애려면 수집기끼리 설정을 맞추는 장치가 필요한데 Redis 를 폐기한 이유(ADR `#31`)와 같은 크기의 비용이다.

**OTel 과 반대 방향인 것** : 우리 공식은 비율에 대해 단조라서 깨지는 방향이 정해져 있다. OTel `probabilistic_sampler` 가 이것을 `consistent probability sampling` 으로 문서화하면서 `자식 >= 부모` 를 권하는데(고아를 허용하고 꼬리 잘림을 막는다), 우리는 화면이 요청 수를 세고 트리를 그리므로 루트가 빠지는 쪽이 더 아프다. 그래서 단조성을 쓰게 되면 방향이 `상류 >= 하류` 로 반대가 된다. "루트 보존을 위해 상류를 크게" 라고 적힌 공식 문서는 찾지 못했다(우리 추론이다).

## 이 결정을 어떻게 내렸나

- 레포 리서치 1 · 2절 → **1차 질문 8개** → 4절 → 조사 서브에이전트 1건(업계 일곱 제품 · 폴링 주기 · 인스턴스 간 엇갈림) → 5절 선택지 **일곱** → **2차 질문 12개**(Q9 ~ Q20) → 7절에서 **넷으로 추림**(D · C · E · B) → 승조가 8절에 결정 프롬프트를 썼다. 질문은 합쳐 **스무 개**다
- 프롬프트 원문은 [`research.md`](research.md) 8절 · [`prompts.md`](prompts.md) · ADR `#53` 안. 세 곳이 글자 단위로 같다. 여기에는 베끼지 않는다
- **조사가 선택지 C 를 새로 만들었다.** 그 전까지는 "비율이 다르면 트레이스가 조각난다" 고만 보고 **깨지는 방향이 둘이고 성격이 다르다는 것을 놓쳤다.** 우리 공식 `abs(hash) < ratio * Long.MAX_VALUE` 가 비율에 대해 단조이므로, `r_상류 >= r_하류` 이면 하류가 남긴 트레이스(`hash < r_하류 * MAX`)는 `r_하류 * MAX <= r_상류 * MAX` 이라 상류에서도 반드시 남는다. 부모 없는 자식이 **생길 수 없다.** 조사가 OTel 의 `consistent probability sampling` 문서를 찾아 이것을 확인해 줬고, 그래서 C(단조성 강제)가 선택지로 올라왔다. C 가 없었으면 "안전한 길은 최댓값뿐" 이라는 틀린 전제로 결정했을 것이다
- **조사가 바꾼 것이 둘 더 있다.** ① 선택지 D("루트 서비스 비율")를 처음 "업계 방식과 같다" 로 적었는데, 맞지만 비용이 전혀 달랐다 : 업계는 루트에서 판정하고 전파하니 공짜이고 우리는 전파가 없어 같은 뜻을 구현하면 버퍼가 붙는다. 그래서 선택지를 A(루트 기준)와 F(트레이스 모으기)로 쪼갰다 ② 30초 캐시와 "실패 시 마지막 값" 이 업계 표준이라는 것을 확인했다(Elastic APM Server 기본값이 정확히 30초, 마지막 값 유지는 Jaeger · OTel · Elastic · SkyWalking 공통)
- **2차 질문이 5절의 과장을 둘 잡았다.** C 의 대가를 "고아 0" 으로만 적어 "자식이 사라진다" 를 뺐고(Q16), C 가 숫자 비 모순까지 고치는 것처럼 적었다. 선이 하나인 D · E 만 숫자 비를 고친다

### 테스트가 잡은 것

**`upperBound` 를 생성자에서 한 번 계산하면 PG 를 읽어도 판정이 안 바뀐다.** 비율이 30초마다 바뀌는데 경계선이 생성 시점 값으로 굳어 있으면, `rates()` 는 새 값을 돌려주고 로그에도 새 비율이 찍히는데 실제로 남는 스팬 수만 옛 비율대로다. 에러도 경고도 없고 로그가 거짓말을 하는 모양이라 찾기 어렵다.

그래서 계산을 `upperBound(ratio)` 로 옮기고 `TraceSamplerTest` 에 "공급자가 주는 비율이 중간에 바뀌면" 을 넣었다. 같은 샘플러 하나에 비율 `0.0` 으로 스팬 3개를 넣어 0개가 남는 것을 보고, 공급자 값을 `1.0` 으로 바꿔 다시 넣어 3개가 남는 것을 본다. 생성자 계산으로 되돌리면 두 번째 단언이 깨진다.

기존 테스트도 같이 바뀌었다. `TraceSamplerTest` 가 `SamplingProperties(ratio = ...)` 로 비율을 직접 넣고 있었는데 그 칸이 "PG 를 못 읽었을 때 쓸 기본값" 자리가 되었으므로, 가짜 공급자(`SamplingRateSource { ... }`)를 끼우는 모양으로 바꿨다. 기존 단언 10건은 그대로 살았다.
