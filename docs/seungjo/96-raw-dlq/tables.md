# 표에 미친 영향 : `#96`

> 컬럼 정본은 [`db/clickhouse/`](../../../db/clickhouse/) 의 DDL 이다. 여기서는 베끼지 않고 **왜 이 자리에서 건드려야 했나**만 적는다.

## 바꾼 표

**DDL 은 0줄.** 표 구조는 하나도 안 바꿨다. 그런데 **처음으로 데이터가 들어가는 저장소**가 하나 생긴다 : Kafka 토픽 `raw.dlq`. `compose.yaml` 이 만들어 두기만 했고(`#3` `#7`, 파티션 1 · 30일) 지금까지 `raw.dlq:0:0` 이었다. 이번 이슈가 거기에 넣는 첫 코드다.

## 건드린(영향받은) 표

```
수집기 ─▶ Kafka raw (7일) ─▶ 적재 처리기 ─▶ spans · metrics_raw · logs ─▶ MV 7개 ─▶ 집계 표 7개
                                  │
                                  │ 적재 실패 (ADR #51 로 세 갈래)
                                  │   독성          → 바로
                                  │   모르는 실패   → 1분 뒤
                                  │   일시 장애     → 10분 뒤 (그 안에 되살면 안 간다)
                                  ▼
                            Kafka raw.dlq (30일)  ← 이번에 처음 데이터가 들어간다
```

| 저장소 | 주인(쓰는 쪽) | 전에는 | 이번 작업 뒤 |
|---|---|---|---|
| `spans` · `metrics_raw` · `logs` | 적재 처리기 | ClickHouse 가 죽은 동안 들어온 메시지는 **영구 유실**(4초 재시도 뒤 오프셋이 넘어감). 재현 : 정지 중 스팬 4개 → 되살려도 226,417줄 그대로 | **10분 안에 되살면 전부 들어온다.** pause 로 기다렸다가 자동 적재 |
| 집계 7표 (`service_health_1m` 등) ← MV | MV 자동 | 유실된 만큼 집계도 빠졌다. 그리고 `319` 재시도가 생기면 **같은 스팬이 두 번 세어질 수 있었다**(MV 는 insert 시점에 세고 merge 를 안 본다) | 빠지는 것이 없어지고, `319` 를 재시도에서 빼서 **중복 세기도 막는다** |
| `raw.dlq` 토픽 | **적재 처리기 (프로듀서)** | 비어 있었다. 쓰는 코드가 없었다 | 독성 메시지 · 10분 넘긴 일시 장애 · 1분 넘긴 모르는 실패가 들어간다. 헤더 `x-dlq-attempt` · `x-dlq-reason` · `kafka_dlt-original-*` 가 붙는다 |
| `raw` 토픽 | 수집기 (프로듀서) · 적재 처리기 (컨슈머) | 실패해도 오프셋이 넘어가 **메시지는 있는데 아무도 안 읽는** 상태 | 실패하면 **오프셋이 머문다.** 7일 안에 되살면 그 자리에서 이어 읽는다 |

**`raw.dlq` 의 컨슈머 그룹은 아직 없다.** 적재 처리기는 거기에 쓰기만 한다. 읽는 쪽(재처리 잡)은 ADR `#34` 가 "같은 이미지 · K8s Job · 다른 `group-id`" 로 정했고 이 이슈 범위 밖이다.

## 왜 표 주인이 아닌 에러 핸들러에서 고쳤나

`spans` 의 주인은 적재 처리기지만, 고친 곳은 `RawConsumer.onMessage` 가 아니라 **그 밖의 에러 핸들러**다. 두 가지 이유다.

**① `onMessage` 안에서 잡으면 안 된다.** 에러 핸들러는 리스너가 **예외를 던졌을 때** 동작한다. `onMessage` 안에 `try-catch` 를 넣으면 예외가 안 올라가서 재시도도 DLQ 도 안 된다. 그래서 `onMessage` 는 한 줄도 안 건드렸다.

**② 집계에 영향 가는 수정은 `spans` 에 들어가기 전이어야 한다.** `#83`(`peer_service` 를 적재 전에 채움) · `#92`(헬스체크를 발행 전에 버림)와 같은 교훈이다. MV 는 insert 시점에 계산하고 그 줄을 다시 안 본다. 그래서 중복(`319`)도 유실도 **insert 전**에 막아야 하고, `ReplacingMergeTree` 같은 표 엔진으로는 늦다.

## 이 표들이 고장 나면

| 가정 | 무슨 일이 생기나 | 막아 둔 것 |
|---|---|---|
| ClickHouse 가 10분 **안에** 되살아난다 | `spans` 등에 **빠짐 없이** 들어간다. 집계도 그대로 | pause 10분. 리밸런스는 안 난다(`poll` 이 계속 돈다) |
| ClickHouse 가 10분 **넘게** 죽어 있다 | 오프셋마다 10분씩 기다리다 `raw.dlq` 로. **10분에 한 건씩**이라 홍수가 아니다. 나머지는 `raw` 에 남아 있다(7일) | `FailedRecordTracker` 가 오프셋마다 예산을 따로 센다 |
| `319` 가 온다 | 재시도 없이 `raw.dlq`. **`spans` 와 MV 에 중복이 안 생긴다** | `FailureClassifier.POISON_CODES` 에 `319` |
| 디스크가 꽉 찬다 (`243`) | 10분 기다린다. 그 안에 늘려 주면 유실 0 | `TRANSIENT_CODES` 에 `243`. 빠뜨렸어도 UNKNOWN(1분) 으로 떨어져 유실은 아니다 |
| `raw.dlq` 발행 자체가 실패한다 | 예외가 올라와 **오프셋이 안 넘어간다.** `raw` 에 그대로 있다 | `setFailIfSendResultIsError(true)` |
| `raw` 파티션 1 · 2 에서 실패한다 | `raw.dlq` 는 파티션이 1개뿐이지만 **들어간다** | `verifyPartition`(기본 `true`)이 목적지에 없는 번호를 비워 Kafka 가 고르게 한다 |
| 적재 처리기가 여러 대가 된다 | pause 가 **컨테이너 단위**라 한 대 안의 파티션 전부가 같이 멈춘다. 지금은 저장소가 하나라 그게 맞는 동작이다 | ADR `#51` 되돌림 ③ : 파티션별로 다른 저장소를 쓰게 되면 `pausePartition` 으로 좁힌다 |

## 다른 파트에 알릴 것

- **알림(ukong) · 화면(Nova)** : ClickHouse 가 짧게 죽었다 살아난 뒤 **그 구간의 집계가 비지 않고 뒤늦게 채워진다.** 전에는 그 구간이 영구히 비었다. 시간축에 "늦게 도착한 데이터" 가 생기는 것이 정상이다
- **배포(승조)** : `raw.dlq` 에 데이터가 쌓이기 시작한다. 30일 보관이라 디스크를 조금 쓴다. 쌓이는 속도가 10분에 1건 이상이면 ClickHouse 가 10분 넘게 죽어 있다는 뜻이다
