# `#135` 수집기 · 적재 처리기 헬스체크 probe : 저장소를 안 보고, 업무 포트에도 연다

- 2026-10-10 / 승조(`@SeungJo-02`) / 결정 ADR `#58` / 이슈 [`#135`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/135)
- 유저 플로우에서 어디: 쿠버네티스(kubelet) → **수집기 · 적재 처리기 파드의 두 주소** → 200 이면 트래픽을 보내고 살려 두고, 아니면 빼거나 다시 띄운다. 화면 · 에이전트 · 저장소 코드는 0줄 바뀐다. 바뀐 것은 두 모듈의 설정과 compose · 점검 스크립트다

## 문제

쿠버네티스가 파드에 묻는 두 질문(살았나 · 받을 준비됐나)에 수집기 · 적재 처리기가 **답할 주소가 없다.** 없으면 쿠버네티스는 컨테이너가 떠 있다는 것만 보고 트래픽을 보내고, 멍하니 멈춘 프로세스도 그대로 둔다.

| 재 본 것 (2026-10-10) | 값 |
|---|---|
| 수집기 · 적재 처리기 설정에 probe 가 | **없다.** `/actuator/health/liveness` 를 부르면 404 |
| 두 모듈의 `/actuator/health` · `/actuator/metrics` 가 열린 곳 | **업무 포트**(8081 · 8082). 관리 포트가 없어서 밖으로 보인다 |
| 명세(`api-spec.md` §0)가 적은 주소 | `/healthz` · `/readyz` · `{"status":"ok"}` · 서비스 6개 |
| 먼저 켠 탐지 · 알림이 실제로 쓴 주소 | `/actuator/health/liveness` · `/readiness` · 관리 포트 8081 · readiness 에 `db` |
| 규약이 수집 쪽에 적은 readiness 확인 대상 | 수집기 = Kafka · PG 설정 캐시, 적재 처리기 = Kafka · ClickHouse |
| 그중 Spring Boot 가 자동으로 확인해 주는 것 | **PG 하나.** `KafkaHealthIndicator` 는 2018 년에 들어왔다가 빠지고 안 돌아왔다. 적재 처리기의 ClickHouse 는 JDBC 가 아니라 안 잡힌다 |
| 규약의 관리 포트 8081 | **수집기 업무 포트와 겹친다.** 탐지 · 알림이 그래서 local 프로필에 포트 덮어쓰기를 두고 있다 |

**무엇이 깨지나**: 명세대로 `/healthz` 를 열면 다섯 서비스 중 둘만 다른 주소가 된다. 규약대로 저장소를 readiness 에 넣으면 **저장소가 하나라 흔들릴 때 파드가 전부 동시에 빠지고**, 쿠버네티스는 원인을 못 보고(1초에 끊는데 답은 30초 뒤), 수집기가 빠지면 에이전트가 신호 보낼 곳이 없어 그 시간대 데이터가 영구히 사라진다. 규약대로 관리 포트만 쏘면 **업무 포트가 막혀도 "정상"** 이 나온다(Spring Boot 공식 문서가 경고하는 모양).

## 선택지

| 묶음 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| readiness 에 저장소 | **안 넣는다** | 규약대로 다 넣기 = 확인 기능 둘을 직접 짜야 하고 파드가 전부 동시에 빠진다 · PG 만 넣기 = 수집기는 PG 없이도 일하는데 스스로 빠져 데이터를 버린다 |
| 업무 포트에 probe 주소 | **연다** (`/livez` · `/readyz`) | 관리 포트만 = 업무 포트가 막혀도 통과한다(공식 경고) |
| 관리 포트 번호 | **업무 포트 + 10** (8091 · 8092) | 8081 지키고 수집기 업무 포트 옮기기 = 쇼핑몰 레포까지 번진다 · 안 나누기 = `/actuator/metrics` 가 밖에 보인다(`/env` 는 두 모듈이 열어 둔 적이 없다) |
| 수집기 gRPC 수신 확인 | **안 한다** | 상태 값 읽기 = 멍하니 멈춘 경우를 못 잡는다 · 네이티브 grpc probe = 라이브러리 추가 + 포트를 이름으로 못 가리킨다 |

같이 정한 것 : `/actuator/**` 가 관리 포트로 가면서 깨지는 **둘을 범위에 넣는다.** 점검 스크립트 둘은 관리 포트를 읽고(compose 가 호스트에 연다), compose 헬스체크 둘은 업무 포트 `/readyz` 를 찌른다.

## 결정

- **고른 것**: 설정만 바꾼다. 관리 포트 8091 · 8092 로 `/actuator/**` 를 옮기고, `probes.enabled` + `add-additional-paths` 로 관리 포트의 규약 주소와 업무 포트의 `/livez` · `/readyz` 를 함께 연다. `group` 은 적지 않아 두 그룹 다 자기 상태만 본다. 코드 0줄, 시험은 모듈마다 7건
- **2026-10-11 바뀐 것(`#148` · ADR `#61`)**: 관리 포트 번호 규칙을 **업무 포트 + 10000**(18081 · 18082)으로 바꿨다. +10 의 8091 · 8092 가 monimo-shop order · payment 의 호스트 포트와 겹쳐 두 compose 를 한 컴퓨터에 못 띄웠다. 이 조사가 "다섯 모듈을 한 컴퓨터에 다 띄워도 안 겹친다" 고 적은 것은 우리 모듈끼리만 본 것이다. 나머지 결정(저장소 안 봄 · 업무 포트 추가 주소 · 그룹 안 적음)은 그대로다
- **버린 것과 이유**: 위 표. 규약과 다르게 간 둘(저장소 안 봄 · 업무 포트에도 연다)은 ADR `#58` 에 사유와 되돌리는 조건을 남겼다
- **되돌리는 조건**: 저장소가 파드마다 다른 구성이 오면 readiness 에 넣는 것을 다시 본다 · 에이전트가 버퍼링 · 재시도를 하게 되면 "데이터가 사라진다" 사유가 없어진다 · Spring Boot 가 Kafka 지표를 다시 넣으면 적재 처리기 쪽을 다시 본다 · 팀이 포트 규칙을 다르게 정하면 따른다(쿠버네티스는 포트를 이름으로 가리켜 배포 설정은 하나다) · gRPC 수신이 "뜬 뒤 조용히 죽는" 일을 실제로 겪으면 확인 수단을 다시 꺼낸다

## 어떻게 확인했나

- 모듈마다 `HealthProbeTest` **7건** : 업무 포트 `/livez` · `/readyz` 200 에 본문 `{"status":"UP"}` · 관리 포트 규약 주소 둘 200 · 업무 포트 `/actuator/health` · `/metrics` 404 · `db` 지표는 등록돼 있는데 두 그룹 어디에도 없음 · **PostgreSQL 컨테이너를 멈춘 뒤 전체 `/actuator/health` 503 인데 probe 둘 200**
- 전체 시험 · compose 실측은 [`research.md`](research.md) 9 절에 숫자로

## 장애가 나면

| 보이는 것 | 원인 | 보는 곳 |
|---|---|---|
| probe 주소가 404 | `probes.enabled` 가 빠졌거나 프로필이 덮어썼다. 에러가 아니라 조용히 없다 | 두 모듈 `application.yml` 의 `management.endpoint.health.probes` |
| `/livez` 는 200 인데 쿠버네티스가 파드를 뺀다 | 쏘는 쪽 주소 · 포트가 다르다. 그룹 이름을 오타 내면 오타 난 주소가 하나 더 열리고 원래 것은 그대로다 | 매니페스트의 `httpGet.path` · `port` 와 `kubectl describe pod` 의 probe 실패 메시지 |
| 저장소가 죽었는데 파드가 그대로 받는다 | **의도한 동작이다.** 수집기는 받아서 Kafka 로 넘기고, 비율은 낡은 값으로 돈다(`#54` 의 낡음 게이지가 오른다). 저장소 장애는 저장소 쪽 경보로 본다 | `/actuator/metrics` 의 샘플링 낡음 게이지 · 탐지의 저장소 경보 |
| 점검 스크립트가 "카운터 조회 실패" | 관리 포트가 호스트에 안 열렸다(compose 를 옛 것으로 띄웠거나 `.env` 가 포트를 바꿨다) | `docker compose ps` 의 PORTS 에 18081 · 18082 가 있나(`#148` 전 이미지는 8091 · 8092) |
| `up --wait` 가 150초 뒤 "container is unhealthy" 로 실패한다 | **이 브랜치를 받은 뒤 `--build` 없이 띄웠다.** compose 는 있는 이미지(`monimo/collector:dev` · `monimo/ingester:dev`)를 다시 안 만들어서 옛 jar 에는 `/readyz` 가 없고, 헬스체크가 5초 × 30회 전부 실패한다. 아니면 `add-additional-paths` 가 꺼져 있다 | `docker compose --profile collector --profile ingester up -d --wait --build` 로 다시 만든다 · `docker compose logs collector` 에 `/readyz` 404 가 있나 |
