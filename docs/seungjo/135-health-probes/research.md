## 1. 이번 작업은 무엇을 하는 일인가

**지금 무엇이 잘못됐나** : 우리 서비스는 자기 상태를 밖에 알려 줄 수단이 없다. 쿠버네티스는 서비스 속을 못 보고 프로세스가 떠 있으면 멀쩡한 줄 안다. 수집기 · 적재 처리기에 그 수단이 없다(탐지 · 알림은 먼저 켰고, API 서버는 팀 규약이 재범 몫으로 정했다). 그리고 두 모듈 모두 관리용 주소를 업무 포트와 나누지 않아서 `/actuator/health` 와 `/actuator/metrics` 가 손님이 들어오는 포트에 붙어 있다.

**그래서 무엇을 하나** : 두 모듈에 질문 두 개에 답하는 주소를 만든다. "불 켜져 있어?"(아니면 쿠버네티스가 재시작한다) 와 "지금 손님 받을 수 있어?"(아니면 손님만 다른 쪽으로 보낸다). 그리고 관리 주소를 손님 쪽에서 가린다.

**안 하면 어떻게 되나** : 안에서 멈춘 파드를 갈아 끼우지 못한다. 새 버전으로 바꾸는 중에 준비 안 된 파드로 요청이 가서 버려진다. 배포 설정에 이 주소를 적는 자리가 있어 비워 둘 수 없으므로 배포 7~9단계를 시작할 수 없다. 관리 주소가 외부에 열린 채로 공개된다.

## 2. 작업하기 전에 알아야 하는 것

꼭 알아야 하는 것 다섯 개다. 이 다섯이 구현을 가른다. 그 밖에 알아 두면 좋은 것은 2.6 에 짧게 모았다.

### 2.0 이 글에서 "저장소" 는 무엇을 말하나

우리 앱 바깥에 있고 데이터를 넣고 꺼내는 것들이다. 셋이다. git 레포를 뜻하지 않는다(이 레포는 git 쪽을 "레포" 로 부른다).

| | 무엇에 쓰나 | 누가 쓰나 |
|---|---|---|
| PostgreSQL | 설정값 · 사용자 · 경보 규칙 · 에이전트 명단 | 다섯 모듈 전부 |
| ClickHouse | 신호(스팬 · 메트릭 · 로그) | 적재 처리기가 쌓고 API 서버가 읽는다 |
| Kafka | 수집기와 적재 처리기 사이의 통로 | 수집기가 넣고 적재 처리기가 꺼낸다 |

### 2.1 두 문은 하는 일이 다르고, 한쪽에는 저장소를 넣으면 안 된다

둘 다 쿠버네티스가 10초마다 보내는 HTTP 요청이다. 다른 것은 **아니라고 답했을 때 쿠버네티스가 하는 일**이다.

| | 3번 연속 아니라고 답하면 | 파드는 | 되돌아오는 방식 |
|---|---|---|---|
| `readiness` | 손님 목록에서 **뺀다** | 계속 살아 있다 | 다시 된다고 답하면 저절로 들어온다 |
| `liveness` | 파드를 **죽이고 새로 만든다** | 없어진다 | 처음부터 다시 뜬다 |

파드가 **무엇을 보고 답할지**가 설정이다. 기본은 자기 상태만 본다.

**`liveness` 에 저장소를 넣으면 안 된다.** 공식 문서 원문이다.

> The 'liveness' probe should not depend on health checks for external systems. If the liveness state of an application is broken, Kubernetes tries to solve that problem by restarting the application instance. This means that if an external system (such as a database, a Web API, or an external cache) fails, Kubernetes might restart all application instances and create cascading failures.

PostgreSQL 이 10초 흔들리면 다섯 서비스의 **모든 파드가 동시에 죽고 새로 뜬다.** 새로 떠도 PostgreSQL 은 여전히 흔들리는 중이라 새 파드도 똑같이 못 붙는다. 또 죽이고 또 만든다. 무한히 반복한다.

`readiness` 는 공식 문서가 정답을 주지 않는다.

> As for the 'readiness' probe, the choice of checking external systems must be made carefully by the application developers. ... you have to make a judgement call: Include it in the readiness probe and expect that the application is taken out of service when the external service is down or leave it out and deal with failures higher up the stack, perhaps by using a circuit breaker in the caller.

**그래서 이번에 고를 것은 하나뿐이다 : 세 모듈의 `readiness` 에 저장소를 넣을까.** `liveness` 는 셋 다 안 넣는 것으로 정해져 있다.

### 2.2 저장소 확인은 기본이 아니었다. 먼저 한 쪽이 일부러 넣은 것이다

탐지 · 알림 설정에 `readiness` 가 PostgreSQL 을 보라는 한 줄이 있다. 그걸 보고 "원래 그렇게 되는 기능" 이라고 생각했다. **아니었다.**

> By default, Spring Boot does not add other health indicators to these groups.
> For this reason, Spring Boot does not include any additional health checks in the readiness probe.

라이브러리 안에 실제로 박힌 글자도 꺼내 봤다. 문서와 같았다.

```
묶음 이름            liveness · readiness
그 묶음에 기본으로 든 것   livenessState · readinessState   (자기 상태 하나씩)
추가 경로 기본값        /livez · /readyz
```

**이게 왜 중요한가** : 원래 그런 기능이면 그냥 켜면 되고 고민할 것이 없다. 그 사람이 고른 것이면 **우리도 골라야 한다.** 그리고 우리 사정이 다르다. 수집기는 이전에 두 번 "저장소가 죽어도 수집은 계속 돌고 비율만 낡는다" 로 정해 뒀고 낡은 정도를 밖에서 보는 수치까지 넣었다. 거기에 저장소 확인을 넣으면 그 결정을 뒤집는다.

내가 "원래 그런 것" 이라 믿고 갔으면 설정을 베끼면서 그 결정을 **모르는 채로 뒤집었을 것이다.**

### 2.3 저장소를 넣으면 파드가 전부 동시에 빠지고, 쿠버네티스는 원인을 못 본다

`readiness` 의 원래 쓸모는 **아픈 파드만 골라 빼는 것**이다. 파드마다 답이 달라야 작동한다.

```
파드 1 의 네트워크만 꼬였다
  파드 1 -> "못 받는다"     -> 쿠버네티스가 파드 1 만 뺀다
  파드 2 -> "받을 수 있다"
  파드 3 -> "받을 수 있다"   -> 요청이 2 · 3 으로 간다. 서비스는 계속 된다
```

저장소를 보게 하면 답이 갈리지 않는다. **저장소는 파드 전부가 같이 쓰는 하나다.**

```
PostgreSQL 이 죽었다
  파드 1 -> 연결 실패 -> "못 받는다"
  파드 2 -> 연결 실패 -> "못 받는다"
  파드 3 -> 연결 실패 -> "못 받는다"
  -> 쿠버네티스가 셋 다 뺀다. 손님 목록이 0개가 된다
```

골라내는 일이 아니라 전멸이 된다. 핵심은 이것이다. **파드마다 다른 것**(자기 상태)을 넣으면 골라낼 수 있고, **파드가 다 같이 쓰는 것**(저장소)을 넣으면 다 같이 아프거나 다 같이 괜찮다.

**그리고 쿠버네티스는 왜 빠졌는지 모른다.** 숫자가 어긋나기 때문이다.

앱이 저장소를 쓰는 단계가 셋이고 한도가 각각 따로다.

| 단계 | 하는 일 | 한도 | 누가 정했나 |
|---|---|---|---|
| 1 연결 얻기 | 미리 만들어 둔 연결 묶음에서 하나를 받는다 | **30초** | 기본값 |
| 2 살았나 확인 | 받은 연결이 쓸 수 있나 본다 | 5초 | 기본값 |
| 3 대답 기다리기 | 질문을 보내고 바이트를 기다린다 | 10초 | 앞선 작업이 넣음 |

저장소가 죽으면 **1단계에서 막힌다.** 연결을 만들 수가 없으니 그 작업은 30초를 꽉 채우고 실패한다. 2 · 3단계까지 가지 못하므로 3단계의 10초는 쓰이지 않는다.

그런데 쿠버네티스가 응답을 기다리는 한도는 **1초**다(기본값).

```
쿠버네티스가 보내는 것    파드의 관리 포트로 HTTP 요청 하나
쿠버네티스가 기다리는 것   그 요청에 대한 응답. 한도 1초

1초 안에 응답이 오면      200 이면 성공, 503 이면 실패로 센다
1초 안에 응답이 안 오면    연결을 끊고 실패로 센다. 받은 것은 아무것도 없다
```

저장소가 죽으면 앱은 1초 안에 응답을 만들 수 없다. 30초째 연결을 기다리는 중이다. 그래서 쿠버네티스가 받는 것은 **503 이 아니라 아무것도 없음**이다.

```
만약 앱이 1초 안에 503 을 보냈다면
  쿠버네티스 쪽 기록 : "응답 503, 본문에 db DOWN"   <- 원인이 보인다

실제로 벌어지는 것
  쿠버네티스 쪽 기록 : "probe failed: timeout"      <- 원인이 안 보인다
```

쿠버네티스 입장에서 앱이 멈춘 것인지, 저장소 때문인지, 네트워크가 끊긴 것인지 구별할 수 없다. 전부 똑같이 `timeout` 이다.

**바로잡은 것** : 처음에는 여기에 "확인하는 일 자체가 저장소를 더 막는다" 를 셋째 문제로 적었다. 숫자를 안 재고 단정한 것이다. 세어 보니 동시에 기다리는 확인 작업이 두세 개이고 API 서버 기본 스레드가 200개다. 영향이 작다. 그리고 그 작업은 연결을 **쥐고 있는 것이 아니라 줄에 서서 기다리기만** 한다. 지웠다.

**모듈마다 잃는 것이 다르다.**

| 모듈 | 파드가 전부 빠진 동안 |
|---|---|
| API 서버 | 화면이 연결조차 못 한다. 안 넣었으면 오류 응답이라도 받아 "데이터를 못 불러왔습니다" 를 보여 줄 수 있다 |
| 수집기 | **에이전트가 신호를 버린다.** 아래 참조 |
| 적재 처리기 | 손해가 없다. 원래 손님을 안 받고 Kafka 에서 스스로 꺼내 먹는다 |

수집기가 특히 나쁘다. 쇼핑몰 앱의 에이전트는 보낼 것을 메모리에 잠깐 모아 두는데 그 칸이 정해져 있다(기본 2048개). **칸이 차면 새로 들어오는 것을 버린다.** 버려진 신호는 다시 만들어지지 않으므로 그 시간대 관측 데이터가 영구히 빈다. 하필 그 시간대가 장애 시간대다.

그런데 수집기는 PostgreSQL 을 **샘플링 비율 하나 읽는 데만** 쓴다. 30초마다 다시 읽고 못 읽으면 마지막 값을 그대로 쓴다. 즉 PostgreSQL 이 죽어도 **신호를 받아 Kafka 에 넣는 일을 그대로 할 수 있다.** 저장소 확인을 넣으면 **할 수 있는 일을 스스로 포기하고 데이터를 버리는 것**이 된다.

### 2.4 관리 포트를 나누는 것이 정답이 아니고, 번호가 수집기와 겹친다

- **포트** : 서비스가 요청을 받는 문 번호. **한 프로세스 안에서 같은 번호를 두 번 열 수 없다**
- **한 문에 섞인 두 종류** : 업무 주소(화면 · 에이전트가 쓰는 것) · 관리 주소(앱이 자기 속을 보여 주는 것)
- **나누면 좋은 점** : 외부는 인그레스에 적힌 문만 닿는다. 관리 문을 안 적으면 밖에서 들어올 길이 없다
- **쿠버네티스는 예외** : 인그레스를 안 거치고 파드에 직접 붙는다. 그래서 관리 문에도 닿는다
- **나누기만 하면 안 되는 이유** : 두 문이 일꾼과 연결 묶음을 따로 가진다
- **거짓 정상** : 업무 문 일꾼이 다 차서 요청을 못 받는데 관리 문 일꾼은 한가해서 "정상" 이라고 답한다
- **공식 권장** : 업무 문에도 같은 주소를 열어라. 업무 문이 막히면 그 주소도 같이 막혀 알아차린다

그래서 **결정이 둘로 갈린다.** 섞으면 안 된다.

- **probe 주소는 업무 문에** : 업무 문이 막힌 것을 알아차리려고
- **나머지 관리 주소는 다른 문에** : 밖에서 안 보이게. **probe 와 상관없는 일이다**

번호 쪽 사정이다.

- **공식 관례** : 없다. 공식 예시는 숫자 대신 빈칸으로 둔다
- **먼저 한 쪽이 고른 번호** : 8081. 관습이고 표준이 아니다
- **막히는 곳** : 수집기가 8081 을 업무 문으로 이미 쓴다. 한 프로세스 안이라 못 겹친다
- **수집기 번호를 옮기는 비용** : 쇼핑몰 에이전트가 그 번호로 명령을 받으러 온다 + 로컬 구성 셋 · 점검 스크립트 둘 · 안내 문서 넷
- **이미 생긴 부작용** : 한 컴퓨터에서 수집기와 탐지를 같이 띄우면 겹친다. 그래서 탐지 · 알림이 **로컬 전용 설정 파일을 따로** 쓰고 있다

```
수집기 8081 · 적재 처리기 8082 · API 서버 8080   관리 문 없음
탐지 8083 · 알림 8084                           관리 문 8081 (로컬만 8083 · 8084)
```

### 2.5 팀이 규약을 이미 바꿨고, 그 규약의 전제 하나가 틀렸다

조사에서 가장 늦게 찾았고 가장 많이 바꾼 것이다.

처음에는 "설계 명세와 먼저 한 쪽이 어긋나 있다" 로 봤다. 명세는 `/healthz` · `/readyz` 를 적었는데 탐지 · 알림은 `/actuator/health/liveness` 로 구현했기 때문이다. **그래서 명세대로 되돌리는 쪽을 고르려 했다.**

틀렸다. 먼저 한 쪽의 커밋 첫 줄이 이렇게 적혀 있었다.

```
헬스체크 규약(/healthz · /readyz -> Actuator probe)에서 알림 파트 몫. 코드 없이 설정만.
```

**팀이 규약을 바꾼 것이었다.** 규약 원문(재범, 2026-09-30)이 사유까지 적어 뒀다.

> `/healthz` 가 liveness 인지 통합 체크인지 애매하다. 쿠버네티스도 같은 이유로 자기 `/healthz` 를 버리고 둘로 쪼갰다(v1.16 deprecated). 경로 이름은 앱이 정하는 것이라 쿠버네티스 것과 같을 필요가 없고, Spring Boot 공식 probe 예시도 위 경로를 쓴다

낡은 것은 명세였고 **나는 낡은 쪽을 따라가려 했다.** 결과물만 보고 커밋 메시지를 안 읽은 탓이다.

규약이 정한 것 셋이 더 있다.

| | 규약 |
|---|---|
| 서비스 수 | 6개가 아니라 **5개**. 파수꾼은 평소 떠 있지 않아 HTTP 주소가 없다 |
| 응답 모양 | `{"status":"ok"}` 가 아니라 `{"status":"UP"}` · `{"status":"DOWN"}` |
| 누가 켜나 | API 서버 = 재범 · **수집기 = 승조** · **적재 처리기 = 승조** · 탐지 · 알림 = 유경 |

**API 서버는 내 몫이 아니었다.** 내가 범위에 넣은 것이 잘못이다.

규약은 서비스별로 무엇을 확인할지도 적어 뒀다.

```
수집기       readiness 가 확인할 것 : Kafka 연결 · PG 설정 캐시
적재 처리기   readiness 가 확인할 것 : Kafka · ClickHouse
```

**그런데 그 전제가 틀렸다.** 규약은 이렇게 적었다.

> `HealthIndicator` 자체는 Spring Boot가 클래스패스를 보고 자동 등록하지만(PostgreSQL `DataSourceHealthIndicator`, Kafka `KafkaHealthIndicator`)

`KafkaHealthIndicator` 가 **Spring Boot 에 없다.** 2018년에 한 번 들어왔다가 빠졌고 그 뒤 안 돌아왔다.

> We've got several community feedback on the health indicator for Kafka ... We've been looking at it issue most of today and came to the conclusion it isn't mature enough for us to provide a health indicator out of the box.

`3.5.16` 자동 등록 목록에도 없다. 즉 규약이 내 몫으로 적은 "Kafka 연결" 은 설정 한 줄이 아니라 **구현체와 타임아웃을 새로 짜는 일**이다. ClickHouse 도 적재 처리기 쪽은 붙는 방식이 달라 안 잡힌다(API 서버는 잡힌다).

**규약이 안 담은 것도 하나 있다.**

> probe는 kubelet이 클러스터 안에서 파드에 직접 붙으므로 8081이어도 문제없다

공식 문서는 반대 방향으로 경고한다(2.4). 관리 포트만 쓰면 업무 포트가 막혀도 통과한다. 규약을 쓴 사람이 이 경고를 못 본 것으로 보인다. 그래서 내가 하는 일은 **규약을 깨는 것이 아니라 한 줄을 보태는 것**이 된다.

마지막으로 규약 자신이 명세 반영 목록을 적어 뒀는데(`H1` · `H2` · `H3`) **아직 반영되지 않았다.** `api-spec.md` 는 여전히 `/healthz` · 서비스 6개 · `{"status":"ok"}` 다.

### 2.6 추가로 알아 둘 것

**조용히 틀리는 자리가 셋 있다.** 켜는 설정을 빼먹으면 주소가 **404** 로 그냥 없다(에러가 아니다). 묶음 **이름**을 오타 내면 **아무 일도 안 나고** 오타 난 이름의 주소가 하나 더 열린다(이름이 자유 문자열이라 검증 대상이 아니다). 안에 넣을 항목 **ID** 를 오타 내면 앱이 안 뜬다(이건 시끄러워서 괜찮다). 앞의 둘은 시험으로 고정해야 한다.

**저장소가 공짜로 확인되는 모듈이 다르다.** 표준 기능은 특정 방식으로 붙은 저장소만 자동으로 잡는다. API 서버는 PostgreSQL 과 ClickHouse 가 둘 다 그 방식이라 **한 줄로 둘 다 확인된다**(명세가 적은 것과 같아진다). 적재 처리기는 ClickHouse 가 다른 방식이라 안 잡힌다. 수집기는 PostgreSQL 만 쓴다.

**`readiness` 는 Service 로 트래픽을 받는 것에만 의미가 있다.** 적재 처리기는 Kafka 에서 스스로 꺼내 먹으므로 `readiness` 가 아니라고 해도 하는 일이 바뀌지 않는다. 막는 것은 새 버전 교체뿐이다.

**관리 포트를 나눠도 보안이 자동으로 갈라지지 않는다.** 나누는 것은 노출 범위를 줄이는 일이고 누가 들어올 수 있나는 별개로 설정하는 일이다. 라이브러리 쪽에 보고된 미해결 문제도 있다. 다행히 업무 포트에 추가로 연 주소 둘만 골라 열어 주는 표준 수단이 있다. 지금 API 서버는 보안 설정이 "나머지는 다 열어 둔다" 로 덮고 있어서, 열린 양은 작지만 **다음 사람이 관리 주소를 하나 더 열면 문턱 없이 같이 열린다.**

**쿠버네티스는 포트를 번호 대신 이름으로 가리킬 수 있다.** 그래서 번호는 모듈마다 달라도 되고 이름만 맞추면 배포 설정이 하나로 유지된다. 단 신호 받는 쪽을 그쪽 규격으로 직접 찌르는 방식은 이름을 못 쓴다.

**수집기의 신호 받는 쪽은 확인 코드가 필요 없다.** 뜰 때 자리를 못 잡으면 앱 기동 자체가 실패해 프로세스가 죽고, 그러면 쿠버네티스가 알아서 다시 띄운다. 남는 경우는 "뜬 뒤에 조용히 죽는" 것뿐이고 아직 겪지 않았다.

**끄는 신호를 받으면 `readiness` 가 먼저 거짓이 되고 그 뒤에 처리 중이던 요청을 끝낸다.** 다만 그것만으로는 요청이 샐 수 있어서 배포 설정에 잠깐 기다리는 단계를 넣으라고 공식 문서가 권한다. 배포 설정을 쓸 때의 일이다.

**쿠버네티스 기다림 기본값** : 처음 지연 0초 · 묻는 간격 10초 · 한 번 기다림 1초 · 3번 실패하면 처리. 기동이 느린 앱은 "다 떴나" 를 따로 묻는 단계를 둘 수 있는데 값은 실제 기동 시간을 재서 정해야 하므로 배포 설정을 쓸 때의 일이다.

**수집기가 거르는 헬스체크 목록은 안 건드려도 된다.** 우리 모듈에는 신호를 만드는 에이전트가 안 붙어 있고 쇼핑몰도 이 기능이 없어서 늘어난 주소가 신호를 만들지 않는다. 쇼핑몰이 켜거나 우리 모듈에 에이전트를 붙이면 그때 더해야 한다.

### 2.7 측정 흐름

```
(한 회차)
세 모듈을 띄운다
  -> 관리 포트에서 두 주소가 200 인지
  -> 업무 포트에서 추가 주소 둘이 200 인지
  -> 업무 포트에서 관리 주소가 404 인지
  -> PostgreSQL 을 끈다
  -> readiness 가 거짓이 되고 liveness 는 참으로 남는지 (걸린 시간도 적는다)
  -> PostgreSQL 을 다시 켠다 -> readiness 가 저절로 돌아오는지
  -> 전체 시험 · 로컬 관통 점검
```

### 2.8 자주 헷갈리는 것

절반 가까이가 승조가 되물어서 잡힌 것이다.

| 헷갈리는 것 | 실제 |
|---|---|
| `readiness` 가 아니라고 하면 파드를 살리거나 죽인다 | 둘 다 아니다. 손님 목록에서 빼고 다시 넣는 것만 한다. 파드는 계속 살아 있다 |
| `liveness` 가 아니라고 하면 바로 죽인다 | 바로가 아니다. **연속 3번**(기본값) 실패해야 한다. 10초 간격이라 약 30초다 |
| 프로세스가 죽은 것을 probe 가 잡는다 | 프로세스가 죽으면 쿠버네티스가 이미 알아채고 다시 띄운다. probe 가 메우는 구멍은 **프로세스는 살아 있는데 안이 멈춘** 경우다 |
| 먼저 한 쪽이 넣은 저장소 확인은 기본값이다 | 아니다. 기본은 자기 상태만 본다. 그 사람이 일부러 넣었다 |
| `readiness` 가 저장소를 볼 때 연결을 붙잡고 있다 | 아니다. 저장소가 죽으면 연결이 아예 없어서 **받은 것이 없다.** 줄에 서서 기다리기만 한다 |
| 그 기다림이 진짜 요청을 밀어낸다 | **내가 과장했다.** 동시에 둘셋이고 스레드는 200개다. 영향이 작다. 숫자를 안 재고 단정한 것을 승조가 되물어서 고쳤다 |
| probe 가 30초 뒤 거짓 응답을 받는다 | 안 받는다. 쿠버네티스는 1초에 포기하고 "답 없음" 으로 센다 |
| 앞선 작업이 넣은 10초가 이 지연을 줄인다 | 다른 단계다. 연결을 얻으려고 기다리는 30초는 그대로다 |
| 관리 포트를 나누는 것이 더 안전하니 정답이다 | 공식 문서는 반대도 경고한다. 업무 포트가 막혀도 통과하는 거짓 양성이 생긴다 |
| 관리 포트를 나누면 관리 주소가 보호된다 | 노출 범위만 줄어든다. 누가 들어올 수 있나는 따로 설정해야 한다 |
| 업무 포트에 관리 주소가 다 열려 있다 | 아니다. 기본 노출은 하나다. API 서버는 그 하나, 수집기 · 적재 처리기는 둘이다. **조사 중에 내가 이걸 틀리게 적었다가 고쳤다** |
| 그래서 API 서버가 가장 많이 새고 있다 | 반대다. 열린 양은 API 서버가 가장 적다. API 서버를 짚은 이유는 양이 아니라 **다음 사람이 하나 더 열 때 문턱이 없다**는 것이다 |
| `readiness` 는 모든 모듈에 같은 뜻이다 | 아니다. Service 로 트래픽을 받는 것에만 의미가 있다. 적재 처리기는 새 버전 교체만 막힌다 |
| 명세가 적은 주소 이름은 못 만든다 | 만들 수 있다. 추가 주소의 이름을 바꾸면 된다 |
| 명세가 적은 응답 모양도 설정으로 된다 | 안 된다. 표준 기능의 값이 코드에 박혀 있다 |
| Kafka 확인은 한 단어 더하면 된다 | 기능이 아예 없다. 직접 만들어야 한다 |
| 저장소 확인은 두 모듈 모두 공짜다 | API 서버만 공짜다. 적재 처리기는 붙는 방식이 달라 안 잡힌다 |
| 신호 받는 쪽이 죽으면 probe 가 필요하다 | 자리를 못 잡는 경우는 기동 실패로 드러나 프로세스가 죽는다. 남는 것은 "뜬 뒤 조용히 죽는" 경우뿐이다 |
| 포트를 이름으로 가리키면 모든 확인이 번호에서 자유롭다 | 업무 주소 쪽만 그렇다. 신호 받는 쪽 규격으로 직접 찌르면 이름을 못 쓴다 |

## 3. 1차 질문 (사람 차례)

승조가 2 를 읽고 물은 것들이다. 묻는 과정에서 내가 틀린 것이 넷 드러났고 범위가 한 번 바뀌었다.

**Q1. 여기서 "저장소" 가 뭘 말하나**

PostgreSQL · ClickHouse · Kafka 셋을 묶은 말이다. git 레포를 뜻하지 않는다. 2.0 으로 올렸다.

**Q2. "관리 주소가 손님 포트에 열려 있다" 가 무슨 말인가**

서비스는 포트 하나로 모든 요청을 받고, 그 포트에 업무 주소와 관리 주소가 섞여 있다는 뜻이다. 다만 **내가 열린 범위를 과장해서 적었다.** `/actuator/**` 가 다 열린 것처럼 썼는데 실제 기본 노출은 하나뿐이다. 수집기 · 적재 처리기가 `health` 와 `metrics` 둘을 열어 뒀다. 고쳤다.

**Q3. readiness 에 저장소를 넣는 것이 괜찮은 방법 아닌가. 트레이드오프가 뭔가**

넣는 쪽이 자연스러워 보이지만 **저장소가 하나라서** 뒤집힌다. readiness 의 원래 쓸모는 아픈 파드만 골라 빼는 것인데, 파드 전부가 같은 저장소를 보면 답이 갈리지 않아 전멸이 된다. 2.3 으로 올렸다.

**Q4. 30초와 1초가 어긋난다는 게 무슨 말인가**

저장소가 죽으면 앱이 답을 만드는 데 30초가 걸리는데 쿠버네티스는 1초만 기다린다. 그래서 쿠버네티스는 "못 받는다" 를 한 번도 못 받고 "답 없음" 만 본다.

여기서 **내가 과장한 것이 드러났다.** 처음에는 "확인하는 일이 저장소를 더 막는다" 를 셋째 문제로 적었는데, 세어 보니 동시에 기다리는 확인 작업이 두세 개이고 스레드는 200개다. 숫자를 안 재고 단정했다. 지웠다.

**Q5. 쿠버네티스가 네 주소에 다 쏘나**

아니다. **둘만 쏜다.** 배포 설정에 liveness 하나 readiness 하나만 적는다. 나머지는 아예 안 본다. 그래서 문제의 모양은 "둘 다 보고 한가한 쪽을 택한다" 가 아니라 **"하나만 보는데 그 하나를 어디에 두느냐"** 다.

**Q6. 지금 업무 주소 · 관리 주소가 있긴 한가**

업무 주소는 원래 있다. 관리 주소도 있는데 **업무 포트에 섞여 있다.** probe 주소(`/healthz` · `/actuator/health/liveness`)는 내 두 모듈에 하나도 없다.

**Q7. 탐지 · 알림이 `/healthz` 를 안 쓴 이유가 있을까**

**이 질문이 조사를 뒤집었다.** 찾아보니 팀이 규약을 바꾼 것이었고 사유까지 적혀 있었다. 나는 낡은 명세를 따라가려 했다. 2.5 를 통째로 다시 썼고, 그 과정에서 **API 서버가 내 몫이 아니라는 것**과 **규약의 Kafka 전제가 틀렸다는 것**도 같이 나왔다.

## 4. 1차 정리

**정해진 것** (고를 거리가 아니다)

| | 왜 |
|---|---|
| liveness 에는 저장소를 안 넣는다 | 공식 문서가 금지한다. 저장소가 흔들릴 때 파드 전부가 동시에 재시작해 더 큰 고장이 된다 |
| 주소 이름은 `/actuator/health/liveness` · `/readiness` | 팀 규약이 사유와 함께 정했다. 명세가 낡은 것이다 |
| 응답 모양은 `{"status":"UP"}` | 표준 기능이 내놓는 값이고 바꿀 수 없다. 규약도 그렇게 정했다 |
| 범위는 수집기 · 적재 처리기 둘 | 규약이 API 서버를 재범 몫으로 적었다 |

**질문으로 남은 것** (5 에서 고른다)

| | 왜 고를 거리인가 |
|---|---|
| readiness 에 저장소를 넣을까 | 규약은 넣으라고 적었는데, 그 전제(Kafka 확인 기능이 있다)가 틀렸고 수집기는 이전 결정과도 부딪친다 |
| 업무 포트에도 probe 주소를 열까 | 규약이 이 경고를 안 담았다. 보태는 쪽이 맞는지 |
| 관리 포트 번호를 어떻게 할까 | 규약이 고른 번호를 수집기가 업무용으로 쓴다 |

**조사가 바꾼 내 생각 셋**

- 처음 : 선례를 복사한다 → 실제 : 선례가 따른 규약을 찾아 읽고 그 전제를 검증해야 했다
- 처음 : 명세대로 `/healthz` 를 연다 → 실제 : 팀이 버리기로 이미 정한 이름이었다
- 처음 : 세 모듈 → 실제 : 두 모듈

## 5. 선택지와 설명

### 묶음 1. readiness 에 저장소를 넣을까

규약은 수집기에 `Kafka 연결 · PG 설정 캐시`, 적재 처리기에 `Kafka · ClickHouse` 를 적었다.

| 방법 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A 안 넣는다** | 자기 상태만 보고 답한다 | 저장소가 흔들려도 수집기가 살아서 신호를 계속 받는다. 이전에 두 번 정한 "저장소가 죽어도 수집은 돈다" 를 지킨다. 새로 짤 코드가 0줄이다 | 규약과 다르다. 사유를 남겨야 한다. "준비됨" 이 저장소 상황을 전혀 말하지 않는다 |
| B 규약대로 다 넣는다 | Kafka · PG · ClickHouse 를 본다 | 규약과 같아 설명이 짧다 | **Kafka 와 ClickHouse 는 확인 기능이 없어 직접 짜야 한다.** 이 작업이 두 배가 된다. 저장소가 흔들릴 때 수집기 전부가 빠져 **에이전트가 신호를 버린다.** 이전 결정도 뒤집는다 |
| C PG 만 넣는다 | 공짜로 잡히는 것만 | 설정 한 줄로 끝난다. 탐지 · 알림과 모양이 같다 | 수집기에 PG 는 샘플링 비율 읽는 용도뿐이라 **없어도 일할 수 있다.** 일할 수 있는데 스스로 빠져 데이터를 버린다. 적재 처리기 PG 는 적재 본업이 아니라 얻는 것이 더 작다 |

고른 것 : **A**. 사유는 셋이다. 저장소가 하나라 파드가 전부 동시에 빠진다 · 쿠버네티스가 원인을 못 본다 · 수집기가 빠지면 에이전트가 신호를 버려 그 시간대 데이터가 영구히 사라진다.

### 묶음 2. 업무 포트에도 probe 주소를 열까

| 방법 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A 연다** | 관리 포트의 주소는 그대로 두고 업무 포트에 둘을 더 연다. 쿠버네티스는 업무 포트 쪽을 쏜다 | 업무 포트가 막히면 그 주소도 같이 막혀 **거짓 정상이 사라진다.** 공식 권장이다. 설정 한 줄이다 | 규약에 없던 것을 보탠다. 완전히 같은 모양이 되려면 다른 파트 둘도 나중에 맞춰야 한다 |
| B 규약대로 관리 포트만 | 지금 탐지 · 알림과 같다 | 다섯이 같은 모양이다. 고칠 것이 가장 적다 | **공식 문서가 경고한 거짓 정상을 그대로 안는다.** 업무 포트 일꾼이 전부 묶여도 "정상" 이 나온다 |

고른 것 : **A**. 추가 주소 이름은 기본값 `/livez` · `/readyz` 를 쓴다(한 조각이어야 해서 긴 주소는 못 쓴다).

### 묶음 3. 관리 포트 번호

규약은 다섯 모듈 전부 `8081` 로 적었는데 수집기가 그 번호를 업무용으로 쓴다.

| 방법 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A 업무 포트 + 10** | 수집기 8091 · 적재 처리기 8092 | 번호 겹침이 사라진다. **다섯을 한 컴퓨터에 띄워도 안 겹쳐서** 탐지 · 알림이 쓰는 로컬 전용 덮어쓰기도 없앨 수 있다. 외울 규칙이 하나다. 쿠버네티스가 이름으로 가리킬 수 있어 배포 설정 틀은 하나로 유지된다 | 모듈마다 번호가 다르다. 망 접근 규칙을 공통 하나로 못 쓴다. 다른 파트가 따라와야 다섯이 같아진다 |
| B 수집기 업무 포트를 옮긴다 | 수집기 업무를 다른 번호로 바꾸고 8081 을 관리용으로 | 규약의 `8081` 을 그대로 지킨다 | **다른 레포까지 번진다.** 쇼핑몰 에이전트가 그 번호로 명령을 받으러 온다. 로컬 구성 셋 · 점검 스크립트 둘 · 안내 문서 넷도 바뀐다 |
| C 안 나눈다 | 관리 주소를 업무 포트에 그대로 둔다 | 가장 단순하고 거짓 정상이 없다 | **관리 주소가 외부에 보인다.** 규약이 나누라고 정한 이유(`/actuator/metrics` · `/env`)를 포기한다 |

고른 것 : **A**. 내가 실제로 바꾸는 것은 `8091` · `8092` 둘뿐이고 나머지는 제안으로 전한다.

### 묶음 4. 수집기의 신호 받는 쪽을 확인할까

| 방법 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A 안 한다** | 확인 코드를 안 만든다 | 코드가 0줄이다. 자리를 못 잡는 경우는 기동 실패로 드러나 프로세스가 죽고 쿠버네티스가 다시 띄운다 | "뜬 뒤 신호 받는 쪽만 조용히 죽는" 경우를 못 잡는다 |
| B 상태 값을 읽어 보탠다 | 이미 있는 값을 쓴다 | 비용이 거의 0 이다 | 그 값은 "끄라고 불렀나" 를 보는 것이라 **안에서 멍하니 멈춘 경우는 여전히 못 잡는다.** 가장 그럴듯한 고장을 놓친다 |
| C 그쪽 규격으로 직접 찌른다 | 쿠버네티스가 신호 포트를 직접 확인하게 | 가장 정직하다 | 라이브러리를 더한다. **포트를 이름으로 못 가리켜** 묶음 3 에 예외가 생긴다. 확인 수단이 두 벌이 된다 |

고른 것 : **A**. 안 겪은 일을 위해 코드를 더하지 않는다.

### 딸려 오는 것 둘

`/actuator/**` 가 관리 포트로 옮겨가면 둘이 깨진다. 같이 고친다.

- `check-pipeline.sh` · `check-wiring.sh` 가 업무 포트의 `/actuator/metrics` 를 쓴다. 관리 포트를 호스트에 열고 주소를 바꾼다
- `compose.yaml` 의 두 헬스체크가 업무 포트의 `/actuator/health` 를 찌른다. `/readyz` 로 바꾼다. 오히려 뜻에 더 맞는다

## 7. 2차 정리

5 에서 고른 넷을 그대로 확정한다.

| 묶음 | 고른 것 |
|---|---|
| readiness 에 저장소 | **안 넣는다** |
| 업무 포트 추가 주소 | **연다** (`/livez` · `/readyz`) |
| 관리 포트 번호 | **업무 포트 + 10** (수집기 8091 · 적재 처리기 8092) |
| 신호 받는 쪽 확인 | **안 한다** |

**규약과 다르게 가는 것이 둘**이라 결정 기록에 사유와 되돌리는 조건을 남긴다.

| 다른 점 | 사유 |
|---|---|
| readiness 에 저장소를 안 본다 | 규약의 전제(Kafka 확인 기능이 있다)가 틀렸다 + 저장소가 하나라 파드가 전부 빠진다 + 수집기가 빠지면 에이전트가 신호를 버린다 + 이전에 두 번 정한 "저장소가 죽어도 수집은 돈다" 를 지킨다 |
| 업무 포트에도 주소를 연다 | 규약이 공식 문서의 경고를 안 담았다. 관리 포트만 쏘면 업무 포트가 막혀도 통과한다 |

**딸려 오는 것 둘을 범위에 포함한다.** `/actuator/**` 가 관리 포트로 가면 업무 포트에서 404 가 되어 둘이 깨진다.

| 깨지는 것 | 왜 | 어떻게 |
|---|---|---|
| 점검 스크립트 둘 | 업무 포트의 `/actuator/metrics` 를 쓴다 | 관리 포트로 주소 변경 + compose 에서 관리 포트 공개 |
| compose 헬스체크 둘 | 업무 포트의 `/actuator/health` 를 찌른다 | `/readyz` 로 변경. 원래 하려던 일("준비됐나")에 더 맞고 쿠버네티스가 쏠 주소와도 같아진다 |

설정
  수집기 관리 포트 8091 · 적재 처리기 관리 포트 8092 (업무 포트 + 10)

같이 고칠 것

  liveness 그룹에 저장소가 없다
  readiness 그룹에도 저장소가 없다 (규약과 다른 선택이라 꼭 고정한다)

PG 를 멈추는 시험이 다른 스펙을 깨지 않는 것은 이 스펙의 컨텍스트 키(RANDOM_PORT + 고유 속성)가 어느 스펙과도 안 겹쳐 저장소 컨테이너가 따로 뜨기 때문이다. 대가는 모듈마다 인프라 한 벌이 더 뜨는 것(적재 처리기는 PG · Kafka · ClickHouse 셋)이고, 지금 전체 시험 4분 19초 안에서 감당된다.
