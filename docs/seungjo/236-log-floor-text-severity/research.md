# 리서치 : 로그 하한이 숫자 0 인 레코드를 글자로 판정한다

- 날짜 2026-10-20 / 관련 이슈 [`#236`](https://github.com/2026-techeer-project-team-b/monimo-backend/issues/236) (앞 이슈 `#215` · PR `#228` 머지, ADR `#59` · `#38` ④ · `#55` 되돌림 ③)
- 쓴 도구: 레포 직접 읽기(`collector/filter/LogLevelFilter.kt` · `ingester/transform/LogTranslator.kt` · `common/` · 두 테스트 · ADR `#59`)

> **읽는 순서가 곧 쓰는 순서다.** 1 → 2 를 쓰고 멈춰서 승조가 3 을 묻는다. 답하고 4 를 쓴다.
> 5 를 쓰고 멈춰서 승조가 6 을 묻는다. 답하고 7 을 쓴다. 8 은 승조가 쓴다.
> **3 · 6 · 8 은 사람 차례다.** 비어 있으면 아직 거기까지 온 것이고, 대신 채우지 않는다.

## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 로그 등급은 숫자 칸과 글자 칸 둘로 온다. 수집기는 숫자만 보고 「숫자가 비면 모른다, 남긴다」 로 하고, 적재 처리기는 「숫자가 비면 글자를 읽는다」 로 한다. 그래서 숫자가 비고 글자가 `DEBUG` 인 줄은 수집기를 그대로 지나 `DEBUG` 로 쌓인다
- **그래서 무엇을 만드나** : 수집기도 숫자가 비면 글자를 읽어 하한 아래면 버린다. 글자를 읽는 규칙은 적재 처리기와 **같은 것 하나**를 쓴다
- **안 하면 어떻게 되나** : 하한을 INFO 로 두어도 숫자를 안 채우는 생산자(다른 언어 · 손으로 만든 전송)의 DEBUG 는 `logs` 에 들어온다. `#215` 가 막으려던 홍수가 그 길로는 그대로 열려 있다

| | |
|---|---|
| 건드리는 모듈 · 파일 | `collector/filter/LogLevelFilter.kt`(판정) · `ingester/transform/LogTranslator.kt`(판정을 꺼내 같이 쓴다) · 판정을 둘 곳(`common` 후보) · 테스트 셋(`LogLevelFilterTest` · `OtlpGrpcReceiverTest` · `LogTranslatorTest`) · `LogLevelFilter` 주석 |
| 건드리지 않는 것 | 하한 설정 이름 · 기본값(`monimo.collector.log.min-level` = `INFO`, 비우면 끔) · 숫자가 있을 때의 판정 · ClickHouse `logs` 표 · 별칭 표의 내용(ADR `#59` 그대로) · 헬스체크 거르기 · 샘플링 |
| 이 이슈 범위 밖 (후속) | 하한 설정값에 별칭을 받기(`min-level: WARNING` 같은 것. 지금은 여섯 이름만 받고 나머지는 기동 때 터진다) · 앱별 하한 · 원래 글자 보존(ADR `#59` 되돌림 ①) · 세 거르기(헬스체크 · 샘플링 · 로그 하한) 공통화 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- OTel 로그는 숫자(`severity_number`, 1~24)와 글자(`severity_text`)를 따로 들고 오고 둘 다 선택이다. 숫자 0 은 「안 적힘」 이다
- 적재 처리기는 `#144`(ADR `#59`)로 「숫자가 정본, 없을 때만 글자를 별칭 표로」 를 정했다. 수집기 하한은 `#215` 에서 숫자만 보게 짰다
- 우리가 붙이는 OTel Java 에이전트는 숫자를 늘 채운다. 그래서 지금 우리 트래픽에서는 이 갈래가 안 밟힌다

**알고 싶었던 것**

- ① 숫자 0 인 레코드를 **실제로 누가 보내나**. 우리 트래픽 · 쇼핑몰 · `telemetrygen` · 남의 앱 중 어디서 오나
- ② 판정 규칙을 **어디에 하나로 두나**. `common` 에 두면 「공유 모델만 둔다」 는 그 모듈의 약속과 맞나
- ③ 숫자가 **규약 밖(25 이상 · 음수)** 인 레코드는 어떻게 하나. 적재 처리기는 그것도 「숫자 없음」 으로 보고 글자를 읽는다
- ④ 글자로 판정해 버린 것을 **지금 카운터에 어떻게 세나**. 꼬리표 `level` 은 숫자에서 이름을 뽑는데 숫자가 0 이다
- ⑤ 이 변경이 ADR `#59` 와 `#215` 결정 중 **무엇을 바꾸는 것인가**. 새 번호를 달아야 하나

## 2. 작업하기 전에 알아야 하는 것

### 2.1 로그 등급 칸 둘 : 숫자와 글자

- OTLP 의 로그 한 줄(`LogRecord`)에는 등급 칸이 둘 있다
  - `severity_number` : 1~24 의 숫자. 여섯 구간이 네 칸씩이다 : TRACE 1~4 · DEBUG 5~8 · INFO 9~12 · WARN 13~16 · ERROR 17~20 · FATAL 21~24
  - `severity_text` : 생산자가 부르는 이름 그대로인 자유 글자. Logback 은 `WARN`, java.util.logging 은 `WARNING` · `FINE`, Python 은 `CRITICAL`
- 둘 다 **선택**이다. 숫자가 0 이면 「안 적힘(UNSPECIFIED)」 이고, 「아주 낮은 등급」 이라는 뜻이 아니다
- 규약은 「크기를 비교할 때는 숫자를 쓰라」 까지만 말하고, 숫자가 없을 때 무엇을 하라고는 정하지 않았다 (ADR `#59` 근거)

### 2.2 지금 두 모듈이 같은 줄을 어떻게 판정하나

- **수집기** `LogLevelFilter.isBelow` (`#215`)
  ```kotlin
  val number = record.severityNumberValue
  return number != 0 && number < min   // min = INFO 면 9
  ```
  - 숫자만 본다. 0 이면 「무엇인지 모르는 것을 버리면 안 된다」 로 남긴다 (클래스 주석)
- **적재 처리기** `LogTranslator.levelOf` (`#144`, ADR `#59`)
  ```kotlin
  fromNumber(record.severityNumberValue) ?: fromText(record.severityText)
  ```
  - `fromNumber` 는 1~24 만 이름으로 바꾸고 **0 과 규약 밖은 `null`** 이다. 그러면 글자를 별칭 표(`ALIASES`, 24개)로 읽는다. 표에 없으면 빈 글자
- 하한이 `INFO` 일 때 같은 줄이 어떻게 갈리나

  | 숫자 | 글자 | 수집기 (지금) | 적재 처리기가 쌓는 `level` | 맞나 |
  |---|---|---|---|---|
  | 5 | `DEBUG` | 버림 | (안 옴) | 맞다 |
  | 9 | `DEBUG` | 남김 | `INFO` (숫자가 이긴다) | 맞다 |
  | 0 | `DEBUG` | **남김** | **`DEBUG`** | **어긋남** |
  | 0 | `FINE` | **남김** | **`DEBUG`** | **어긋남** (java.util.logging 이름) |
  | 0 | `INFO` | 남김 | `INFO` | 맞다 |
  | 0 | `blah` · 빈 글자 | 남김 | `''` | 맞다 (모르는 것은 남긴다) |
  | 99 | `DEBUG` | **남김** (99 ≥ 9) | **`DEBUG`** (99 는 숫자 없음으로 본다) | **어긋남** (알고 싶었던 것 ③) |

- 즉 **숫자가 이길 때는 둘이 같고, 숫자가 없을 때만 갈린다.** 수집기는 「없음 = 모름」 이고 적재 처리기는 「없음 = 글자를 본다」 다

### 2.3 데이터는 어디로 흐르나

```
앱의 로거 ──(에이전트가 숫자 · 글자를 채워 OTLP 로)──▶ 수집기 :4317
                                                        │
                    OtlpLogsService.export (inbound/otlp/OtlpExportServices.kt)
                        ① 수신 카운터 +N   (거르기 전 숫자)
                        ② LogLevelFilter.drop  ← 여기서 하한 미만을 뺀다  ★ 이번에 고치는 곳
                           └ 버린 수 monimo.collector.dropped{reason=log_level, level=…}
                        ③ 남은 게 0줄이면 Kafka 에 안 보내고 OK 응답
                        ④ 남은 요청을 바이트 그대로 Kafka raw 로
                                                        │
                                                        ▼
                                  적재 처리기 LogTranslator.toRows
                                     levelOf = 숫자 → 없으면 글자(별칭 표) → 없으면 ''
                                                        │
                                                        ▼
                                          ClickHouse monimo.logs.level
```

| 질문 | 답 |
|---|---|
| 버린 줄은 어디에 남나 | 안 남는다. 카운터만 는다 (헬스체크 거르기와 같은 약속) |
| 에이전트는 무엇을 받나 | OK. 버렸다고 알리지 않는다 (에이전트가 재전송하지 않게) |
| 하한을 끄는 법 | `MONIMO_COLLECTOR_LOG_MIN_LEVEL` 을 비운다 |
| 지금 숫자 0 인 줄이 들어오나 | 우리 모듈 · 쇼핑몰은 OTel Java 에이전트라 숫자를 늘 채운다 (`LogTranslator.fromText` 주석). **실측은 아직 안 했다** (알고 싶었던 것 ①) |

### 2.4 `common` 모듈

- 수집기 · 적재 처리기 · API 서버 등이 같이 쓰는 코드 자리다. `common/build.gradle.kts` 첫 줄 주석이 「공유 모델만 둔다. Entity · Repository · Service 금지」 다
- 지금 든 것은 Kafka 쪽 둘뿐이다 : `common/kafka/RawHeaders.kt`(raw 메시지 머리말 이름) · `RawSignal.kt`(신호 종류)
- `opentelemetry-proto` 를 `api` 로 내므로, `common` 에 둔 코드는 `LogRecord` 를 그대로 받을 수 있다
- 수집기 · 적재 처리기 둘 다 `implementation(project(":common"))` 이다
- 별칭 표 같은 「값의 뜻을 정한 표」 가 「공유 모델」 에 드는지는 이 문서가 정할 일이다 (알고 싶었던 것 ②)

### 2.5 지금 테스트가 고정해 둔 것

- `LogLevelFilterTest` : 숫자 0 레코드는 **남는다**를 고정한다 (`listOf(info, warn, 0)` 기대). 이번 변경은 이 기대를 「0 + 판정되는 글자면 판정대로」 로 바꾼다
- `OtlpGrpcReceiverTest` (`#215` 리뷰로 더해짐) : DEBUG 만 보내면 raw 에 새 메시지가 없고 수신 카운터는 늘어난다 · DEBUG + INFO 면 INFO 만 남는다. 둘 다 숫자로 등급을 준다
- `LogTranslatorTest` (`#144`) : 별칭 표 · 경계값 · 「숫자가 규약 밖(99) + 글자면 글자로」 를 고정한다. 판정을 옮겨도 이 기대는 그대로여야 한다

### 2.6 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| 숫자 0 은 TRACE 보다 낮은 등급이다 | 「안 적힘」 이다. 등급이 아니다. 그래서 숫자만 보면 「모름」 이 맞다 |
| 수집기가 글자를 보면 ADR `#59` 와 어긋난다 | `#59` 는 「숫자가 정본, **숫자가 없을 때만** 글자」 다. 수집기가 그 순서를 그대로 따르면 오히려 맞춰진다 |
| 「모르는 것은 버리지 않는다」 가 깨진다 | 별칭 표에 있는 글자는 「아는 것」 이다. 표에 없는 글자 · 빈 글자는 지금처럼 남긴다 |
| 이건 우리 트래픽에서 지금 생기는 문제다 | 우리가 붙인 에이전트는 숫자를 채운다. 숫자를 안 채우는 생산자가 붙을 때 열리는 길이다 (`#55` 되돌림 ③ 의 「남의 앱」) |
| 버린 걸 셀 때 등급 이름은 숫자에서 뽑으면 된다 | 지금 `levelNameOf` 는 `(숫자 - 1) / 4` 로 뽑는다. 글자로 판정해 버린 줄은 숫자가 0 이라 이 식으로는 이름이 안 나온다 (알고 싶었던 것 ④) |

## 3. 1차 질문 (사람 차례)

2026-10-20 대화에서 승조가 물은 것을 그대로 적는다. 답은 한 줄로 줄였다.

- **Q. 정리하면 이런 것인가 : 숫자가 0 이면 수집기는 「아직 안 적혔다」 하고 넘기는데, 적재 처리기는 글자로 읽으니 `DEBUG` · `TRACE` 가 그대로 CH 에 들어간다**
  - A. 맞다. 다만 적재 처리기는 **글자만** 읽는 것이 아니라 「숫자가 정본, 숫자가 없을 때만 글자」다(ADR `#59`). 숫자가 있으면 둘의 판정이 같고, **갈리는 것은 숫자가 없을 때 하나뿐**이다
- **Q. 그러면 적재 처리기가 안 버리고 넣어 버리는 것 아닌가**
  - A. 적재 처리기에는 **버리는 역할이 없다**. 버리는 문은 수집기 하나이고(헬스체크 거르기 · 샘플링 · 로그 하한 셋 다), 적재 처리기는 들어온 것의 등급을 정해 적는 일만 한다. 그래서 이것은 「적재가 잘못 넣었다」가 아니라 **「수집기가 못 버렸다」** 다
- **Q. 그러면 적재 처리기 쪽에서 글자를 읽을 때 버리게 하면 되지 않나**
  - A. 거기서 버리면 그 줄은 **이미 네트워크와 Kafka 를 다 지나온 뒤**라 `#215` 가 줄이려던 비용이 그대로 든다. 고칠 자리는 수집기다
- **Q. 숫자가 9보다 커지는 경우가 문제인가**
  - A. 아니다. 13(WARN) · 17(ERROR)처럼 9보다 큰 정상 값은 숫자로 제대로 판정된다. 문제는 **규약 밖(25 이상 · 음수)** 인 값이다. 적재 처리기가 그것을 「숫자 없음」으로 보고 글자를 읽는다
- **Q. 이 문제를 한 문단으로 다듬으면 어떻게 되나**
  - A. 아래 4절 「한 문단」 에 적었다

## 4. 1차 정리

**한 문단**

OTel 로그에는 등급 칸이 둘(숫자 · 글자) 있고 둘 다 선택이다. 규약은 「크기를 비교할 때는 숫자를 쓰라」까지만 말하고 **숫자가 없을 때 무엇을 하라고는 정하지 않았다.** 그 빈칸을 수집기는 「모르는 것은 안 버린다」로, 적재 처리기는 「글자를 별칭 표로 읽는다」로 각자 메웠다. 그래서 숫자가 0 이거나 규약 밖인데 글자가 `DEBUG` 인 줄은 수집기를 그대로 지나 `DEBUG` 로 쌓인다. 고칠 자리는 수집기 하나이고, 숫자가 없을 때 **적재 처리기와 같은 글자 규칙**을 한 번 더 보게 하면 된다.

- **확실한 것** (2절과 대화로 닫혔다)
  - 둘이 갈리는 지점은 **숫자가 없을 때 하나**다. 숫자가 있으면 판정이 같다
  - 버리는 문은 **수집기 하나**다. 적재 처리기는 등급을 적을 뿐이라 거기서 버리면 비용이 이미 다 든 뒤다
  - **규약 밖 숫자(99)도 같은 갈래**다 : 수집기는 99 ≥ 9 라 남기고 적재 처리기는 「숫자 없음」으로 본다. 그래서 이번 범위에 같이 넣는다 (알고 싶었던 것 ③ 닫힘)
  - ADR `#59` 와 **어긋나지 않는다** : `#59` 가 정한 순서(숫자 → 없으면 글자)를 수집기가 따라가는 것이다
  - 지금 우리 트래픽에서는 안 밟힌다 : 우리 모듈 · 쇼핑몰은 OTel Java 에이전트라 숫자를 늘 채운다. 숫자를 안 채우는 생산자가 붙을 때 열리는 길이다(`#55` 되돌림 ③ 의 「남의 앱」)
- **아직 모르는 것** (5절에서 닫는다)
  - ① 숫자 0 인 레코드가 실제로 들어오는가 : **재현으로 확인한다**(글자만 있는 로그를 수집기에 보내 CH 까지 보기)
  - ② 글자 판정 규칙을 어디에 두나 : `common`(「공유 모델만」 약속과 맞는지) · 수집기에 복사 · 적재 처리기 것을 노출 중 무엇인지
  - ④ 글자로 버린 줄의 카운터 꼬리표(`level`)를 무엇으로 하나 : 지금 식(`(숫자 - 1) / 4`)은 숫자가 0 이면 이름이 안 나온다
  - ⑤ ADR 을 새로 다나, `#59` 에 한 줄 보태나

## 5. 선택지와 설명

### 우리 데이터로 확인한 것 (2026-10-20, 로컬 스택 실측)

수집기 이미지를 develop(`#215` 포함)으로 다시 만들고 하한을 `INFO` 로 둔 채, 손으로 만든 OTLP 로그 일곱 줄을 `collector:4317` 로 보냈다. `telemetrygen` 은 `--severity-number` 를 **1~24 로 강제**해서 이 갈래를 못 만든다(그래서 파이썬으로 OTLP 요청을 직접 지었다. 이것도 사실 하나다 : 흔한 시험 도구로는 이 길이 안 나온다).

| 보낸 것 (숫자 · 글자) | CH `logs` 에 남았나 | 적힌 `level` | 맞나 |
|---|---|---|---|
| 5 · `DEBUG` | **안 남음** | — | 맞다 (수집기가 버렸다) |
| **0 · `DEBUG`** | **남음** | **`DEBUG`** | **샌다** |
| **0 · `FINE`** (java.util.logging) | **남음** | **`DEBUG`** | **샌다** (별칭 표가 DEBUG 로 본다) |
| **99 · `DEBUG`** (규약 밖) | **남음** | **`DEBUG`** | **샌다** |
| 0 · `INFO` | 남음 | `INFO` | 맞다 |
| 0 · `blah` (모르는 글자) | 남음 | 빈 글자 | 맞다 (모르는 것은 남긴다) |
| 9 · `INFO` | 남음 | `INFO` | 맞다 |

- 2.2 표가 예측한 그대로다. **새는 줄은 셋**이고 전부 「숫자가 없거나 규약 밖 + 글자가 아는 이름」 이다
- 버린 수 카운터의 `level` 꼬리표에 지금 들어 있는 값은 `TRACE` · `DEBUG` 둘뿐이다. 글자로 판정해 버린 줄이 생기면 이 꼬리표를 **무엇으로 채울지 정해야 한다**(알고 싶었던 것 ④)
- 「숫자 0 을 실제로 누가 보내나」(알고 싶었던 것 ①)는 **우리 트래픽에서는 0건**이다 : 우리 모듈 · 쇼핑몰은 OTel Java 에이전트라 숫자를 늘 채운다. 손으로 만든 전송과 다른 언어 SDK 가 붙을 때 열리는 길이고, 이번 실측이 그 길을 재현한 것이다

### 선택지 A : 어디서 버리나

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **수집기가 숫자 없을 때 글자를 본다 (고를 안)** | 네트워크 · Kafka · ClickHouse 앞에서 막는다. `#215` 가 세운 「막는 문은 수집기 하나」가 그대로 유지된다 | 글자 규칙을 수집기도 알아야 한다(아래 B) |
| 적재 처리기가 버린다 | 글자 규칙이 이미 그 모듈에 있다 | 이미 네트워크와 Kafka 를 지나온 뒤라 `#215` 가 줄이려던 비용이 그대로 든다. 적재 처리기에 「버리는 역할」이 새로 생겨 DLQ · 되넣기와 뜻이 섞인다 |
| 양쪽 다 본다 | 어느 쪽이 빠져도 막힌다 | 같은 규칙이 두 곳에 생기고 둘이 갈릴 때 조용히 어긋난다 |
| 안 고친다 | 코드 0줄 | 남의 앱이 붙는 순간 `#215` 의 구멍이 그대로 열린다. ADR `#55` 되돌림 ③ 이 그 조건을 이미 「남의 앱이 붙을 때」로 적어 두었다 |

### 선택지 B : 글자 판정 규칙을 어디에 두나

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **`common` 에 공용 판정 하나 (고를 안)** | 수집기 · 적재 처리기가 **같은 표**를 본다. 어긋날 수 없다 | `common` 의 「공유 모델만 둔다」 약속에 「값의 뜻을 정한 표」가 드는지 정해야 한다 |
| 수집기에 별칭 표를 복사 | `common` 을 안 건드린다 | 표가 두 곳이 되어 한쪽만 고치면 조용히 갈린다. `#144` 가 묶어 둔 것을 다시 푸는 셈 |
| 수집기가 적재 처리기 코드를 참조 | 표가 하나 | **모듈 경계 위반**이다. 모듈끼리는 `:common` 만 의존한다(빌드가 막는다) |
| 수집기는 「숫자 없음이면 버린다」 | 표가 필요 없다 | 모르는 글자 · 빈 글자까지 버린다. 「모르는 것은 안 버린다」를 깬다 |

### 선택지 C : 버린 수의 `level` 꼬리표

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **판정된 이름을 쓴다 (고를 안)** : 글자로 `DEBUG` 라고 봤으면 `level=DEBUG` | 숫자로 버린 줄과 같은 축에서 센다. 대시보드가 그대로다 | 「숫자로 버렸나 글자로 봤나」는 이 꼬리표로 구분이 안 된다 |
| 꼬리표를 하나 더 둔다 (`by=number\|text`) | 어느 길로 버렸는지 보인다 | 꼬리표가 늘어 카디널리티와 설명이 는다. 지금 묻는 사람이 없다 |
| `level=unknown` 으로 몰아 센다 | 구현이 제일 짧다 | 「무엇을 버렸나」를 못 본다. 하한을 잘못 둔 사고를 못 잡는다 |

### 선택지 D : 결정을 어디에 적나

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **ADR `#59` 에 한 줄 보탠다 (고를 안)** : 「이 순서는 적재 처리기만이 아니라 **수집기 하한 판정에도** 같이 쓴다」 | `#59` 가 정한 것(숫자 정본 · 없을 때 글자)을 **넓히는 것**이라 새 결정이 아니다 | 확정 ADR 본문에 줄을 더하는 것이라, 소급 수정으로 보이지 않게 날짜와 이슈를 같이 적어야 한다 |
| 새 ADR 번호를 단다 | 기록이 독립적이다 | 바꾸는 내용이 「`#59` 의 순서를 한 모듈에 더 적용」 뿐이라 번호를 하나 더 쓰기엔 가볍다 |
| ADR 을 안 적는다 | 문서 0줄 | 「수집기가 글자를 본다」가 `#59` 와 어긋나 보여서 다음 사람이 되묻는다 |

### 레포 · 라이브러리를 직접 열어 확인한 것

| 확인 | 결과 |
|---|---|
| 수집기 판정 | `LogLevelFilter.isBelow` = `number != 0 && number < min` : 숫자만 본다. 기동 로그가 「severity_number 가 INFO(9) 미만인 로그 레코드를 버린다」로 그 사실을 찍는다 |
| 적재 처리기 판정 | `LogTranslator.levelOf` = `fromNumber(…) ?: fromText(…)` : 숫자 1~24 만 이름이 되고 0 과 규약 밖은 `null` 이라 글자를 별칭 표(24개)로 읽는다 |
| 모듈 경계 | 모듈끼리는 `:common` 만 의존한다(`build.gradle.kts` 가 막는다). 수집기가 적재 처리기 코드를 쓰는 길은 없다 |
| `common` 의 약속 | 「공유 모델만 둔다. Entity · Repository · Service 금지」. 지금 든 것은 `RawHeaders` · `RawSignal` 둘뿐이고 `opentelemetry-proto` 를 `api` 로 내보낸다 |
| 시험 도구 한계 | `telemetrygen logs --severity-number` 는 1~24 만 받는다. 0 · 99 는 플래그 단계에서 막혀 전송 자체가 안 된다 |

### 확인 못 한 것

- 다른 언어 SDK(Python · Go)가 실제로 숫자를 비우는 비율 : 우리 레포 밖이라 안 쟀다. 재현으로 「열려 있다」는 보였으므로 비율은 이 결정에 필요 없다
- 하한 설정값에 별칭을 받는 것(`min-level: WARNING`) : 범위 밖으로 적어 둔 후속
