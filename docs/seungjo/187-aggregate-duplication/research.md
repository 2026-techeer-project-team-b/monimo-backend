## 1. 무엇을 하려는 것인가

적재 처리기가 **ClickHouse 에 넣은 뒤 Kafka 오프셋을 커밋하기 전**에 죽으면, 다시 뜰 때 같은 레코드를 또 넣는다. 원본은 `(trace_id, span_id)` 로 가려낼 수 있지만 **집계 표는 합쳐진 숫자라 가려낼 수 없다.** 같은 1분의 에러율이 실제 10% 인데 집계는 18.18% 로 답한다(실측 4회, 기준선 §4).

### 왜 수집 몫인가

| | 주인 |
|---|---|
| `spans` · 집계 표 · ClickHouse 마이그레이션 | 수집 (ADR `#20` 표 주인 · `#57` Flyway CH) |
| 적재 처리기 코드 | 수집 (ADR `#32`) |
| 발견한 쪽 | 알림 (탐지 에러율이 틀어져서) |

유경이 1단계(재현)와 2단계 계획을 했고 **공유 환경과 develop 은 한 줄도 안 건드렸다.** 바꾸는 일은 이쪽이다.

### 왜 지금

- `AGENTS.md` §6 에 "재현됨, 미해결" 로 있고 `30-failure-modes.md` ④ 와 `10-requirements.md` 는 `#182` 에서 이미 중복을 적도록 고쳐졌다. **문서는 바로잡혔고 고치는 일만 남았다**
- 앱 파드를 Spot 에 띄우기로 했다(ADR `#62` ②). 회수 · OOM · 노드 장애가 이 경로다
- 탐지 에러율이 틀어지면 오발화 · 놓침이 생긴다. 핵심기능 2번이다

### 이미 밝혀져 있는 것 (다시 재지 않는다)

| 무엇 | 어디 |
|---|---|
| 커밋 방식은 Spring Kafka 기본 `BATCH`(poll 묶음을 다 처리한 뒤 한 번에). `max.poll.records=500` | 기준선 §2-1, 중단점 스택으로 확인 |
| `spans` 는 `MergeTree` 이고 중복 제거 기록 창이 0 이라 장치가 없다 | 기준선 §2-2 |

## 2. 꼭 알아야 하는 것 다섯

### 2.1 표가 여섯이 아니라 열이다

2단계 계획 §4 가 켤 표로 여섯(`spans` · `server_map_1m` · `service_health_1m` · `transactions` · `url_stats_1m` · `heatmap_1m`)을 적고 "메트릭 · 로그 표도 같은 문제가 있을 텐데 이번 범위에 넣을지" 를 물었다. DDL 을 그려 보면 답은 **넣어야 한다** 다.

```
spans ──┬─> mv_transactions      ─> transactions ─> mv_heatmap_1m ─> heatmap_1m
        ├─> mv_url_stats_1m      ─> url_stats_1m
        ├─> mv_server_map_1m     ─> server_map_1m
        └─> mv_service_health_1m ─> service_health_1m

metrics_raw ─> mv_metrics_1m ─> metrics_1m ─> mv_metrics_1h ─> metrics_1h

logs  (MV 없음. 그래도 원본이라 중복된다)
```

| 적재 처리기가 직접 넣는 표 | 그 아래 MV 대상 표 |
|---|---|
| `spans` | `transactions` · `heatmap_1m` · `url_stats_1m` · `server_map_1m` · `service_health_1m` |
| `metrics_raw` | `metrics_1m` · `metrics_1h` |
| `logs` | 없음 |

**열이다.** 그리고 연쇄가 두 군데(`transactions` → `heatmap_1m`, `metrics_1m` → `metrics_1h`)인데 **연쇄는 예비 행렬에 없었다.** 2단계 계획 §4 도 그 사실을 적어 뒀다. 연쇄 2단은 `deduplicate_blocks_in_dependent_materialized_views=1` 이 몇 겹까지 이어지는지에 달려 있어 **직접 확인해야 한다.**

`thread_dumps` 는 API 서버가 넣는 표라 범위 밖이다.

### 2.2 "변환이 결정적이라 바이트가 같다" 는 전제에 구멍이 하나 있다

창만 켜는 안(안 1)은 **같은 레코드가 같은 바이트를 내야** 걸러진다. 2단계 계획 §3 이 그것을 "검증 필요" 로 적어 뒀다. 코드를 읽어 보니 대부분은 결정적이고 **딱 한 자리가 아니다.**

| 칸 | 어디서 오나 | 결정적인가 |
|---|---|---|
| `trace_id` · `span_id` · 시각 · 이름 · 상태 · HTTP | 레코드 안의 protobuf | 결정적 |
| `attributes` | `associate { }` → `LinkedHashMap` 이라 protobuf 목록 순서 그대로 | 결정적 |
| `agent_id` | resource 속성 셋을 정해진 순서로 고름 | 결정적 |
| `events.*` | 한 목록에서 세 번 뽑아 길이가 저절로 같다 | 결정적 |
| **`peer_service`** | **PG 에서 읽은 감시 대상 이름 목록**(`serviceCatalog.activeNames()`)으로 채운다 | **아니다** |
| 지금 시각 | `Instant.now()` 는 PG `agents` 목격 기록에만 쓰고 CH 행에는 안 쓴다 | 해당 없음 |

즉 **첫 처리와 재처리 사이에 감시 대상이 등록되거나 제외되면 같은 레코드가 다른 `peer_service` 를 낸다.** 그러면 바이트가 달라 창이 못 거르고, 조용히 중복이 남는다. 창은 40초 안의 일이라 확률은 낮지만 **"결정적이다" 라고 적으면 거짓이다.**

토큰을 쓰는 안(안 2)은 바이트를 안 보므로 이 구멍이 없다.

### 2.3 토큰에는 반대 방향의 위험이 있다

C2 가 보여 준 것은 "내용이 다른데 같은 토큰이면 멀쩡한 데이터를 버린다" 다. 토큰을 `토픽-파티션-오프셋-표` 로 두면 그 위험은 **설계상 없다** : 오프셋 하나 = 레코드 하나 = 그 표에 넣을 행 묶음 하나다. 같은 토큰이 다른 내용을 가리키는 경우가 생기지 않는다.

다만 원자료에 토큰과 연쇄에 관한 설정 하나가 더 찍혀 있다 : `update_insert_deduplication_token_in_dependent_materialized_views` 가 **0** 이다. 이름 그대로 "MV 로 이어질 때 토큰을 갱신하나" 인데 꺼져 있다. 연쇄 2단에서 토큰이 어떻게 이어지는지는 이 설정에 걸려 있을 수 있어 2.1 의 확인과 같이 본다.

**확인 안 된 것이 하나 있다** : insert 하나가 ClickHouse 안에서 **블록 여러 개로 쪼개지면** 두 번째 블록부터 같은 토큰으로 들어가 버려질 수 있다. 쪼개지는 조건은 행 수(`max_insert_block_size`)와 비동기 insert 묶기다. 우리 레코드 하나는 스팬 수백 개라 평소에는 한 블록이겠지만, **이것이 깨지면 데이터가 조용히 사라지는 쪽**이라 안 1 의 구멍보다 위험이 크다. 토큰을 고르면 이 확인이 먼저다.

### 2.4 창은 ClickHouse 가 기억하는 것이고 적재 처리기 재시작과 무관하다

중복 제거 기록(`non_replicated_deduplication_window`)은 **ClickHouse 쪽**이 최근 블록 N 개의 해시를 들고 있는 것이다. 우리 사고 모양에서 죽는 것은 적재 처리기이고 ClickHouse 는 그대로 떠 있으니 기록이 남아 있다. 그래서 G · H 가 통했다.

뒤집히는 경우 둘을 적어 둬야 한다

- **ClickHouse 도 같이 죽으면**(노드 장애 · 재시작) 기록이 남아 있는지 확인되지 않았다. 디스크에 있으면 살고 메모리면 죽는다
- **창보다 많은 insert 가 지나가면** 기록이 밀려 나간다(E). 창 크기를 재처리까지 걸리는 40초 동안 들어오는 insert 수보다 넉넉히 둬야 한다

### 2.5 이 중 어느 것도 "같은 스팬이 새 레코드로 다시 온 경우" 는 못 막는다

재처리는 세 종류다 (2단계 계획 §3)

| 종류 | 언제 | 창 | 토큰 |
|---|---|---|---|
| ① 같은 오프셋 재처리 | 커밋 전 크래시 · 리밸런싱. **이번 재현이 이것이다** | 바이트가 같을 때만 | 막는다 |
| ② 새 오프셋 재발행 | 에이전트 재전송 · 수집기 재시도로 같은 스팬이 다른 레코드로 | 묶음이 같을 때만 | **못 막는다** |
| ③ 창 밖 | DLQ 재처리 잡(ADR `#34`) · 오프셋 되감기 · 7일 재생 | **못 막는다** | **못 막는다** |

②③ 을 막으려면 **내용 기준 키**(`trace_id` · `span_id`)로 걸러야 하는데, 그 길은 집계 표에서 막힌다 : MV 는 insert 시점에 이미 더해 버리므로 나중에 원본에서 중복을 지워도 집계는 그대로다(팀원의 DLQ 조사도 같은 결론). 그래서 ②③ 의 진짜 해법은 **원본에서 그 구간을 다시 집계하는 경로** 하나다. 이번에 그것까지 할지가 6절의 선택이다.

2절을 읽으며 되물은 것들이다. 순서 그대로 둔다.

| 물어본 것 | 답이 간 곳 |
|---|---|
| 2.1 을 쉽게. 표 열 개가 각각 무슨 표인지 한 줄씩 | 2.1 에 표 목록과 그림 |
| "카프카가 커밋 전에 죽다가 다시 살아나면 중복으로 메시지를 보내는 것" 인가 | 아니다. 죽는 것은 적재 처리기이고 카프카는 정상이다. 커밋을 못 들었으니 그 앞자리부터 다시 준다(최소 한 번) |

| "지문은 이론상 생길 수 있지만 측정해 보니 없었다" 인가 | **반만 그렇다. 이 되물음이 구멍을 하나 더 드러냈다** (아래 ③) |
| 2.3 · 2.4 를 쉽게 | 이름표 위험이 둘이고 하나는 설계로 없어진다. 창은 CH 쪽 수첩이다 |

| 2.5 를 쉽게 | 재처리 경로 셋과 각 경로를 무엇이 막나 |

| 재집계 잡은 시간만 있으면 좋은 방법인가. 아니면 운영해 보고 패턴이 생기면 넣는 것인가 | 후자다. 치료기보다 탐지기가 먼저이고 팀이 같은 판단을 이미 두 번 했다(ADR `#55` · `#66` ①) |

### 유경이 물은 셋에 대한 답

1. **창 설정을 스키마에 넣어도 되나** : 된다. 표 주인이 수집이고 `#119` 로 ClickHouse 마이그레이션 수단이 이미 있다. 다만 **표 열 군데 전부** 켠다(여섯이 아니다, 2.1)
2. **적재 처리기 코드(토큰)까지 가는 안도 비교해 볼지** : 비교는 좋지만 이번에 채택하지는 않는다. 틀렸을 때 **데이터가 사라지는 쪽**이라 발표 전에 더 나쁜 실패 모양을 들이지 않는다(6절)
3. **되넣는 잡이 원래 오프셋을 헤더로 들고 오게 할 계획이 있나** : 아직 없다. 그 잡을 만들 때 **재집계와 같이 정한다.** 창도 토큰도 창 밖 재처리를 못 막으므로(2.5 ③) 그 잡의 전제가 재집계다

### 내가 틀렸던 것

① **창 크기 100 의 근거를 "복제 표 기본값이 100" 으로 적었다.** 실험 원자료를 보니 `replicated_deduplication_window` 는 **10000** 이다. 최신 문서의 기억을 그대로 쓴 것이고 **원자료가 바로 옆에 있었는데 안 봤다.** 비복제 표만 0 이라는 것이 이 건의 핵심인데 그 숫자를 틀리게 적었다.

② **5.3 의 선택지와 추천이 서로 어긋났다.** 표에는 "원본만 본다" 라고 적고 추천에는 "고쳤는데 가끔 그대로를 아는 유일한 장치" 라고 적었다. 승조가 두 문단을 나란히 놓고 "다른 거 아닌가" 로 잡았다. 원인은 **틀어지는 모양이 둘인데 하나로 보고 있었던 것**이다 : 원본과 집계가 같이 중복되는 경우와, 원본은 깨끗한데 집계만 중복되는 경우. 둘째가 연쇄 2단 미확인과 정확히 겹치는 가장 걱정되는 경우였는데 그걸 못 보는 장치를 "유일한 장치" 라고 불렀다. ㄷ' 로 고쳤다.

③ **"비동기 쪽은 쟀으니 안 1 은 안전해 보인다" 고 적었는데, 구멍이 둘인 것을 안 갈랐다.** 승조가 "측정해 보니 없었다는 건가" 로 되물어 다시 보니 비동기 구멍은 쟀고(각 1회) **`peer_service` 구멍은 실험이 건드릴 수 없는 구조**였다 : 기준선 실험이 서비스 이름을 `exp-reprocess-<시각>` 으로 써서 PG 감시 대상에 없었고, 그래서 `peer_service` 가 두 번 다 빈 글자였다. 즉 "안 생겼다" 가 아니라 **"생길 조건을 만들지 않았다"** 다. 검증 계획에 그 조건을 만드는 단계를 넣는다.

## 4. 1차 정리

- **새 결정이 아니다.** 유경이 재현과 비교 계획을 다 해 뒀고, 표 주인 쪽에서 고를 일만 남았다
- 고칠 자리는 카프카가 아니라 **받는 쪽(ClickHouse)** 이다. 넣는 것과 커밋하는 것이 한 번에 되는 일이 아니라는 것은 카프카의 정상 성질이다
- 구조가 2층이다 : **1층 창(수첩)** 이 없으면 아무것도 안 되고, **2층**에서 지문으로 볼지 이름표로 볼지가 갈린다. 창과 이름표는 나란한 선택지가 아니다
- 켤 표는 **열**이다(2.1). 그중 **연쇄 2단 둘**이 확인 안 됐다
- 안 둘의 **위험 방향이 반대**다 : 창(지문)은 놓치는 쪽(중복이 남는다, 지금과 같은 증상)이고 이름표는 버리는 쪽(데이터가 사라진다, 더 나쁜 증상)이다. 이것이 6절 선택의 중심이 됐다
- 막는 안 어느 것도 **창 밖 재처리와 새 자리 재발행은 못 막는다**(2.5). 그 둘의 해법은 재집계 하나뿐이고 제자리는 되넣는 잡 이슈다

## 5. 선택지 정리

### 5.0 무엇을 고치려는 것인지 먼저 가른다

| 목표 | 뜻 |
|---|---|
| **ㄱ 숫자를 맞춘다** | 같은 오프셋 재처리(①)에서 집계가 안 틀어지게 한다. 이번 재현이 그것이다 |
| **ㄴ 복구할 수 있게 한다** | 틀어졌을 때 원본에서 그 구간을 다시 집계해 되돌릴 수 있게 한다. ②③ 까지 덮는다 |
| **ㄷ 알 수 있게 한다** | 틀어진 것을 사람이 알게 한다(중복이 생겼다는 신호) |

지금 셋 다 없다. ㄱ 만 해도 이번 재현은 닫힌다. ㄴ 은 범위가 커지고 ㄷ 은 싸다.

### 5.1 ㄱ 을 어떻게 (정확성)

| 안 | 바꾸는 곳 | 장점 | 단점 |
|---|---|---|---|
| **0 아무것도 안 한다** | 없음 | 비용 0. 재현했고 문서에 적었다는 기록은 남는다 | 숫자를 못 믿는 상태가 유지된다. Spot 회수 때 발표 중에도 날 수 있다 |
| **1 창만 켠다** (표 열) | CH 마이그레이션 하나 | 코드 0줄. 스키마 한 겹이라 되돌리기 쉽다 | `peer_service` 가 바뀌면 못 거른다(2.2). 연쇄 2단이 되는지 확인 필요 |
| **2 창 + 레코드 토큰** | CH 마이그레이션 + 적재 처리기 | 바이트와 무관해 2.2 의 구멍이 없다 | 블록 쪼개짐 위험(2.3)을 먼저 확인해야 한다. 세 저장소 insert 호출을 다 고친다 |
| **3 커밋 폭 줄이기** (`ack-mode: RECORD`) | 설정 한 줄 | 가장 싸다. 다시 들어가는 양이 최대 500 레코드에서 1 레코드로 | **정확성을 고치지 않는다.** 커밋 수가 레코드마다로 늘어난다 |
| **4 원본 기준 키로 거르기** (`ReplacingMergeTree`) | CH 스키마 크게 | ②③ 까지 원본은 덮는다 | **집계는 그대로 틀어진다.** MV 가 insert 때 이미 더한다. `ORDER BY` 를 바꿔야 해 표를 다시 만든다 |

1 과 3 은 배타가 아니다. 2 는 1 을 포함한다.

### 5.2 ㄴ 을 할지 (복구 경로)

| 갈래 | 장점 | 단점 |
|---|---|---|
| **ㄱ 안 한다** | 범위가 작다. ①만 막고 ②③ 은 "못 막는다" 로 문서에 적는다 | DLQ 재처리 잡(ADR `#34`)을 만들 때 그 잡이 집계를 틀어뜨린다 |
| **ㄴ 재집계 잡을 지금 만든다** | ②③ 까지 덮고 DLQ 재처리 잡의 전제가 된다 | 한 구간을 지우고 원본에서 다시 넣는 일이라 집계 표 쓰기 권한 · 멈춤 구간 · 되돌림이 붙는다. 하루 이상 |
| **ㄷ 절차만 문서로 적어 둔다** | 싸다. 사람이 손으로 복구할 수 있다 | 손이 든다. 실제로 돌려 보지 않으면 `#119` 에서 겪은 것(적은 절차가 안 되는 것)을 또 한다 |

### 5.3 ㄷ 을 할지 (알 수 있게)

틀어지는 모양이 **둘**이라는 것을 먼저 적는다. 처음에 이것을 안 갈라서 선택지를 틀리게 적었다(3절 「내가 틀렸던 것」 ②).

| 틀어지는 모양 | 원본 | 집계 | 원본만 세면 보이나 |
|---|---|---|---|
| 창이 아예 못 걸렀다 (`peer_service` 가 바뀌어 지문이 달라짐) | 중복 | 중복 | 보인다 |
| 원본은 걸렀는데 집계가 못 걸렀다 (연쇄 2단이 안 이어짐) | 깨끗 | 중복 | **안 보인다** |

두 번째가 지금 가장 걱정하는 경우다 : 연쇄 2단이 확인 안 됐고, 예비 행렬 B 가 바로 그 모양(원본 10 · 집계 20)이다.

| 갈래 | 어떻게 | 비용 |
|---|---|---|
| **ㄱ 안 한다** | | 0 |
| **ㄴ 중복 제거가 걸린 수를 센다** | ClickHouse 가 블록을 버릴 때를 적재 처리기가 알 수 있나부터 확인해야 한다 | 확인 먼저 |
| **ㄷ 원본에서만 세어 본다** | `uniqExact(trace_id, span_id)` 와 `count()` 를 비교한다 | 1시간. **다만 위 표의 둘째 모양을 못 본다** |
| **ㄷ' 원본과 집계를 대조한다** | 같은 1분에 대해 원본에서 직접 센 값과 집계 표에서 읽은 값을 비교한다. 연쇄 2단도 같은 식으로(`transactions` ↔ `heatmap_1m`, `metrics_1m` ↔ `metrics_1h`) | 2시간. 두 모양을 다 잡는다 |

ㄷ' 는 알림용만이 아니다 : **안 1 이 제대로 되는지 검증하는 도구 그 자체**다. 연쇄 2단 확인에 어차피 이 대조가 필요하다. 그래서 검증에 쓰고 그 결과를 점검 스크립트에 남기는 순서가 된다.

### 5.4 창 크기를 얼마로

| 갈래 | 근거 | 위험 |
|---|---|---|
| **100** | 적재 처리기가 1대면 죽은 동안 넣는 쪽이 없어 작아도 된다 | 여러 대로 띄우면 나머지가 계속 넣어 밀려 나간다 |
| **1000** | 예비 행렬이 1000 으로 통과했다 | 기억할 해시가 열 배. 크기는 재 봐야 한다 |
| **insert 빈도에서 역산** | 평소 · 부하 때 초당 insert 수를 재서 40초 × 여유 | 재는 일이 하나 늘지만 숫자에 근거가 생긴다 |

창의 단위는 **시간이 아니라 묶음 개수**다. 실험 원자료에서 읽은 실제 값 : `non_replicated_deduplication_window` **0**(우리 표가 쓰는 것) · `replicated_deduplication_window` 10000(복제 표용, 우리는 복제를 안 쓴다). 복제 표에는 기본으로 켜져 있고 **비복제 표만 0** 이다.

그리고 **적재 처리기 대수가 이 계산을 바꾼다** : 1대면 죽어 있는 40초 동안 넣는 쪽이 아무도 없어 창이 거의 안 밀린다. `raw` 가 파티션 3개라 쿠버네티스에서 최대 3대까지 뜨는데, 그러면 나머지 대들이 계속 넣어 창이 밀린다. **로컬에서 통한 창 크기가 쿠버네티스에서도 충분한지는 별개의 숫자다.**

## 7. 2차 정리

### 이 선택이 만드는 것

| 무엇 | 범위 |
|---|---|
| ClickHouse 마이그레이션 하나 | 표 **열 군데**에 `non_replicated_deduplication_window = 100`. `#119` 의 Flyway CH 로 넣는다. `MODIFY SETTING` 은 설정 바꾸기 전에 쓰인 조각에도 먹으므로 표를 다시 만들지 않는다 |
| 적재 처리기 설정 한 줄 | `ack-mode: RECORD`. 사고 때 다시 들어가는 양이 최대 500 레코드에서 1 레코드로 |
| 대조 조회 | 원본에서 직접 센 값 ↔ 집계 표에서 읽은 값. 대표 세 쌍(`spans` ↔ `service_health_1m`, `transactions` ↔ `heatmap_1m`, `metrics_1m` ↔ `metrics_1h`)으로 **연쇄 2단까지** 덮는다. 검증에 쓰고 점검 스크립트에 남긴다 |
| 복구 절차 문서 | 집계가 틀어졌을 때 사람이 손으로 되돌리는 절차. **한 번 돌려 보고 적는다**(`#119` 에서 안 돌려 본 절차가 실제로는 안 되는 것을 겪었다) |
| 문서 | ADR · `AGENTS.md` §5 · §6 · `30-failure-modes.md` ④ |

### 검증에서 반드시 만들어야 하는 조건 둘

기준선 실험이 구조상 만들 수 없었던 것들이다(3절 ③).

1. **`peer_service` 가 바뀌는 조건** : 등록된 서비스 이름으로 실험하고, 첫 처리와 재처리 사이에 그 서비스를 제외했다가 되돌린다. 안 1 이 그때 놓치는 것을 **확인하고 문서에 적는다**(고치지는 않는다)
2. **연쇄 2단** : `heatmap_1m` · `metrics_1h` 가 중복되지 않는지 본다. 안 이어지면 그 둘만 틀어지므로 그때 다시 고른다

### 안 바꾸는 것 (범위 밖)

- **적재 처리기 코드의 insert 경로** : 토큰을 안 넣는다. `JsonEachRow` 와 저장소 셋은 그대로다
- **`transform` 패키지** : 카프카 좌표가 포트로 들어가지 않는다. 경계를 그대로 둔다
- **표 구조** : `ORDER BY` · 엔진을 안 바꾼다. 설정만 바꾼다
- **재집계 잡** : 안 만든다. 되넣는 잡 이슈에서 같이 한다
- **새 자리 재발행 · 창 밖 재처리** : 못 막는다는 것을 문서에 명시한다
- **메트릭 · 로그 표의 중복** : 창은 켜지지만 대조 조회는 대표 세 쌍만 본다

### 되돌림 조건

1. 안 1 을 켠 뒤에도 중복이 **실제로 관측되면**(대조 조회가 어긋나면) 안 2(이름표)로 올린다. 그때 블록 쪼개짐을 먼저 확인한다
2. 적재 처리기를 **2대 이상**으로 띄우면 창 크기 100 을 다시 본다. `raw` 가 파티션 3개라 최대 3대까지 뜬다
3. 연쇄 2단이 안 이어지는 것이 확인되면 `heatmap_1m` · `metrics_1h` 를 따로 다룬다
4. **손으로 복구한 일이 실제로 두 번** 생기면 재집계 잡을 만든다
5. 되넣는 잡을 만들 때는 **반드시** 재집계를 같이 정한다(창 밖 재처리를 아무것도 못 막으므로)
6. ClickHouse 가 적재 처리기와 같이 죽는 경우에 수첩이 사는지 확인되면 2.4 를 갱신한다

  점검 스크립트 + 문서
- ingester 의 insert 코드(JsonEachRow · 저장소 셋 · transform) : 손대지 않는다
- api-server · collector · detector · notifier · monimo-web : 손대지 않는다
- 표 구조(ORDER BY · 엔진 · MV 정의) : 바꾸지 않는다. 설정만 바꾼다

[① ClickHouse 마이그레이션]
- 파일 하나를 db/clickhouse 에 새로 만든다. 이름 규칙은 #119 가 정한
  V{년월일시분}__{동사}_{대상}.sql 이다. 기존 V202609221908 보다 뒤가 되어야 한다
- ALTER TABLE monimo.<표> MODIFY SETTING non_replicated_deduplication_window = 100
  을 표 열 군데에 넣는다 :
    원본 셋  spans · metrics_raw · logs
    집계 일곱 transactions · heatmap_1m · url_stats_1m · server_map_1m ·
             service_health_1m · metrics_1m · metrics_1h
- thread_dumps 는 넣지 마라. API 서버가 넣는 표라 이 문제와 무관하다(2.1)
- 원본만 켜는 중간 상태를 만들지 마라. 원본만 켜면 원본과 집계가 오히려 어긋난다
  (예비 행렬 B). 한 마이그레이션에서 열 군데를 같이 켠다
- 머리말 주석에 적을 것 : 왜 열인가(연쇄 둘 포함) · 왜 100 인가(적재 처리기가 1대라
  죽어 있는 동안 넣는 쪽이 없다) · 2대 이상이면 다시 본다는 조건 ·
  단위가 시간이 아니라 묶음 개수라는 것
- 적용 뒤 표를 다시 만들지 않아도 되는 근거는 #119 에서 확인했다
  (MODIFY SETTING 이 설정 바꾸기 전에 쓰인 조각에도 먹는다). 그 사실을 주석에 적어라
- db/clickhouse/README.md 의 절차 규칙을 지킨다. MV 는 건드리지 않으므로
  MODIFY QUERY 는 쓰지 않는다

[② 커밋 폭]
- ingester/src/main/resources/application.yml 에
  spring.kafka.listener.ack-mode: RECORD 를 넣는다
- 지금은 설정이 없어 Spring 기본값 BATCH 다. 그래서 poll 묶음(max.poll.records=500)을
  다 처리한 뒤 한 번에 커밋하고, 사고 때 최대 500 레코드가 다시 들어간다
- 주석에 적을 것 : 이것은 정확성을 고치는 것이 아니라 피해 크기를 500 레코드에서
  1 레코드로 줄이는 것이다. 창(①)이 놓치는 경우에도 피해가 500분의 1 이 된다
- 커밋 횟수가 레코드마다로 늘어난다. 처리량에 영향이 있는지 재서 결과를 README 에 적어라.
  1% 표본이라 무시할 수준일 것으로 보지만 재지 않고 적지 마라

[③ 원본과 집계 대조]
- 목적이 둘이다 : ①이 제대로 되는지 검증하는 도구 + 나중에 틀어진 것을 아는 장치
- 같은 1분 구간에 대해 원본에서 직접 센 값과 집계 표에서 읽은 값을 비교한다.
  대표 세 쌍으로 연쇄 2단까지 덮는다 :
    spans ↔ service_health_1m        (countMerge · sumMerge)
    transactions ↔ heatmap_1m        (cnt 합, 연쇄 1단 뒤)
    metrics_1m ↔ metrics_1h          (연쇄 2단)
- 원본 자체의 중복도 같이 가른다 : count() 와 uniqExact(trace_id, span_id) 비교
- scripts/check-pipeline.sh 선례를 따른다. 어긋나면 종료 코드를 0 이 아니게 한다
- 이것은 상시 감시가 아니다. 점검 스크립트가 돌 때만 본다. 그 한계를 주석에 적어라

[④ 검증 : 유경 도구로 돈다]
- docs/kafka-reprocess/experiments/reprocess_exp.sh (v2)를 쓴다. 새로 만들지 마라
- 기준선과 같은 실패 지점 : 정상 90 커밋 → 오류 10 저장 후 커밋 전 kill -9 →
  같은 그룹 재시작
- 기대값 : 원본 100 · 고유 100 · 에러율 10%. 집계 표 다섯이 재시작 전후 같아야 한다
  (도구에 표를 더해야 한다)
- 안마다 최소 3회. 결과는 기준선처럼 도구 판 · 실행 환경과 함께 남긴다
- 기준선 실험이 구조상 만들 수 없었던 조건 둘을 이번에 일부러 만든다(7절) :
  ㄱ peer_service 가 바뀌는 조건 : 등록된 서비스 이름으로 실험하고, 첫 처리와 재처리
    사이에 그 서비스를 제외했다가 되돌린다. 안 1 이 그때 놓치는 것을 확인하고 적는다.
    고치지는 마라. 그것이 되돌림 조건 1 의 재료다
  ㄴ 연쇄 2단 : heatmap_1m · metrics_1h 가 중복되지 않는지 본다.
    안 이어지면 그 둘만 틀어지므로 그 사실을 적고 멈춰서 물어라
- 창 밖 재처리와 새 자리 재발행을 못 막는 것도 실제로 확인한다 : 창을 작게(예 2) 두고
  다른 레코드 여러 개 뒤 재처리 · 같은 스팬을 새 레코드로 다시 발행

[⑤ 복구 절차 문서]
