# 하네스 : 승조가 AI 와 일한 방법

> 이 문서는 **승조(수집 · 쇼핑몰 · 배포 파트, `@SeungJo-02`) 의 작업 방식**만 적는다.
> 다른 파트는 각자 방식으로 일하고, 그 방식을 여기서 대신 말하지 않는다.
> 이 문서가 다루는 범위는 `collector/` · `ingester/` · `common/` · `db/` · `compose.yaml` · `scripts/` · `.github/` 와 `monimo-shop` · `monimo-deploy` 레포다.

하네스 = AI 가 일하는 작업 환경. 규칙 파일, 역할을 나눈 보조 에이전트, 끝났다고 주장하면 검사하는 절차를 묶어 부르는 말이다.

## 한 줄 요약

AI 에게 일을 시킬 때 **규칙은 파일로, 절차는 에이전트와 스킬로, 검증은 만든 쪽과 다른 자리에서** 한다. 그리고 AI 가 틀린 것을 이 문서 맨 아래에 그대로 남긴다.

## 구성

| 무엇 | 파일 · 도구 | 넣은 이유 |
|---|---|---|
| 규칙 | [`AGENTS.md`](../../AGENTS.md) §0~§7 (backend · shop · deploy · web 4개 레포), `CLAUDE.md` 는 "AGENTS.md 를 먼저 읽어라" 한 줄 | 모듈 경계 · 표 주인 · 마이그레이션 · 테스트 스타일을 대화마다 다시 설명하지 않으려고. 파일이 대화마다 통째로 읽히므로 짧게 쓴다 |
| 설계 절차 | `모니모니터링` 스킬 (개인 설정) | 결정 4요소(채택 · 기각 · 기각 사유 · 되돌리는 조건)가 없으면 결정으로 기록하지 못하게 막는다. 결과가 [`docs/design/01-decisions.md`](../design/01-decisions.md) |
| 착수 · 마무리 | `issue-starter` · `push-merge` 에이전트 (개인 설정) | 이슈 → 브랜치 → PR 을 같은 모양으로. PR 머지는 사람이 누른다 |
| 계획 · 실행 | `/ralplan` · `/ralph` (oh-my-claudecode) | 구현 전에 계획을 받아 읽고, 실행은 검증 기준을 통과할 때까지 돈다 |
| 검증 | critic · verifier 에이전트, CI (`build` · `dev-infra` · `docker-image`) | 만든 쪽이 스스로 통과시키지 못하게. `dev-infra` 는 `scripts/check-pipeline.sh` 로 수집기 → Kafka → 적재 처리기 → ClickHouse 가 실제로 이어지는지 PR 마다 본다 |
| 가드(hooks) | **없음** | 규칙은 아직 글로만 있다. 마이그레이션 수정 차단 · 모듈 경계 차단을 걸 예정 : 아래 "안 된 것" 에 걸어야 할 이유가 있다 |

## 작업 흐름

```
이슈 → 브랜치 → 바탕화면 가이드 .md → 코드 → 검증 → PR → (사람이) 머지 → AGENTS.md §5 · §6 갱신
```

| 단계 | 사람(승조)이 하는 것 | AI 가 하는 것 |
|---|---|---|
| 이슈 · 브랜치 | 무엇을 할지 고른다 | `issue-starter` 가 `origin/develop` 에서 브랜치를 판다 |
| 가이드 .md | **읽고 모르는 줄을 그 자리에서 묻는다** | 코드를 쓰기 전에 "왜 · 고치는 파일 · 새로 나오는 것 · 확인 순서 · 자주 틀리는 것" 을 사람이 읽을 글로 먼저 쓴다 |
| 코드 | diff 를 남의 PR 처럼 읽는다 | 한국어 설명 주석을 붙여 쓴다. DDD 는 모듈이 허락하는 만큼 |
| 검증 | 결과를 본다 : "될 겁니다" 는 증거가 아니다 | 테스트 + compose 관통 + 일부러 깨뜨려 보기(제약 위반 · ClickHouse 정지) |
| PR | 머지 버튼을 누른다 | PR 본문 작성. 커밋 · PR 에 AI 서명을 남기지 않는다 |
| 기록 | 노션에 내 말로 다시 정리한다 | `AGENTS.md` §5 · §6 을 같은 PR 에 갱신한다 |

**가이드 .md 를 코드보다 먼저 쓰는 것**이 이 방식의 핵심이다. 코드가 나오기 전에 글로 설명이 되지 않으면 그 설계는 아직 내 것이 아니다. 가이드는 이슈가 끝나면 노션 페이지(요약 → 흐름 → 파일마다의 역할)로 옮긴다.

## 역할 분리 : 만든 쪽과 검사하는 쪽

같은 대화에서 자기가 쓴 것을 자기가 통과시키지 않는다. 실제로 걸러낸 사례:

- **2주 작업 보고서**(2026-10-03) : ralph 로 쓴 뒤 critic 에이전트가 따로 검수. PR 번호 전수 대조에서 누락 1건(deploy `#5`)을 찾아 추가했다
- **`peer_service` 채우기**(`#83`) : 구현 뒤 리뷰 단계에서 "SERVER 스팬에도 채워진다" 가 나왔다. telemetrygen 이 `--telemetry-attributes` 를 SERVER 스팬에도 붙이기 때문인데, 실제 에이전트의 SERVER 스팬 `server.address` 는 자기 주소라 채우면 틀린 간선이 생긴다. 채우기를 CLIENT · PRODUCER 로 한정했다

## 넣기 전과 후 (비교 실험 : 예정)

"하네스를 쓰니 줄었다" 고 말하려면 비교가 있어야 한다. **아직 하지 않았다.** 비슷한 크기의 작업 3개를 골라 A(한 줄 프롬프트 · 규칙 파일 없이) / B(다섯 칸 프롬프트 · `AGENTS.md` · 계획 먼저) 로 각각 새 대화에서 하고, 토큰만이 아니라 고쳐 물은 횟수 · 테스트 통과 · 걸린 시간을 같이 적는다.

| 작업 | 방식 | 총 토큰 | 왕복 횟수 | 고쳐 물은 횟수 | 테스트 | 걸린 시간 |
|---|---|---|---|---|---|---|
| (1) | A | | | | | |
| (1) | B | | | | | |
| (2) | A | | | | | |
| (2) | B | | | | | |
| (3) | A | | | | | |

## 배운 것

### 잘 된 것

- **코드보다 가이드 .md 먼저** : `#66`(파드 등록)은 "다음 업무 진행할 수 있는 상태까지만 만들고 진행은 하지 말라" 고 시켜 가이드만 먼저 받았다. 읽고 묻고 고친 뒤 구현에 들어가니 구현 중 방향 수정이 없었다
- **CI 가 숫자를 대조한다** : `check-pipeline.sh`(`#44` · `#62`)가 수집기 수신 건수와 적재 처리기 소비 건수, ClickHouse 줄 수 증가를 PR 마다 본다. 적재를 깨뜨리는 변경은 사람이 보기 전에 CI 에서 걸린다
- **일부러 깨뜨려 본다** : CHECK 제약 위반 · ClickHouse 정지 상태에서 적재 처리기가 어떻게 되는지 직접 확인했다. 성공 경로만 본 검증은 검증이 아니다

### 안 된 것 : AI 가 틀렸고, 어떻게 잡았나

| 무엇이 틀렸나 | 어떻게 잡았나 | 남긴 것 |
|---|---|---|
| `#66` `@Transactional` 을 같은 클래스 안에서 부르는 private 메서드에 붙였다. 컴파일은 되지만 프록시를 거치지 않아 **트랜잭션이 열리지 않는다** | PR 전 점검에서 | 애노테이션을 `AgentRepository.insertIfAbsent` 로 옮김. "컴파일 통과 ≠ 동작" |
| `#83` 테스트 스팬에 시각을 안 넣어 1970년이 됐고, `spans` 표 TTL(93일)이 insert 시점에도 적용돼 **넣는 즉시 사라졌다**. 로그는 "1줄 적재", 조회는 0줄 | "로그와 조회가 다르다" 를 끝까지 추적 | 테스트 스팬은 항상 현재 시각. 가이드 "하면서 알게 된 것" 에 기록 |
| `#52` 이미 머지된 Flyway 마이그레이션의 **주석 한 줄**을 고쳤다. 체크섬이 바뀌어 그 전에 DB 를 만든 팀원의 `postgres-migrate` 가 멈췄다 | 팀원(ukong) 피드백 → `#67`/`#68` 되돌리기 → `repair` | 규칙을 "주석 한 글자도 안 된다" 로 조임. **hooks 로 막아야 하는 이유** |
| `#58` `spans` 컬럼을 1:1 로 옮기면서 `events`(스팬 하나에 사건 여러 개, 1:多)만 모양이 달라 미뤘다가 **잊었다**. 가짜 데이터가 채워 넣어 화면이 멀쩡해 보였다 | 팀원(ukong) 이 "컬럼은 있는데 채우는 코드가 없다" 지적 | `#79` 로 채움. 가짜 데이터는 빈 곳을 가린다 |
| `#83` telemetrygen 이 속성을 SERVER 스팬에도 붙여 `peer_service` 가 SERVER 에도 채워졌다 | 리뷰 단계에서 | CLIENT · PRODUCER 로 한정. 시험 도구의 버릇이 실제 에이전트와 다를 수 있다 |

공통점: **다섯 건 중 세 건은 테스트가 통과한 상태에서 틀려 있었다.** 그래서 테스트 통과를 끝으로 치지 않고, 팀원 피드백과 별도 리뷰 자리를 흐름에 넣어 둔다.
